*Mirrored from Meerkat Meta main at [9af8b0788d62](https://github.com/lukacf/meerkat/commit/9af8b0788d62008cedc358d7d9d71721cedf8762) on 2026-11-10; Meta version 0.9.11 at that commit.*

Meta ships a web-based operator console through its HTTP composition. The
console/admin `meta_gateway` serves it directly. A persistent, SDK-driven
`rpc_gateway` also mounts the console routes, but the two binaries are not
interchangeable: SDK hosts drive `rpc_gateway` over stdio, while
`meta_gateway` accepts its init handshake and then serves console/admin HTTP.
The console provides real-time visibility into agents, conversations, events,
logs, approvals, and recovery actions. The stock shell is built from shared
`@console-core` and `@console-components` packages, while app-specific policy
stays in runtime config and host code.

## Accessing the console

Once the runtime is serving HTTP, open the console at:

```
<http_base_url>/console
```

Both gateway binaries bind an available loopback port and report the exact
`http_base_url` in their init result. A Rust library host chooses its own bind
address. `http://localhost:8080/console` is correct only when your host or
reverse proxy explicitly publishes Meta there.

The HTML, JavaScript, and CSS are compiled into the binary via `include_str!`, so no build step is required at deployment time. The stock CSS carries its fonts, Inter Tight and IBM Plex Mono (SIL Open Font License 1.1), inline as `data:` URLs, so the console requests no font from another origin and looks the same on a host without internet access. A Content-Security-Policy in front of the console that restricts fonts must allow `font-src data:`.

For development with instant hot-reload, see the [development workflow](#development-workflow), including the current Vite proxy limitations:

```bash
cd console
npm run dev    # starts Vite at http://localhost:5199 with proxy to gateway
```

## Developer custom panels

Products embedding Console can add panels directly to its sidebar. A panel is
trusted application code and is independent of MCP Apps inline widgets.

```tsx
const customPanels = [{
  id: "inventory/overview",
  title: "Inventory",
  mount(element, context, signal) {
    element.textContent = "Product inventory";
    return { dispose() { element.replaceChildren(); } };
  },
}];
createConsoleApp(root, { baseUrl: "/console", customPanels });
// Or: <ConsoleApp baseUrl="/console" customPanels={customPanels} />
```

A mount owns its container and may mount React, Vue or another framework inside
it. Return `dispose()` to release resources, and optionally `update(context)`
to receive context changes without remounting. The host aborts the mount's signal
on disposal. A failing panel shows a local fallback while stock views remain
available. Keep the registration array stable across React renders.

For the stock served bundle, list developer-hosted modules at the top level of
`console.toml`. Each module's default export is an array of panel definitions:

```toml
panel_modules = ["/panels/inventory.js"]
```

The application or reverse proxy serves the module with a JavaScript MIME type
on the Console origin. Relative paths resolve against `baseUrl`. Realm overlays
can replace the list, including `panel_modules = []`. Reload after changing it.
This is a frontend loading option; tools do not supply these modules. The
application host owns module integrity and should serve versioned, audited assets.

Each panel needs a unique namespaced `id`, a `title`, and a `mount` function.
Console adds its sidebar button and pane-menu entry and owns tabs, splits and
layout restoration. Removing a registration leaves a restored unavailable
placeholder. It does not execute missing code or call a tool.

`ConsolePanelContext` supplies `baseUrl`, `experience`, `readOnly`, the host's
`authority`, current `selection`, and the panel's pinned `conversation`. Use
`openPanel(id, { intent: "split_right" })` for another registered developer panel.
Optional `instanceKey`, JSON `params`, and a pure `validateParams` function allow
multiple instances. Layout storage contains selectors only: never put private
results or secrets in panel parameters. Set `followSelection: true` to follow the
selected conversation instead of pinning it. Context and pending requests are
discarded when the host authority changes. Layout keys include the authority
and principal scope; opening and restoring conversation
panels checks current visibility.

Panels can use `context.request({ path, method, body }, signal)`. The default
service uses same-origin authenticated requests, rejects redirects, blocks
non-GET operations in view-only mode, and never retries a request. It sends
`X-Console-Authority` and `X-Console-Conversation` as URI-encoded JSON locators.
These headers are not authorization proof: the application must derive the viewer
from its authenticated session and enforce access on every request. Panels are
trusted application code, so browser checks do not replace server policy.

Embedded hosts may inject `panelService(request, scope, signal)` to use their
existing application service, forwarding the scope locators through its own
authenticated API. The host still applies view-only and lifetime
checks. The request scope includes the original panel conversation, not whichever
conversation happens to be focused later.

See `examples/console-extensions` for a module and local stock Console preview.

## Inline MCP Apps

Inline widgets use the [MCP Apps standard](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx).
An MCP server supplies tool metadata, a `ui://` HTML resource, and the original
tool result. No panel module or Console-specific app manifest is needed.

Enable the stock host in `config/console.toml`:

```toml
mcp_apps_sandbox_url = "http://127.0.0.1:5001/sandbox.html"
```

Run the sandbox on a separate origin, with the exact Console origin allowed:

```sh
MCP_APPS_HOST_ORIGIN=http://127.0.0.1:5000 MCP_APPS_SANDBOX_PORT=5001 npm --prefix console run mcp-apps:sandbox
```

Both gateway binaries embed the sandbox proxy, so a released gateway is all
you need to run it outside a source checkout. Have the gateway write it into a
directory, then start it with Node.js. It uses only the standard library, so
it needs no `npm install`:

```sh
meta_gateway --write-mcp-apps-sandbox ./mcp-apps-sandbox   # or rpc_gateway
MCP_APPS_HOST_ORIGIN=http://127.0.0.1:5000 MCP_APPS_SANDBOX_PORT=5001 node ./mcp-apps-sandbox/mcp-apps-sandbox.cjs
```

`--write-mcp-apps-sandbox <dir>` writes two files, creating the directory and
replacing earlier copies, prints each file's SHA-256 and path, and exits
without starting a gateway:

| Written file | Repository source |
| --- | --- |
| `<dir>/mcp-apps-sandbox.cjs` | `console/mcp-apps-sandbox.cjs` |
| `<dir>/src/mcp-apps/sandbox.js` | `console/src/mcp-apps/sandbox.js` |

The proxy loads `src/mcp-apps/sandbox.js` relative to its own file. The two
files and the Console embedded in the gateway share an internal sandbox
protocol, so write them again from the new binary whenever you upgrade the
gateway. The Python package and the npm package do not include the proxy.

Gateways before 0.9.2 do not embed the proxy. For those, copy the two
repository files from the release tag that matches your gateway into one
directory, keeping the layout above, and check your copies against these
SHA-256 digests (identical for 0.9.0 and 0.9.1):

| File | SHA-256 |
| --- | --- |
| `console/mcp-apps-sandbox.cjs` | `157fed890922c4c3fe7c9b7a6319455f0604e9c789818f9c38d45bc115a98ad6` |
| `console/src/mcp-apps/sandbox.js` | `4e3592ba5b8bf198322126ccb27919a8d4c4c1976a198f9c497c16833f6c3024` |

The originating member profile selects its MCP servers through
`tools.mcp_servers`, or uses its existing host tool provider. Global server
configuration alone does not grant every member access to those tools.
The bundled gateways enable native MCP Apps negotiation when this sandbox URL
is configured. Rust library hosts opt in with `UnifiedRuntime::builder().mcp_apps(true)`
and set `ConsolePolicy.ui.mcp_apps_sandbox_url` on their Console policy.
Hosts that create their own external MCP connections must also negotiate the
standard UI extension, for example with `McpAppsClientServiceFactory`; this
cannot be added after a connection's handshake.
Headless hosts omit the capability. An unavailable widget retains its ordinary
text tool result.

The host retains the original tool, arguments, complete result and available UI
resource with the canonical session. The declared HTML is preloaded before tool
execution; the app receives invocation inputs and results through MCP Apps
messages. Reopening a retained view never repeats
its original tool call or waits for the current agent turn. The resolved
`canCallTools` capability describes access to the live host action surface;
actual calls still require fresh native admission and the original connection.
During a continuing model turn, an actor- and run-bound native observation
exposes accepted tool results for display without changing committed history.
Completed-run replay uses the runtime's committed session. These observations
carry no action authority. UI-only `_meta` is excluded from model requests and the
public transcript. Timeline frames carry locators, not private HTML or metadata.
Every lookup rechecks the authenticated viewer and session ownership. Uncached
resource reads and app actions also require `agent.send`, an editable Console
and the original live MCP connection with negotiated MCP Apps; replacing or
retiring it cannot silently redirect an old widget. View-only users can read
the exact retained renderer without fresh member-credential IO. Disabling the
sandbox URL also disables the Console's app HTTP operations.

Tool visibility follows `_meta.ui.visibility`: omitted permits model and app,
`["model"]` permits only the model, `["app"]` permits only the app, and `[]`
permits neither. A model-only launch tool can still own a view. App actions use
fresh native authorization, pre- and post-tool hooks and normal execution
policy, including review when required. A post-hook refusal withholds the result
while preserving already settled effects. View-only users cannot invoke them.
An app action runs for the Console caller who makes it: on a console that
requires sign-in, a person's action carries that person as its original
requester, and on an open console, or for a service or a token principal, it
carries none. It never borrows the requester of the model run whose result
the app shows.

App resource reads and tool execution can proceed while the model turn is still
running. A response with no session effects or hook notices does not wait for
that turn or trigger a session save, so several mounted widgets can poll for
fresh data. If the call produces session effects or hook notices, the native
actor applies and persists them before publishing the response; this settlement
can wait for the active turn. This distinction follows the actual execution
outcome, not a tool's `readOnlyHint`. Each request still requires fresh admission
and the original actor and MCP connection.

The current host profile supports inline rendering, resource reads and tool
calls. It does not advertise conversation handoff, model-context updates,
external links or downloads. The sandbox restricts fetches and frames through
CSP and denies sensitive browser permissions. It rejects CSP grants covering
configured Console hostnames. Browser support limits network containment:
Chromium 140 ignores the emitted standard `webrtc 'block'` directive. Navigation
retirement is best-effort lifecycle handling, with every fresh action still
subject to native admission. Serve the sandbox without Console cookies or
application APIs; production hosts should use a dedicated HTTPS origin.

An ordinary MCP App can render a versioned generated document from its result
data today. The app supplies the renderer; the runtime does not impose a
component language. Keep generated content inside the app sandbox, separate
from trusted developer panels, and route external actions through the same
native admission path. Streaming updates and conversation handoff require their
own explicit lifecycle and provenance contracts when added.

## Runtime contract

The bundled console uses a small set of stable protocol surfaces:

| Surface | Purpose |
|---------|---------|
| `GET /console/experience` | Initial runtime snapshot, affordances, topology, health, and `console_config`. |
| `GET /console/modules` | Configured module-ID summary. |
| `GET /console/identities` | Identity-first list and inspection summary. |
| `GET /console/timeline` | Replayable console frames for initial load and older-history paging. |
| `GET /console/timeline/stream` | Bounded replay followed by live timeline frames. |
| `GET /console/identity/{identity}/stream` | Identity-filtered timeline stream convenience route. |
| `POST /console/mcp-apps/{resolve,read-resource,call-tool}` | Authenticated operations bound to the originating tool invocation. |
| `POST /console/rpc` | JSON-RPC 2.0 endpoint for console commands. |
| `POST /console/rpc/multipart` | Multipart JSON-RPC for image send/upload. |
| `GET /blobs/{blob_id}` | Blob/image retrieval for rendered media. |

`/console/modules` returns IDs from `RuntimeDecisionState.modules`. It is a configuration inventory, not confirmation of successful startup, current liveness, or health.

The console contract version is `0.5.0` in `console/src/lib/contract.ts` and `docs/rct/console-rest-sse-contract-v0.5.0.json`. The runtime JSON-RPC contract is separately versioned by `META_CONTRACT_VERSION`.

Gateway custody also differs. `rpc_gateway` installs a SQLite console timeline
store only when its init request configures `persistent_state`; long-lived
`--persistent` process mode alone does not make the timeline durable. Without
persistent state, its timeline stays in memory. The console-only
`meta_gateway` installs the same store in its state directory when it runs
with `persistent_sessions: true`, and keeps its timeline in memory without
them. Do not infer timeline durability from the presence of the same browser
shell and route names.

The console audit log (`meta/console/audit`, which `audit.view` reads) and
the gating state follow the metadata store the same way: durable for
`rpc_gateway` over persistent state or a host store realm and for
`meta_gateway` with persistent sessions, kept for the process otherwise.
Both reads report it as `retention`.

### Sidebar - controls and roster

The left column is navigation. It can show stock controls such as topology, roster, logs, health, and approvals, plus app-defined buttons. Clicking an agent opens chat; details and profile-style data belong in roster surfaces.

Agents can be grouped by configured selectors. The default useful pattern is labels first, then structural fallbacks:

```toml
[agent_list]
group_by = ["labels.console_group", "labels.group", "role"]
subgroup_by = ["labels.org", "labels.realm"]
section_order = ["Personal", "Initiatives", "Internal"]
fallback_group = "Agents"
fallback_subgroup = "Other"
default_pinned_agent_ids = ["identity:ops-lead"]
collapse_single_subgroup = true
```

A sidebar button can open a stock `control`, link to an `href`, or dock an operator `panel`. A `panel` is a same-origin path (one leading `/`, at most 2048 UTF-8 bytes, no whitespace, control characters or backslashes, and no `.` or `..` segment in any spelling, `%2e` included) that the console shows in a docked frame. The path is used exactly as written; surrounding whitespace is refused, not trimmed. It cannot be combined with `control` or `href`; an invalid button is dropped.

<Warning>
An operator panel is trusted code, not an isolated frame. A same-origin page runs with the viewing operator's console session and can do anything that operator can do in the console. Configure only pages you would trust with that session. The path comes only from static operator configuration, and the console reads it from the current configuration whenever the panel opens.
</Warning>

The console and flow editor documents are served with `Content-Security-Policy: frame-ancestors 'self'`, so only their own origin can frame them. A deployment that frames the console from another origin must change before Meta 0.9; same-origin framing (for example behind a reverse proxy on the console's origin) and top-level use are unaffected. A panel page that a reverse proxy serves outside the gateway must send its own framing policy; the gateway's header does not cover responses it does not serve.

Operator panels depend on a few host constraints:

- The console sets no `frame-src` restriction, so same-origin panel paths stay framable. A host's own same-origin review page can be configured as a panel.
- The panel frame is not sandboxed, so a host page's form posts keep their real `Origin`. A sandbox without `allow-same-origin` would send `Origin: null` and break same-origin form admission.
- A page served with `frame-ancestors 'none'`, such as a secret-entry page, cannot be framed and must not be configured as a panel.

Each agent row shows:
- The agent's display name or, for an agent without one, its identity in words
  (`router:main` reads "Router main"; a generated id reads as the agent's kind
  and the id's last six characters, such as "Reviewer 4e5f60")
- A second line with what the agent is (its role, else its group) and what it
  is doing in words, or how long ago it was last active, for example
  `Router · working` or `Router · active 3 min ago`
- A pin action on hover, and beside it, when you point at the pin or reach the
  row with the keyboard, a copy action: pinned agents move to a Pinned section
  at the top, and the copy action copies the agent's identity, which the row's
  tooltip also shows

#### Ordering and grouping the roster

Two controls under the search box set how the roster lists agents:

- **Group**: *Category* lists agents under their categories and subgroups (the
  `[agent_list]` grouping above); *None* lists every agent in one list. Either
  way, Pinned stays on top and an agent spawned by another, or a side chat,
  stays nested under it.
- **Sort**: *Manual* keeps your own order; *Name* sorts by display name, with
  numbers in order (`Agent 2` before `Agent 10`); *Last activity* lists the
  most recently active agents first and agents with no known activity last.

In *Manual*, drag an agent by the grip that appears at its left edge on hover,
or focus the agent and press <kbd>Alt</kbd>+<kbd>↑</kbd> or
<kbd>Alt</kbd>+<kbd>↓</kbd>; a screen reader hears each move. An agent moves
among the agents that share its place: its category and subgroup, or the agent
it is nested under, and its nested agents move with it. One order serves every
view: it orders each category, the flat list, and Pinned. Until you move an
agent, each category keeps its default order and the flat list follows the
categories in their order; the first move keeps that order for every agent,
and a move changes only where the moved agent stands, in either view. A new
agent appears at the end of its place, and a renamed agent keeps its place,
since the order is kept by identity. Agents do not move while you sort by name or last activity, or while
a search or an activity filter is on. Categories and subgroups reorder the same
way: drag a header, or focus it and press <kbd>Alt</kbd>+<kbd>↑</kbd> or
<kbd>Alt</kbd>+<kbd>↓</kbd>.

Last activity is the newest time the console's frame log recorded the agent
acting (a live runtime event, a message sent to it or a tool application),
which `/console/experience` reports as `last_activity_ms`, or a newer event the
console has since seen. History the console rebuilds, lifecycle records
(respawn, retire, reset, delete), interaction failures and memory events do not
count. Reading it wakes no agent.

The browser keeps these preferences in local storage, per signed-in user and
console: the manual order, the Group and Sort choices and the pins follow the
user and are kept when the `[agent_list]` configuration changes. The order of
categories and subgroups and which of them are collapsed are kept per user too,
for that configuration, and start over when it changes. Pins set in two tabs
are both kept, and every tab shows them. Pins, and the category order and
collapse an earlier console kept for every user of the runtime, carry over
once.

Non-addressable agents (e.g., Gate, Health Monitor) appear dimmed and cannot be messaged.

An identity-first agent whose identity binding moved (after a reset or a
delete), and that the console could not collect again within 2 s, has state
unknown and offers no send or retire until a later read collects it. Its
records carry an `unobserved` marker with reason `refresh_pending` (see
[`GET /console/experience`](/meta/api/rest#get-%2Fconsole%2Fexperience)). The
topbar shows the mob as unknown, with an amber dot, when the health snapshot
does not say whether the mob runs; a stopped mob's dot is red.

### Approvals

Open **Approvals** from the sidebar or **Needs you** to inspect current requests.
**Needs you** also counts host-provided attention items when the console configuration
names `[[attention.sources]]`. The inbox lists them after the approvals, as cards with one
**Open** link to the host's page, which owns the decision. A source that cannot be read is
named and hides nothing else (see [host-provided attention items](/meta/reference/configuration#host-provided-attention-items)).
A source with a `decide_href` gives a read-only console a **Decide in** link on each pending approval, in the inbox and in an agent's chat, to the host page that decides it.
Expand **Complete request details** before deciding. Stale or unavailable approval
data does not mean there are no pending requests; use **Refresh approvals** to
reload it. Read-only consoles cannot submit decisions. Where the connection
offers no approvals (a gateway without `meta/gating/pending`, or an aggregate
console, whose inbox lists host attention items only), the Approvals header
reads **Not available on this connection** instead of pending and automatic
counts.

| Tab | What it shows |
| --- | --- |
| Pending | Current requests, each marked **For you** or **Waiting for** its approver, with Approve, Reject, and Escalate controls when the caller can decide them; requests decided elsewhere stay, saying by whom. |
| Auto | Recorded `evaluated` events whose outcome is `allowed` or `allowed_with_audit`. |
| Audit | Read-only records with the requesting actor, event, decision, approver, and outcome when supplied. A decision whose record names its verified decider reads "Decided by" that principal, the approver label it decided as, and the assurance it was authenticated with (for example "alice@example.test (as Release manager) - person authenticated"); an older record keeps the approver label. |
| Policies | A placeholder; policy details and editing are not available in this console. |

When the gateway keeps the gating records in its memory (`meta/gating/audit`
reports `retention: "process"`), the Audit and Auto tabs say so: "Kept in the
gateway's memory: decisions from before a gateway restart may be missing."

Risk tiers display in words with their code: R0 Minimal, R1 Low, R2 Elevated and
R3 High. A request's chip reads "High risk", with the tier code in its tooltip, and
an audit row reads "Risk: High (R3)". A missing tier reads "Unknown"; an
unrecognized one reads "Unknown" followed by the recorded value. The current Meta
R2 path normally allows with audit.
It does not run the proposed native model reviewer. An approval record does not
confirm execution: the caller remains responsible for enforcing the returned
outcome and carrying out any permitted action. See [Gating](/meta/concepts/gating) for
current tier, timeout, and decision behavior.

The stock console decides as the signed-in person: its decisions name no
approver, and the console takes the approver from the connection (see
[Gating](/meta/concepts/gating)). When `meta/console/whoami` reports a caller that is
not a person (no token on an open console, a service token, a token that names
no human, or a shared-account token), the inbox shows requests read-only and
says to sign in as yourself to decide: such a caller can read them but not
decide them. A request pinned to an approver id is decided by a person who
holds that id through the access configuration's `approvers` bindings.

Approval cards are personal. A request pinned to an approver id the caller does
not hold reads **Waiting for** that approver and offers no decision; for a
signed-in person, a request pinned to an id they hold, or pinned to no one,
reads **For you**. **Needs you** counts only the requests that are not waiting
for someone else (with any host items), and the sidebar's **Approvals** count
counts the same requests. A request for the caller that someone
else decides keeps its card, which says how and by whom (for example
"Approved by" the deciding person, read from the gating audit), or "Decided
elsewhere" when the audit cannot say.

The same holds for memory quarantine reviews and WorkGraph goal confirmations:
the console offers them only to a signed-in person. A WorkGraph claim is owned
by the caller who makes it, so the WorkGraph panel offers Claim only to a
caller with a token, and Release on the caller's own claims and, to an access
admin, on anyone's: the work graph records an admin's release with the admin
and the claim released. Claims the stock console makes carry no lease, so
someone else's claim ends when an access admin releases it, when the host
releases it on its stdio RPC gateway (`rpc_gateway`; `meta_gateway` serves
none), or when its item is closed.

Configure action tiers through the host's gating configuration. For SDK-launched
stdio gateways, see [`gating_config_path`](/meta/reference/configuration#sdk-and-gateway-runtime-options).
That option does not configure unrelated HTTP or library entrypoints.

### Dock — Chat panels

The center area is a multi-panel tabbed workspace. Each panel contains a `ConversationPane` with a `ConsoleComposer`.

**Tab strip** at the top:
- Click a tab to switch panels
- `+` to create a new empty tab
- `×` to close a tab

**Split panels** — click the split controls (← → ↑ ↓, visible on hover) to divide a panel. This lets you chat with multiple agents side-by-side.

**Composer** at the bottom of each panel:
- Textarea with `Message {agent}...` placeholder
- Send button (↑) — also supports Enter to send, Shift+Enter for newline
- Footer shows: target agent, member ID, profile, and status

### Side chats

**Fork to side chat** in a conversation's header branches the agent's
conversation into a side chat: a new member that starts from the agent's
committed transcript and opens in a pane beside the agent. You continue the
side chat on its own; the agent's session, transcript and queued work stay
as they were.

- The side chat runs with the agent's role, profile and model overrides and
  tools, and inherits the agent's labels.
- It records who opened it: your console principal, in its
  `side_chat_creator` label (nothing on an open console when you sent no
  token). The record grants nothing, and the console shows it only to you
  and to the admins of an enforced access policy: other viewers of the side
  chat see it without the label.
- On a console with sign-in, a side chat is private to the person who
  opened it: its audience is the agent's narrowed to that person, plus the
  access admins (`admins`). Everyone else meets it on no surface (sidebar,
  member lists, topology, timeline, streams, events, flow runs, peer lists,
  inspection, memory, the audit log, the runtime's routing, delivery,
  reconcile and storage reads). A request of theirs that names it, to
  read it, send to it, close it or fork it, gets the answer that method
  gives a member that does not exist (for example `-32602` `member not
  found` from `meta/get_member`, or `404` `unknown_identity` from
  `POST /console/send`); a request that would record something for it (an
  announcement subscription, a schedule, a remembered fact, a topology edge,
  a WorkGraph goal, attention target or supervisor, whether it names the
  member, its owner key or its session) is refused as naming an unknown
  member (`-32001`). This holds with or without an access configuration
  (the SDK gateway's stdio plane is the trusted host plane: see
  [Known limitations](/meta/concepts/access-control#known-limitations)). Its
  header says who can see it:
  **Private: only you and access admins can see it.**, or, to an access
  admin, that it is private to the person who opened it. The members a
  private side chat creates (a helper or member its turn spawns, the members
  of a mob it creates and the helpers `delegate` runs for it, a `fork_off`
  child, a helper forked from it) are private to the same person too, after
  the side chat is closed as well. A private side chat convenes no council:
  its `council` call is refused as a policy denial
  (`private_member_council`), since the council's participants would carry
  its conversation to members others share. The schedules its agent writes
  are aimed at itself only (`private_member_schedule_target` refuses any
  other target), and the schedule tools of an agent not private to you
  neither list, read nor change them. A WorkGraph goal for it is refused for
  you too (`private_member_workgraph_target`): it is built without WorkGraph
  tools, so no binding can serve it.
- On a console without sign-in, a side chat stays shared, and so does one
  opened by a caller who is not a signed-in person (a service token) or
  before side chats were private. A shared side chat's audience is exactly
  the agent's: every agent check on it is the agent's, so whoever may see
  the agent, send to it or retire it may do the same with its side chats, a
  deny on the agent hides them, and a grant on the side chat's own name
  grants nothing (see [Side chats](/meta/concepts/access-control#side-chats)).
  Its header says it is shared.
- A side chat's memory is its own: its `memory` tool writes to the side
  chat's identity, never to the agent it was forked from. The memory
  distiller never reads a private side chat's conversation, and the memory
  steward never dreams over its memory or promotes any of it. A private
  side chat's `memory` tool proposes nothing to its mob, and no one else is
  shown a proposal it wrote.
- A private side chat is where personal accounts on MCP servers are used:
  a server the operator marked personal acts with the account of the person
  who opened the side chat, for that person's own messages only (see
  [Personal accounts on MCP servers](/meta/reference/configuration#personal-accounts-on-mcp-servers)).
  An access admin who revokes a person's sessions suspends that person's
  accounts in the side chats they opened before the revocation, while a side
  chat opened after a fresh sign-in uses them again and the credentials are
  kept.
- It is never wired to a peer, whatever the agent's role: no other agent can
  address it, and none lists it as a peer. The runtime seats it exempt from
  the mob definition's wiring rules (`auto_wire_orchestrator`,
  `role_wiring`), so no agent seated after it is wired to it either, and the
  definition-wiring reconcile and the topology's declared edges leave it
  out, as they leave out every member exempt from those rules. A host's own
  edge discovery policy is never handed one either. No role-wide flow step
  dispatches to it: only a run that names it in its `role_targets` reaches
  it. A durable fork of it (its `fork_off` child, a helper forked from it)
  is seated exempt in the same way.
- It is listed under its agent in the sidebar, marked **Side chat**, and is
  kept until you close it: across a console reload and a gateway restart. It
  never idle-retires. **Close side chat** in its pane retires it, which, as
  every check on a side chat, needs `agent.retire` on its agent; the agent
  is not touched. `meta/reset_all` retires side chats with the other members
  that have no registered identity. A host that reconciles the whole mob
  against a declared roster (`UnifiedRuntime::reconcile`, without
  identity-first authority) retires them too, since no declared roster names
  them; the stock gateway does not.
- A side chat is never respawned or reset: its pane offers neither, and
  `meta/respawn`, `meta/respawn_member` and `meta/reset` refuse it
  (`side_chat_restart_refused`), since its successor would be no fork of the
  agent. An agent's `mob_respawn` tool refuses it too, and `meta/reset_all`
  reports it as a member it could not reset where a host declares a
  baseline member under its name. Close it and fork the agent again.
- A side chat is never adopted as an identity:
  `mob/adopt_member_identity_declaration` refuses it
  (`side_chat_adoption_refused`), since an adopted identity is rebuilt from
  its declaration, which no fork made.
- The action is offered only to a viewer who may spawn members
  (`agent.spawn`) and send to the agent (`agent.send`), and only where the
  gateway's sessions persist or its composition did not record whether they
  do. It is disabled while the agent works and enabled when it is idle. An
  agent seated and never woken has no conversation to fork: the fork is
  refused, and the agent is not woken for it. An agent the console's
  visibility policy hides cannot be forked, nor can an agent whose lineage
  already fills the access rules' walk (the agent and seven ancestors), by
  any viewer, an admin included.
- Under `runtime_options.member_auth_binding`, an agent whose session
  records another binding or none (one created before the launch named the
  binding) cannot be forked: the runtime would seat the side chat off the
  binding. A side chat forked before a launch named the binding is refused
  at its rebuild under that launch; close it and fork again.
- Instructions the agent activated (`meta/member_activate_instruction`) are
  inherited when they are in effect in the agent at the fork. Any other
  inherited instruction stays inactive, and the side chat's pane names it:
  the side chat cannot answer until a host activates it.

The fork takes the agent's conversation as it is now. Side chats are
`meta/fork_member` on the console RPC.

### Private replies

Some replies are meant for the one person who asked, such as an answer that
a data owner released after reviewing it. Such a reply never lands in a
shared conversation:

- A request made in a conversation private to the person (their own side
  chat on a console with sign-in, or a member such a side chat created) gets
  the reply in that conversation, which only they and the access admins see.
- A request made in a shared agent gets the reply as an item of the person's
  own attention list (`meta/console/attention`), which only that person
  reads and dismisses (`meta/console/attention/dismiss`). Nothing is added to
  the agent's conversation, and no other viewer's stream carries it. So does
  a request whose private conversation is gone by the time the reply comes.

The console counts the person's items in **Needs you** and lists them in its
inbox after the approvals. Each names the agent that answered and opens the
chat it answers, and **Dismiss** takes it off the list (a read-only console
offers no Dismiss). A reply whose text a payload policy hid reads
**Content hidden by policy** and is dismissed the same way. A reply in the
person's own conversation reads there as the agent's message.

An item shows no more of its reply than the conversation would: the
console's payload policy applies as the list is read, and an item is listed
only while the person may view the agent it came from.

Each console send records where it came from (its `user_input` frame's
`thread`): the agent, the interaction, and who may read the replies to it.
Only a person signed in on a console with sign-in can receive private
replies: a request from an open console, a service or a token that names no
person has no private reply route, and a reply to it is refused. The
attention list is kept in the realm's metadata store, as the console audit
log is: across restarts for `rpc_gateway` over a state directory or a host
store realm and for `meta_gateway` with persistent sessions, and for the
life of the process otherwise.

### Schedules

An agent's details pane (**Details** in the roster, or **Inspect agent** in
its conversation's header) lists the agent's **schedules**: messages the
Console sends to the agent later, as the person who defined them. A viewer
who may message the agent adds one with **New schedule**: the message, an
optional name, and when to send it, either once at a date and time,
repeating every so many minutes, hours or days (the first send one interval
from now unless you set a start), or daily at a time of day, on the
weekdays you pick, in a named time zone. Each schedule shows when it sends,
its next send while it is active and, to a viewer who may message the agent,
who it sends as, with **Edit**, **Pause** or **Resume**, and **Delete**,
which asks you to confirm. An edit keeps the timing unless you change it.

- Each send is a Console send by the schedule's sender, judged when it goes
  out: the Console must still admit the sender as it would admit them then
  (sign-in where it is required, the allowlist, the trusted issuer, and no
  sessions revoked since the schedule was defined), and the send needs what
  a message sent then would need, `agent.send` on the agent under the access
  policy at that time, a writable console, and an agent that takes console
  messages. A refused send fails that time only; the schedule keeps its
  later times.
- Creating a schedule makes you its sender, and so does editing or resuming
  one you send. Editing or resuming a schedule someone else sends takes it
  over: the Console first says who it sends as and asks you to confirm, and
  only then makes you its sender; keeping its sender changes nothing. The
  schedule keeps the senders it was taken over from, and its details name
  them. On a console without sign-in the sender is the console's shared
  account, as it is for a message you send there; once the console requires
  sign-in, such schedules stop sending until someone signed in edits them.
- An edit or a resume names the version of the schedule the pane showed: one
  made after someone else changed the same schedule is refused and the list
  is read again: check the schedule and repeat the change. A pause and a
  delete name no version: they act on the schedule as it is.
- A deployment can let people message an agent without changing its
  schedules: schedule changes also need `schedule.manage`, which an access
  configuration that names no schedule action grants wherever it grants
  `agent.send`.
- A schedule repeats at most once a minute.
- Viewers who may see the agent but not message it, or message it but not
  manage its schedules, see its schedules read-only, and so does everyone on
  a read-only console or on a gateway that does not offer schedule changes;
  the pane says why.
- An agent whose input is governed takes no schedule (a governed send needs
  its human present, and a scheduled send has none), and an agent that
  takes no console messages cannot be scheduled.
- The pane lists the schedules defined in the Console only. The agent's own
  schedules (its schedule tools) are not listed, and the agent's tools
  neither see nor change the Console's.

The section appears where the gateway keeps console schedules. A gateway
that sends none of them (a candidate launch, for one) lists them read-only.
Schedules are the `meta/schedule/*` methods on the console RPC (see
[Console schedules](/meta/api/rpc#console-schedules-console)).

### Local action feedback

When a host supplies a recognized native refusal or audit fact, the Console
shows feedback for the affected action. A permitted sibling or later reply
can still appear in the same run.

| Card | Meaning |
|------|---------|
| Action refused | The action was refused under the current authorization, so it did not run. The host does not say why: a policy denial, an authorization that changed after the action was prepared, and request details the authorization could not evaluate all arrive as the same refusal, so the card names no cause. |
| Action could not start | Required process confinement was refused before the action ran. The card retains the exact typed cause. |
| Action blocked by hook | A pre-tool hook explicitly denied this call. Its typed hook reason remains distinct from operation permission. |
| Hook could not start | A pre-tool hook failed to launch. This is infrastructure feedback, without an invented permission or confinement cause. |
| Audit update unavailable | Recording the action's outcome failed. Its actual result is unchanged; this notice does not justify repeating the action. |

Custom workspace hosts should retain `ConversationMessageEntry.operationFeedback`
when transforming shared timeline entries. The reusable `ConversationTranscript`
renders this metadata automatically. A custom renderer can display its `title`,
`detail` and supplied `toolCallId` or `operationId`; preserve those identifiers
verbatim. The shared projection classifies supported typed payloads, rather than
interpreting arbitrary tool messages as decisions.

Cards cover recognized current typed payloads. An unknown cause or malformed
payload does not acquire a permission or confinement classification. Unrecognized
tool results use the ordinary tool-result display and may show raw output; no
dedicated fallback card is promised for every event. A missing card is not a permission decision or evidence
of success. Preserve unfamiliar payloads in the host's authorized diagnostics.

Keep run state attached to the controller's runtime lifecycle events. A local
feedback card does not end a run. Rendering these cards does not configure
native authorization, process confinement or durable audit; the host supplies
those runtime capabilities separately.

### Voice conversations

When the gateway has an authenticated OpenAI Live configuration, a blue
waveform button appears beside Send. Voice is not offered without OpenAI
authentication, in a view-only console, or for an agent you cannot message.
Microphone access requires HTTPS or localhost and your browser's permission.
Source builds must enable the `openai-live` Cargo feature. Public GPT Live
requires a compatible OpenAI API-key binding; a ChatGPT OAuth login alone
does not enable this feature.

Voice is an explicit gateway registration, not a setting in `console.toml`.
For `meta_gateway`, supply `console_voice` in the init parameters alongside
your `auth_config` and enable `persistent_sessions`:

```json
{
  "persistent_sessions": true,
  "console_voice": {
    "principal": "alice@example.com",
    "realm": "ops",
    "auth_binding": { "realm": "ops", "binding": "openai" },
    "voice": "marin",
    "summary": { "model": "gpt-5.4-mini", "max_input_bytes": 65536, "max_output_bytes": 4096 }
  }
}
```

The optional `summary` block bounds the concurrent context summary (see
"Context preparation" below). Every field is optional: `model` defaults to
the background agent's own text model, `max_input_bytes` to 65536 (64 KiB)
and `max_output_bytes` to 4096 (4 KiB); zero is rejected. The input bound
degrades rather than fails: when the newest message alone exceeds it (a
large tool result, say), that one whole message is summarised; only
Meerkat's 4 MiB capture ceiling refuses a snapshot outright. In Rust the
same knobs are `PublicLiveRegistration.summary` (`ConsoleVoiceSummaryConfig`);
the SDK builders take them on `OpenAiLiveGatewayConfig`:

```ts
gateway.consoleVoice({
  principal: "alice@example.com", realm: "ops",
  authBinding: { realm: "ops", binding: "openai" }, voice: "marin",
  summary: { model: "gpt-5.4-mini", maxInputBytes: 65536, maxOutputBytes: 4096 },
});
```

```python
gateway.console_voice(OpenAiLiveGatewayConfig(
    principal="alice@example.com", realm="ops",
    auth_binding=LiveAuthBindingRef(realm="ops", binding="openai"), voice="marin",
    summary=OpenAiLiveSummaryConfig(model="gpt-5.4-mini", max_input_bytes=65536, max_output_bytes=4096),
))
```

The binding must already be configured in the gateway's Meerkat host config.
The principal must match the authenticated console subject. For an SDK-driven
`rpc_gateway`, place the same `console_voice` registration under
`runtime_options` and use the gateway's persistent session configuration.
The SDK builders expose this as `.consoleVoice(config)` in TypeScript and
`.console_voice(config)` in Python, using `OpenAiLiveGatewayConfig`.
A Rust host that embeds `UnifiedRuntime` through its builder registers the
same thing with `.console_voice(PublicLiveRegistration)` (plus `.live(...)`
for the external channel) and serves
`build_reference_app_router_with_live(decisions)`; the decision state must
require app auth, for example `parse_console_auth_config` with
`provider: "oidc"` for a Google-fronted console. See the Unified Runtime guide.
Credentials stay on the server. The console checks readiness for the selected
agent before offering voice and checks it again before microphone capture;
registration or model availability alone does not enable the button.

Click the waveform button to start a `gpt-live-1` conversation with the
selected agent as its background agent. Audio connects without waiting for a
summary of that agent's context; it does not change the background agent's text model.
The voice strip above the composer names the voice agent and shows separate
waveforms for your microphone and the live model's audio.

The microphone is requested during the click, alongside the gateway readiness
check (**Allow microphone access**); a negative readiness releases it again
without opening a channel. Startup then distinguishes **Starting voice** from
**Connecting audio**. As soon as the microphone is open the primary status reads
**Listening, you can talk**; nothing about context gates it. Context
preparation is a secondary hint beside that status: **Context arriving** while
the initial summary is read, generated, and sent (the tooltip names the stage),
then **Context supplied** once the provider acknowledged it, which does not
mean the model has recalled or spoken it. Context failures stay visible
without disabling the connected audio; a failed status read is shown separately
and retried.

Context preparation is a separate, tool-free summary request using the background
agent's credentials; it does not change that agent's model or reasoning
settings. It reads the most recent 64 KiB of the serialized transcript (older
turns are dropped whole; a size bound, not a content heuristic; a newest
message larger than the window is kept whole), asks for
compact notes rather than replayed logs, uses low or disabled OpenAI reasoning
where the model catalog supports it, and caps the result at 4 KiB. The public
GPT Live transport delivers the summary in UTF-8 fragments of at most 500
bytes, each waiting for its own provider receipt, so the 4 KiB cap bounds
delivery at nine fragments; the prompt itself aims for about 200 words. The
summary model defaults to the background agent's own model because Meerkat's
catalog exposes a support tier, not a speed tier; set `summary.model` to a
faster model on the same provider when the agent's model is slow to first
token. A produced summary is cached per member, keyed by the source session's
transcript cursor and a digest of the exact summarised window, so reopening
voice on an unchanged transcript reuses it without another model call. The
defaults come from measurement: with the previous 4 MiB input and 16 KiB
output bounds a 40-turn session took 4 to 6 seconds to summarise; the 64 KiB
window keeps that cost flat as histories grow. Meerkat orders the captured
history and newer conversation updates, and cancels or fences context work
when the call closes or changes. A context job from an old call cannot update
a replacement call.

The microphone and speaker controls are independent. Muting speakers silences
local playback, not the conversation; the model's output waveform continues
to show incoming audio. End the conversation with the close button.

Voice stays with its original agent when you select another chat, switch
tabs, or open an operator panel. Starting voice on another agent ends the
previous voice conversation before opening the new one. Text composers remain
usable throughout, including for the agent currently in voice mode.

A gateway may also register `live: true` beside `console_voice` so an external
client (for example an embodiment daemon opening `meta/live/open` over
`{base}/live/ws`) shares the same live host. The two take turns: the newest
engagement wins. When the external client opens a channel, the console call
ends with "Voice moved to the external live channel", and readiness for the
console reports `available: false` with `reason: "external_live_active"` and
the holder until that channel closes. Starting voice again from the console
takes the path back and closes the external channel with a typed
`superseded_by_console_voice` reason.

With GPT Live client delegation, typed messages go to the background agent;
the composer labels that destination during voice. Its canonical context and
results are mirrored into the voice conversation. This follows
[OpenAI's typed-input contract](https://developers.openai.com/api/docs/guides/live-delegation#accept-typed-input):
typed text is user data for the backend, not a live-model instruction or a
native spoken turn. Chats with other agents do not change the voice target.
For local session-backed agents, console messages use explicit conversational
user admission, preserving the console interaction identity in canonical
history. Internal events and recalled memory are not relabeled as human input.

Voice ends automatically after **15 minutes of silence**, not after 15
minutes of total call time. Text messages do not extend that audio inactivity
window. Ending voice or closing the console releases the browser's microphone
and playback resources. The close button immediately mutes microphone
transmission and playback, retaining the muted WebRTC transport for up to five
seconds while the server finalizes. Transport and capture resources are then
released even if finalization fails; an unconfirmed close remains retryable.
If Meerkat provides a recovery connection, the console
reconnects to the same voice agent without changing your mute settings;
unrecoverable audio connection loss ends voice.

#### Voice acceptance tests

The offline browser lane uses real local WebRTC peers without paid provider
calls. The opt-in live lane starts a separate authenticated console and uses
real `gpt-live-1`, real `gpt-5.5` background/peer calls, and original synthetic
speech fixtures instead of capturing a person's microphone:

```bash
npm --prefix console run e2e:voice
node console/voice-e2e-live.cjs --self-test

# Requires OPENAI_API_KEY; this lane makes billed OpenAI calls.
npm --prefix console run build
npm --prefix console run e2e:voice:live
```

The live runner builds the voice-enabled gateway through `scripts/repo-cargo`.
Set `META_VOICE_GATEWAY_BIN` to an already-built current gateway to reuse it.
Missing credentials fail the selected live lane; they do not produce a skip
that looks like a passing acceptance run. The runner does not use an existing
console or record microphone input.

Coverage includes spoken requests, typed-value recall, peer results arriving
after an initial answer, and close/reopen while background work remains pending.
Expected native transcript content must have fresh non-silent audio nearby;
packets, old audio peaks, or mirrored voice text masquerading as a background
answer are not sufficient. Late ordinary background facts may reach the new
voice conversation through current canonical context, but old receipts must
not control it.

The public API does not expose pending canonical-mirror acknowledgements.
Exact close while an append awaits its provider acknowledgement is therefore
covered separately by deterministic Meerkat owner tests. The paid console lane
does not infer that hidden state from an unfinished background task.

The optional summary-latency benchmark makes three billed `gpt-5.5` calls and
checks a five-second summary budget while retaining exact context values:

```bash
./scripts/repo-cargo test -p meerkat-meta --features openai-live --lib \
  console_voice_summary_live_latency_and_context_retention -- --ignored --nocapture
```

### Signals rail - event feed

The right column shows user-meaningful signals: requests, assistant replies, peer messages, image events, relevant tool activity, and alert levels. Low-level transport envelopes, scaffold prompts, raw checksum tokens, and raw tool metadata are filtered out before reaching the user-facing view.

### WorkGraph panel - Tree and Graph views

The WorkGraph panel (sidebar nav entry, visible when the runtime wires a WorkGraph service) reads `meta/workgraph/snapshot` and offers two views of the same data via the Tree | Graph toggle in the panel head. Tree is the default: an indented item list with claim/close actions plus the attention-binding and recent-event sections. Graph draws a read-only layered DAG - roots leftmost, one column per parent-edge depth, solid arrows into parents, dashed amber `blocks` edges, node borders/dots in the item-status palette (pulsing blue in progress, green completed, red failed, amber blocked, struck-through cancelled). Drag to pan, wheel to zoom, Fit resets, clicking a node shows its id/status/owner detail underneath. The view caps at 200 nodes and reports the overflow; all mutations stay in the tree and attention sections.

## Agent grouping

Agents are grouped in the sidebar by `console_config.agent_list`. Selectors support `labels.<key>`, `label:<key>`, raw label keys, and direct fields such as `group`, `subgroup`, `role`, `kind`, `identity`, `member_id`, and `agent_id`.

Prefer mob member labels for domain-specific grouping:

```rust
use std::collections::BTreeMap;

use meerkat_mob::ids::AgentIdentity;
use meerkat_mob::{ProfileName, SpawnMemberSpec};

fn labels(pairs: &[(&str, &str)]) -> BTreeMap<String, String> {
    pairs.iter().map(|(k, v)| (k.to_string(), v.to_string())).collect()
}

SpawnMemberSpec::new(
    ProfileName::from("lead"),
    AgentIdentity::from("domain:billing"),
)
    .with_labels(labels(&[
        ("display_name", "Billing"),
        ("console_group", "Domain"),
        ("org", "Payments"),
    ]));
```

### Well-known labels

| Label | Purpose |
|-------|---------|
| `display_name` | Human-readable name shown on every console surface; without it the console names the agent by its identity in words |
| `console_group` | Recommended domain grouping selector for the stock console |
| `group` | Legacy/sidebar group fallback |
| `org` / `realm` | Common subgroup selectors |
| `addressable` | Set `"false"` to hide send-message actions for internal agents |
| `singleton` | Set `"true"` to prevent agent retirement |

The console fetches its initial state from `GET /console/experience`, which returns agent data, topology, and health information. The key field for the sidebar is `agent_sidebar.live_snapshot.agents`:

```typescript
interface ConsoleAgent {
  agent_id: string;
  member_id: string;
  label: string;
  kind: string;           // "mob_agent" or "module_agent"
  profile?: string;
  state?: string;
  group?: string;         // sidebar grouping
  addressable?: boolean;
  affordances?: {
    can_send_message?: boolean;
    can_manage_schedules?: boolean; // under enforced access: agent.send and schedule.manage
    can_retire?: boolean;

}
```

Identity-first status and inspect payloads use lowercase wire enums for addressability:
`"addressable"` and `"internal_only"`.

## Messaging protocol

<Steps>
  <Step title="Seed the timeline">
    Panels load recent visible frames with `GET /console/timeline?identity=identity:alice&mode=recent&limit=...`. Older history is paged with `before`; live continuation uses `latest_cursor`.
  </Step>
  <Step title="Send message">
    Identity-addressed panels call `meta/console/send` through `POST /console/rpc`:
    ```json
    {
      "identity": "identity:alice",
      "content": "What is on my calendar tomorrow?",
      "origin": "console:panel-1",
      "origin_kind": "operator",
      "idempotency_key": "panel-1:3f9c1c2e-6f7a-4c1b-9d2e-0b1a2c3d4e5f",
      "handling_mode": "queue"
    }
    ```
    Returns `{ "interaction_id": "...", "identity": "..." }`.

    `origin` is the caller's free-form identifier for audit and routing.
    `origin_kind` is optional and typed: `operator`, `operator_probe`,
    `connector`, `scheduler`, `policy`, `flow` or `system`. It is stored on
    the `user_input` frame, and the transcript labels the turn from it
    ("Operator", "Operator probe", "Scheduled turn", ...). Any other value
    is refused. `scheduler`, `connector`, `flow`, `policy` and `system` belong
    to Meerkat's own internal emitters, such as a schedule's fire, so a send
    over HTTP that declares one is refused (400 `reserved_origin_kind`).
    Automated checks such as release-gate probes should send
    `operator_probe`; the stock console sends `operator`. A declared
    `origin_kind` is part of the idempotent request, so a retry must repeat it.

    The `user_input` frame names its `sender`, set by the Console from the
    caller it authenticated (the connection), never from the request:
    `kind`, `assurance`, `display_name` and `caller_scope`, as
    `meta/console/whoami` reports the caller. A client shows its own
    messages by comparing the frame's `caller_scope` with its own. An
    automated check names itself by sending with its service token. On a
    console that requires sign-in, a person's send carries the person's
    qualified principal to the agent's run as the run's original requester
    (Meerkat's `ToolDispatchContext::requester`); the stored frame keeps it
    and no view returns it, neither on the send's frame nor on the run's
    transcript identities that the session history's frames, the run's
    event frames and the agent and mob event streams show. Other callers'
    sends carry none, and so does
    every ungoverned send on an Open console (see
    [Access control](/meta/concepts/access-control#requesters-on-an-open-console)).

    On a console that requires sign-in, the agent's model also reads each
    person's message with a sender label: an injected-context row "Message
    from" and the person's display name, right before the message, a steer
    included. The agent tells people apart from it without parsing the
    message. A service's, a token principal's and an anonymous caller's
    messages, a schedule's fire and every message on an Open console carry
    no label.

    `idempotency_key` must be unique per send; the stock console mints one
    UUID per send. An idempotent retry reuses the same key in the same
    caller/runtime/identity/origin namespace with identical content and
    effective `handling_mode` (default `queue`). The caller is the
    authenticated principal (anonymous callers of an open console share one
    local account), so another user's identical key is a different send. An
    open console without an access controller does not resolve tokens, so all
    of its callers share that one account; isolating users needs
    `require_app_auth` or an access controller.
    The original acceptance is returned and the turn is not run again. Changed
    content or handling mode in that namespace is rejected with HTTP `409` /
    JSON-RPC `-32009 idempotency_conflict`. A different identity or origin is
    a different send namespace, not a guaranteed replay.

    A retry of a send the gateway accepted but stopped before submitting is
    dispatched then, once, into the session the send recorded; a retry of a
    send the runtime already admitted only settles it. `meta/console/recover_send`
    (`POST /console/send/recover`) reports a send's status and what the runtime
    holds for it, for the caller's own sends only.

    `skill_refs` is optional: typed, source-pinned skills selected for this
    turn (`[{"kind": "structured", "source_uuid": "...", "skill_name": "..."}]`,
    the same shape as meerkat `turn/start`). The addressed member resolves
    them natively and commits a durable `SkillContext`; the console never
    renders skill bodies into the message. A nonempty selection is part of the
    idempotent request: a replay must repeat the same selection in the same
    order, and a changed selection under the same key is
    `-32009 idempotency_conflict`. Only local session-backed members accept a
    selection.

    The legacy `POST /console/send` route still exists for compatibility. New console clients should prefer JSON-RPC.
  </Step>
  <Step title="Receive response frames">
    The timeline stream delivers canonical console frames:
    ```
    id: console:241
    event: console_frame
    data: {"type":"console_frame","frame":{"id":"frame-1","cursor":"console:241","dedupe_key":"example:frame-1","timestamp_ms":1750000000000,"runtime_key":"example","identity":"identity:alice","kind":"text_delta","status":"delivered","frame_version":1,"payload":{"text":"done"},"source":{"kind":"console_event"},"interaction_id":"example-interaction"}}
    ```
    This is the SSE wire envelope: `type` wraps a `frame` with `kind` and
    `payload`. The frontend normalizes these into its internal `event`/`data`
    representation; that normalized object is not the SSE wire shape.

    Correlate a send with its terminal by `interaction_id` on frames whose
    `source.kind` is `console_event`. Session-history backfill re-emits past
    turns as frames with `source.kind = "session_history"`; they carry the
    persisted interaction id of the turn they replay and are never fresh
    completions, so clients MUST exclude them from live turn handling (the
    rule is stated with the frame shape under `meta/console/query_timeline`
    in the [JSON-RPC reference](/meta/api/rpc)).

    If a requested cursor is no longer replayable, the stream returns `409 replay_unavailable`; refetch a recent page and resume from its `latest_cursor`.

    A replay from a cursor is sent as it is read, one page at a time. If the
    log stops holding what follows while the stream replays (it was
    cleared), the stream sends a `replay_unavailable` event and ends: handle
    it as the `409`. If a later page cannot be read, the stream ends after the
    frames it sent: reconnect with the last frame's cursor as
    `Last-Event-ID`.
  </Step>
</Steps>

## Console routes

| Route | Method | Response |
|-------|--------|----------|
| `/console` | GET | HTML page |
| `/console/assets/console-app.js` | GET | React bundle (JavaScript) |
| `/console/assets/console-app.css` | GET | Stylesheet (CSS) |
| `/console/experience` | GET | Experience metadata (JSON) |
| `/console/modules` | GET | Configured module IDs (JSON), not startup/liveness/health confirmation |
| `/console/identities` | GET | Identity-first records |
| `/console/timeline` | GET | Replayable console timeline page |
| `/console/timeline/stream` | GET | Timeline SSE replay and live continuation |
| `/console/identity/{identity}/stream` | GET | Identity-filtered timeline SSE |
| `/console/send` | POST | Legacy console send |
| `/console/rpc` | POST | JSON-RPC 2.0 endpoint |
| `/console/rpc/multipart` | POST | Multipart JSON-RPC for images/blobs |
| `/blobs/{blob_id}` | GET | Blob/image retrieval |

Primary RPC methods on `/console/rpc`:

- `meta/console/send` - identity-addressed console send
- `meta/console/query_timeline` - timeline replay query
- `meta/console/list_identities` and `meta/console/inspect_identity` - identity-first inspection
- `meta/blob/upload` - multipart blob upload
- `meta/reload_member` - non-destructive cold reload of one identity's live
  member (same session, same generation); the repair for a member whose sends
  fail with the reload-required class. Gated by the `agent.respawn` action.
  `meta/member_health` is the matching read (`agent.view`): lifecycle
  state, last delivery error class, and the actor-loop probe verdict with the
  open `stall_id`, from in-process reads that answer during a stall.
- `meta/identity/warm` - builds one identity's member without a turn and
  writes its tool record, with the result and error codes of the stdio
  gateway's [`meta/identity/warm`](/meta/api/rpc#meta%2Fidentity%2Fwarm). Gated by the
  `agent.respawn` action.
- `meta/retire`, `meta/respawn`, `meta/reset`, and `meta/reset_all` -
  operator lifecycle actions. `meta/retire` releases the member, which stays
  seated on its session at its generation. A member that no identity holds
  and no host adopted, such as a side chat, is retired by Core instead: it
  leaves the roster with the members it spawned. `reset_all` resets every
  identity the identity runtime knows, whatever its state (generation advance, one
  `identity_reset` lifecycle frame each, listed under `reset`): each reset is
  Core's rotation, which seats a `dormant` identity Core holds no member for
  on a fresh session too, and starts a `broken` one over. It retires only
  members with no registered identity, such as raw delegates (listed under
  `retired_delegates`); a member that is retiring appears in no list. A
  registered identity on a runtime without a session bridge fails the
  preflight with `identity_reset_requires_session_bridge` and nothing is
  touched. An identity whose own reset fails is listed under `failed`, the
  identities beside it are still reset, and the call answers `-32000` with
  the full body in `error.data`
- `meta/send_message` - legacy member-addressed send path
- `meta/fork_member` - forks an agent's conversation into a side chat (see
  [Side chats](#side-chats)); gated by `agent.spawn` for the side chat and
  `agent.view` and `agent.send` for the agent, and offered where sessions
  persist or the composition did not record whether they do
- `meta/schedule/list`, `meta/schedule/create`, `meta/schedule/update`,
  `meta/schedule/pause`, `meta/schedule/resume` and `meta/schedule/delete` -
  an agent's console schedules (see [Schedules](#schedules)); the list is
  gated by `agent.view` and the writes by `agent.send` and `schedule.manage`
  for the agent, and each send is a Console send by the schedule's sender
- `meta/console/attention` and `meta/console/attention/dismiss` - the
  caller's own attention items (see [Private replies](#private-replies)); a
  caller reads and dismisses only its own
- `meta/topology/query`, `meta/topology/plan`, `meta/topology/apply`,
  `meta/topology/operation/get`, and `meta/topology/audit/query` - optional,
  revisioned connection management and separately permissioned durable audit

The identity routes take the durable identity or its current generated
runtime id, `rt:<identity>:<generation>`. After a reset, the predecessor's
runtime id is refused with `-32000` and `error.data.kind`
`stale_identity_runtime_binding`, naming the current binding
(`registered_runtime_member_id`, `registered_session_id`). A hidden identity's
runtime id answers `identity_hidden_by_policy`, and a runtime id of an
identity the runtime does not know answers `identity not found`.
`meta/console/inspect_identity` refuses a stale runtime id the same way
before it looks the identity up in the console aggregator. A runtime id
whose identity's binding cannot be read right now is never let through: it
is refused as unreadable, retryable, with `error.data.kind`
`identity_history_unavailable`. The code is `-32052` when the route's
identity lookup or its runtime id check meets the failed read, and can be
`-32000` when the route's own status read fails after its lookup, or when
the id names a live member whose binding cannot be read.

Topology management is opt-in at the runtime. With the default disabled
policy, the stock console remains a passive topology viewer and does not show
the Connections tab. Read-only mode exposes searchable connection state with
server-provided denial reasons. Editable mode offers only pairwise actions
authorized for both endpoints; bulk controls appear only when a host supplies
an explicitly bounded action and the runtime advertises `topology.bulk`.

The reusable `TopologyPanel` keeps the authority-local and bilateral CAS
contracts distinct. Stock JSON-RPC hosts supply the scalar query `revision`.
Same-process coordinator hosts also supply the exact
`authority_revisions` map as `authorityRevisions`; mutation callbacks receive
that map as `expectedAuthorityRevisions` and must pass it to the bilateral
coordinator as `expected_revisions`. Cross-authority hosts must never collapse
that map to the scalar local revision or route the intent through the local
JSON-RPC adapter. They may use `topologyAuthorityRevisionToken` as the
component's scalar view token when the coordinator snapshot has no scalar
revision, but never as the coordinator CAS value.

Editable mode requires a durable runtime state path; Meta fails closed
rather than accepting reconnect/suppression intent that would disappear on
restart:

```rust
use meerkat_meta::{TopologyControlMode, TopologyControlPolicy, UnifiedRuntime};

let runtime = UnifiedRuntime::builder()
    .definition_path("config/mob.toml")
    .persistent_state(".meta/state")
    .topology_control(TopologyControlPolicy {
        mode: TopologyControlMode::Editable,
        allow_bulk: false,
        max_batch_size: 1,
        allow_cross_authority: false,
        ..TopologyControlPolicy::default()
    })?
    .build()
    .await?;
```

## Authentication

Coarse console access is governed by `ConsolePolicy`:

```rust
ConsolePolicy {
    require_app_auth: true,   // the default; set false only for local development
    read_only: false,         // set true for view-only deployments
    ..ConsolePolicy::default()
}
```

`require_app_auth` defaults to `true`. The SDK builders expose the opt-out as
`consoleAuthRequired(false)` (TypeScript) and `console_auth_required(False)`
(Python); `rpc_gateway` reads it as `runtime_options.console_require_app_auth`.

When `require_app_auth` is `true`, protected console JSON, RPC, blob, and stream
requests are checked against the `AuthPolicy`. The shell, static assets, and
`/healthz` remain public. See [authentication](/meta/guides/authentication) for the
exact HTTP surface boundary.

When `read_only` is `true`, the console can inspect identities, timelines,
logs, and topology, but chat sends, uploads, lifecycle controls, and other write
RPCs are denied server-side.

For per-principal and per-agent authorization, install Meta's optional
`AccessController` from `config/access.toml` or the runtime builder. When
enabled, its ABAC policy is deny-by-default with deny-overrides across console
REST, JSON-RPC, and SSE. JSON-RPC denials use code `-32030` with
`data.kind = "access_denied"`; REST and SSE return HTTP 403. `mob.observe`
authorizes mob-level observation but does not grant `agent.view` for every
agent. To observe everything, a principal needs both `mob.observe` and an
applicable `agent.view` grant.

In **Console access**, open **Groups** and choose **Inspect access** beside a
member to prefill that exact subject in **Preview**. Select an action and
optional agent, then choose **Evaluate** to ask the access controller. The
shortcut does not evaluate automatically or change policy, and remains
available to authorized administrators on a read-only connection. A preview is
an observation, not permission for a later action or a native tool grant.

Upstream hosts that already know a user's ACL can also force the stock console UI
into view-only mode without changing Meta auth: set
`window.__META_CONSOLE_READ_ONLY__ = true` before loading the console bundle,
or append `?console_read_only=true` (also accepted:
`meta_console_read_only=true` or `view_only=true`) to the console URL. This is
a frontend-only affordance for per-user UX; direct RPC calls are still governed
by the server-side `ConsolePolicy.read_only` setting.

Console mutation endpoints assume non-ambient credentials: pass bearer tokens
explicitly in the `Authorization` header (a `GET` may carry the token as the
`auth_token` query parameter, since an `EventSource` stream or an image load
cannot set headers; a write whose only token is in the query string is refused
401). An open console
(no sign-in) answers only requests addressed to a host it serves: a loopback
name, its listen address, or the host of the gateway's public base URL
(`http_public_base_url`). Any other `Host` gets 403 `host_not_served`, so a
page that rebinds its own name to the console's address cannot drive it. If a
host proxy converts console auth into cookies
or another browser-ambient credential, that host must add origin and CSRF
protection before exposing mutation routes such as `/console/rpc`,
`/console/rpc/multipart`, or `/console/send`.

### Who the console acts as

The top bar names the caller the console acts as, from
`meta/console/whoami`: the signed-in person, a shared account (a token that
names no person), a service, or **Not signed in** on an open console. Its menu
offers **Sign out** when the console configuration names `[sign_out]` (see
[sign-out](/meta/reference/configuration#sign-out)).

The stock console reads `whoami` once for each console it loads and names that
caller on every console request (`expected_caller_scope`, and
`expectedCallerScope` on an MCP Apps tool call): the `caller_scope` that read
reported. A later answer for someone else never changes whom it names. Its
first change waits for that read. While no read has answered, no console
request that names a caller leaves: a message sent then reads **Not sent**, a
queued message stays queued, the console commands that read (approvals and the
other panels that read through them) are refused too, and the top bar shows no
identity chip, so **Sign out** is not offered. The console reads its caller
again with its next read of the console experience, and loads again at once
when another tab of the console learns it. The gateway refuses a change made
for another caller (`caller_changed`), so a message queued by one person is
never sent as another.

When someone else signs in to the same browser, every tab of the console
notices at once: a tab that learns its caller tells this browser's other tabs
of the console, and a tab whose caller differs, or whose request was refused
with `caller_changed` (a voice call, an MCP Apps tool call or a blob upload
included), drops what it shows (transcripts, approvals, host items, the
previous caller's queued messages and drafts), stops its streams and loads
again as the new caller. A queued message the console sends on its own (an
agent became idle) waits for a fresh read of the console experience first, so
it is never sent under a login that changed meanwhile.

A login that ends puts the console in one sign-in state: a 401,
`caller_not_current`, or a front that redirects a console request to its
sign-in page. No view of the ended login stays on screen. **Sign in** reloads
the console page so the front can sign the browser in again, and signing in
again in another tab, or coming back to the tab, brings the console back, with
the message being written and the images attached to it. Console requests do
not follow redirects, so a front's redirect to its sign-in page reads as "sign
in", never as an unknown outcome: a send it stopped reads **Not sent**.
Messages already queued stay saved in this browser.

### What this browser keeps

The browser keeps each signed-in user's console data apart. Queued messages
(in local storage) and unsent drafts (in each tab's session storage) are kept
under the user's storage scope, the `storage_scope` of `/console/experience`;
a host that passes `storageNamespace` gets it combined with that scope. The
display settings, the sidebar's and the activity rail's collapse and the agent
list's arrangement are kept per user too, and each tab saves the panel layout
only when it changes it, so a tab left open does not undo what another tab
arranged.

**Sign out** removes the user's queued messages and drafts from this browser,
in every tab of the console; preferences stay. On an origin without Web Locks
(plain HTTP), the queue's storage lock keeps a copy of each queue in IndexedDB;
signing out removes those copies too, and the browser leaves for the sign-out
once they are gone, or after at most 1.5 seconds. A queue an earlier console kept
for everyone using the browser (one that named no user, or a host namespace
alone) is offered once as **Older queued messages**: importing it moves it to
the user who imported it and removes the earlier copy, so no other user of
the browser is offered it. A preference an earlier console kept for everyone
is read once in the same way, by the first user who loads the console.

## Build system

The console has two build modes:

| Mode | Tool | Format | Use case |
|------|------|--------|----------|
| Production | esbuild | IIFE (browser) + CJS (library) | Embedded in Rust binary |
| Development | Vite | ESM with HMR | Instant hot-reload at localhost:5199 |

The production build resolves `@console-core` and `@console-components` as local workspace packages via esbuild aliases. The browser bundle and CSS are embedded in the gateway binary.

### Development workflow

```bash
# Terminal 1: start the gateway
META_REF_ADDR=127.0.0.1:63220 META_REF_HTTP_MODE=serve \
  ./scripts/repo-cargo run -p meerkat-meta --example library_mode_reference

# Terminal 2: start the Vite dev server (proxies API calls to gateway)
cd console && npm run dev
```

The checked-in Vite proxy targets port `63220`, but currently omits
`/console/timeline` (including `/stream`), `/console/identities`, and `/blobs`.
Full-contract development through Vite requires adding proxy entries for
those paths to the same backend. Alternatively, use the embedded console at
`http://127.0.0.1:63220/console` for full-contract validation; rebuild the
production console assets and Rust host to test frontend changes there.

When using Vite, edits in `console/src/` or `packages/` appear instantly in the browser.
