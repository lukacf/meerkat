## Version

```python
from meerkat import CONTRACT_VERSION
print(CONTRACT_VERSION)  # "0.9.8"
```

## Primary handles

```python
from meerkat import MeerkatClient, Session, DeferredSession, LiveChannel, Mob
```

- `MeerkatClient` owns the runtime process and transport.
- `Session` is a live multi-turn handle.
- `DeferredSession` is a created session that has not run its first turn yet.
- `LiveChannel` is the session-bound wrapper for the `live/*` RPC surface.
- `Mob` is a first-class mob control handle.

### `Usage`

- `input_tokens: int`
- `output_tokens: int`
- `cache_creation_tokens: int | None`
- `cache_read_tokens: int | None`
- `accounting: ProviderTokenAccounting | None`

### `ProviderTokenAccounting`

- `provider: str`
- `model: str`
- `presented_tokens: int`
- `convention: str`
- `aggregation: str`

One `Usage` type serves two different accounts. When present on the
`TurnCompleted` event it is per-call usage: `input_tokens` is the raw provider counter (for Anthropic,
uncached input only) and `accounting` names the resolved provider/model plus the
normalized `presented_tokens` for that call. On `RunResult.usage` and the
`RunCompleted` event it is the **session**-cumulative total: `input_tokens` is
already the sum of every recorded call's `presented_tokens`, it is persisted with
the session so it keeps growing across turns, and `accounting` is `None` because
a session may span models.

Do not sum the cumulative value with anything - take the latest one - and sum
`accounting.presented_tokens` rather than per-call `input_tokens`. An
agent-loop call publishes a `turn_completed` row when its turn completes;
extraction requests publish theirs on the extraction outcome event, and
compaction summaries and turns that fail after the provider answered publish
none, even when the failed turn's assistant row was already committed (a
committed row does not imply a `turn_completed`). So the `turn_completed` rows
need not reconcile with the cumulative total. See
[Usage accounting](/reference/usage-accounting) for the worked example.

`TurnCompleted.usage` is `Usage | None`. `None` is honest unmeasured
accounting, not a zero-token call. Skip the row; the paired
`turn_usage_accounting_unmeasured` wire event carries the reason.

## Session runtime input helpers

Immediate creation and turn methods accept host-owned context separately from
the user prompt:

- `injected_context: list[ContentInput] | None` is ordered durable
  user-channel context immediately before the prompt
- `transient_turn_context: str | None` is request-only host context
- turn methods also accept `self_hosted_server_id` for an exact configured
  local model route

Deferred creation can store `injected_context` for its eventual first turn but
does not accept `transient_turn_context`; pass transient facts to
`DeferredSession.start_turn(...)`.

### `inject_context`

```python
await client.inject_context(session_id, text, source=None, idempotency_key=None)
await session.inject_context(text, source=None, idempotency_key=None)
```

### `stop_run`

```python
result = await session.stop_run(run_id, reason="user pressed stop")
result = await mob.stop_member_run(agent_identity, run_id, reason="...")
```

Stops exactly `run_id` (read it from the `run_started` event's
`identity.run_id`) and terminalizes every input already bound to that run,
including durable steers that joined it. Returns `StopRunResult` /
`MobStopMemberRunResult` whose `receipt["outcome"]` is `stopped` (with
`contributors`), `not_current` (the run is no longer current; nothing was
touched), or `not_stoppable`.

### `send_external_event`

```python
await client.send_external_event(session_id, event_type, payload, blocks=None, idempotency_key=None)
await session.send_external_event(event_type, payload, blocks=None, idempotency_key=None)
```

Returns `ExternalEventOutcome` (runtime admission outcome payload). With
`idempotency_key`, a retry admits nothing new: it answers `outcome_type`
`deduplicated` and names the first admission in `existing_id`. The same key
with other event content raises `INPUT_IDEMPOTENCY_CONFLICT`. The key is
scoped to the session and needs a server contract of 0.9.5 or later; against
an older server the SDK raises `CAPABILITY_UNAVAILABLE` instead of sending it.

`send_mob_member_content(..., idempotency_key=None)` and `Member.send(...,
idempotency_key=None)` take the same key, deduplicated for the member
identity. A keyed send answers `continuation` (`delivery_id`,
`committed_at_ms` and a `status` of `pending`, `admitted` with `session_id`
and `input_id`, `stranded` or `refused`); see `mob/member_send` keys in the
RPC reference.

### Transcript and input reconciliation

```python
await client.input_state(session_id, idempotency_key="turn-42")
await client.export_session_atif(session_id)
await client.read_session_transcript_revision(session_id, revision_id)
await client.list_session_transcript_revisions(session_id)
await client.fork_session_at(session_id, message_index)
await client.fork_session_replace(session_id, message_index, replacement)
await client.rewrite_session_transcript(session_id, selection, replacement, reason)
await client.update_system_prompt(session_id, key, content)
await client.restore_session_transcript_revision(session_id, revision_id, reason)
```

A fork child runs under its source's session configuration, without the
source's shell environment, MCP attachments or mob operator authority; see
[what a fork child inherits](/api/rpc#what-a-fork-child-inherits). Since 0.9.4
a fork child can run turns. A child forked by 0.9.3 or earlier that never ran a
turn cannot: fork its source again.

Both fork calls take `inherited_instructions`, the fork instruction policy for
the instruction activations the prefix carries: `"require_explicit_activation"`
(the default), `"reactivate_inherited"` or `"refuse"`. A forked child is not
materialized, so under the default and under `"refuse"` a prefix that carries
activation rows is refused before anything is committed with
`FORK_INSTRUCTION_REFUSED`; `MeerkatError.details` carries the typed
`fork_instruction_refusal` (its cause and keys). Pass `"reactivate_inherited"`
to give the child its own activation of every key that was effective in the
source; `SessionForkResult.reactivated_instruction_count` counts those rows,
which `message_count` includes. A prefix without activation rows forks the same
way under every value. See
[session/fork_at](/api/rpc#session%2Ffork_at).

### Detached jobs and monitors

The public job wrappers are `jobs_get`, `jobs_list`, `jobs_cancel`,
`jobs_progress`, `jobs_result`, `jobs_artifacts`, `jobs_retry`, `jobs_health`,
`jobs_subscribe`, and `jobs_unsubscribe`. `monitors_start` creates a detached
monitor job. Meta worker implementations additionally use the six
`meta_job_*` authority-checked mutation methods.

Every public Python RPC wrapper binds its request and result transport boundary
to generated RPC-schema contracts. The job request and result dataclasses in
0.8.24 are available from `meerkat.generated.types`, but are not re-exported
from `meerkat`:

```python
from meerkat.generated.types import JobsListParams

jobs = await client.jobs_list(JobsListParams(session_id=session.id))
```

### Approvals, artifacts, and projected events

- approvals: `request_approval`, `list_approvals`, `get_approval`,
  `decide_approval`
- artifacts: `list_artifacts`, `get_artifact`, `download_artifact`
- cursor-based event recovery: `latest_event_cursor`, `list_events_since`,
  `event_snapshot` when host event projection is enabled

Approval calls maintain audit records only; they do not automatically gate,
authorize, or execute an action. Records persist when the RPC bundle exposes a
store path and otherwise remain process-local. See
[JSON-RPC approvals](/api/rpc#approvals).

When projection is enabled, use cursor replay or a snapshot after reconnect or
a typed live-stream lag marker. A live subscriber is an observation surface,
not the persistence boundary. Explicitly ephemeral memory realms do not expose
the replay APIs.

## Live channels

`RealtimeChannel` and the old realtime convenience helpers are no longer public
SDK handles. The current helper is `LiveChannel.session(client, session_id, ...)`,
which binds a session id and stores the `channel_id` returned by `live/open`.

```python
from meerkat import LiveChannel, MeerkatClient

client = MeerkatClient()
await client.connect(live_ws=True)
session = await client.create_session(
    "Open a live channel",
    model="gpt-realtime-2",
    provider="openai",
)
channel = LiveChannel.session(
    client,
    session.id,
    turning_mode="explicit_commit",
    seed_max_chars=24_000,
)
opened = await channel.open()
await channel.send_input_text("hello")
await channel.commit_input(response_modality="text")
await channel.refresh()
await channel.close()
await client.close()
```

Direct `MeerkatClient` helper names mirror the RPC methods:

- `live_open(session_id, turning_mode=None, transport=None, seed_max_chars=None)`
- `live_webrtc_answer(channel_id, token, offer_sdp)`
- `live_status(channel_id)`
- `live_close(channel_id)`
- `live_send_input_text(channel_id, text)`
- `live_send_input_audio(channel_id, data_base64, sample_rate_hz, channels)`
- `live_send_input_image(channel_id, idempotency_key, mime, data_base64)`
- `live_send_input_video_frame(channel_id, codec, data_base64, timestamp_ms)`
- `live_commit_input(channel_id, response_modality=None)`
- `live_interrupt(channel_id)`
- `live_truncate(channel_id, item_id, content_index, audio_played_ms)`
- `live_refresh(channel_id)`

`live_send_input_image` requires a caller-stable, session-scoped key. Its
return value proves queue acceptance only; durable success is the later
`user_content_committed` observation carrying that same key.

Pass a positive `seed_max_chars` to bound serialized seed messages and request
a core-owned whole-turn suffix at open time. Omission preserves the complete
seed; zero is rejected. Every ordered System message must fit; an existing compaction
summary may be retained, and any truncation reports degraded continuity.
Canonical image identity, tombstone, and accounting sidecars remain complete.

`live_open` returns a discriminated transport object. The `websocket` variant
has `url` and `token`. The `webrtc` variant has `token`, `answer_method`, and
an optional `http_url`; create an SDP offer and pass it to
`live_webrtc_answer`. Do not assume every transport has a URL.

WebRTC requires `connect(live_webrtc=True)` and an `rkat-rpc` binary compiled
with its non-default `live-webrtc` Cargo feature. The 0.8.24 auto-downloaded
release binary does not include that feature. Add an audio track or the
`meerkat.live` data channel, set the browser peer's local description, wait for
ICE gathering to complete, then send `peer.localDescription.sdp`. The protocol
has no candidate-trickle RPC. Install the returned `answer_sdp` as the browser
peer's remote description before sending live input.

`MeerkatClient.parse_live_observation(raw)` type-narrows a frame from the live
transport against `WireLiveAdapterObservation`. Since 0.9.4 that union includes
`turn_failed`, a response the provider ended without completing. Its `failure`
is a `WireLiveResponseFailure`: route on `status` (`"failed"`, `"incomplete"`,
`"in_progress"`, or `{"unknown": {"debug": ...}}` for a status without a wire
name); `reason`, `code` and `message` are diagnostics only.
`WireLiveResponseFailure` and `WireLiveResponseFailureStatus` are exported from
`meerkat`. See the [realtime guide](/guides/realtime) for what the channel does
next.

## Event compatibility note

The parser raises `MeerkatError` with code `UNKNOWN_EVENT_TYPE` only when a
present event type is outside the generated known-event inventory. An
inventory-known type without a handwritten parser class arrives as
`UnknownEvent`, preserving the wire type in `event.type` and the complete
payload in `event.data`. A missing event type or a malformed payload for a
handwritten parser class is preserved as `UnknownEvent` with
`type="malformed_event"`.

The current inventory includes `server_tool_content`, all four
`model_fallback_*` events, `transcript_rewrite_audit_receipt_committed`,
`boundary_append_applied`, and `boundary_appends_discarded`. These currently
use the raw-preserving `UnknownEvent` path, as do `reasoning_delta`,
`reasoning_complete`, `assistant_image_appended`,
`turn_usage_accounting_unmeasured`,
`turn_usage_accounting_identity_disputed`, `interaction_callback_pending`,
`peer_content_ingested`, and `provider_cache_breakpoints_discarded`. See the
[RPC event reference](/api/rpc#notifications) for their wire contracts.

`live_channel_closed` has a handwritten parser class and arrives as a typed
`LiveChannelClosed` event: `session_id`, `channel_id`, `reason` and
`reopen_recommended`. It is published once for every committed close of one of
the session's live channels. `reason` is one of the `LiveChannelCloseReason`
values `client_requested`, `client_disconnected`, `provider_closed`, `error`,
`media_fault`, `replaced` or `open_abandoned`; any other value is preserved as
`UnknownEvent` with `type="malformed_event"`. `reopen_recommended` is true
only for a `media_fault` whose session may still reopen the channel with its
retained context.

`RunStarted.input` preserves the typed `RunInput`: either
`{"kind": "content", "content": ...}` or
`{"kind": "pending_tool_results"}`. Content may be text or content blocks;
the continuation variant does not fabricate a prompt. `RunFailed` accepts
the current `error_report` and derives its `error_class` and `error` display
fields from that report.

Since 0.9.4 a run that failed because the provider refused or filtered the
response (`error_class` `content_filtered`) carries `error_report.reason` as an
`AgentErrorReason` with `reason_type == "content_filtered"`, `stop`
(`"refusal"` or `"content_filter"`) and `detail`, the provider's own account as
a dictionary tagged by `"provider"` (`anthropic`, `open_ai` or `gemini`), or
`None` when the provider gave none. A `detail` that is not a provider-tagged
dictionary reads as `None`, and a `stop` the SDK does not know reads as an
unknown reason with the wire object in `raw`. SDKs before 0.9.4 read every such
reason as unknown and keep it raw.

`ToolConfigChanged.payload` is a `ToolConfigChangedPayload` whose `settled`
field replaces `persisted` in 0.9.4. It says whether the change is a settled
lifecycle fact rather than a pending or draining step, derived from
`status_info` the way `rkat-rpc` derives it; the stored bit (`settled`, or
`persisted` from `rkat-rpc` 0.9.3 and earlier) is used only for a status the
SDK does not know. It says nothing about configuration: whether a change was
written there is the `persisted` of the `mcp_add`, `mcp_remove` and
`mcp_reload` responses.
Stored notices in session history stay raw and can carry either key. A 0.9.3
SDK requires `persisted` and fails on every `tool_config_changed` event from a
0.9.4 `rkat-rpc`. The binary the SDK downloads always matches it, so this
happens only with a binary you supply (`MEERKAT_BIN_PATH`, an explicit
`rkat_path`, or `rkat-rpc` on `PATH`); upgrade the SDK with the binary.

`CompactionCompleted` carries two fields new in 0.9.4:

- `summary_source` (`CompactionSummarySource`): who wrote the summary.
  `kind` is `provider_call` (with `source_bound`, a
  `SummarizationSourceBound` whose `kind` is `whole`, `trimmed` with
  `through` = `tool_results`, `context` or `user_requests`, or
  `requests_only` with `kept` and `of`), `host_curator` or
  `mechanical_fallback`. A kind this SDK does not know is `unknown`, with the
  wire kind in `raw_kind` and the wire object in `raw`. `None` for a
  completion recorded before 0.9.4.
- `estimated_history_tokens_after`: the estimated history tokens the rewrite
  left, in the unit of `CompactionStarted.estimated_history_tokens`; `None` for
  a completion recorded before 0.9.4 or when the history could not be
  measured.

`Retrying` parses the current wire shape, which carries one typed `retry`
schedule: `attempt`, `max_attempts`, `error` and `delay_ms` are projections of
`retry.plan.attempt`, `retry.plan.max_retries`, `retry.failure.message` and
`retry.plan.selected_delay_ms`, and the schedule itself is kept in `retry`.
The flat legacy shape is still accepted. `HookFailed.reason` contains a known
native cause or an `UnknownHookFailureReason` with `reason_code="unknown"`.
Unknown wire reason codes and confinement refusal strings retain the exact
original dictionary in `reason["raw"]` and its original reason code in
`reason["raw_reason_code"]`; their `error` display is `"unknown hook failure"`.
Known native dictionaries stay unchanged. Read their `reason_code` and, for
confinement refusal, `refusal` instead of parsing the display-only `error`.
Check field types before using values inside the unknown wrapper's `raw`.

The legacy flat `error` wire remains accepted with `reason=None`. A present
`reason` is authoritative even when `error` is also supplied. Malformed
required fields in a known cause still produce
`UnknownEvent(type="malformed_event")` with the raw payload preserved, without
falling back to the legacy error.

`request_reasoning_lowered` is likewise recognized through the generated
inventory and arrives as `UnknownEvent` with its payload in `event.data`.

`hook_launch_refused` is recognized through the current generated inventory
and arrives as `UnknownEvent` with the full wire payload in `event.data`,
including `reason` and the exact optional `tool_use_id`. This mechanical
prelaunch fact is separate from a permission denial or a terminal run event.

### Assistant message identity

`TurnStarted`, `TextDelta`, `TextComplete`, `TurnCompleted` and `Retrying`
carry an optional `assistant_message_id`. It equals `assistant_message_id` on
the `block_assistant` `SessionMessage` that history returns for the same
message, so join live rows to history by that id, never by text or position.
`RunCompleted.assistant_message_id` names the message whose text `result`
repeats. The raw-preserving `UnknownEvent` payloads of `reasoning_delta`,
`reasoning_complete`, `server_tool_content` and `assistant_image_appended`
carry the same key in `event.data`. The value is `None` on data written before
0.8.45. Only a history row carrying the id is the commit: `TurnCompleted` is a
live signal that can arrive before work that still fails the run, and can be
missing for a committed row, so reconcile against history when the run ends.
Rows the realtime transcript materializer commits have no id; their
`SessionMessage.realtime_origin["provider_item_ids"]` match the provider item
ids on the live transport's realtime observations. See
[assistant message identity](/reference/session-contracts#assistant-message-identity)
for retry, compaction and rewrite semantics.

## Capability and error model

Capabilities:

```python
client.capabilities
client.has_capability("comms")
client.require_capability("comms")
```

Errors:

```python
from meerkat import (
    BinaryIntegrityError,
    CapabilityUnavailableError,
    MeerkatError,
    SessionNotFoundError,
    SkillNotFoundError,
)
```

All SDK errors derive from `MeerkatError`.

`BinaryIntegrityError` (code `BINARY_INTEGRITY_MISMATCH`) means the
auto-downloaded `rkat-rpc` archive, the binary inside it or its cached copy
does not match the sha256 the package pins; it carries `asset`, `path` (the
cached binary, or `None` for a download), `expected_sha256` and
`actual_sha256`, and the SDK never falls back to another binary.
`BINARY_DIGEST_UNAVAILABLE` means the package pins no digest for this version
and platform (a source or git install), so it will not download one; its
message names the exact release asset URL. `BINARY_DOWNLOAD_FAILED` is a
transport fault (a detected cut-off body included): a transport fault the SDK
can detect is never reported as tamper. `BINARY_DOWNLOAD_TOO_LARGE` is an archive over
256 MiB. See
[The rkat-rpc binary](/sdks/python/overview#the-rkat-rpc-binary).

When the `rkat-rpc` child exits by itself (a crash, for example), pending and
later requests fail with `CONNECTION_CLOSED`, keeping the child's stderr tail.
Since 0.9.4 they fail at most about a second after the exit, even while a
process the child started still holds its output pipes; before, they could
wait until those pipes closed. `MeerkatClient.close()` likewise returns once
the child has exited: it terminates the child, waits up to 5 seconds, then
kills it. On Python 3.11 and 3.12, and on 3.13 and 3.14 before the fix for
CPython issue 119710, `close()` used to wait the full 5 seconds for a child
that had already exited.

A failed `session.send(...)` carries the server's typed `CommsSendErrorData`
in `MeerkatError.details`, tagged on `code` (`peer_not_found_or_not_trusted`,
`peer_unreachable`, `peer_admission_dropped`, `peer_input_rejected`,
`peer_wake_refused`, `send_ambiguous`, `send_failed`, `invalid_command`).
`peer_wake_refused` is a seated member whose wake was refused: nothing was
delivered, `refusal["kind"]` says why and `retryable` whether a later send can
succeed. `comms_send_error(error)`
returns it, or `None` for any other error. Branch on `code`, never on the
message text. `send_ambiguous` means the delivery may already have landed
(`retry_safe` is `False`, `required_action` is `"reconcile"`): reconcile by its
`envelope_id` before any new attempt, since a retry can duplicate it.

```python
from meerkat import MeerkatError, comms_send_error

try:
    await session.send(kind="peer_message", to=peer_id, body="Hello!", handling_mode="queue")
except MeerkatError as error:
    failure = comms_send_error(error)
    if failure is None or failure["code"] != "peer_unreachable":
        raise
    print(f"{failure['peer']} is unreachable: {failure['reason']}")
```

A mob destroy that did not finish (`mob_destroy`, or `mob_lifecycle` with
`"destroy"`) fails with code `mob_destroy_incomplete`; its `details` carry
the `destroy_report` and `retryable: True`.
`mob_destroy_incomplete_report(error)` returns that report as a
`WireMobDestroyReport`, or `None` for any other error. Retry the destroy
later: `member_reload_refusals` names each member whose reload the runtime
refused, with its typed `refusal` (a kind this SDK does not know reads as
`{"kind": "unknown"}`).

```python
from meerkat import MeerkatError, mob_destroy_incomplete_report

try:
    await client.mob_destroy(mob_id)
except MeerkatError as error:
    report = mob_destroy_incomplete_report(error)
    if report is None:
        raise
    for refused in report.member_reload_refusals or []:
        print(f"{refused.member}: {refused.refusal['kind']}")
```
