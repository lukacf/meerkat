- A persistent `meta_gateway` (`persistent_sessions: true`) with no mob definition file (`config/mob.toml` or `<workspace>/definition.json`) starts again after an upgrade on the state directory that holds its mob, with no operator step. Such a launch runs the built-in default mob, whose id was derived from the launch, the release version included; the state directory keeps the id it was created with, so the first start of every later release was refused: `the supplied mob definition diverges from the canonical definition in this storage, in: id` (answered as `-32603` `failed to bootstrap local runtime`). Meta 0.9.9, the oldest release looked at, through 0.9.16 had this. The gateway now takes the mob id the state directory records (`definition.id` in `<state directory>/event_log.sqlite3.composition.json`) for the built-in default mob. The 0.9.16 upgrade step, copying that `definition` to `<workspace>/definition.json`, is no longer needed; a workspace that has the file keeps starting, and a definition file still names its own mob. A state directory that records no mob gets an id derived from the launch without the release version, so a mob created by this release keeps its id under the next one. The definition is still judged: a launch with no definition file on a state directory whose mob was created from a definition file that differs from the built-in default in a field other than its id is refused with `-32019` `divergent`, naming the fields that differ. The log can mislead here: with no definition file the check of the definition still names a newly derived id in two WARN lines (`mob profile declares keys the profile does not define`, with `mob_id=tux-...`), and no line says that the recorded id was taken. Nothing is written under the derived id, and the id the gateway serves is the one `meta/init` answers (the WARN lines: seen in runs of a candidate build on states of the published 0.9.15 and 0.9.16; that nothing is written: read from the source). Going back: a gateway of Meta 0.9.9 through 0.9.16 (earlier ones were not looked at) on a default mob that this release created derives its own id and refuses as before, unless the workspace has the `definition.json` of the 0.9.16 step. Rust: `mob_composition_manifest::recorded_definition_id` reads the recorded id.
