## Known limitations

The known limitations of Meerkat 0.9.16 are in the release's own notes: section 0.9.16, Known limitations, of CHANGELOG.md at this tag (https://github.com/lukacf/meerkat/blob/v0.9.16/CHANGELOG.md). Read the Upgrade notes of the same section before you upgrade or roll back. Entries added after the release will be in CHANGELOG.md on main, not at the tag; each will also be printed below, with its date.

- Added 2026-11-17, after the release. A `[confinement]` table in a project's `.rkat/config.toml` is not read, and `rkat` does not warn about it: an agent's shell is not confined by it. State confinement in the user document, `~/.rkat/config.toml`, as `[confinement.all]` with `mode = "workspace"`, so that it covers every launch kind; do not rely on a realm document as its only statement. The `--confinement` flags are for the one command that carries them. Whichever you use, check that command's stderr for the confinement lines: three, one for each launch kind, when a requirement applies, and none when none does; where none is printed, the command is not confined. On Linux a start that confines every launch kind while the realm state lies inside the directory the command is started in, which is the default with `rkat`, is refused and asks for `--state-root <dir>` outside the project. The section "Confinement for one project" of the CLI configuration page says what else changes under confinement. (That the project file is not read and that the user document and the flags are, by runs of the published 0.9.16 `rkat` on Linux x86_64 on a host without a confinement backend; reported by a user on 0.9.15 on macOS; macOS and 0.9.15 were not run by the maintainers.) A fix is planned.

- Added 2026-11-17, after the release. TypeScript SDK (`@rkat/sdk`): when the `rkat-rpc` process the client started exits, or is killed, while the program is still using the client, a call that writes to it after it is gone and before Node has processed its exit ends the Node program with `Error: write EPIPE` reported as `Unhandled 'error' event`, exit code 1, instead of the call rejecting. That is the case when the process is gone (a few milliseconds after a kill) and the program has not returned to its event loop since, for example a synchronous stretch of 20 ms or more between the process's end and the next call. This holds for every request method, for starting a streaming session or turn, for subscribing to a session's, a mob's or a mob member's events, and for the reply to a tool call that the process asked the program to run. It is rare; a program that must not end this way installs a `process.on("uncaughtException", ...)` handler before `connect()` and keeps it while the client is connected: in the handler, ignore only this error (`error.code === "EPIPE"` and `error.syscall === "write"`); for any other error, print it and exit with a non-zero code; do not throw from the handler. The call then rejects with `PROCESS_EXITED` (18 of 18 starts on the published 0.9.16 on Linux with Node 22, with 20 or 50 ms of synchronous work between the kill and the call; without the handler the program ended in 17 of 18 such starts; not run on macOS or on Windows). Where the write was the reply to a tool call, the call that was waiting on the process rejects. While it is installed the handler also swallows a `write EPIPE` on the program's own output. This is so in every release of the TypeScript SDK since 0.3.0 (read from the source at the release tags). A fix is planned.

- Added 2026-11-17, after the release. Peer requests: on a host whose realm is on disk, a session that has sent a peer request stops running when a response to that request arrives without a result. That is `rkat`, `rkat-rpc`, `rkat-rest` and `rkat-mcp` on any realm on disk, whatever the session format (a JSONL realm keeps the runtime's rows in SQLite too), and a Rust host on the disk composition or one that hands in the SQLite runtime store; the tell is a file `sessions.sqlite3` (SQLite realm) or `runtime.sqlite3` (JSONL realm) in the realm directory (read from the source). A response is what the agent tool `send_response` sends, or a host's or SDK caller's `peer_response` through the comms send; its `result` is optional (the documented `comms/send` call lists it as optional, and a call that leaves it out sends a response without a result: the Python and TypeScript SDKs' `send`, RPC, REST and the MCP tool `meerkat_comms_send`; read from the source, not run), and the instruction a responding agent is shown with each request gives `completed` without a result as its example. Messages (`send_message`, `reply_to_peer`) are not responses and are not affected, and the responses Meerkat itself sends always carry a result (read from the source). When the requesting session has handled such a response, the SQLite runtime store refuses, at every try, to record that run as finished; the session's loop logs `ERROR meerkat_runtime::runtime_loop: failed to durably publish directed interaction terminal ... terminal completion finalization lost the exact durable CAS` and `WARN meerkat_runtime::runtime_loop: runtime-loop exit teardown did not complete; the registration is detached until an explicit resume completes its unregister` (on this release that resume does not complete it; read from the source), and the session runs nothing further; an unregister of the session is refused. On `rkat-rpc`, `runtime/health` then answers `status` `degraded` with `session_runtime_loop` `degraded`, where both read `ok` before; the answer names no session (shown by two runs of the published 0.9.16). A response that carries a result does not stop the requester. If the host is then ended and started again, the session can be unable to run for good: after a stop caused by a progress response (`accepted`) its first drain, a stop and an unregister are refused with `Recovery corruption: pending terminal owner <id> is absent from the live shell`, and after a refused stop or unregister every later registration too; the same refusal follows any end of a host while a run that was started by, or consumed, a peer's progress response is unsettled. The session's committed history can still be read (`session/read`). Before any restart keep a copy of the realm directory together with the sessions' comms identity directory (with the default in-process comms), which is not inside it: `~/.rkat/session_comms_identity` for `rkat` and `rkat mob host`; for `rkat-rpc`, `rkat-rest` and `rkat-mcp` the per-user state directory (`$XDG_STATE_HOME/meerkat/session_comms_identity`, else `~/.local/state/meerkat/session_comms_identity`, on Linux; `~/Library/Application Support/meerkat/session_comms_identity` on macOS; `%LOCALAPPDATA%\meerkat\session_comms_identity` on Windows); or, for any of the four, `<root>/.rkat/session_comms_identity` where `--user-config-root` names a root; and, for `rkat mob host`, its host identity directory (`<state root>/host-identity` unless `--identity-dir` or `[mob_host].identity_dir` names another) (shown by runs of the published 0.9.16 `rkat` and `rkat-rpc` on Linux; the rest read from the source). For a mob on Meta, see the entry of the same date on the Meta 0.9.16 release page (https://github.com/lukacf/meerkat/releases/tag/meta-v0.9.16), which says what an operator sees, what was run and what not to do. Affected: the stop, 0.9.5 through 0.9.16 (by the source at the release tags, and shown by runs on builds of the 0.9.5, 0.9.11 and 0.9.15 tags; a build of the 0.9.4 tag did not stop, 3 of 3); the refusal after a restart, 0.8.11 through 0.9.16 (by the source at the release tags). A host on a memory realm, and a Rust host whose runtime state is in a runtime store of its own implementation and not in the SQLite runtime store, do not get the stop (read from the source). (Shown by runs of the published Meta `rpc_gateway` 0.9.16, 0.9.15 and 0.9.14, by two runs of a mob of two members on the published `rkat-rpc` 0.9.16, and by runs on a build of the release commit.) Fixes are being prepared.
