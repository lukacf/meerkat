- Mobs: a second store file for the same mob in the mob root can become the file the mob runs on, and what the mob then writes is lost if that file is removed later. `rkat`, `rkat-mcp`, `rkat-rest`, `rkat-rpc` when its realm paths are resolved (so, inferred, the Python and TypeScript SDKs that start it), a Meta gateway whose storage is durable, and a Rust host that builds its mob state with a persistent storage root restore their mobs from `<the realm's root>/mobs` (read from the source; `rkat-mob-mcp`, a state built without a root and the browser runtime do not). They take for a mob's store every regular file directly in that directory whose name begins with `mob--` and whose extension is exactly `db`; nothing between is looked at, and the mob's id is read from the records in the file, not from its name. Taken: `mob--x-copy.db`, `mob--x (copy).db`, `mob--x.bak.db`. Not taken: `mob--x.db.bak`, `mob--x.bak`, `mob--x.db.orig`, `mob--x.DB`, `copy-of-mob--x.db` and any file in a subdirectory. Where two taken files hold the same mob id, the mob is served from whichever of the two the directory lists first, which can be the copy; the other is refused at its resume and kept as it was found. From then on what the mob writes into its own store (a member added, for one) goes into the file it is served from; if that file is removed later, whether it is the copy or the original, the next start serves the other one, stale, with no error, and those changes are gone. The members' session histories are not in that store and are not lost. The sign is two warning lines in the host's log at the first mob access after each start while both files are there, about a millisecond apart; neither names the file: `WARN meerkat_comms::inproc: refusing inproc registration that would unbind a live route under this name` with `peer_name=<id>/__mob_supervisor__`, then `WARN meerkat_mob_mcp: quarantining a persisted mob store: the rest of the restore goes on mob_id=<id> class=resume_refused`; the inventory's list of quarantined stores stays empty for it. To avoid it, keep a backup of a store file outside the mob root or under a name that is not taken: a copy kept as `mob--<id>.db.bak` in the mob root was left alone, byte-identical, with no warning (two runs of two starts each). Where the lines are in the log, find which of the two files the mob runs on before removing either: count the rows of `mob_events` in each (`sqlite3 -readonly <file> "select count(*) from mob_events;"`, with the host running or stopped; the read leaves the `.db` file byte-identical). The file with more rows is the one the mob runs on (4 against 3 in the runs, in both orders); equal counts tell nothing (both files answer the same until the mob has written something), and a modification time alone is not a safe sign (a fresh copy is newer than the original until the original is written again). Then stop the host and take the other file out of the mob root: run in both orders, the next start served the remaining file with its members, ran turns and logged no warning. Affected as described: 0.9.9 through this release (shown by runs on a build of the 0.9.16 tag, 14 passes, on Linux ext4, none of them through one of the binaries named above; read at 0.9.9; the releases between by a search of all tags by content). Earlier releases differ, read from the source and not run: in 0.8.24 through 0.9.3 (read at both) a refused second file fails the whole restore, every mob access answers the error and nothing is destroyed; in 0.9.4 through 0.9.8 the second file is kept aside and the restore goes on, with another warning (not traced further); before 0.8.24 the mob resumed second could be destroyed, and the first could be the copy: on those releases leave no copy in the mob root. Read from the source, not run: that the restore of other mobs goes on beside a refused file (the runs had one mob), and that a taken file which holds no events is removed by the restore. Not run: a second process on the same root; other platforms. Not read: which RPC or CLI calls answer from the inventory. This release holds no fix for it (read from the source).
