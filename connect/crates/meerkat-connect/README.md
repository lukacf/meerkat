# Meerkat Connect native conversation

This page distinguishes current private source wiring from historical component checks. The standalone product still awaits native and installed-product qualification. Current native composition depends on the selected candidate sources, not merely the older released version numbers in the historical examples below. See the [implementation evidence](../../docs/IMPLEMENTATION.md) and [availability](../../docs/site/availability.mdx) for qualification limits.

With a coherently assembled private product, run `meerkat-connect` in an interactive terminal, or `meerkat-connect --realm family` for an explicit realm. The source implements this sequence:

1. Choose a stored realm or name a new one. Connect verifies and prepares its supplied resource bundle, then asks for protected setup-helper access. Accepted realm, configuration and grant changes can remain saved if later setup stops.
2. Use the selected model's existing credentials, create its first supported API-key connection, or follow the terminal's configured sign-in/key-entry flow. `--choose-model` opens model setup. Review the setup assistant's model and tools before the conversation opens.
3. Describe the task, for example, "Add tools for reading Hacker News, with read-only access." The agent can use the catalog or research another integration, then request the exact available installation and access reviews. Enter credentials only in the protected controls, never in chat.
4. Read the reported installation, account, configuration and grant outcomes separately. After confirmed setup shutdown and cleanup, the host can finalize the reviewed change and resume this same setup conversation with its actual result. Additional integrations need fresh checks and reviews.

This continuation does not establish successful service use or resume an unrelated exited `rkat` command. Run the business request through an ordinary agent in the selected realm under current native policy; fresh-session use still needs the corresponding acceptance evidence. There is no `rkat connect` command. REST and outer-MCP Connect entry points remain deferred; MCP services used as integrations remain in scope.

Ordinary `meerkat-connect` now lets the agent request the paired host selection after hearing the person's frontend request. No `--paired-host` flag or service/frontend mode menu is required. `paired_host_select_host({})` pauses conversation progress and asks for the running host and a remembered or memory-only pairing choice in the protected terminal. The original native session, provider binding and history remain in place. The model receives a nonsecret selection result and current tool availability; the origin, code, cookie and credential-store choice are not supplied as model arguments or results. Once captured, the host cannot be replaced in that conversation. `--paired-host <origin>` pairs with the selected host before the conversation while retaining the same checked service preparation capability for hybrid setup; host selection is not offered again.

Selection is a mutating human handoff, so the native caller's read-only or narrower policy can refuse it before any prompt or host request. It authorizes no frontend submission, secret creation or cancellation: those retain their separate exact native decisions and uncertainty restrictions. Native configured global/per-tool timeouts are unchanged. When the protected interaction is active, expiry, cancellation or a lost handoff makes the terminal cancel and join the turn and exit without pairing retries; any host enrollment already completed remains PairedHost-owned. A confirmed paired client becomes visible only when the still-live native tool call consumes the private terminal handoff. Native aggregate turn limits may still prevent a subsequent model answer.

Ordinary CLI startup locates and prepares the supplied service bundle before model setup, the paired host pairing or conversation input. The protected helper review and native setup stage precede `open_native_setup`. Once the conversation opens, `toolkit_prepare_services({})` exposes that retained setup connection; it does not authorize a replacement preparer or bypass install review. The native router owns connection readiness and catalog publication. The [older lazy-services report](../../docs/verification/20261007-connect-lazy-services/REPORT.md) records its historical composition and limits, not the current standalone startup sequence.

The ordinary session offers `list_integration_recipes` and `read_integration_recipe` after native setup opens. List up to 20 compact summaries, optionally using an exact package `name` chosen by the agent. All matching publishers and versions remain in stable identity order; preserve the name, snapshot and cursor when paging. Read a listed identity and digest for its complete provenance, assessments and requirements. The inventory combines the canonical 101 adopted entries and 10 discovery recipes without changing their separate origins, roles, scoped operations, strategies or evidence. It performs no semantic matching, ranking, host request, credential access or execution. Native caller policy still applies; after an uncertain effect, the existing exact-status restriction also refuses these reads.

Recipe metadata is investigation evidence, not a statement that this platform has matching resources, an installed integration, an authenticated account or runtime readiness. The agent can investigate outside the inventory using its available public research tool. If concrete runtime preparation is needed, the actual supplied bundle and its native `setup_catalog`/`setup_catalog_entry` observations remain separate. Rust console hosts can attach the same public `RecipeTools` dispatcher as described below; the six-tool the paired host preparation API is unchanged.
