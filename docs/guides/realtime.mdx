Live channels in Meerkat provide low-latency audio and text streaming plus model-gated still-image input through the `live/*` JSON-RPC methods. To use a live channel, create a session on a realtime-capable model (for example `gpt-realtime-2`) and call `live/open` to start the channel explicitly. Channel creation, status, refresh, input, interruption, truncation, and close are all caller-initiated through the live surface.

This guide covers how to open live channels, send input, and observe channel state.

## What this guide is for

Use this guide when you want to:

- open a live audio/text channel on a session
- send audio, text, or model-supported image input to a live channel
- understand live channel lifecycle and capabilities
- reason about live channels in the context of the normal session model

<Note>
`ModelCapabilities.realtime` remains the capability bit that gates whether `live/open` succeeds. Image input is a separate per-channel capability: check `LiveOpenResult.capabilities.image_in` before sending an image. The `--live-ws <addr>` flag on `rkat-rpc` enables the WebSocket audio transport.
For WebRTC, the binary must be compiled with the `live-webrtc` feature and
started with `--live-webrtc`. At least one of these runtime transport flags is
required for the `live/*` methods to be advertised.
</Note>

## Mental model

A session has exactly one conversation history. The session's LLM client is the active delivery mechanism for that history; most models deliver via request/response (e.g. Anthropic `claude-opus-4-8`, OpenAI `gpt-5.6-sol`), a small class delivers via a persistent bidirectional socket (e.g. OpenAI `gpt-realtime-2`). The only thing a realtime-capable model changes is *how* the model is reached — the session still owns history, tools, context, and turn boundaries.

```text
        +--------------------------+
        |   Session (history,      |
        |   tools, context)        |
        +--------------------------+
                     |
                     | session.model = "gpt-realtime-2"
                     v
        +--------------------------+
        | Live channel (caller-    |  audio/text at turn boundaries;
        | initiated via live/open) |  images after provider ACK +
        +--------------------------+  durable redacted receipt
```

Key invariants:

- **One canonical history.** The session is the source of conversational truth. Committed audio and text join the same history as non-live turns at turn boundaries. A provider-acknowledged image is materialized and persisted as canonical context before the channel emits its redacted `user_content_committed` receipt.
- **Capability gates channel open.** `ModelCapabilities.realtime` is the signal that determines whether `live/open` succeeds. No channel is opened automatically.
- **Channel lifecycle is caller-initiated.** Call `live/open` to start a channel, `live/close` to end it, and `live/send_input` / `live/commit_input` / `live/interrupt` / `live/truncate` to control flow.
- **Refresh without history replay.** `live/refresh` applies mutable session config (instructions, tools, audio format) to an open channel without interrupting audio flow. Identity swaps (model/provider) and canonical transcript or user-content-registry rewrites cannot be hot-applied; they return a typed reopen-required error and require `live/close` + `live/open`.

## Realtime-capable models

`ModelCapabilities.realtime: bool` is set per model in the curated catalog (`meerkat-models`; the `ModelCapabilities` type lives in `meerkat_core::model_profile`). Capability is catalog data, not prefix inference:

- **OpenAI**: `gpt-realtime-2` — the only realtime-capable model in the current catalog, with still-image input advertised as `capabilities.image_in == true`.
- **Gemini**: reserved for future `*-live*` endpoints — no production models today.
- **Anthropic**: no realtime-capable models today.
- **Self-hosted**: `realtime = false` by default.

Use `GET /models/catalog` (REST) or `models/catalog` (RPC) to inspect which models advertise `realtime == true` in the running runtime.

## Opening a live channel

A live channel is opened by creating a session on a realtime-capable model and
then calling `live/open`. These are separate lifecycle steps.

### Create, then open

Create a session on a realtime-capable model, then call `live/open`:

<CodeGroup>
```json JSON-RPC (create session)
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "session/create",
  "params": {
    "prompt": "Let's talk.",
    "model": "gpt-realtime-2",
    "provider": "openai"
  }
}
```

```json JSON-RPC (open live channel)
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "live/open",
  "params": {
    "session_id": "01936f8a-7b2c-7000-8000-000000000001"
  }
}
```

```python Python SDK
from meerkat import MeerkatClient

client = MeerkatClient()
await client.connect(realm_id="team-alpha", live_ws=True)
try:
    session = await client.create_session(
        prompt="Let's talk.",
        model="gpt-realtime-2",
        provider="openai",
    )
    channel = await client.live_open(session.id)
finally:
    await client.close()
```
</CodeGroup>

`live/open` returns a `LiveOpenResult` containing a discriminated transport
bootstrap, `WireLiveChannelCapabilities`, and `WireLiveContinuityMode`. Omitted
`transport` prefers WebSocket when its listener is configured and otherwise
selects WebRTC when that is the only enabled transport. Request
`"transport": "websocket"` or `"transport": "webrtc"` when the choice must be
stable. WebSocket requires `rkat-rpc --live-ws <addr>`.

<Note>
The direct WebSocket input path accepts JSON text chunks and negotiated raw
PCM audio only, with a 2 MiB aggregate and per-frame ceiling. It does not
accept inline images. Send every image through JSON-RPC `live/send_input`;
the JSONL control plane accepts frames up to 64 MiB (excluding the newline),
which accommodates the documented 20 MiB decoded-image ceiling plus base64
and envelope overhead.
</Note>

### WebRTC SDP exchange

WebRTC is a feature-gated runtime transport. A binary without the
`live-webrtc` Cargo feature does not expose `--live-webrtc` or
`live/webrtc/answer`. Start a capable binary with:

```bash
rkat-rpc --live-webrtc
```

You can enable both transports at once:

```bash
rkat-rpc --live-ws 127.0.0.1:4900 --live-webrtc
```

Open the channel explicitly as WebRTC:

```json JSON-RPC
{
  "jsonrpc": "2.0",
  "id": 3,
  "method": "live/open",
  "params": {
    "session_id": "01936f8a-7b2c-7000-8000-000000000001",
    "transport": "webrtc"
  }
}
```

The result carries the channel-bound signaling material:

```json Result shape
{
  "channel_id": "ch_01936f8a-...",
  "transport": {
    "transport": "webrtc",
    "token": "single-use-bootstrap-token",
    "answer_method": "live/webrtc/answer"
  },
  "capabilities": {
    "audio_in": true,
    "audio_out": true,
    "text_in": true,
    "text_out": true,
    "image_in": true,
    "video_in": false,
    "transcript_supported": true,
    "barge_in_supported": true,
    "provider_native_resume": false
  },
  "continuity": {"mode": "fresh"}
}
```

The browser creates the offer. Include an audio track or the
`meerkat.live` data channel before `createOffer()` so the SDP contains a media
section, set the local description, and wait for ICE gathering to finish. Send
that complete offer through JSON-RPC and install the returned answer:

```javascript Browser signaling sketch
async function waitForIceGatheringComplete(peer) {
  if (peer.iceGatheringState === "complete") return;
  await new Promise((resolve) => {
    function changed() {
      if (peer.iceGatheringState === "complete") {
        peer.removeEventListener("icegatheringstatechange", changed);
        resolve();
      }
    }
    peer.addEventListener("icegatheringstatechange", changed);
  });
}

const peer = new RTCPeerConnection();
const observations = peer.createDataChannel("meerkat.live");
const media = await navigator.mediaDevices.getUserMedia({ audio: true });
for (const track of media.getAudioTracks()) peer.addTrack(track, media);

const offer = await peer.createOffer();
await peer.setLocalDescription(offer);
await waitForIceGatheringComplete(peer);

const answered = await rpc("live/webrtc/answer", {
  channel_id: opened.channel_id,
  token: opened.transport.token,
  offer_sdp: peer.localDescription.sdp,
});
await peer.setRemoteDescription({ type: "answer", sdp: answered.answer_sdp });
```

Here `opened` is the `live/open` result and `rpc` is the application's normal
JSON-RPC request helper. The bootstrap token expires after 60 seconds, is
single-use, and is bound to the returned channel. Replay, expiry, or a channel
mismatch fails typed. JSON-RPC is the canonical signaling path; the optional
`http_url` field in the transport union is only a convenience when a host
provides one.

### Bounding the initial seed

By default, `live/open` projects the full canonical history into the
new realtime provider session. Long-lived sessions can request a smaller seed
with the optional positive `seed_max_chars` parameter:

<CodeGroup>
```json JSON-RPC
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "live/open",
  "params": {
    "session_id": "01936f8a-7b2c-7000-8000-000000000001",
    "seed_max_chars": 24000
  }
}
```

```python Python SDK
result = await client.live_open(session.id, seed_max_chars=24_000)
```

```typescript TypeScript SDK
const result = await client.liveOpen({
  session_id: session.id,
  seed_max_chars: 24_000,
});

const channel = LiveChannel.session(client, session.id, {
  seedMaxChars: 24_000,
});
```
</CodeGroup>

The core counts the serialized projected seed messages and selects a recent
whole-turn suffix; it never slices an individual turn just to fill the budget.
`System` and `SystemNotice` rows do not consume this replay budget because
OpenAI Realtime does not replay them as conversation items. Their instruction
projection is derived separately from the full active materialized transcript,
so even a System larger than `seed_max_chars` remains exact. An existing
compaction summary may be retained as the head before the suffix.

If selection omits any history, `LiveOpenResult.continuity` reports
`mode: "degraded"`. Omitting `seed_max_chars` preserves the full-seed behavior.
The value must be positive; the server rejects zero.

Ordered transcript instructions, image identity, tombstones, and aggregate
accounting are outside the seed-message window and remain complete even when
older dialogue is omitted. Runtime instructions have no separate provider
sidecar.

### Configuration defaults

The session's default model can be set in config (`~/.rkat/config.toml` or project-local) via `default_model`. Any session created without an explicit `model` parameter inherits the configured default — so setting `default_model = "gpt-realtime-2"` makes live channels available by default. See the [Configuration guide](/concepts/configuration).

## Live channel methods

| Method | Purpose |
|--------|---------|
| `live/open` | Open a live channel on a session; optionally bound its serialized seed messages with positive `seed_max_chars` |
| `live/webrtc/answer` | Answer a browser SDP offer for an already-open WebRTC channel |
| `live/status` | Read live channel status |
| `live/send_input` | Send an audio, text, or model-supported image chunk to a live channel |
| `live/commit_input` | Commit pending input on a live channel (turn boundary) |
| `live/interrupt` | Interrupt the assistant turn on a live channel (barge-in) |
| `live/truncate` | Truncate assistant output at a client-tracked playback cursor |
| `live/refresh` | Apply mutable session config (instructions/tools/audio) to an open channel |
| `live/close` | Close a live channel |

<Warning>
The shared `live/*` family is registered when at least one live transport is
enabled: the WebSocket listener (`rkat-rpc --live-ws <addr>`) or a binary built
with `live-webrtc` and started with `--live-webrtc`.
`live/webrtc/answer` is registered only for the second case. When no WebSocket
listener is configured, `live/open` defaults to WebRTC; with neither runtime
flag, the live methods are not registered.
</Warning>

## Live observations and durable history

The media transport and the session event log answer different questions.
WebSocket or WebRTC carries low-latency channel input, output, and observations;
committed turn content still lands in the canonical session transcript.

The associated session-level `session/subscribe` event stream is a bounded
live subscription. A lagging consumer receives a typed `stream_truncated`
event with `reason.kind: "stream_lagged"` and `reason.dropped`, then continues
from the retained tail. This reports a gap in that subscriber's view, not a
truncated transcript or durable event log.

Built-in realm-backed persistent sessions can feed a separate durable event
audit projector through an unbounded queue independent of the UI ring. The
audit projection is asynchronous derived state, so when event evidence matters,
resume from the last available durable cursor with `events/list_since` and
reconcile against current session or channel state. Media frames and event
projection are not session commit authority; the committed transcript and
The `RuntimeStore`/backend carrier owns restart authority. `SessionStore` rows
are component/content state, not a second currentness owner.

## Sending image input

Image input is turn context, not a response trigger by itself. Check the
channel's `image_in` capability, submit the image with a caller-stable
`idempotency_key`, wait for its durable receipt, then follow it with dependent
text or audio. On an explicitly committed channel, `live/commit_input` can
request a response from image-only context after that receipt arrives.

<CodeGroup>
```json JSON-RPC
{
  "jsonrpc": "2.0",
  "id": 4,
  "method": "live/send_input",
  "params": {
    "channel_id": "ch_01936f8a-...",
    "chunk": {
      "kind": "image",
      "idempotency_key": "turn-42-diagram",
      "mime": "image/png",
      "data": "iVBORw0KGgo..."
    }
  }
}
```

```python Python SDK
result = await client.live_open(session.id)
if not result["capabilities"]["image_in"]:
    raise RuntimeError("bound realtime model does not accept image input")

await client.live_send_input_image(
    result["channel_id"],
    "turn-42-diagram",
    "image/png",
    image_data_base64,
)
# `status: "sent"` is queue acceptance. Wait for the matching
# `user_content_committed` observation before sending dependent input.
# (Transport observation-loop code is omitted here.)
await client.live_send_input_text(
    result["channel_id"],
    "What is the dominant color in this image?",
)
```

```typescript TypeScript SDK
const result = await client.liveOpen({ session_id: session.id });
if (!result.capabilities.image_in) {
  throw new Error("bound realtime model does not accept image input");
}

await client.liveSendInputImage(
  result.channel_id,
  "turn-42-diagram",
  "image/png",
  imageDataBase64,
);
// Resolution is queue acceptance only. Wait for the matching durable
// user_content_committed observation before sending dependent input.
// (Transport observation-loop code is omitted here.)
```
</CodeGroup>

The key is session-scoped and must be non-empty, at most 128 UTF-8 bytes, free
of control characters, and have no leading or trailing whitespace. Keep it
stable until the durable receipt arrives. Retrying the same key with the same
canonical MIME type and image bytes does not resend the image to the provider;
it returns the already-committed identity through another receipt. Reusing the
key for different content fails closed with
`image_input_idempotency_conflict`.

The `data` value contains the encoded image bytes as standard base64; do not
include a `data:` URL prefix. OpenAI Realtime currently admits PNG and JPEG,
verifies that the byte signature agrees with the declared MIME type, and
enforces a 20 MiB decoded-image safety ceiling before provider send. Invalid
keys, malformed base64, unsupported MIME types, content mismatches, and oversized images use the
typed rejection reasons `image_input_idempotency_key_invalid`,
`image_input_invalid_base64`, `image_input_unsupported_mime`,
`image_input_content_mismatch`, and `image_input_too_large`. Before provider
send, Meerkat also checks the canonical session's cumulative decoded image
history. A new image that would take that history above 40 MiB is rejected as
`image_input_history_budget_exceeded`; it is not sent or persisted. A binding
without image support uses `image_input_not_implemented`.

Do not place an image behind uncommitted text or audio. Commit that input first,
then submit the image as the first content in the fresh sequence; otherwise the
adapter rejects it with `image_input_requires_commit`. This keeps the durable
predecessor identity unambiguous.

### Acceptance, rejection, and durability

`live/send_input` has deliberately layered outcomes:

| Evidence | What it proves | Client action |
|----------|----------------|---------------|
| Typed JSON-RPC error with `LiveSendInputErrorData.error_code` | The request failed wire validation or queue admission; it was not accepted | Correct the request or retry after backpressure |
| `LiveSendInputResult { status: "sent" }` (or a resolved TypeScript helper promise) | The adapter command queue accepted the command | Continue observing the live channel; do not treat the image as durable yet |
| `command_rejected` observation | A queued command failed a scoped adapter/provider check; the channel remains usable | Route on `code.reason.kind`, correct it, and retry as appropriate |
| `user_content_committed` observation with the matching `idempotency_key` | Provider acknowledgement was projected into canonical history and persisted | The image is durable context; dependent input may proceed |

The same rejection reason can be immediate or asynchronous depending on which
layer detects it. For example, malformed base64 or an invalid key is rejected
before queue acceptance, while a content conflict discovered against durable
session identity is reported after the command drains. A terminal live error
or a missing receipt is never evidence of persistence.

For a WebRTC or direct-WebSocket channel, send the image through JSON-RPC
`live/send_input`, not the WebRTC data channel or direct WebSocket. The data
channel's fixed message ceiling is suitable
for control/audio coordination but not full images. An image envelope delivered
whole and decoded within the effective 65,535-byte ceiling receives the scoped
`image_input_transport_unsupported` rejection, and that data channel remains
open. A larger envelope may be rejected by the browser or SCTP transport before
Meerkat can classify it, so it cannot receive a server-side typed rejection.
Route every image through JSON-RPC; the data channel carries the receipt
described below.

If the adapter's bounded image queue or provider-ack window is full,
`image_input_backpressured` reports the byte ceiling without retaining another
caller payload. Retry the same key after earlier image receipts arrive.

The public transport does not echo image bytes back. After Meerkat has applied
the image to canonical session history, it emits a redacted
`user_content_committed` observation containing the item identity, content
index, media type, and caller `idempotency_key`. WebRTC callers must wait for
that receipt before sending RTP audio that depends on the image.

Reopening the same session hydrates blob-backed user images and replays the
typed images to the provider. Canonical live image history has a 40 MiB
aggregate decoded-image ceiling (two maximum-size images); every history
occurrence counts, including repeated references to the same blob. The live
input gate enforces that same ceiling before accepting each new image, so a
successfully committed live image cannot make an otherwise valid session
unreopenable later. Existing legacy or out-of-band history above the ceiling,
a missing blob, or bytes that do not match the durable content-addressed
identity still fail `live/open` instead of trimming or silently changing
visual context. Reduce canonical history explicitly or start a fresh session;
reconnect never substitutes placeholders for accepted images.

## End-to-end example

```python
from meerkat import MeerkatClient

client = MeerkatClient()
await client.connect(realm_id="team-alpha", live_ws=True)
try:

    # 1. Create a session on a realtime-capable model.
    session = await client.create_session(
        prompt="Ready for live audio.",
        model="gpt-realtime-2",
        provider="openai",
    )

    # 2. Open a live channel (returns channel_id + transport bootstrap).
    result = await client.live_open(session.id, transport="websocket")
    channel_id = result["channel_id"]
    # result["transport"] is the WebSocket URL + single-use token bootstrap
    # result["capabilities"] describes supported input/output modalities,
    # including model-gated image_in

    # 3. Send audio input and commit at turn boundaries.
    await client.live_send_input_audio(channel_id, audio_data, 24000, 1)
    await client.live_commit_input(channel_id)

    # 4. Close the channel when done.
    await client.live_close(channel_id)

    # 5. The session's history accumulates committed turns — same as a text session.
    history = await client.read_session_history(session.id)
finally:
    await client.close()
```

## Live channels and mobs

Each mob member has its own session, so live channels are per-member by construction. To make a member live-capable, set its profile's `model` to a realtime-capable model (for example in the `MobDefinition` TOML):

```toml
id = "live-demo"

[profiles.host]
model = "gpt-realtime-2"
provider = "openai"
peer_description = "Live audio host"
```

Open a live channel against the member's session after the member is spawned.
The dedicated CLI and RPC member-live controls are currently WebSocket-only,
for both local and placed members. Session-scoped `live/open` plus
`live/webrtc/answer` works only when the caller can address the owning session
directly, such as a controller-local member. Controller `session/*` methods do
not proxy a placed member's host-local session in multi-host v1, and
`mob/member_live_open` rejects WebRTC.

## GPT Live (public OpenAI Live API)

`gpt-live-1` is OpenAI's continuous voice model on the public Live API. It is a
different protocol from Realtime: audio runs continuously with provider-owned
speech scheduling, and the voice model does not run tools. Instead the session is
started with a *client delegation*: when the voice model decides a request
needs tools, files, or reasoning, Meerkat runs the work through the channel's
ordinary durable executor and returns the result as commentary that the voice
model speaks from. The canonical conversation persists through Meerkat's normal
transcript authority.

The path is compiled with the `openai-live` feature (`meerkat`, `meerkat-rpc`,
`meerkat-mob`, `meerkat-mob-mcp`; `meerkat-openai/live`). The host composes
`ExperimentalGptLiveOpenAuthority::new_public(PublicGptLiveOpenAuthorityConfig)`
with an OpenAI API-key binding in the realm, the model `gpt-live-1`, a voice,
and optional trusted session instructions. No operator, Gate0, or realm
admission applies: the catalog row and the configured binding are the
admission. The `gpt-live` model family never selects the Realtime WebSocket
factory.

The voice must be one of the public Live voices: `alloy`, `ash`, `ballad`,
`beacon`, `bossa`, `cedar`, `cinder`, `coral`, `delta`, `echo`, `gleam`,
`marin`, `meridian`, `quartz`, `ripple`, `sage`, `shimmer`, `stone`, `tempo`,
`verse`, `vesper`, `willow`. This set does not overlap with the private
experimental protocol's voices; an unknown name (for example `cove`) is
refused by the provider with HTTP 403 "Voice session access denied", which is
not an entitlement failure. The broker logs a warning naming the known voices
when a configured voice is outside this list.

Consumers open the channel through the existing execution-identity seam:

```json
{"method":"live/open","params":{
  "session_id":"...",
  "transport":"webrtc",
  "execution_identity":{"version":"v1","profile_id":"openai.gpt-live-1.client-context.v1"}
}}
```

Then post the browser's SDP offer with `live/webrtc/answer` and apply the
answer in the peer. The browser must not send `session.start`; the server
already started the session. Capability atoms are `live.execution_identity.v1`
and `live.execution.client_context.v1`, exactly as for the deprecated
experimental profile.

Public Live has no authoritative turn identifiers, completed-turn events, or
delegation task text. Meerkat synthesizes turns from transcript role
alternation and joins each delegation to the open or most recent user turn,
frozen to the transcript prefix observed before the delegation offset; the
resulting delegated transcript is a Meerkat-derived fact. Transcript
boundaries never prove playback completed.

Assistant output may begin on a fresh channel from startup context or later
canonical updates, without microphone input. Generated runtime authority keeps
an existing foreground correlation when present; otherwise it admits a fresh
assistant-only interaction with `ProviderInitiated` attribution. That attribution
does not claim which context append caused the speech or prove provider
consumption. It never creates a user transcript row. Later user input cannot
rewrite an already admitted assistant output's interaction or playback handle.

Missing transcript events do not establish silence or completion. In particular,
Meerkat does not finish assistant output after a quiet interval or after a
delegation-result acknowledgement: a delayed readout retains its output identity.
Applications must keep transcript grouping, playback evidence, and backend task
completion separate; see [OpenAI's session guidance](https://developers.openai.com/api/docs/guides/live-conversations).

On open and reopen, the selected canonical dialogue is supplied in native
`session.input` at provider session creation. User text and visible assistant
text retain their order and roles; executor System rows, SystemNotice rows, tool
calls, and raw tool results are not voice-session instructions or dialogue.
History is not injected as a speech-prompting `session.commentary.append`.
The provider allows up to 128 startup messages and 8,192 combined tokens.
Meerkat does not silently trim the selected seed to fit: select a bounded history
window at the shared open-projection seam, or resolve an oversize-seed rejection
before retrying. The canonical session history itself is unchanged.

### Generated context summaries for an existing agent

A dedicated host can opt in to a **generated factual summary**, rather than a
replayed history window. This is a Rust host composition seam, not a caller
prompt field and not transcript compaction:

```rust
use meerkat::session_runtime::live_summary::LiveContextSummaryPolicy;
use std::time::Duration;

let policy = LiveContextSummaryPolicy::new(
    summary_service, // Arc<dyn LiveContextSummarizer>
    256 * 1024,      // maximum serialized input bytes
    8 * 1024,        // maximum returned UTF-8 bytes
    Duration::from_secs(20),
)?;
let member_host = member_host.with_context_summary_policy(policy);
```

Implement `LiveContextSummarizer::summarize(LiveContextSummarySnapshot<'_>)`
as an asynchronous, tool-free model call returning `Result<String,
LiveContextSummaryError>`. The snapshot exposes `session_id()`, `messages()`,
`llm_identity()`, `canonical_message_cursor()`, and `max_output_bytes()`.
`messages()` contains the entire current model-boundary context window,
including context and tool-result rows and canonical voice transcript blocks
marked `TranscriptSource::SpokenUnmeasured`. Media remains typed references
rather than newly hydrated images. Observed speech is not a new user request
or proof of playback. Treat all source text as data; produce facts, decisions, ongoing
work, and uncertainties, not executable instructions or assurances that the
user heard unmeasured speech.

`llm_identity()` is the existing background text identity before the voice
override. A host can build a separate client using
`AgentFactory::build_llm_client_for_identity(&config, snapshot.llm_identity())`.
This resolves the configured binding through the factory/auth owner without
changing the agent's model, running its tools, or adding a transcript turn.
An independently configured summary model must likewise resolve through that
factory seam.

Use the ordinary `open_with_execution_identity` method with `seed_window: None`.
The host policy also regenerates summaries for both canonical-context and
delegation-result replacement opens. Combining a summary policy with a replay
window is rejected. Input overflow, empty or oversized output, timeout, source
change during generation, and producer errors refuse opening without falling
back to raw history. Limits count bytes, not characters or provider tokens;
the provider's independent startup token limit still applies.

The shared owner seals the summary to the source session, exact body revision,
rewrite generation, text identity, canonical cursor, and complete projected
context digest. The deferred provider open and seed acknowledgement recheck the
exact canonical source prefix. Observed transcript rows also advance the
canonical revision/cursor and follow ordinary append-only catch-up. A
conflicting body or rewrite cannot be disguised by an unchanged row count.
The summary enters public Live
as explicitly factual, unprivileged startup `session.input`, never
`session.instructions`. Continuity is `degraded`, not a claim of lossless replay.
`ExperimentalGptLiveWebrtcTransport::bound_context_summary(channel, session)`
exposes read-only, channel-scoped summary provenance until unbinding.

#### Concurrent historical context

`BeforeOpen` remains the default. A dedicated public Live host can instead
start native media without waiting for summary generation:

```rust
use meerkat::session_runtime::live_summary::LiveContextBootstrapMode;

let member_host = member_host.with_context_summary_policy(
    policy.with_bootstrap_mode(LiveContextBootstrapMode::Concurrent),
);
```

Configured binding and existing-member authorization still happen first.
The shared owner captures one exact committed source and its text identity
without acquiring the active background turn's mutation guard or hydrating
media. The original agent keeps its identity, model, tools, and full context.
The callback runs concurrently; append-only growth does not restart it.

The native session opens with no historical seed and no delivered canonical
prefix. Generated authority reserves the captured prefix separately, then
advances delivered coverage only after the exact quiet-context append is
acknowledged. Historical facts enter the provider's thinking lane, not
speakable commentary or trusted session instructions. Mirrorable post-snapshot
canonical text and peer rows follow that summary in order; newer live corrections are
reasserted as factual context rather than fabricated user turns.
Existing origin classification is unchanged: a generic inbox notice is not
promoted into conversational human input by this policy.

Read `context_preparation()` on the existing receipt-validated
`ExperimentalLiveChannelCustodyStatus`. Its `NotRequested`, `Preparing(stage)`,
`ProviderAcknowledged`, and `Failed(reason)` values are independent of the
channel's media `Pending`/`Active` phase. A host may display "Listening, loading
context" only after actual media activation. `ProviderAcknowledged` proves an
exact provider receipt, not model consumption, spoken output, or playback.
Summary failure remains visible while media can remain active; it never
silently changes to ready or falls back to raw history.

The provider owner bounds the total append and fragments it within the public
500-token limit. A complete acknowledgement requires every exact fragment
receipt. A native rejection can follow partial delivery and is therefore
ambiguous, not permission to replay the append blindly; actual channel-close
interruption remains a separate outcome.

Concurrent preparation is channel-owned. Exact close, identity change, or
replacement cancels and fences that channel's job. A late old result cannot
populate a new channel. The same opt-in policy applies to replacement opens;
their independent pending and activation receipts remain mandatory.

For an availability indicator, call
`ExperimentalLiveOpenAuthorityProvider::probe_execution_readiness(session,
execution_identity)`. Unlike catalog capability atoms, this checks the exact
durable source and configured credential binding. It prepares and drops an
unbound factory: no summary generation, text-model call, channel reservation, or
provider session is started. Auth resolution can acquire or refresh its normal
lease/credential, so this is not a zero-I/O status getter. Opening always
revalidates; a previous successful probe is not an admission receipt.

### Delegate to the selected existing member

The normal live delegation composer continues to create an isolated durable
fork. A console host that intentionally wants the selected agent to perform
voice-delegated work in its existing session can opt in at the mob feature
boundary:

```rust
use meerkat_mob_mcp::live_delegation::{
    compose_experimental_live_delegation_coordinator_with_policy,
    LiveDelegationExecutionPolicy,
};

let coordinator = compose_experimental_live_delegation_coordinator_with_policy(
    runtime,
    mobs,
    LiveDelegationExecutionPolicy::ExistingMember,
);
```

The coordinator resolves the source member from the channel's authoritative
session binding; the browser does not select a worker or supply an execution
session. Voice work uses the member's ordinary text model and generated input
admission. Concurrent ordinary text remains independent work. Close and
supersession cancel the exact voice operation, never retire the existing member
or interrupt whichever unrelated user turn happens to be running. Operation
ownership is retained with recovery evidence rather than reconstructed from the
host's current policy. Compose the returned coordinator into the same shared
context-mirror/activation host as the default coordinator.

### Continuous media without fabricated playback completion

Direct public Live WebRTC provides no per-utterance rendered-completion event
or mapping from media samples to Meerkat's opaque output handles. Neither
transcript grouping, `response.done`, audio-element `ended`, analyser silence,
nor output-address publication establishes playback completion.

For continuous console voice, opt in on the same public authority used by
initial and replacement opens:

```rust
use meerkat::experimental_gpt_live::PublicGptLivePlaybackPolicy;

let authority = authority.with_public_playback_policy(
    PublicGptLivePlaybackPolicy::ProviderManagedUnmeasured,
)?;
```

The default `CallerConfirmedSnapshots` mode remains available for hosts that
can genuinely measure playback. In `ProviderManagedUnmeasured`, generated
document authority settles each observed segment internally as unmeasured; it
does not publish an actionable playback output handle or wait for a browser
`playback_complete` call. Strict media-owner registration and activation still
apply. Ordinary observation transport acknowledgement is never playback or
hearing evidence.

Observed assistant text is retained as canonical `Transcript`
blocks with `TranscriptSource::SpokenUnmeasured`, through a distinct
`AssistantUnmeasuredSnapshotCommitted` event. Committed-live provenance advances
coverage without echo before segment advancement. Ordinary
`messages_for_model_boundary()`, summaries, compaction, and reload therefore
consume the same canonical history; there is no separate observation-position
ledger or `messages_for_live_context()` overlay. The source marker must remain
unmeasured when rendering or summarizing these rows. An observed snapshot has
`BlockAssistantMessage.stop_reason: None`: it does not manufacture
`StopReason::EndTurn`. Independently observed provider stop evidence remains
optional throughout persistence and wire projection. Normal completed model
responses still use `Some(stop_reason)`; consumers must not substitute a
completion for an absent value.

Public admission diagnostics include the failing stage and typed cause (for
example, `missing_default_binding`, `lease_absent`, or
`openai-live-openai-api-backend`) without logging credentials, provider payloads,
or connection URLs. These diagnostics do not change admission policy.

For public Live, `live/playback_complete` is an explicit caller-confirmed
snapshot cut: it commits the transcript prefix observed at that ordered
checkpoint, without waiting for the next user turn or a close. It does not
claim that the provider finished its turn or that a person heard the text.
Later continuation remains in the same interaction and provider group but
receives a fresh one-use playback output handle after the cut settles. A late
group final cannot replay a committed prefix or extend an earlier playback
report to cover later text. Callers may await playback completion and then
close sequentially.

Explicit `live/truncate` prefixes use the same ordered snapshot checkpoint and
must match its exact prefix; they do not wait for a provider final. Omitting a
prefix remains unmeasured. Every terminal kind, including unmeasured and legacy
complete/prefix reports, records exact settlement facts before its target is
retired. Internal retry after a lost projection receipt reuses those facts,
never a new caller report, changed accounting, or an expanded prefix.

Closing drains provider observations, canonical transcript projection, and the
bound control consumer before channel terminality and resource retirement.
Already-admitted output publications retain access to their lifecycle custody
during drain; terminal close takes its exclusive lifecycle lease afterward.
Failed projection or publication retains the exact observation and completed
steps. Retrying close resumes those steps without re-admitting output or
duplicating already committed transcript text.
Exactly correlated pending-append errors during close become
`InterruptedByClose`: completion failed, but partial provider consumption is
unknown. They are neither acknowledgements nor proof of zero consumption;
generated authority permits no retry or automatic replacement. They do not
prevent draining the subsequent close confirmation.
An independently reported playback completion can join a final transcript
that arrives during close; closing itself never proves playback or hearing.
Output without playback evidence remains explicitly unmeasured.

Canonical context appends are claimed by generated authority. A concurrent
drain of the same pending edge defers without reminting send authority; an
already acknowledged edge is not resent. A provider turn that wins the
boundary also produces a typed deferral, not a projection failure. Local
cursor/row bookkeeping is serialized only during projection and receipt
realization, never while waiting for a provider acknowledgement.
Enqueue acknowledges store-sealed canonical staging, not provider delivery.
An owned, channel-scoped drain retains submission and error custody independently
of the committing turn or any cancelled observer; exact close flushes that
worker's quiescence before committing terminality. A historical post-commit
delivery/recovery failure remains observable and is reported during close, but
cannot block cleanup once its worker stopped and physical retirement is proven.
This does not bypass failed canonical transcript projection: that still blocks
the physical drain. A streamed service turn that promotes
its provisional tail still projects the exact promoted store boundary.
Provider turn-finish callbacks wake that owned task without awaiting it, including
empty or idempotent transcript completions. Generated close revocation defers
new sends; a generated ambiguity recovery realizes its own old-channel close
without trying to join the worker that is performing that recovery.
Assistant rows attributed by generated authority to an existing voice worker
are executor trace for generic mirroring: their result has the separate
delegation-specific delivery path. Later ordinary background interactions
remain eligible for generic context delivery.

Ordinary runtime-backed turns, including RPC `turn/start` and the mob-owned
executor used for asynchronous peer work, notify an owned
context-projection task after the CoreExecutor acknowledges the committed
boundary. That task reads the store-sealed canonical body after executor locks
are released; it never reconstructs history from turn results or UI events.
It rechecks the target channel after each read, so a delayed read cannot publish
through an old channel after close/reopen. A failed post-commit source read or
classification is retained for explicit drain observers and reported during
close; a later commit notification retries the canonical scan. Close does not
wait for a source read held behind unrelated background work. This derived
context delivery is distinct from committing incoming live transcript evidence:
a failure of the latter still blocks the physical drain.

Mirroring classifies each committed row independently. User speech retains
session-, channel-, and row-scoped domain provenance before canonical hashing,
including when materialization is deferred behind another transcript item.
Thus a live callback cannot swallow preceding ordinary text rows, and a text
callback cannot echo speech already present on that channel. Generic transcript
rewrites clear replacement-row provenance; another session, channel, or row
cannot reuse it. Attributed realtime sidecar events and snapshots use schema 2;
new readers verify both schemas 1 and 2, while older readers reject schema 2.
This domain provenance is used with the store witness and generated channel
binding, not as a standalone transport authorization token.

Both channel-addressed RPC close and exact-receipt host close revoke generated
append and recovery custody before physical retirement. A delayed committed
source read therefore cannot turn an explicit close into a fresh replacement
channel. Context and result recovery use separate sealed close paths that
preserve their own replacement authority; they are not ordinary explicit closes.
Both recovery activations require playback-owner readiness, retain the original
pending receipt, and mint a fresh activation receipt in the generated answer
commit. An activated replacement remains exactly closeable. Revoked or closed
replacements cannot be published by a late registration callback.

Provider ingress routes append receipts before the control consumer, so a
control task committing its final user transcript cannot wait on its own
receive loop. Duplicate high-volume transcript notifications stay on the
adapter projection path rather than filling the control queue. Canonical
delegation-final commits include live-provenance context projection before
releasing their evidence to the worker. The `MobSessionService` method
`commit_live_delegation_final_transcript` requires the same `MeerkatMachine`
reference explicitly; decorators must forward it, not inherit a default.

A failed projection, missing drain receipt, or unconfirmed physical retirement
retains the exact channel custody and returns an error. Retry the same channel
after the blocking work settles; a timeout does not cancel or repeat an
in-flight provider close.

A terminal provider read failure (including a dropped sideband socket without
`session.closed`) is different: the shared owner drains the known observation
prefix, retires the failed local transport, commits generated channel close,
then projects the retained terminal fault before releasing registration.
This can return `Closed` without a graceful remote close acknowledgement; it
does not assert a successful model turn, final transcript, or playback.
If fault projection fails after generated close, exact close must still be
retried: the owner retains the reporting obligation and replays it without
duplicating a completed publication. Do not skip exact close just because
status already says `Closed`, and do not infer terminality from a generic
transport error in a surface handler.
Pending fault reporting pins its transport projection past the normal
post-close cache TTL. Once cleanup completes, exact receipt replay relies on
generated custody, not that cache. The generated-close/host-commit handoff
continues in an owned task if the close observer is cancelled.
The sideband owner declares `ProviderWebrtcEofEvidence`: EOF defaults to
`Unconfirmed`, while `ProviderConfirmed` requires its explicit protocol receipt.
An unconfirmed clean EOF is retained as a `ConnectionLost` fault, not a graceful
provider close. The public OpenAI broker rejects both pre-close and mid-close
WebSocket EOF lacking `session.closed` as transport failure. Known terminal
drain evidence can retire a hung close request locally; an unfinished
projection or control consumer still blocks successful cleanup.

An ordinary session turn
holding pending tools may return a busy close-settlement error; closing a live
channel does not authorize cancellation or fabricate those tools' results.

Ambiguous-delivery replacement bootstraps retain their machine-issued
`pending_receipt`. Register the replacement playback owner with that receipt
before answering its offer, just as for an initial strict open.
The shared `ExperimentalLiveReplacementRequired` value exposes `open()`,
`pending_receipt()`, and `canonical_seed_cursor()`. Project it to a strict pending
handle, register the new media owner, answer that replacement's offer, publish
answer-delivery custody, and obtain its active receipt from status. Do not issue
a second fresh open or reuse the old channel's activation receipt. Ordinary text
updates do not switch the durable text model; a lost replacement notification
can be recovered by pulling the same pending bootstrap until its answer binds
or that exact channel closes.

Explicit user close must call the shared exact-receipt close even when the
known channel already reports `Closed` or `Revoked`. Recovery can have closed
its old transport while a summary or credential preparation is still pending.
`close_experimental_live_pending_channel` accepts the original pending receipt;
`close_experimental_live_active_channel` accepts its activation receipt. Generated
close authority cancels only that channel's outstanding recovery candidates,
refuses their late admission or activation, and retires any admitted candidate.
It cannot cancel a later independent open on the same session. The internal
recovery handoff close does not cancel its own replacement. Retained replacement
bootstraps are mechanical publication custody: closing a never-activated
replacement removes its entry, and delayed old close feedback cannot remove a
newer entry.

For the default `BeforeOpen` policy, cancellation invalidates generated recovery authority; it does not forcibly
drop an arbitrary host summary or credential future. Until that bounded
preparation finishes or times out, its existing projection-memory reservation
may temporarily backpressure another open. Hosts should surface that refusal
and retry within their own bound, not infer a new channel or bypass the shared
reservation.

The private ChatGPT-brokered path (`experimental-gpt-live`, `gpt-live-1-codex`)
is deprecated and will be removed after the public path has shipped for at
least one release.

## Limitations and known gaps

- **OpenAI Realtime API only.** The shipped provider integration is OpenAI's Realtime API (`gpt-realtime-2`). Azure OpenAI (`azure_openai`) and other providers are not yet wired into the live transport layer.
- **One live channel per session.** A session has at most one live channel at a time. For per-member live channels in mobs, open channels against individual member sessions.
- **Deferred sessions are model-gated.** `live/open` may materialize a deferred session whose resolved model is realtime-capable; a deferred non-realtime session is rejected before channel creation.
- **Identity/history rewrites require close/reopen.** `live/refresh` applies config-only changes (instructions, tools, audio format); model/provider swaps and canonical transcript or user-content-registry rewrites require `live/close` + `live/open`.
