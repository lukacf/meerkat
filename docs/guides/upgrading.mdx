This page has two parts: the steps for any upgrade, then one section per
release, newest first. Read every release section between the version you
run and the version you are moving to. The full list of changes for each
release is in
[CHANGELOG.md](https://github.com/lukacf/meerkat/blob/main/CHANGELOG.md).

## How to upgrade

Meerkat is pre-1.0, and patch releases can carry declared breaking changes.

- **Keep everything on the same patch version.** The SDK handshake accepts
  any `rkat-rpc` with the same major and minor version, so a mismatched
  patch connects without complaint. Upgrade `rkat-rpc`, `meerkat-sdk`,
  `@rkat/sdk` and `@rkat/web` together.
- **Bump Rust pins together.** The `meerkat*` crates are versioned in lock
  step: move every `=0.9.x` pin at once.
- **Expect one-way migrations.** A release can migrate durable state forward
  the first time it opens it, after which older binaries refuse it. Each
  release section below says whether it does.

### Steps

1. Stop every process that shares the state root: the CLI, `rkat-rpc`,
   `rkat-rest`, `rkat-mcp` and SDK applications.
2. Back up the realm state root. Without a backup, a release that migrates
   durable state cannot be rolled back.
3. Run `rkat storage doctor` (read-only) and keep its report.
4. Upgrade the binaries and SDKs (table below).
5. Start the new version. It migrates durable state on first open. To
   migrate offline instead, run `rkat storage migrate` as a dry run, then
   with `--apply` (see [Storage Operations](/guides/storage-operations)).
6. Run `rkat storage doctor` again and compare.
7. Once the rollback window has passed, remove migration backups with
   `rkat storage prune`.

| Install path | Upgrade command |
|---|---|
| Homebrew | `brew update && brew upgrade rkat` (upgrades all four binaries) |
| Release archives | Download the new per-binary archives, verify them against `checksums.sha256`, and replace the binaries (see [Linux without Homebrew](/quickstart#linux-without-homebrew)) |
| Cargo | `cargo install rkat --locked --force`, and the same for `meerkat-rpc`, `meerkat-rest` or `meerkat-mcp-server` if you use them |
| Python | `pip install -U "meerkat-sdk==<version>"` |
| TypeScript | `npm install @rkat/sdk@<version>` (and `@rkat/web@<version>`) |
| Rust | Set every `meerkat*` dependency to `=<version>` |

### Verify

- `rkat --version` and `rkat-rpc --version` print the new version.
- `rkat doctor` passes.
- `rkat storage doctor` reports no new problems.
- An SDK `connect()` succeeds.

## Upgrading to 0.9.15

0.9.15 is not published yet; what is said here about 0.9.15 describes the coming release.

This section is for systems running 0.9.14 or 0.9.13. The full list of
changes is in the CHANGELOG under `## [0.9.15]`.

Until Connect 0.9.15 is published, the Connect release to
use with Core 0.9.15 and Meta 0.9.15 is Connect 0.9.14. A Python environment
with the `native-host` extra of Connect 0.9.14's `meerkat-toolkit` cannot
take `meerkat-meta` 0.9.15 until Connect 0.9.15 is published: the extra
requires `meerkat-meta==0.9.14`. In that pairing:

- Connect 0.9.14's archives are built with Core 0.9.14 and Meta 0.9.14. What
  0.9.15 changes in Core and Meta is not in the Connect CLI or the Connect
  gateway until Connect 0.9.15.
- `@rkat/toolkit` 0.9.14 accepts `@rkat/sdk` 0.9.15 and `@rkat/meta-sdk`
  0.9.15 beside it: its optional peers accept 0.9.14 and later below 0.10.0.
- Without that extra, the Python `meerkat-toolkit` 0.9.14 puts no
  requirement on `meerkat-meta`.

That pairing was not run as a whole, in either direction: it rests on the
version requirements Connect 0.9.14 published.

State that 0.9.14 or 0.9.13 persisted loads under 0.9.15 as it is. What
that rests on differs by store:

- **Core's stores** (the mob, schedule, session and runtime stores: the
  SQLite stores and, for a realm kept in the host's own database, the stores
  the host store SPI carries): no migration and no adoption step. No store
  schema, journal, session or machine state version changes, and each stored
  field 0.9.15 adds is written only when it is set and read as unset when
  absent. This rests on a comparison of the stored forms of the two releases
  and on the tests of the forms that gained a field, not on loading state
  that a 0.9.14 binary wrote.
- **Meta's own stores:** no change was found in the serialized form or the
  schema version of a stored Meta type. This rests on a read of this
  release's changes to Meta, not on an audit of each stored form.
- **A store the host implements itself** (a host-supplied schedule store,
  for example) holds Core's serialized forms, so the same holds for it
  provided it stores them whole and keeps the keys it does not know.

Connect's own stored forms were not audited: what is said above covers these
three kinds of store only.

### Configuration documents are readable by their owner only

On Unix the engine writes every configuration document readable by its
owner only (mode 0600), whatever the process umask: a config document
(`~/.rkat/config.toml`, a project's `.rkat/config.toml`, a realm's own
`config.toml`), the `config_state.json` beside it, and `mcp.toml`
(`~/.rkat/mcp.toml`, a project's `.rkat/mcp.toml`). Through 0.9.14 these
files took the umask's mode. The one exception is a directory that has the
setgid bit: the documents written there are 0640, readable by the
directory's group. A document the engine writes is never writable by its
group and never readable by others. See
[File permissions](/concepts/configuration#file-permissions).

**Do:**

- A document an earlier release wrote keeps its mode until the engine next
  rewrites it. To make the existing ones owner-only now, run `chmod 600` on
  each that exists: `~/.rkat/config.toml`, `~/.rkat/config_state.json` and
  `~/.rkat/mcp.toml`; a project's `.rkat/config.toml` and `.rkat/mcp.toml`;
  and each realm's `config.toml` and `config_state.json` in its realm
  directory (`<project-root>/.rkat/realms/<realm>/` for the CLI, or
  `<state-root>/<realm>/`).
- Where several local accounts read a document through group permissions (a
  project checkout or a realm directory shared by a group, or an install
  that runs a helper or a verifier under another account), the group loses
  that read at the document's next rewrite unless the document's directory
  has the setgid bit. Set it once on each shared directory, with
  `chmod g+s <dir>` (the `.rkat` directory of a shared project, a shared
  realm directory): the documents written there are then 0640 with the
  directory's group. A document the engine already rewrote as 0600 stays
  0600: run `chmod g+r` on it once.
- An install that cannot set the bit grants the read itself after each
  write, with `chmod g+r` or an ACL on the document. A write replaces the
  file, so a grant on the file before it does not carry over, and a default
  ACL on the directory does not reach a file that is created 0600.

The admission fence file keeps its own rule: `admission.lock` is 0640 with
its directory's group in every directory.

### `rkat run --comms-binding-out` replaces what is at its path

`rkat run --comms-binding-out <PATH>` no longer writes into what is already
at the path. It removes the file there and creates a new one that only its
owner can read (0600 on Unix), whatever the umask and whatever mode the
older file had. The flag is described under
[CLI usage](/guides/comms#cli-usage) in the comms guide.

**Do**, where an install relied on the old write:

- **A symbolic link at the path:** give the flag the path of the file
  itself. The link is replaced by a regular file, whether it pointed to a
  regular file or to nothing. Through 0.9.14 the binding was written through
  the link into the file it named; now that file is left as it was, or not
  created, and does not receive the binding.
- **A named pipe, a socket, a device or a directory at the path**, or a
  symbolic link to one of them, is refused and left untouched. So is any
  path in `/proc` or in `/dev`, whatever it holds; `/dev/shm`, a memory file
  system for ordinary files, is the one exception.
  `--comms-binding-out /dev/stdout`, or a named pipe a supervisor reads the
  binding from, worked before and is now an error: write the binding to a
  regular file (one under `/dev/shm` will do) and have the supervisor read
  that.
- **The directory of the path** must let `rkat` remove and create a file in
  it. A binding file that was created for `rkat` in a directory it cannot
  write could be rewritten in place before, and now fails: give `rkat` a
  directory it can write.
- **A supervisor under another account** than `rkat` can no longer read the
  binding file (under the common umask 022 it could). Run the supervisor
  under the same account, or grant it the read after each write (`chmod`,
  or an ACL on the file): the file is a new one every time, so a grant on
  the older file does not carry over.
- **A binding file an earlier release wrote** keeps its mode until it is
  written again: run `chmod 600` on it, or delete it once the supervisor
  has read it.

The descriptor file of `rkat mob host --descriptor-out` is owner-only in
the same way.

### `rkat run --output json`: a failed run prints a failure document

A failed `rkat run --output json` (or `--json`, with or without `--resume`)
now ends stdout with a JSON failure document, `{"error": {...}}`. Through
0.9.14 a failed run wrote no document to stdout. The exit statuses and the
stderr text are unchanged, and text and HTML output print no document. See
[JSON failure document](/cli/configuration#json-failure-document).

**Do:** a script must not read non-empty stdout as success, nor parse the
last stdout document as a run result without looking at it. Decide by the
exit status, or by the document's top-level key: `error` is a failure,
`status` (`"pending_tool_call"`) a run waiting for an external tool result,
and anything else the run result.

### A definition update that drops a profile agents were created on

`MobStorage::update_definition` (on Meta, a declared definition update:
`runtime_options.declare_spec_update`) refuses an update that drops a
profile, or renames it, while a created agent's row names the profile: the
answer is the diagnostic `profile_held_by_identity` at `profiles.<name>`,
which names the agents, and nothing is written. Earlier releases accepted
the update, and such an agent then failed each restore.

**Before such an update:** keep the profile, or update those agents to
another profile or remove them. An archived agent holds its profile; a
removed one does not. A start that carries no update starts as before.

**After a rollback from a later release:** a created agent's row that
release wrote may not be readable by this one. While the mob has such a
row, an update that drops or renames a profile is refused the same way, at
`profiles`, naming those agents, since such a row may name the profile.
Keep the profile, or run the update on the release that reads the rows.

**Exported agents:** an import of exported agents
(`MobHandle::import_created_identities`) restores their rows without
judging their profiles against the definition, and between the purge and
the import the check reads no row. Keep the profiles of exported agents
until the import.

**Code that reads diagnostics:** a consumer that reads diagnostic codes as
text meets a code it did not know, `profile_held_by_identity`. Rust code
that matches `meerkat_mob::DiagnosticCode` exhaustively adds an arm for
`ProfileHeldByIdentity`, which is appended last.

### Schedules paused for their target and a rollback

A schedule can be paused for its target (`ScheduleService::pause_for_target`):
it is stored as a paused schedule whose machine state carries
`paused_for_target: true`, and only such a schedule is resumed when its
target takes deliveries again. Nothing changes for a schedule that is not
paused that way, and the upgrade needs no step.

**Rolling back:** an earlier release reads such a schedule as paused and
never resumes it on its own. It ignores the mark, and drops it when it
writes the schedule while it is paused (an update, a pause by name, a
target snapshot sync, a late supersession acknowledgement); a schedule it
does not write keeps the mark. After returning to 0.9.15, a schedule whose
mark was dropped stays paused when its target comes back: resume by name
the schedules of the targets that take deliveries again and are still
paused. The loss is on the safe side: such a schedule never fires at a
target that takes no delivery.

### Store-owned agents: seats an earlier release recorded

A store-owned identity is an agent whose record is its row in the mob's
identity store, an agent created at run time for example. Two notes apply
to a mob that holds such agents from 0.9.9 through 0.9.14. Neither needs a
step for the upgrade itself.

**A seat recorded ephemeral.** From 0.9.15 the seat of a store-owned
identity is a durable identity's, whatever its profile says of durability.
A seat that was recorded ephemeral (by a release from 0.9.9 through 0.9.14,
for an identity on a profile without `durable = true`, or kept by an
adoption from a plain worker) is not converted at a start or at the
adoption. The identity joins the durable resume gate and Core's lists of
durable identities (`MobHandle::durable_identity_members`,
`MemberBindingHistory::durable_identity_bindings`) at its next seat, or at
a respawn of its member (`MobHandle::respawn_member`), which keeps its
conversation.

**Do:** a host whose checks read those lists respawns the members it needs
listed now.

**Seat labels an earlier release left behind.** 0.9.9 through 0.9.14 kept
a seated member's labels at a label update of its identity, so such a seat
can carry other labels than its row. Those releases wrote no record of an
owed restamp, so no start and no build of 0.9.15 moves the seat's labels.
`MobHandle::identity_record_census()` counts such seats in `seats_stale`.

**Do:** while `seats_stale` is above zero, bring each such seat up to date
before the host adopts `MemberBuildPreparer::prepare_store_owned_seat` or a
spawn customizer that sets labels. Respawn the member with its row's labels
(`MobHandle::respawn_member` with `MemberRespawn::new().with_labels(..)`),
or update the identity while its member is idle: any update then makes the
seat equal the row. A host that answers such a member's seat from its row
is otherwise refused the member's build, with a refusal that names the
label keys that differ. A seat whose owed restamp 0.9.15 recorded itself
(see [Rolling back to 0.9.14](#rolling-back-to-0-9-14)) is counted in
`seats_stale` too and needs no step here: its builds are compared with the
row's labels.

### Operator instruction limits bound a member's snapshot

No action is needed to upgrade. A mob's operator instruction limits (64
records and 1 MiB of Active bodies) now bound one member's snapshot, the
shared records plus the member-targeted records that name the member, not
the mob as a whole. A mob can hold a member-targeted record for each of any
number of members, and a member's session and status row no longer list
other members' member-targeted records. For a session that 0.9.14 wrote,
this holds from the mob's next write of the member's snapshot: until then
the session keeps the slots it was given. Shared records (targeted at every
member or at a profile) keep the bound they had. See
[Operator instructions](/guides/mobs#operator-instructions).

Rust code that matches on the kernel's
`meerkat_machine_kernels::generated::mob::TransitionId` by variant: the enum
gains `SetOperatorInstructionAdvanceSlotLimitExceededRunning` and
`SetOperatorInstructionAdvanceSlotLimitExceededStopped`, appended last, so
an exhaustive match needs the two arms and no existing variant's
discriminant moves.

### Operator instructions for a member and its forks

No action is needed to upgrade: a member-targeted record stays its member's
alone unless it is written with `include_forks`, and a fork then runs under
the records written for the first member of its fork family and its forks
(see
[Operator instructions](/guides/mobs#operator-instructions)). One behaviour
changes without the field: a durable fork child has its operator instruction
snapshot, with the records the mob targets at every member or at its
profile, recorded before it is seated, and a fork whose snapshot
cannot be recorded is refused `fork_member_provision_failed`.

Rust code: `meerkat_mob::OperatorInstructionTarget::Member` and
`meerkat_contracts::WireInstructionTarget::Member` gain the field
`include_forks` (`false` keeps the meaning the variant had); the machine
types gain the items the CHANGELOG lists under Breaking, each appended
last.

Clients and servers of an earlier release: a client that decodes operator
instruction targets with an earlier release's `meerkat-contracts` refuses a
`mob/instruction_status` page that lists a record written with
`include_forks` (its target type denies unknown fields), so upgrade such
clients before the first such write; a page with no such record is
unchanged, because the field is left out when false. A server of an earlier
release refuses a `mob/set_instruction` whose target carries the field.

Forks seated by an earlier release: a fork seated by a release before
0.9.15, or while rolled back to one, has no lineage root on its stored spawn
row. No record written with `include_forks` ever selects it, and a record
written for it and its forks reaches its own forks, which are rooted at it.

Rolling back: a release before 0.9.15 reads a record written with
`include_forks` as a record for the member alone, and ignores the lineage
root that a fork's stored spawn row carries (there the fork is a member with
no fork family), so on that release these records do not select the forks.
Nothing is refused. What the return to 0.9.15 restores depends on the mob's
store:

- **SQLite store**: no stored row is rewritten. The lineage of every fork
  seated on 0.9.15 is restored from its spawn row and the records select
  those forks again.
- **Host store** (a realm kept in the host's own database through the host
  store SPI): the earlier release writes the mob's journal again at its next
  checkpoint, from what it read, without the fork scope of the records and
  without the lineage roots. They do not come back: after the return those
  records are their members' alone and the forks seated before have no
  lineage. Write the records again, at a new revision, with
  `include_forks`; they then select the forks seated from then on.

### Reasoning effort: one setting for every provider

0.9.15 is not published yet; what is said here about 0.9.15 describes the coming release.

0.9.15 adds the provider-neutral `reasoning_effort` option (see
[Reasoning effort](/concepts/providers#reasoning-effort)). A caller who
sets no level gets 0.9.14's behavior on every route: the same requests,
the same defaults, and provider-specific parameters
(`provider_params.provider_tag`) work as before. Two things such a caller
can still see: the models catalog read lists `reasoning_effort_levels` for
each catalogued model (an added member), and a turn's reasoning preference
(set by a host, for example by a GPT Live channel for its delegated member
turns) is judged by the route of the client that serves the request where
that route states levels itself, a GitHub Copilot account or a self-hosted
route (the four differences are listed under Changed in the changelog).

- **Moving from a provider-specific effort.** Replace the raw effort
  (`provider_tag.reasoning_effort` for OpenAI, `provider_tag.effort` for
  Claude, `provider_tag.thinking_level` for Gemini) with `reasoning_effort`,
  or keep the raw parameter. Setting both is accepted when they name the
  same level and refused as a typed conflict when they differ.
- **Strictness.** A raw effort the model does not accept can be dropped or
  refused by the provider. The neutral level is checked first: a level the
  model or its route does not accept is refused before any provider request
  with `INVALID_PARAMS` and `reasoning_effort_refused` data, and Meerkat
  never lowers it, changes the model or moves to another route. On a GitHub
  Copilot route the levels are the ones the account's model list states for
  the model, which can be fewer than the provider's own API accepts.
- **Spelling.** The neutral level is `xhigh` only. The Claude-specific
  effort keeps accepting `xhigh` and `x_high`.
- **Older servers.** A server before 0.9.15 refuses the `reasoning_effort`
  field on `turn/start` and `mob/turn_start` and ignores it on
  `session/create` and in REST bodies. The nested key
  `provider_params.reasoning_effort` is refused by `session/create`,
  `turn/start`, the MCP tools and a mob definition read from a TOML file or
  a mobpack, and ignored in a REST `POST /sessions` body, on
  `mob/turn_start` and in a mob profile sent to `mob/create`. The
  `resume_overrides` value `reasoning_effort` is refused in every mob
  profile. The Python and TypeScript SDKs therefore refuse to send the
  field to a server whose contract is below 0.9.15
  (`CapabilityUnavailableError`).
- **Member hosts.** A member host that runs 0.9.14 refuses a member spec
  that carries a level: it fails closed with a spec digest mismatch and
  does not ignore the level. Upgrade member hosts before a profile sets a
  level.
- **SDKs.** Upgrade the SDK before setting a level. A session that carries
  a level emits the event `request_reasoning_effort_resolved`, and a Python
  or TypeScript SDK older than 0.9.15 raises `UNKNOWN_EVENT_TYPE` on it,
  wherever the level was set: on a request, by another client or in a mob
  profile. A session without a level emits no such event.
- **The flat key.** From 0.9.15, `provider_params.reasoning_effort` on the wire is
  read as the provider-neutral level and judged. 0.9.14 ignored it in a
  REST `POST /sessions` body, on `mob/turn_start` and in a mob profile sent
  to `mob/create`, so a client that sent the key there by mistake can
  be refused from 0.9.15. A schedule's session settings do not take the
  key in 0.9.15: a schedule whose `create` spec carries it is refused when
  it is created or updated (0.9.14 refused it there as an unknown field).
- **CLI scripts.** `rkat run --reasoning-effort <LEVEL>` exits 2 when the
  level is refused; with `--output json` stdout then ends with a failure
  document (`{"error": {...}}`) instead of a run result, so a script that
  reads stdout as a result checks the exit status or the `error` key first.
- **Rolling back.** Before rolling back to 0.9.14, remove the reasoning
  effort level from every session that set it (`rkat run --resume <SESSION>
  --no-reasoning-effort "<PROMPT>"`, or a turn with `reasoning_effort`
  `{"action":"clear"}`), and let accepted turns that carry it finish. A
  session whose stored provider params hold the level, and an accepted
  input whose turn carries the field, are refused by 0.9.14 and earlier
  with ``unknown field `reasoning_effort` ``. Replacing or clearing
  `provider_params` does not remove the level. A mob is different, and
  storing a level in one is a one-way step: its event history records
  every definition and each member's profile snapshot, and 0.9.14 reads the
  whole history when it resumes the mob. A mob whose history holds a
  profile with a level, or the `resume_overrides` value `reasoning_effort`,
  cannot be read by 0.9.14, and removing the level afterwards, or a reset,
  does not help: before rolling back, destroy the mob on 0.9.15 and create
  it anew without the level (its members and history are not kept). On
  0.9.14 a Core host (`rkat-rpc`) starts and serves its other mobs, and
  quarantines such a mob at its first request (`store_unreadable`, not
  retryable, content retained): reads, turns, a restore retry and a create
  under its id get the same answer. A Meta gateway on 0.9.14 does not
  start on the state directory of such a mob. Neither writes to the mob's
  store, and 0.9.15 loads it again with the level. A realm profile that
  stores either cannot be read by 0.9.14: there the realm's profile list
  fails as a whole and a read of that profile fails. Unlike a mob's
  history, a realm profile keeps no earlier content: update it on 0.9.15
  so that it names neither (or delete it) before rolling back; an update
  of it on 0.9.14 also succeeds and drops the level. To keep the option of
  rolling back, set the level on a session or
  a turn, not in a mob definition, a member profile or a realm profile.
  There is no `rkat storage doctor` finding or count for stored levels yet:
  to find affected mobs before rolling back, page each mob's stored events
  (`rkat mob logs <MOB> --json`) and list the realm profiles, and search
  both for `reasoning_effort`.
  Sessions and mobs that never carried a level are written exactly as
  before and read on either release. What 0.9.14 does with a mob
  definition and a realm profile that hold a level was confirmed by runs
  with development builds of both releases; the session, accepted input,
  member snapshot and member spec cases were read from the source of both
  releases, not run; the removal on 0.9.15 before a rollback was not run.
  Three more stored forms (a session's model-routing history, the record
  of a turn that failed for a refused level, the stored event log) and
  each item's own grade are under
  [Rolling back to 0.9.14](#rolling-back-to-0-9-14).

### Meta 0.9.15

Meta 0.9.15 pins Core `=0.9.15`. The full list is in `meta/CHANGELOG.md`
under `## [0.9.15]`.

- Identity policy: an enabled policy that names an approval outcome or a
  preparation mode this release does not carry out is refused at init. That
  is the approval outcome `notify` or `review`, in a rule or as the default,
  and the preparation mode `constructed`, in `runtime_options.identity_creation`
  or in the policy a native Rust host returns from
  `GatewayHostComposition::identity_creation_policy`. The refusal names the
  policy path (`approval.rules[<n>].outcome.kind`, `approval.default.kind`
  or `preparation.<profile>.mode`) and what to write instead. 0.9.14
  accepted `notify` and `review`, and accepted `constructed` on a launch
  with a native Rust host composition (it refused it on every other
  launch), and nothing acted on them: no notice reaches an approver for
  `notify`, no reviewer decides for `review`, and no method holds or
  activates a construction. **Do:** write `allow` where the policy
  says `notify` (the consent a change committed under reads back from
  `meta/identity/get`, `meta/identity/list` and `meta/identity/operation`);
  write `require_approval` where it says `review`, or review the request in
  your own code before you ask under `allow`; and write the preparation
  mode `required` where it says `constructed`, which the host settles with
  `meta/identity/settle_preparation`. The page
  [Identity policy](https://docs.rkat.ai/meta/reference/identity-policy) of
  Meta's reference describes the policy.
- A Rust host that composes its runtime through `UnifiedRuntime::bootstrap`
  or the `bootstrap_with_*` family must complete the bootstrap before an
  agent created at run time can be built: with an identity bootstrap
  (`install_and_bootstrap_identity_first_context`, or
  `bootstrap_installed_identity_first_context` and its held variants) or
  with `activate_without_identity_context`. Until one of them returns,
  every build of such an agent is refused for now, with a reason that names
  both calls, and one warning is logged per process. An agent that starts at
  its creation (it was given a first message, or its profile runs as an
  autonomous host, the default) and one the mob's start owes its seat stay
  owed their seat, and the call that completes the bootstrap seats them. A
  delivery to an agent seated dormant is refused retryable
  (`host_preparation_pending`) and nothing is delivered: the sender sends
  it again once the bootstrap is complete. Creating an agent that builds
  nothing (no first message, a turn-driven profile) is unchanged. Through
  0.9.14 such an agent was built from its record at once.
  `UnifiedRuntimeBuilder` and both gateway binaries complete the bootstrap
  themselves. **Do:** a host of that kind calls one of them after its
  bootstrap.
- Rust: `identity_creation::ChangeClass` gains the variants `Archive` (an

### Rolling back to 0.9.14

What this subsection says an earlier release does was established by reading
the 0.9.14 source, except where an item says it was confirmed by a run. Unless
an item names the builds of its own run, such a run was made with a 0.9.14
gateway built from the release tag, over state written by a gateway built from
the development source for 0.9.15 (main on 13 November), with a scripted model
in place of a provider.

0.9.14 and earlier releases read most of what 0.9.15 writes without a
refusal. The items below are where a rollback differs: configurations that
make a 0.9.14 gateway refuse to start, stored forms an earlier release
refuses, and what it reads without a refusal but serves differently while
rolled back or changes by what it writes.

Most items have a step to take: before the rollback, on 0.9.15, unless the
line says otherwise.

- Settle every owed label restamp.
- Bring each mob within the earlier totals of operator instruction records,
  counting the agents' instruction records.
- For a mob kept in a host store, list the records written with
  `include_forks`.
- End every change of an agent that waits for approval.
- Remove the new agent actions from the access rules, and `archive` and
  `adopt` from the identity policy.
- Unarchive, settle or remove each agent that must not stay as it is.
- Pause the Console schedules of agents created at run time
  (`meta/schedule/pause`); resume them after the return
  (`meta/schedule/resume`).
- Remove each agent created at run time that an access rule by role or by
  label keeps from someone, or add a deny rule that names it.
- While rolled back, send no message from the Console to an agent created at
  run time.
- Clear the reasoning effort level from every session that set it, and let
  accepted turns that carry it finish.
- Destroy every mob whose definition or a member profile ever stored a
  reasoning effort level, or listed `reasoning_effort` in `resume_overrides`,

- Replace or delete every realm profile that holds
  `provider_params.reasoning_effort` or lists `reasoning_effort` in

  `expected_revision`.

Each item below says what an earlier release does and what to do.

**A created agent's row that records an owed label restamp.** The row of a
store-owned identity carries the key `label_restamp_owed` while an update
of the agent has committed labels that its seated member's seat row does
not carry yet: the member held work at the update, say. The row lets the
key go once a seat row carries the row's labels, and an archive or a
removal drops it. A row that owes none carries no such key and reads on
earlier releases as before.

Releases 0.9.9 through 0.9.14 read a row that carries the key as
unreadable, for that agent only. The mob starts, and its other agents are
unaffected. While the host runs the earlier release, every change of that
agent is refused, commands and work addressed to it are refused, and
nothing is spawned or seated under its name; a member that is already
seated stays seated. The row is kept as stored, on the SQLite store and on
a host store, so 0.9.15 reads it again after the return: the agent is out
of service while rolled back, and nothing of it is lost. An earlier release
cannot settle the owed restamp, since it cannot read the row: settle it on
0.9.15 before the rollback, or return to 0.9.15.

Before a rollback, on 0.9.15, read `MobHandle::identity_record_census()`
(with no running mob, `MobStorage::read_identity_record_rows` for a store
file or `MobStorage::identity_record_rows` for a storage). While
`label_restamps_owed` is above zero, settle each owed restamp:

- retry the update, or update the agent again
  (`MobHandle::update_store_owned_identity`), while its member is idle;
- or respawn its member with the row's labels (`MobHandle::respawn_member`
  with `MemberRespawn::new().with_labels(..)`);
- a member no same-session successor can serve (a placed member, a member
  wired to a placed member, a member on a session service that keeps no
  durable sessions) is settled by none of these: rotate it
  (`MobHandle::rotate_member`), or archive or remove its agent.

`rkat storage doctor` and Meta's storage doctor do not report this count,
and a host that uses only the SDKs has no read for it in 0.9.15: the Rust
calls above are the read.

**Operator instruction records past an earlier release's totals.** An
earlier release bounds the mob as a whole at 64
records and 1 MiB of Active bodies, and puts every record of the mob in
every member's snapshot. Only 0.9.15 admits more, as member-targeted
records, in two ways:

- **more than 64 records** in the mob (a revoked record keeps its slot and
  counts);
- **more than 1 MiB of Active bodies** over all the mob's records together,
  with 64 records or fewer (five members that each hold a 256 KiB record of
  their own, for example).

An earlier release does not refuse such a mob when it starts: its release
build replays the journal without an error and the mob comes up with its
members. It then cannot serve the mob, because every step that checks the
mob's recovered state against the earlier bounds is refused:

- every spawn into the mob is refused, with an internal error that says the
  mob's state could not be recovered;
- every flow run is refused before it starts, for the same reason;
- with more than 64 records, every member's operator instruction delivery
  is also refused by the member's session (`slot_limit_exceeded`): the
  status read shows the member `owed` with that `last_failure`, and no
  later write reaches it. What a member's session
  already applied stays in effect. A member whose build mints a new session
  fails to build, because the mob cannot carry its snapshot into the
  session.

Turns of the members that are already seated, the roster and the journal
are not affected, and 0.9.15 serves the mob again without a repair. A mob
within both totals is unaffected in either direction, whatever its records'
targets.

Before a rollback, run `rkat storage doctor` on 0.9.15: it lists each such
mob database (`operator-instruction-mob-totals`, with its record count and
its Active bytes). The doctor reads mob databases on disk. For a mob kept
in a host store, read `mob/instruction_status`
(`MobHandle::operator_instruction_status`) without `namespace` and `key`:
`desired` lists every record of the mob, revoked ones included, with each
one's effect and, while it is Active, its `body_bytes`; count the records
and add up the bytes of the Active ones. A revoke lowers the bytes but not
the count: a revoked
record keeps its slot. For each listed mob, do one of these first:

- keep the processes that serve that mob on 0.9.15;
- bring it back within both totals where only the bytes are over: revoke
  records, or write shorter bodies, until the Active bodies of the whole
  mob are at most 1 MiB;
- reset the mob (`mob/lifecycle` with `reset`, `MobHandle::reset`), which
  retires its members and clears its operator instruction records, then seat
  its members and write the records it needs again, at most 64 records and
  1 MiB in total;
- destroy the mob, or move its database out of the mob root, as for a mob
  an earlier release refuses.

then with the earlier text put back). They then select the forks seated from

**A stored reasoning effort level.** 0.9.14 has no `reasoning_effort`

``unknown field `reasoning_effort` ``. Where the level is stored decides

- **A session, or an accepted input.** A session whose stored provider

- **A mob whose definition or a member profile ever stored a level.**

  profile with a level, or the `resume_overrides` value

  Neither writes to the mob's store, and 0.9.15 loads it again with the

  created by a development build of the tree with this change was opened
  by development builds of the commit the tag `v0.9.14` names, on
  `rkat-rpc` and on a Meta gateway, without a provider key and on scratch

  Not run: a level in a spawned member's stored profile, and destroying
  the mob and creating it anew.
- **A realm profile that holds a level,** or the `resume_overrides` value
  `reasoning_effort`. 0.9.14 cannot read such a profile while its stored

  drops the level. Before rolling back, replace the profile on 0.9.15 with
  one that holds neither, or delete it; a profile keeps no history, so the
  replaced row is all 0.9.14 reads (read from the source, not run). A
  member that was spawned from the profile while it held a level

- **The record of a turn that failed for a refused level.** The stored

- **The stored event log.** Where a host keeps a session's event log, a

the session keeps what it stored while
it held the level: its event log, and the routing history record and the

hosted-tool call items and item ids, on the same service too; the steps of

### Host store implementers: token order and conflicted scopes

Two rules of the host store SPI are new or newly enforced in 0.9.11, each
with a row of the host store chapter in `meerkat-store-conformance`:

- **Token order** (the `token_order` row). Every grant answers a token
  above every earlier grant of the realm, in either acquire mode and to any
  caller, a takeover of the caller's own recorded lease included. Core now
  holds a re-acquire's grant to it: a grant at or below the token the
  writer holds loses the realm until it is reopened, with a cause that
  names your store's token order, not another writer.
- **Conflicted scopes** (the `a_conflicted_scope_is_listed_typed` row). A
  store that meets obligation 4 by failing a scope's load with a typed
  conflict (two batches at one of its versions) reports that scope per
  scope in its listings: `list_heads` answers it in `HeadPage::conflicts`
  as `ScopeConflict::new(name, version, commit_ids)`, with the version that
  holds the two batches (the `current` the load's `Conflict` names) and
  their commit ids, ascending, without repeats and the same each time, or
  none. Every `read_rows` of the scope answers the same conflict. It is never
  listed among the heads and never fails the page, and a
  page holds at most `limit` entries across both lists. A page the store
  cannot decide yet (a pending acquire cut) answers `Unavailable`, never a
  conflict. Core quarantines such a scope and opens the rest of the realm
  (see [A Conflicted Scope](/reference/host-store-spi#a-conflicted-scope));
  a store that still fails the page keeps the realm from opening.
  `HeadPage` is `#[non_exhaustive]`: a struct literal no longer compiles.

**Do:**

- Build each listing page with `HeadPage::new(heads, next)`, and add the
  conflicted scopes with `HeadPage::with_conflicts`.
- Answer every grant with a token above every earlier one.
- Run the host store chapter against your store before you upgrade. A
  store that decides between two batches for one version only when it
  folds them implements `HostStoreFactory::fold_now`, so the conflict row
  sees what its loads and listings show once it folded.
- To lift a quarantine, repair the scope in your store (keep one of the two
  batches at that version by your fixed rule, where a lower fence token
  never beats a higher one, and remove the other), then reopen the realm
  and open again each mob storage your host found quarantined
  (`SpiStoredMob::quarantined`). A reopen without the repair quarantines
  the scope again.

### The downgrade cycle of store-owned identities

A release before 0.9.9 does not read a mob's rows of schema version 2 and
later: the rows of store-owned identities (present, pending their host's
preparation or archived) and the tombstones of removed names
(`IdentityRecordCensus::created_rows`, and the `identity-store-rows`
finding of `rkat storage doctor`). A downgrade of a mob that holds any to
such a release is supported through this cycle only, and a host's downgrade
tooling refuses while the census counts any row. A downgrade to 0.9.9 or
0.9.10 needs no cycle: they read the rows.

1. Hold the mob's identity changes (`MobHandle::set_identity_changes_held`).
2. Settle every identity awaiting its host's preparation
   (`preparations_open`) and every held construction (`constructions_held`),
   or remove the identity.
3. Bring each stale seat up to date (`seats_stale`), or remove its identity.
4. Export the set: `MobHandle::export_created_identities` answers a
   `CreatedIdentitySetExport` (schema `meerkat.identity.created_set.v1`)
   that holds every row as sealed, with each identity's session reference
   (its member's session, or its archived session), sealed with a digest.
   Keep it: the import needs it. Session contents, memory and decisions are
   not in it.
5. Purge: `MobHandle::purge_created_identities` with the export's digest,
   as the host operator. One store transaction removes every row of the
   set, and nothing else (no session, journal row or host-adopted intent),
   only while the rows are still the export's. The mob then refuses every
   identity change (`purged`) until it restarts. A purge or an import
   commits at most 256 identities (`IDENTITY_CHANGE_BATCH_MAX`, tombstones
   included): a mob with more rows is refused `batch_too_large`, with
   nothing removed, and has no supported downgrade below 0.9.9 in this
   release.
6. Downgrade.
7. After the roll-forward, import the export:
   `MobHandle::import_created_identities`, as the host operator, under
   imported consent. A retry of its operation replays it.

Under the older release, after the purge, an adopted identity that its
host's roster still lists is a roster identity again, on its session. The
other store-owned members are plain members: its roster pass, a
`retire_stale` reconcile or a former spawner's retirement may retire them,
archiving their sessions. The names of removed identities are free there,
and a roster may seat one.

Rolled forward, a start reads each store-owned identity whose row was purged
as unreadable: its name is reserved, nothing acts on it and nothing seats it
until the import restores its row. The import re-creates each record and
re-binds its session: a member seated under its name is bound in place, on
its session, a plain member only when it is bound to the session the record
names (a member on another session, a new worker the older release seated
or the identity's own on a session the export does not name, is reported
`name_taken_meanwhile` and left as it is: adopt it to take it into store
custody); an identity with no member is seated again, Dormant, on its
archived session, or on a fresh session with the history unavailable notice
when the session store no longer holds it; pending, archived and removed
names are restored as recorded; and an adopted identity whose roster
declared it again returns to store custody by the adoption's step. A name
another holder keeps (a roster or a member seated on it meanwhile, or
another row) is left as that holder has it, and the import's receipt reports
it (`name_taken_meanwhile`). A re-import under a new operation reports a
record whose restored row differs from it (the import left out an owned edge
another identity held, or the identity changed since) as
`name_taken_meanwhile` too: the identity is store-owned already, its row is
left as it is, and a retry under the import's own operation replays its
receipt.

**Do:** upgrade the SDKs together with the server, before any host asks a
session to compact.

### Tool grant run scopes and grant requests

A grant can be scoped to one run of its subject (a session, or the session a
member identity's member holds), and a person can approve a
grant that a host (`tool_grants/request`) or a gated session's agent
(`request_tool_grant`) asked for. Both write grant rows a 0.9.10 binary
cannot read: it reads a run-scoped grant, and the grant an approved request
issued (its id is a version 5 UUID), as unreadable, so it opens nothing there
and lists it under `unreadable`. A 0.9.10 client decodes the status
`run_ended`, the expiry drivers `run` and `recovery` and the audit event
`run_ended` as `unknown`, reads the statuses `requested` and `declined` as
they are (they exist since 0.9.9), and ignores a grant's `scope`.

`rkat-rpc` runs the executor of `tool_grant.issue` decisions on its store and
claims that kind: another process's loop of the kind executes none of them
while it runs. Every grant-gated build mounts `request_tool_grant`, and a
host that takes no grant requests answers its calls with a tool error.

**Do:**

- Upgrade every host that serves gated sessions, and every process that
  executes decisions on their store, before relying on run scopes or
  requests.
- A client that compares a session's tools with its build's gate allows for
  `request_tool_grant`.
- Before rolling back to 0.9.10, revoke the grants approved requests issued,
  or let them expire: 0.9.10 can neither read nor revoke them, and one still
  within its window comes back live on the next upgrade. 0.9.10 executes no
  grant request, so open and approved requests wait for the next upgrade.

or a mob, and the SDKs with their servers.

## Upgrading to 0.9.10

This section is for systems running 0.9.9. The full list of changes is in
the CHANGELOG under `## [0.9.10]`.

Meerkat 0.9.10 is Core 0.9.10, Meta 0.9.10 and Connect 0.9.10, released
together. Meta Forge 0.3.1 ships with them and installs that set.

### Before you upgrade

- **Pin `=0.9.10`.** Move every `meerkat*` dependency to `=0.9.10` at once.
  Meta 0.9.10 pins Core `=0.9.10`, so a host that embeds Meta moves Meta and
  Core to 0.9.10 together (Meta 0.9.9 pinned Core `=0.9.9`). Connect 0.9.10
  is built on Core 0.9.10 and Meta 0.9.10.
- **Upgrade the SDKs with the server:** `meerkat-sdk`, `@rkat/sdk` and
  `@rkat/web` for Core; `meerkat-meta` and `@rkat/meta-sdk` for Meta.
- **Rust 1.97.0 or newer**, as for 0.9.9.
- **No migration step.** 0.9.10 writes no durable state that 0.9.9 cannot
  read, apart from the configuration forms listed under
  [Downgrading to 0.9.9](#downgrading-to-0-9-9).

### Fixes that need no action

- **`session/create` or a first turn no longer hangs during a session
  teardown.** When a session started to unregister during its first turn
  (the first turn of an immediate `session/create`, the first `turn/start`
  of a deferred session, or a cold session's rebuild), the session's
  runtime loop waited on itself and the request never answered. The usual
  trigger was an immediate `session/create` whose first agent build failed,
  for example with `tool_grant_gate_refused`. Such a request now completes,
  and the loop answers its own turn with the retryable
  `runtime_teardown_in_progress` error data. Affects `rkat-rpc`, the Python
  and TypeScript SDKs that drive it, `rkat mob deploy --surface rpc` and
  other hosts of `meerkat_rpc::SessionRuntime`, from 0.8.22 through 0.9.9.
- **Dormant members show their peer address in roster reads.** A member
  seated dormant while its mob ran (a fresh dormant seat, or the next
  incarnation after a rotation or a same-session respawn) now reads with its
  peer id and transport key in `MobHandle::get_member`, `roster`,
  `list_all_members`, `list_members` and the `mob_list_members` tool, as a
  member restored dormant at a restart already did. The read wakes nothing.
  A member on network comms still has no address until its first wake. If
  your host took a missing peer id to mean "not woken yet", read the
  member's state instead.
- **Live voice delegations recover after a restart with dormant members.**
  A host that composes the live delegation coordinator (`openai-live`) with
  lazily restored members (`member_restore: on_demand`, the default)
  retried its restart recovery every second, logging "ClientContext restart
  inventory capture remains pending", for as long as any member stayed
  dormant, and a live channel opened on that host waited with no limit.
  Recovery now leaves dormant members dormant and recovers their
  delegations once, when the member wakes or before the first live channel
  opened on it. A live channel open waits at most 30 seconds for the
  start-up recovery and is then refused with an error that names it: treat
  that refusal as retryable once the mob restores.

### Changes to check

- **Approval files are private on Unix.** `FileApprovalStore` now creates
  every file it writes (the `approvals.json` store, its lock file, and its
  temporary and marker files) owner-only (`0600`), whatever the process
  umask. A store file an earlier release left readable by others becomes
  private on its next commit; an existing lock file is tightened in place,
  and a tightening the filesystem refuses is logged as a warning. Other
  platforms are unchanged. **Do:** if a process that runs as another user
  or group reads these files (a backup or monitoring agent, for example),
  run it as the store's user or read approvals through the API.
- **Per-tool timeouts accept duration strings.** `[tools.tool_timeouts]`
  entries take a duration string (`"840s"`, `"14m"`, `"1h 2m"`), as the
  documentation said, as well as the `{ secs, nanos }` table. Before, a
  string failed the whole config load. Meerkat still writes the table form,
  also when `config/patch` or `rkat config patch` sets a string. **Do:**
  before a rollback to 0.9.9 or earlier, turn hand-written strings back into
  tables: those releases refuse the string form.
- **A refusal before any tool effect reads as not dispatched.** A governed
  tool call refused at its own effect entry
  (`ToolDispatchContext::enter_reviewed_effect`) before any effect of the
  call entered now reaches the model with `tool_invoked: false`, as a
  refusal before the dispatcher already did; it read `"unknown"`. Affects
  0.9.4 through 0.9.9. **Do (Rust):** `OperationRefused::dispatch()` of such
  a refusal is `NotDispatched`, so comparing it with
  `OperationRefused::new(kind)` no longer matches: compare `kind()` and
  `dispatch()`. A tool that runs an effect of its own before its effect
  entry forwards `OperationRefused::new(refusal.kind())`.

### Rebuilds after a completed owner change

Core's governed operations no longer settle a stale read as their outcome when
the owner change that made it stale had already completed: a governed tool
dispatch's prepared entry and its entry stagings, a model request, a
compaction summary, a review's currentness check after its verdict and the
`web_search` helper's model request take the wait after a stale read
(`OwnerChangeChurn::wait_after_stale_read`). With no change in progress they
pause 1 ms and rebuild from the owners, as one of their free rebuilds, within
the same bounds (2 s and 3 free rebuilds per waiting state). The rebuilt
decision is current, or its refusal is the owners' current answer, typed as
before. A model request that reads stale keeps its operation through these
rebuilds, where it rebuilt once at once and, when that read was stale too,
sent the controller feedback request, so a host's operation refusal observer
sees `WaitedForOwnerChange` where it saw `Rebuilt` and `ControllerFeedback`. A
review whose currentness read was stale is superseded and reviewed once more,
where it was retired as an authority change.

Native admission (controller admission, a scoped original's own mandate and
its named contributors' liveness, and the retained-resume checks that share
them) never waits, because it runs inside the session's ingress transaction.
It now makes a read that met an owner change once more, in place, when that
change has completed (`LocalGrantAuthority::owner_change_in_progress` names
none), and answers `ControllerReadinessUnavailable` with `PolicyChanged` as
before for a change still in progress or another one met by that read.

**Do:** keep treating native admission's `PolicyChanged` as retryable. Under
back-to-back changes, wait outside your own locks with a bounded
`meerkat_core::authorization::OwnerChangeChurn::wait_after_stale_read`, then
resubmit once. A host or test that counted operation refusal observer
dispositions for a model request that read stale, or matched an
authority-change retirement for a review whose currentness read was stale,
expects the new ones. See
[Survive owner changes in progress](/rust/native-authorization#survive-owner-changes-in-progress).

### Wrappers and decorators

Forward this new method too. It has a default, so a wrapper without it
compiles, but the default disables what it carries:

- a `DecisionStore` wrapper: `claim_executor`. Its default refuses, so no
  `DecisionExecutorLoop` starts over the wrapper (`DecisionError::Unavailable`).

### A poisoned host store scope

One poisoned host store scope no longer refuses store-wide reads realm-wide:
each such read now depends only on the scope families it reads. A call that
a poisoned scope or a poisoned realm refuses answers the typed
`RuntimeStoreError::ScopeRefused { scopes }`, naming each refused scope with
its poison cause, or `RuntimeStoreError::RealmRefused { cause }`, where it
answered `ReadFailed` or `WriteFailed` with the refusal's text. Behaviour
changes for a poisoned scope:

- A committed session read that the store refuses until its realm is
  reopened surfaces as `SessionError::Store`: its `SessionError::code` is
  `SESSION_STORE_ERROR` (was `AGENT_ERROR`).
- `meerkat_core::service::transport::jsonrpc_code` answers `-32006` for it
  (was `-32000`).
- A wire error built from it (`WireError::from`) carries `INTERNAL_ERROR`,
  JSON-RPC `-32603` (was `AGENT_ERROR`, `-32013`).
- The HTTP status stays 500, and a session method's JSON-RPC error over
  `rkat-rpc` (and the `rkat` exit status) is `INTERNAL_ERROR` either way.
- `MobHandle::wait_one`, `wait_all`, `wait_for_kickoff_complete` and
  `wait_for_members_kickoff_complete` end with `MobError::SessionError`,
  carrying the store's typed refusal, when a member they wait on is not
  final and the store refuses its session. They polled that member's status
  until the caller gave up, a kickoff wait until its timeout.
- `RuntimeDeliveryInbox::pending_delivery_total` and
  `runtimes_with_pending_deliveries` answer while only scopes of other
  families are poisoned, and refuse with
  `RuntimeDeliveryError::Store(RuntimeStoreError::ScopeRefused { .. })`
  while a runtime scope is poisoned.
- Meta: `HostStoreReadiness::is_ready()` no longer counts a scope-only
  poison; a poisoned realm still makes it not ready.
  `HostStoreReadiness::poisoned_scopes`, every poisoned scope with its
  cause, is new.

**Do:** a caller that matched `ReadFailed` or `WriteFailed` for these
refusals matches the new variants; one that only formats the error keeps
compiling. A Meta probe that must keep the earlier rule checks
`readiness.is_ready() && !readiness.scope_poisoned`.

### New

- **GitHub Copilot configured once.** A `[realm.<realm>.copilot]` section
  names a Copilot account's token source once (`env` or
  `external_resolver`) and gives the realm the account's `copilot_openai`,
  `copilot_anthropic` and `copilot_gemini` routes, in place of nine explicit

  - sessions on the zero-config Copilot routes (`global:copilot_openai`,

    (`global:account:github_copilot`) as their credential identity and run

  **Do (Rust):** `RealmConfigSection` gains `copilot` (set it to `None` in

## Upgrading to 0.9.9

This section is for systems running 0.9.8. The full list of changes is in
the CHANGELOG under `## [0.9.9]`. 0.9.9 has no migration step: it opens every
0.9.8 store as it is, and creates what it adds on first use (the
`runtime-tool-grants` schema domain with the first scoped tool grant,
`approval_decisions.sqlite3` with the first durable decision). Some of what
it writes, though, 0.9.8 cannot read: read
[Downgrading to 0.9.8](#downgrading-to-0-9-8) before you plan a rollback,
and back up the state root as the steps above say.

### Before you upgrade

- **Rust 1.97.0 or newer.** Every crate of this release declares
  `rust-version = "1.97.0"` (0.9.8 declared 1.94.0), and Cargo refuses to
  build them, `cargo install rkat` included, with an older rustc.
- **Pin `=0.9.9`.** Move every `meerkat*` dependency to `=0.9.9` at once.
  Meta 0.9.9 pins Core `=0.9.9`, so a host that embeds Meta moves Meta and
  Core to 0.9.9 together (Meta 0.9.7 pinned Core `=0.9.8`).
- **Upgrade the SDKs with the server.** A Python, TypeScript or Web SDK of
  0.9.8 or earlier refuses the new `tool_results_bounded_for_request` event
  type, as it does any event type newer than its contract.
- **Know when a session stops reading on 0.9.8.** 0.9.9 writes a session at
  session envelope 5, which 0.9.8 refuses, once the session holds an
  operator-instruction fact or a retired or moved instruction activation row.
  A session in which a later activation of a key superseded an earlier one
  gets there at its first compaction on 0.9.9, which retires the superseded
  body; a mob member that receives operator instructions gets there at its
  first run that applies them. Every other session stays at envelope 4 and
  still reads on 0.9.8. `rkat storage doctor` on 0.9.9 lists the sessions at
  envelope 5 (`operator-instruction-envelope`) and the mobs 0.9.8 cannot
  restore (`operator-instruction-mob-events`) of a Core realm; for a Meta
  state directory, see [Downgrading to 0.9.8](#downgrading-to-0-9-8).

### Breaking changes and what to do

#### Agent schedule tools answer pages of summaries

The schedule tools' replies changed, for agents and for every generic call
path that runs them: RPC `schedule/call`, REST `POST /schedule/call`, the MCP
server's `meerkat_schedule_*` tools, the Python SDK's `call_schedule_tool` and
the TypeScript SDK's `callScheduleTool`. `meerkat_schedule_list` returns one
page of summaries (`{"schedules": [...], "page": {...}}`, 50 by default, at
most 200) where it returned every live schedule whole; every tool that
returns one schedule returns the public shape of `schedule/get`, without
`machine_state`; and `meerkat_schedule_occurrences` pages every list reply
(at most 200 rows), with summaries by default. The host listings
(`schedule/list`, `schedule/get`, `GET /schedules`, `list_schedules`,
`listSchedules`) return every schedule whole, as before. A schedule's
`superseded_ack_ids` now lists only the occurrences its latest revise or
delete superseded.

**Do:** read one schedule whole with `meerkat_schedule_get`, or every schedule
whole through the host listing; read the public fields where you read
`machine_state`; follow `page.next_cursor`, and pass `view: "full"` for whole
occurrences. Bulk readers use the typed host surfaces, not the agent tools:
RPC `schedule/list` and `schedule/occurrences`, REST `GET /schedules` and
`GET /schedules/{id}/occurrences`, the Python SDK's `list_schedules` and
`list_schedule_occurrences`, and the TypeScript SDK's `listSchedules` and
`listScheduleOccurrences`. See
[Agent-side schedule tools](/guides/scheduling#agent-side-schedule-tools).

#### WorkGraph reads come newest first and report their cut

`list` and `snapshot` (the agent tools, `workgraph/list` and
`workgraph/snapshot`, the REST routes and `rkat workgraph`) return the most
recently updated items first, so a `limit` cut keeps the newest; they
returned the least recently updated first. `ready` and `snapshot` no longer
refuse a namespace with more than 1,000 live items, nor `snapshot` one with
more than 1,000 edges touching a live item or 1,000 attention bindings: they
read the whole namespace, and `limit` (default 100, at most 1,000) cuts the
result. Every list, ready and snapshot result reports its cut
(`total_items`, `truncated`) and names a `next_cursor` when it ended early;
events results report `truncated`, `next_after_seq` and
`event_high_water_mark`. `WorkGraphStore::list_items` of the built-in stores
orders newest first as well.

**Do:** a reader that needs every item follows `next_cursor` (`--cursor` on
the CLI) instead of raising `limit`, and a reader that relied on the
oldest-first order sorts the items itself. A result without the new fields
comes from an older server and may still have been cut. In Rust, set the new
fields where you build `WorkGraphSnapshot`, `WorkGraphItemsResponse`,
`WorkItemsResult`, `WorkGraphEventsResponse` or `WorkEventsResult`
literally; a filter literal that ends with `..Default::default()` keeps
compiling. See
[Filter Semantics](/reference/workgraph-reference#filter-semantics).

#### Scoped tool grant gates need every host upgraded

A session built with `grant_gated_tools` (Rust `SessionBuildOptions` or
`AgentBuildConfig`, or JSON-RPC `session/create`) records its gate in its
tooling metadata, which a binary older than scoped tool grants does not read:
such a binary resumes a gated session with its gated tools ungated. An
`rkat-rpc` older than scoped tool grants also ignores `grant_gated_tools` and
builds the session ungated. The Python and TypeScript SDKs refuse to send a
gate to a server whose contract is older than 0.9.9.

**Do:** upgrade every host that serves gated sessions before relying on a
gate, and do not roll such a host back. A JSON-RPC client that is not one of
the SDKs checks the server's contract version (0.9.9 or later) before it
sends a gate. See [Scoped tool grants](/concepts/tools#scoped-tool-grants).

#### `rkat run` stops waiting for a stdin that stays silent

With the default `--stdin auto`, `rkat run` and `rkat run --resume` read stdin
on a thread of their own: input that has not started within 2 s is skipped
with one warning, and input that started is read to end of file as before.
Before, a run whose stdin was not a terminal and stayed open without writing
blocked forever.

**Do:** a producer that pipes into `rkat run` but starts writing more than
2 s after launch passes `--stdin blob`, which still waits for end of file; a
launcher that hands `rkat run` an open stdin it never writes can pass
`--stdin off` to skip the wait. See
[Stdin modes and Unix pipes](/cli/commands#stdin-modes-and-unix-pipes).

#### Member turns run on the host's runtime

The turns of runtime-backed mob members, and of the sessions an RPC
`SessionRuntime` serves, now run on the host's runtime, as the turns of the
sessions a host creates directly through a session service already did: a
member's on the runtime of the task that provisions it (the mob actor's), an
RPC session's on the runtime the `SessionRuntime` was built on. Before, a
member's turns ran on Core's process-wide `meerkat-machine-cleanup` runtime,
and a deferred or rebuilt RPC session's on `meerkat-runtime-serving`. The
agent loop, model streaming, tool calls and whatever the tools spawn now use
the host's worker threads and their stack, and a member tool that blocks its
thread holds one of the host's workers. A host runtime that stops in the
middle of a turn ends the turn as a crash would: its inputs stay non-terminal
and the next start resumes them, and an RPC session runtime refuses an input
that arrives while the session waits for that start (`host_runtime_stopped`).
The two process-wide runtimes keep the cleanup
and runtime-loop work, and their threads take 16 MiB again when
`RKAT_WORKER_STACK_BYTES` is unset.

**Do:** size the worker stacks of the runtime your mobs and RPC session
runtimes run on for the tools you compose. A Tokio runtime built with default
settings gives its workers 2 MiB (`tokio::runtime::Builder::thread_stack_size`
sets it); Core's host binaries, and an embedding that runs its main future
through `meerkat_runtime::host_stack::run_host`, run their workers on 8 MiB
(`RKAT_WORKER_STACK_BYTES` sets it). Build an RPC `SessionRuntime` inside the
Tokio runtime its sessions should run on, and keep that runtime running while
you serve them: built outside a Tokio runtime it records none, and the actor
of a deferred or rebuilt session is then created on Core's serving runtime,
as before. A `MobSessionService` wrapper forwards
`runtime_turn_lost_its_host_runtime` (see
[Wrappers and decorators](#wrappers-and-decorators)). See
[Worker Stack Budget](/guides/deploying#worker-stack-budget).

#### Compaction projects each request's input

The compaction check now projects each request's input tokens: the
provider's count for the last answered request plus an estimate of only the
rows appended since, so a large tool result that would carry the next request
past the threshold compacts first. A request the provider refused for not
fitting the model's context, or one that carried the run's own tool results
shortened (`tool_results_bounded_for_request`), makes the next run's first
check compact the whole transcript once. The anchor and the refusal ride the
session's compaction cadence in two optional fields that 0.9.8 ignores.

**Do:** nothing for the default compactor. A custom `Compactor` that wants
the projection or the refusal reads the new `CompactionContext` fields. To
leave more room for what one boundary appends, set a lower explicit
`auto_compact_threshold` (config, or a mob profile's): the derived threshold
is four-fifths of the model's context window. See
[Capacity and cadence](/concepts/memory-and-compaction#capacity-and-cadence).

#### Text that models and tests read

- A `policy_denied` tool error reads `Tool call denied (<code>): <message>`
  to the model, from the denial itself, for an application consequence policy
  and a scoped tool grant gate alike.
- The compaction summary request names each image or video in a user row or
  tool result as `[image (<media type>) omitted from this summary request]` or
  `[video (<media type>) omitted from this summary request]`, where it wrote
  `[image: <media type>]` and `[video: <media type>]`, and the compaction
  prompt gains a paragraph saying that such a placeholder tells nothing about
  what the agent could see. The prompt still contains `CONTEXT COMPACTION`.

**Do:** update a client or test that matches either text.

#### Consent, approvals and governed steps

- Approval reads and decisions run host code. `ApprovalService::get`, `list`
  and `decide_consent` call the host's authorization `prepare` and
  `review_operation_context` (and, at a decision or a spend, the route's
  `eligibility`) on the caller's thread, outside the approval owner's locks,
  for a consent whose retained decision an owner publication change made
  stale. `decide_consent` can answer a retryable `StoreUnavailable`, with
  nothing recorded.
- A pending or approved human consent is kept across unrelated authorization
  changes and past the end of its decision's own validity window. It is
  withdrawn as `ContextChanged` when its binding, review tier or presented
  material changes, and as `AuthorityChanged` when its owners refuse the
  operation (an owner change gave `context_changed` before) or its approver
  was revoked or forbidden by policy since deciding.
- The native work owner's operation-time steps answer another actor's hold
  of the work's authorization publication writer as a refusal to rebuild
  (`Refused(ReprepareRequired)`), where they answered `Unavailable`, and
  Core's governed dispatch steps answer `AuthorizationRefused`
  (`ReprepareRequired`) where they answered
  `OperationAuthorizationUnavailable`. A scoped original's admission answers
  an owner change it meets as `policy_changed`, where it answered
  `policy_unavailable`.

**Do:** never hold a lock your authorization owners take while you read or
decide approvals, and retry `StoreUnavailable`. Match the refusal to rebuild
where you matched the unavailable answer for this contention, or take the
steps through their waiting forms
(`run_if_current_within_after_owner_change`,
`issue_child_if_current_within_after_owner_change`,
`GovernedHelperChildIssuance::issue_or_recover_after_owner_change`,
`GovernedHelperAdmissionFence::create_idempotent_after_owner_change`). A
consent route that answers eligibility only for logins within their own
expiry keeps answering for a login through an approval decided in it, until
that login is logged out, replaced or retired; a route that resolves
eligibility with `PublishedConsentEligibility::observe` overrides
`HumanConsentRoute::eligibility_answer` with
`PublishedConsentEligibility::observe_answer`. See
[Human consent](/guides/authorization-integration#human-consent) and
[Owner changes in progress](/guides/authorization-integration#owner-changes-in-progress).

#### Mob hosts (Rust)

- A dormant seat on in-process comms takes the members' comms identity root
  from the mob's session service when the host declares none (see
  [Dormant seats and comms keys](/guides/mobs#dormant-seats-and-comms-keys-rust-hosts)).
  A service that reports `NotKept`, or a root it cannot resolve, has every
  seat refused unless the host declares a root.
- `MobHandle::rotate_member` is durable from its start, and a restarted mob
  finishes it itself. It no longer takes over a retirement of the member that
  started without a rotation: the call is refused retryable
  (`MobError::LifecycleOperationPending`) until that retirement finishes or is
  re-driven (`MobHandle::redrive_retirement`).
- A retire that races a spawn of the same identity is refused
  `MobError::LifecycleOperationPending`, retryable once the spawn settles.
- A spawn, a spawn policy's auto-spawn or a dormant seat of a local session
  member in a mob with no runtime (every profile `TurnDriven`, on a session
  service without a runtime adapter) is refused before anything of it exists,
  with `MobError::MissingMemberCapability` (`outbound_comms_runtime`), where it
  failed `Internal` after the member's session was created.

**Do:** drop a comms identity root you passed only to match your factory's;
keep `MobBuilder::with_network_member_comms` for members on TCP or UDS. After
a restart, read a member once before you re-issue an unanswered
`rotate_member`: a higher generation means the rotation finished, a member
`MobHandle::list_members_including_retiring` lists as Retiring means the mob
finishes it, and the generation the call saw, not Retiring, means it never
started. Retry `LifecycleOperationPending`. See
[Respawn rotation and scoped release](/reference/mob-architecture#respawn-rotation-and-scoped-release).

#### Host store authors

A host store meets obligation 5 (fencing) at commit: it refuses a batch whose
token is below one acquired before the batch's commit point with
`FencedOut`. A store that only hides such a batch at load answers the stale
writer's commit `Ok`, and is outside the host store contract. On a host store
realm, a stopped store writer no longer fails turns: a dispatch, a round
commit or a closing save waits for the writer's re-acquire, and a store fence
gap suspends the run until the fence is back.

**Do:** make the fence check and the commit one transaction, as an
append-only store must. See
[Obligations](/reference/host-store-spi#obligations) and
[Keeping A Realm In Your Own Database](/guides/durable-runs#keeping-a-realm-in-your-own-database).

### Wrappers and decorators

Implement the new required methods; they have no default, so a wrapper
without them no longer compiles:

- a `SessionAgentBuilder` or `MobSessionService` wrapper:
  `session_comms_identity_root` (required, no default). Forward it to the
  builder or service you wrap: a mob seats its dormant members under the
  root it reports. A builder or service that builds no comms of its own
  answers `SessionCommsIdentityRoot::NotKept`.
- a `SessionRuntimeLlmReconfigureService` implementation:
  `live_session_own_operator_instruction_entry_placement`, which says where
  the operator-instruction entry rows a live session wrote itself stand.

0.9.15 is not published yet; what is said here about 0.9.15 describes the coming release.

Forward these new methods too. They have defaults, so a wrapper without them
compiles, but the default disables what they carry:

- a `MobSessionService` wrapper: `record_member_instruction_target`,
  `release_member_instruction_target` and `read_member_instructions`. Their
  defaults refuse `durability_unavailable`, so a mob's operator instructions
  never reach the members behind the wrapper (each is reported blocked), a
  retiring member's target is never released (the mob logs it), and the
  status read reports every member unreadable.
- a `SessionAgent` wrapper: `release_instruction_target_control`, the live
  session's half of that release. Its default refuses the same way.
- a `SessionAgentBuilder` wrapper: `instruction_lowering_for_identity`. Its
  default (`None`) leaves the status read unable to report that a model
  cannot carry operator instructions (`lowering_unavailable`).
- a `MobSessionService` wrapper: `runtime_turn_lost_its_host_runtime`, as you
  forward `live_session_actor_registered`. Its default answers `false`, so a
  member of a stopped host runtime served through the wrapper can have an
  input that reaches it after the stop recorded as a failed run.
- a `MobSessionService` wrapper over a durable session owner:
  `bind_seated_member_session`. Its default refuses, so a dormant resume seat
  over a session that names no member binding is refused.
- an `AgentToolDispatcher` wrapper: `adjudicates_tool_grants` and
  `observes_bindings_only`. Without the first, an agent with a scoped tool
  grant gate refuses to build over the wrapper
  (`ToolGrantGateWithoutAdjudication`).
- an `AuthLeaseHandle` wrapper: `publish_source_credential`. Its default
  fails closed, so a `github_copilot_token` route that reads its token from
  the environment, a command or a resolver fails to resolve over the wrapper.
- a `RuntimeStore` decorator: `load_tool_grant`, `list_tool_grants`,
  `put_tool_grant_if_absent`, `compare_and_put_tool_grant`,
  `append_tool_grant_audit` and `read_tool_grant_audit`. Their defaults
  answer `Unsupported`, so the grant service refuses every grant behind the
  decorator and a gated name stays closed.
- a `SessionCheckpointer` wrapper: `dispatch_fence_ready`. Its default checks
  the fence without waiting, so a run behind the wrapper fails where it would
  wait for a stopped host store writer's re-acquire.
- a custom mob storage: `MobIdentityStore::scan_created_identities_page`. Its
  default reads none, which is right only for a storage that never holds a
  created identity entry.
- a `WorkGraphStore` that serves pages: `list_public_events` and
  `latest_event_seq`, as the built-in stores do. The default
  `list_public_events` pages through `list_events`.
- an `HttpAuthorizer` wrapper: `redact_response_diagnostic`. Its default
  changes nothing, so a credential a provider echoes back reaches the errors
  and logs of the requests signed through the wrapper. (From 0.9.15 the
  default removes the values `visit_signed_credentials` names and
  credential shapes; a wrapper still forwards `redact_response_diagnostic`,
  or the values the wrapped authorizer signed with are not removed by exact
  match.)
- an `AuthLeaseHandle` wrapper: `mark_publication_refused` too. Its default
  fails closed, so GitHub's refusal of a `github_copilot_token` route's token
  fails to be recorded over the wrapper, and the request fails without
  withdrawing the token.

### Declared identity entries

0.9.9 adds the declared apply (`MobHandle::apply_declared_roster`, Rust
only): a host declares its roster of identity entries, and Core seats,
restamps, holds and retires them (see
[The declared apply](/reference/mob-architecture#the-declared-apply)). A
host that never calls it and never spawns or seats with entry custody sees no
change.

- **An entry outlives a retirement.** A host's `retire` of a declared
  identity that its roster still lists ends the identity's member, and the
  entry stays, unseated and owed its seat: the next apply seats it again, on
  the session the retirement archived. To take a declared identity out of
  the roster (unlist it), apply a complete roster without it, or unlist it
  alone (`MobHandle::unlist_declared_identity`): its member retires and the
  entry ends, and listing it again brings it back. Removing an identity
  (`MobHandle::remove_identity`) is permanent: it tombstones the name.
- **Identities retired before the upgrade come back on a fresh session.** The
  session an identity's retirement archived is recorded by 0.9.9 only. An
  identity retired under 0.9.8 or earlier has no record, so when the host
  lists it again the apply seats it on a fresh session, and its earlier
  history stays on its archived session. Core reads no label and no journal
  row to find that session.
- **Apply the roster after every start.** Between a start and the first
  apply after it, Core knows only the entries its journal records: the seated
  ones, and those whose member a retirement other than an unlisting ended.
  An entry no member ever held, a role hold and a held creation are not
  recorded, and the first apply declares them again. Until then, a member
  whose role the host moved while the process was down is not held, and a
  peer delivery can wake it under its previous role.
- **Consume a first-boot request only once it is carried out.** The answer
  names the requests the apply carried out
  (`DeclaredRosterOutcome::first_boot_requests_carried_out`). Keep every
  other request for the next apply: a deferred, refused or failed answer did
  not carry it out.
- **One apply at a time.** An apply called while another apply of the same
  mob runs is refused `MobError::LifecycleOperationPending`, retryable, and
  writes nothing.

**Do:** apply the host's complete roster once after every start, before the
host wakes or seats its identities; consume exactly the first-boot requests
the answer names; unlist an identity to take it out of the roster
(`remove_identity` is permanent: it tombstones the name).

### Created identity entries

0.9.9 reads a second origin of identity entry, `Created`: an entry Core keeps
as a row of its own in the identity store (schema version 2, beside the
host-adopted identity intents of version 1). A start recovers every created
entry row, and a name whose row is removed or that this build cannot read is
reserved, never free (see
[Identity entries](/reference/mob-architecture#identity-entries)). The origin
is provenance and the custody of the entry's desired record only: a created
entry's member is built from its profile like any other member, with its own
roster labels, tools, grants and wiring. A created entry is a store-owned
identity, which Core's own changes create, update, archive and remove (see
below). A mob that holds no created entry row sees no change but the new
read answers.

- **The entry reads have new answers.** `identity_entry` answers
  `IdentityEntryRead::Unreadable` and `Removed`, the entries page lists
  unreadable names apart (`IdentityEntryPage::unreadable`), and the census
  counts created entries and removed and unreadable names;
  `IdentityCensus::is_complete()` is false while a name is unreadable. The
  member binding history answers `MemberIdentityManagement::CreatedEntry` for
  a created entry. The enums are `#[non_exhaustive]`.
- **The declared apply notes created names and refuses reserved ones.** A
  host roster that lists a created entry's name is answered
  `DeclaredEntryOutcome::Noted` (`DeclaredEntryNote::OwnedByStore`) for that
  identity alone, a quiet steady state that changes and retires nothing; a
  removed or unreadable name is answered `Refused`
  (`DeclaredEntryRefusal::NameTombstoned`, `NameUnreadable`). Its seal never
  unlists a created entry.
- **A host store opens over a row it cannot read.** A mob storage on the
  host store SPI reads its identity intents one entry at a time: an entry
  whose row this build cannot decode is kept as stored, read as unreadable
  for its identity alone and written back untouched on every rewrite of the
  group. Before, one such row failed the whole mob's open. An entry it
  cannot attribute to an identity (an envelope or a key it cannot read)
  still fails the open.
- **A SQLite mob adopts beside a created row.** An identity-first adoption
  reads the host-adopted intent rows alone, so a created entry's row no
  longer refuses the adoption of another identity, and the intent list
  leaves created rows out.

### Store-owned identity changes

0.9.9 adds Core's own identity changes (Rust only): a create of store-owned
identities, their update, archive and unarchive, the removal of an identity
of either custody, and the host's preparation of an identity before its first
seat with its held constructions (see
[Store-owned identity changes](/reference/mob-architecture#store-owned-identity-changes)
and
[Host preparation and held constructions](/reference/mob-architecture#host-preparation-and-held-constructions)).
A host that calls none of them sees no change.

- **A removal is for good, for either custody.** `MobHandle::remove_identity`
  of a roster-owned identity writes its name's tombstone to the identity
  store: the name is never an identity or a member again, and a roster that
  still lists it is answered `DeclaredEntryRefusal::NameTombstoned` for that
  identity. Drop the identity from the roster when you remove it. To take a
  roster-owned identity out and keep its name and session for later, unlist
  it (`MobHandle::unlist_declared_identity`, or a complete roster without
  it) and list it again.
- **An archived identity refuses deliveries.** A delivery to an archived
  store-owned identity is refused `MobError::IdentityArchived` until its
  unarchive, and one to an identity awaiting its host's preparation is
  refused retryable (`MobError::MemberWakeRefused`, `HostPreparationPending`).
- **A store-owned update names the spec it was decided against.**
  `StoreOwnedIdentityUpdate` carries the identity's expected spec digest, and
  a change decided against another spec is refused
  `IdentityChangeRefusal::StaleSpec` with the identity's current digest and
  revision: read the record again (`MobHandle::identity_record`) and decide
  the change anew.
- **`SpawnMemberAdmissionObservations` gains two fields.** The public fields
  `binding_present` and `placement_present` (a runtime binding or a placement
  on the request, which a grant with manage scope alone admits) are new, so a
  struct literal outside `meerkat-mob` must set them (`false` keeps the
  previous answer) or end with `..Default::default()`.

**Do:** drop a removed identity from the host's roster; read the record again
after a `StaleSpec` refusal before deciding the change anew.

### WorkGraph evidence refs (Rust)

`WorkEvidenceRef` is `#[non_exhaustive]` and gains the field `withdraws` (see
[Withdrawing Evidence](/reference/workgraph-reference#withdrawing-evidence)),
so a struct literal outside `meerkat-workgraph` no longer compiles. Build a ref
with `WorkEvidenceRef::new(kind, id)` and the builders `with_label`,
`with_summary` and `with_withdraws`, or assign the public fields after `new`.
The constructor sets no confirmation or execution provenance. A ref without
withdrawals keeps its wire form, so stored items, keyed-create digests and
attention continuation keys do not change.

### Quarantined mob stores

A persisted mob store that does not restore no longer fails the restore of
every mob of the realm: it is quarantined (kept exactly as found, with no
actor), and the other mobs restore (see
[Quarantined mobs and degraded members](/guides/mobs#quarantined-mobs-and-degraded-members)).
A call that addresses a quarantined mob fails with the new refusal kind
`mob_quarantined`, and `mob/list` lists the mob under `quarantined`. A mob
start likewise no longer stops for one member whose session read fails: that
member is degraded (`custody_deferred` with `store_unavailable` or
`store_unreadable`). The quarantine is not durable: every start derives it
again, and 0.9.8 reads the same stores (a store that does not restore fails
its whole restore again).

**Do:** a client that branches on mob refusal kinds handles
`mob_quarantined` (the SDKs read it with `mob_quarantined` and
`mobQuarantined`). A host that must still fail its boot on such a store
reads `MobMcpState::quarantined_mobs` (or `mob/list`'s `quarantined`) after
the restore and refuses while it is not empty. **Do (Rust):**
`MobMcpState::unrestored_mobs` is gone (read `quarantined_mobs` or
`mob_inventory`), `held_child_mobs` returns a `Result`, and a
`MobListResult` literal sets `quarantined`. A host store implementation
answers `HostStoreError::Corrupt` for stored data that does not decode or
fails its integrity check.

### Downgrading to 0.9.8

Check for mobs that used operator instructions first. A mob that recorded an
operator instruction journals rows at mob event schema 10. Core 0.9.8 and
0.9.7 refuse such a journal ("unsupported stored mob event
schema_version=10; expected 9"), and their realm restore (the mob roots of
the rkat CLI, RPC and MCP hosts) stops at the first such mob, so every mob of
that realm fails to restore and every mob verb answers the error. A Meta
gateway whose own mob recorded an operator instruction does not resume its
mob. Before any downgrade of a realm to 0.9.8 or 0.9.7 (for a Meta state
directory, see below):

1. Run `rkat storage doctor` on 0.9.9 or later.
2. For each mob listed under `operator-instruction-mob-events`, destroy the
   mob, or move its database (`mobs/<name>.db` in the realm's state
   directory, the path the finding names) out of that directory.
3. Only then start the older binary.

The doctor reads the mob databases on disk only. For a realm on a host store,
look in the host's store for mob events at schema 10. A member session that
recorded its mob's snapshot is written at session envelope 5, which 0.9.8
refuses session by session; the doctor lists those sessions under
`operator-instruction-envelope`.

A Meta gateway's state directory is not a Core realm, and
`rkat storage doctor` covers neither of the files that matter here: it does
not read `runtime.sqlite`, where Meta keeps its sessions, or
`event_log.sqlite3`, the gateway's own mob journal. Its
`schema-from-the-future` error for `sessions.sqlite3` (ledger domain
`session-store` at version 999999) is expected: that file is the retired
stamp that `meta_gateway storage-migrate-native` leaves for Meta 0.9.3 to
refuse. From Meta 0.9.10, Meta's storage doctor (`meta/storage/doctor`)
takes this census of a state directory, read-only, as Info findings that
carry counts only:

- `operator-instruction-envelope`: the sessions of `runtime.sqlite` at
  envelope 5;
- `operator-instruction-mob-events`: the mob events at schema 10, in the
  gateway's own journal and in each child mob's journal under `mobs/`;
- `identity-store-rows`: the identity-store rows of schema version 2 or
  later in the same mob stores (see below).

Each reports one finding for the state directory with its total, 0
included, and one for each file that counts above 0 or could not be
counted, whose `path` names the file. On Meta 0.9.9, take the first two with
two read-only queries (`sqlite3 -readonly <file> "<query>"`) on a state
directory in the default disk layout:

- the sessions at envelope 5, on `runtime.sqlite` (`meta/status_identity`
  names the `session_id` of each identity):

  ```sql
  SELECT session_id FROM session_heads WHERE version = 5
  UNION
  SELECT session_id FROM sessions
   WHERE session_id NOT IN (SELECT session_id FROM session_heads)
     AND json_extract(CAST(session_json AS TEXT), '$.version') = 5;
  ```

- the mob events at schema 10, on `event_log.sqlite3` and on each child mob
  database under `mobs/` that has a `mob_events` table:

  ```sql
  SELECT count(*) FROM mob_events
   WHERE json_extract(CAST(event_json AS TEXT), '$.schema_version') = 10;
  ```

Destroy, or move out of `mobs/`, each child mob database that counts rows.
The gateway's own journal is not in `mobs/`: a gateway whose own journal
counts rows does not start its mob on Meta 0.9.7 or 0.9.6. On Meta 0.9.9,
nothing an SDK host can call writes an identity-store row of schema
version 2, so such a host has none to count; a Rust host counts its mob's
with `MobHandle::identity_record_census()`.

Durable decisions live in their own file, `approval_decisions.sqlite3`,
beside `approvals.json` under the store path; 0.9.9 creates it with the first
hold and changes no other file for them. 0.9.8 never opens that file and reads
`approvals.json` as before, so a downgrade keeps every approval and leaves the
decisions untouched. Nothing serves the decisions under 0.9.8: none expires,
executes or settles its notice. Back on 0.9.9, an open decision past its
deadline expires at its first read, or when a deadline driver reads the due
ones, and owes its notice. An approved decision is listed as owed and runs only
before its deadline; past it, it expires the same way, unless its execution
permit was outstanding at the downgrade: that decision waits for its owner to
settle the permit (record the commit, or release or refuse the permit).

0.9.8 does not know a same-session successor's rotation (a
`MobHandle::respawn_member`, the declared apply's role migration or
runtime-mode restamp, and `MobHandle::respawn` of an identity entry's
member), which 0.9.9 records on the retirement's start row. One that a crash
interrupted after its start and before its end is, for 0.9.8, a plain
retirement: 0.9.8 skips the record, restores the member under its old role
and comms name, and its start re-drives the retirement to its end, which
retires the member and archives the session the successor was to keep. No
successor is seated, under the new role or the old one: the member ends
whole, it is never split across two names, but it is gone. Before a
downgrade, finish every pending same-session successor on 0.9.9. Its member
is listed Retiring (`MobHandle::list_members_including_retiring`); an
identity entry's reads `rotation_in_flight` as `Some(SameSession)`
(`MobHandle::identity_entry`, counted by `IdentityCensus::rotation_in_flight`).
A start of the mob on 0.9.9 finishes it, as do `respawn_member` again under
the profile it started with and `MobHandle::redrive_retirement`; one whose
profile left the definition finishes once that profile is restored.

0.9.8 reads the rows the declared apply writes as plain member rows: its
seats are member spawn rows, and its unlisted retirements plain retirements.
0.9.8 ignores the fields it does not know on them: an entry, the cause on a
retirement's start row, whether a retirement archived the member's session
on its end row, and the history notice on a seat's row. A retirement the
apply's seal started and a crash interrupted finishes under 0.9.8 as a plain
retirement. Entries the apply holds unseated, role holds (with the run-start
holds they place) and held creations live in memory only, so 0.9.8 sees none
of them.

A created identity entry's row is a row 0.9.8 does not know. On SQLite, 0.9.8
reads it as an identity intent row it cannot read, for that identity alone:
its member binding history answers `IntentUnreadable`. Its identity-first
adoption, though, decodes every intent row of the mob, so 0.9.7 and 0.9.8
refuse every new identity-first adoption in a mob that holds a created
entry's row, while their reads stay per identity. A worker reconcile of
0.9.8 that retires stale members can retire a created entry's member; once
the host runs 0.9.9 again, the start re-seats the entry on the session that
retirement archived. A host store is
different: 0.9.8 decodes a mob's identity intents as a whole and does not
open the mob's storage while one of them is a created entry's row. Before a
downgrade, a mob on a host store must hold no created identity entry.

0.9.15 is not published yet; what is said here about 0.9.15 describes the coming release.

A removal writes a row of the same schema for either custody (a removed
roster-owned identity's tombstone included), and so do an archive and a
store-owned identity's pending preparation, so the paragraph above applies to
every mob that holds one. This release has no step that deletes these rows:
a removal writes the name's tombstone and an archive keeps its row, so a mob
that holds any (`IdentityRecordCensus::created_rows` above zero) has no
supported downgrade before the export and purge steps, which 0.9.11 adds
([the downgrade cycle](#the-downgrade-cycle-of-store-owned-identities)).
`MobHandle::identity_record_census()` counts the rows and what a downgrade
must settle first: the mob's rows (`created_rows`, the archived ones, the
tombstones and the unreadable ones), the identities awaiting their host's
preparation (`preparations_open`), the held constructions
(`constructions_held`) and the seated store-owned identities whose member's
last seat row predates their row's labels or profile (`seats_stale`: 0.9.8
rebuilds such a member from its seat row; a respawn with the row's labels,
`MemberRespawn::with_labels`, or a restamp brings the seat row up to date).
From 0.9.15 a label update restamps its idle member
itself, so only a seat an earlier release left behind, or one whose member
was not restamped at its update (it held work, say), counts here. From
that release on, an update that leaves its member's restamp owed records
it in the identity's row (`label_restamps_owed` counts those rows): the
mob's roster reads the row's labels from the update's commit and from each
start on (a host's own respawn of the member with other labels in between
keeps those on its roster entry until the next start or the restamp, while
its builds carry the row's), the member's builds are compared with them,
and a retry of the
update, the identity's next update while the member is idle, or a respawn
with the row's labels settles it. Such a seat needs no step before its
host adopts `MemberBuildPreparer::prepare_store_owned_seat` or a spawn
customizer that sets labels. A seat an earlier release left behind carries
no such record: respawn it with its row's labels, or update the identity
while its member is idle, before the host adopts either, since no start
and no build moves its labels and a host that answers such a seat from its
row is refused the member's build. Releases 0.9.9 through 0.9.14 read a row
that records an owed restamp as unreadable, for that identity alone:
settle the owed restamps before a rollback to one of them (the store-level
row counts below report `label_restamps_owed` with no running mob).
The count names the seat rows a downgrade would read: step 3 of the
downgrade cycle brings them up to date.
Change receipts are rows of the identity store's receipts table under keys
0.9.8 never asks for.

0.9.15 is not published yet; what is said here about 0.9.15 describes the coming release.

From 0.9.10 the rows are also counted with no running mob, by the same
rule, read-only. `MobStorage::read_identity_record_rows` counts a store
file's rows per mob (`IdentityRecordRows`: `created_rows`, `archived`,
`tombstones`, `unreadable`, and from 0.9.15 `label_restamps_owed`, the rows
that record an owed label restamp), and `MobStorage::identity_record_rows` counts a
storage's mob, a host store's included. `rkat storage doctor` reports them
for each mob database that holds any, and Meta's storage doctor for a Meta
state directory, as the Info finding `identity-store-rows` with the counts
only. The doctors do not print the owed label restamp count; the row
counts do (`label_restamps_owed`), so read that count before a rollback.

0.9.8 reads WorkGraph items whose evidence withdraws earlier evidence, but it
ignores `withdraws` and drops the field when it rewrites such an item (any
mutation of the item, including a host sweep such as a lease-expiry
observation). The withdrawing refs stay as ordinary evidence, and the refs
they withdrew read as current again. Two more effects reach only requests and
items that carry withdrawals. 0.9.8 digests a keyed create without the field,
so replaying a key whose request carried `withdraws` answers `Conflict`
instead of `Replayed`. An item with withdrawals projects without the field, so
its attention continuation key changes once and a continuation recorded under
0.9.9 does not match it. Keys, items and continuations without withdrawals
are unaffected.

A session whose document 0.9.9 writes at session envelope 5 does not
downgrade: one that carries operator-instruction facts, one in which a
compaction, or a system-row prune with
`retire_superseded_activation_bodies`, retired a superseded instruction
activation body (or a fork child that copied such a row), and one in which
a rewrite moved an instruction activation row to another offset. 0.9.8 refuses such a session;
`rkat storage doctor` lists them (Info finding
`operator-instruction-envelope`) before you roll back, and on a Meta state
directory Meta's storage doctor counts them under the same code from Meta
0.9.10. Every other session stays at envelope 4 and reads on 0.9.8
unchanged.

0.9.8 does not read a session's scoped tool grant gate, which 0.9.9 records
in the session's tooling metadata: 0.9.8 resumes a gated session with its

`runtime-tool-grants` schema domain, which 0.9.8 leaves alone. A turn that
failed because its session's build refused the gate records
`AgentErrorReason::ToolGrantGateRefused` in its failed-turn completion row,
and 0.9.8 decodes `AgentErrorReason` strictly, so it cannot read a runtime
store whose completion row carries it.

A 0.9.8 mob controller cannot decode a 0.9.9 member host's
`head_body_retired` refusal of a placed fork under `reactivate_inherited`:
the create fails closed with an untyped internal error ("failed to decode
command bridge reply") and creates nothing on either side. A 0.9.8 temporary
council that meets it ends `participant_seating_failed` and keeps a cleanup
debt for that seat that nothing clears, not even an upgrade of that
controller. Upgrade mob controllers together with their member hosts before
relying on `reactivate_inherited` for placed forks of members whose
instruction activations a compaction may have retired.

## Upgrading to 0.9.8

This section is for systems running 0.9.7. The full list of changes is in
the CHANGELOG under `## [0.9.8]`. 0.9.8 is a patch release for hosts whose
own pure observations of a work's authorization publication meet other
actors' owner changes. It needs no storage migration: it changes no stored
format, it opens every 0.9.7 store as it is, and 0.9.7 reads everything it
writes. Back up the state root as the steps above say.

### Breaking changes and what to do

#### An unpublished hold of the publication's writer is a change in progress

The native work owner's `WorkAuthorization::owner_change_in_progress`
(`LocalWorkAuthorization`) also names a reservation of its publication's
writer that has not published: an owner change still being prepared (a grant
issuance before its acknowledged append publishes), a held exclusion
(`LocalGrantAuthority::try_with_owner_changes_excluded`) or another
operation's final entry. `LocalAuthorizationPublication::change_in_progress`
still names published changes only. Every owner-change wait, Core's own and
a host's, now lasts until such a holder releases the writer, within the same
bounds (2 s, or the budget passed when less). The operation-time steps and the
host-facing entries that never wait answer as before; Core's own waits may now
wait, within the same bounds, for such a holder and rebuild where they answered
at once.

**Do:** nothing, unless your code reads the native work owner's
`owner_change_in_progress` as "a published change is in progress": read
`LocalAuthorizationPublication::change_in_progress` for that.

### Wait after a stale read

A host's pure observation of a work's own publication (one that reads owners
and runs no effect) can stay stale after its one rebuild while another actor
issues grants on the same publication: the read waits for the grant owner's
lock during the issuance's append and ends stale only once the issuance
published, often after it completed, so `wait_for_settled_change` answers
`None`. The new `OwnerChangeChurn::wait_after_stale_read` waits for that
case too; see
[Survive owner changes in progress](/rust/native-authorization#survive-owner-changes-in-progress).

**Do:** where such a read answered stale as unavailable, or stopped when
`wait_for_settled_change` answered `None`, take a fresh churn for the check
(`ToolDispatchContext::owner_change_churn` in a tool body), wait with
`wait_after_stale_read` after each stale read, repeat only the observation,
and keep the answer typed as stale once the wait answers `NotSettled`. Hold
nothing across the wait and never repeat an effect.

### Downgrading to 0.9.7

Nothing stored changes, so 0.9.7 opens what 0.9.8 wrote. A downgrade brings
back the 0.9.7 waits, which do not wait for an unpublished holder, and code
that calls `wait_after_stale_read` does not build against 0.9.7.

## Upgrading to 0.9.7

This section is for systems running 0.9.6. The full list of changes is in
the CHANGELOG under `## [0.9.7]`. 0.9.7 is a patch release for systems with
many agents: a mob now restores its members on demand. It needs no storage
migration: it opens every 0.9.6 store as it is, and 0.9.6 reads everything it
writes, except a session that stored the opt-in 12-hour prompt-cache TTL (see
[Downgrading to 0.9.6](#downgrading-to-0-9-6)). Back up the state root as the
steps above say.

### On-demand member restore

A mob's start now materializes only the members that must run: members that
hold durable work (an open or suspended run, queued inputs, a provisional
tail, a pending delivery, a background operation completion not yet
delivered), a member that owes a kickoff, a member wired to a placed member, a
member on a network transport or without a durable endpoint, an orchestrator
the resume notifies, and the members the host requires. Every other member
stays dormant until its first delivery wakes it, while the caller waits. A
dormant member is listed, addressable and reported like an idle live member,
and reads never wake it. `rkat-rpc`, `rkat-rest`, `rkat-mcp` and the CLI start
their mobs this way. A start, and the lift of a stopped mob, restore the
members they must materialize at most
`MobBuilder::with_resume_restore_concurrency` at a time (16 by default); a
member a lift has not reached yet stays dormant, and a delivery to it wakes it
at once.

**Do:** nothing, to take the default. To keep the 0.9.6 start, build the mob
with `MobBuilder::with_member_restore_policy(MemberRestorePolicy::Eager)` and
pass the same policy to `MobMcpState::with_member_restore_policy`; the stock
servers have no setting for it in this release. If a check after a start must
find every broken member, use `MemberRestorePolicy::OnDemandVerified`: under
the default, a member whose durable session cannot be resumed reads active
until its first delivery fails. Expect a dormant member's first delivery to
take as long as the member's build, its MCP servers included.

A Rust host that feeds a member's session through the runtime machine
directly (`MeerkatMachine::accept_input_with_completion` and its variants, on
the member's session id) wakes the member first with
`MobHandle::ensure_member_live`: members start dormant in 0.9.7, and the
machine answers `NotReady { state: Destroyed }` for a session that is not
resident in this process. The mob handle, REST, RPC, the MCP server, runtime
delivery and the schedule host wake a member themselves.

Members on TCP or UDS comms (`MobBuilder::with_network_member_comms`) are not
lazy: every start and every lift of a stopped mob wakes them, whatever the
policy, since a dormant member has no listener for peers that reach it over
the network.

On a host store, the first 0.9.7 start over a realm that 0.9.6 or an earlier
release last wrote wakes every mob member that is not archived, once, and
takes about as long as a 0.9.6 start: those releases' heads cannot show that
no background operation completion is still owed. Each member's next commit
records its state in the 0.9.7 form, and later starts wake only the members
that hold work. Keep `OnDemand` there: `OnDemandVerified` loads each dormant
member's stored session rows at every start.

### Breaking changes and what to do

#### Peer messages to members that are not materialized

`comms/send` gains the error code `peer_wake_refused`, with a typed `refusal`
and `retryable`: a peer message to a seated member whose wake was refused or
did not finish, and to a member of a stopped mob, fails with it. Nothing was
delivered, so a retry cannot duplicate the message.
`peer_not_found_or_not_trusted` now means only a peer that is not a member, or
one the sender does not trust. `CommsSendErrorData` gains `PeerWakeRefused`,
`InprocSendError` gains `WakeRefused`, and both `SendError` enums gain
`PeerWakeRefused`.

**Do:** upgrade the Python and TypeScript SDKs with the server, branch on
`peer_wake_refused` and its `retryable`, and add the arm where you match
`CommsSendErrorData` or `InprocSendError` exhaustively.

#### Machine types

The mob and runtime machine types in `meerkat-machine-kernels`,
`meerkat-machine-schema`, `meerkat-mob` and `meerkat-runtime` gain the member
residency inputs, signals, effects, state fields and transitions, and
`MeerkatSeamSignal` gains `RuntimeRegistrationReleased`. The approval
lifecycle machine (`ApprovalLifecycleMachine`, version 6) in `meerkat-core`,
`meerkat-machine-schema` and `meerkat-machine-kernels` gains the inputs
`AdmitEnteredStep` and `FinishEnteredStep`, their transitions, and the state
fields `review_entered_phase` and `review_entered_steps`. Every new variant is
appended after the released ones, so no existing implicit discriminant
changes.

**Do:** add the arms where you match these enums exhaustively, and set the new
fields in struct literals.

#### The OpenAI 12-hour prompt-cache TTL

`OpenAiPromptCacheTtl`, `WireOpenAiPromptCacheTtl` and `ProviderCacheTtl`
gain `TwelveHours`, and the SDKs read a fork's cache-breakpoint lifetime they
do not know as `{"unknown": <value>}`.

**Do:** add the arms, handle the unknown form of
`ForkAuthoredCacheBreakpoint.ttl`, and upgrade the SDKs before you select
`12h` for a session you fork.

#### Rebuilt members run on their current auth binding

A member rebuilt on its durable session (an explicit resume, a revival or
reload, a Resume-mode spawn, a wake) now runs on the auth binding its current
spec names. A Resume-mode spawn, a restore or a wake that would keep a live
actor running another binding is refused with
`MobError::MemberAuthBindingConflict`.

**Do:** nothing, if each member's spec names the binding it should run on.
Expect the refusal where a live actor on another binding used to be reused.

#### Resuming a stopped mob no longer fails on its orchestrator's notification

`MobHandle::resume` hands the resume notification turn of a turn-driven or
placed orchestrator to the mob and answers without waiting for it, as
`MobBuilder::resume` already did; a failed notification is recorded as an
`OrchestratorResumeNotificationFailed` mob event, and the mob keeps running.

**Do:** if you relied on the resume failing when that notification failed,
watch for the event instead.

#### A governed helper step its review settles answers `Denied`

`GovernedHelperAdmissionFence::from_dispatch` and
`GovernedHelperChildIssuance::from_dispatch` now answer `Denied`, not
`Unavailable`, when the dispatch's review settles the step: an R2 or R3
decision at the fence, a review already spent, an ended dispatch, or a
refused review. The review owner's own unavailability (contention, an
unconfirmed store, unreadable review material, a failed reviewer) still
answers `Unavailable`.

**Do:** treat `Denied` as final for that dispatch and stop retrying it; a new
call is reviewed anew. To run several governed helper steps under one review,
enter the operation once (`ToolDispatchContext::enter_governed_operation`) and
build the steps with `GovernedHelperAdmissionFence::from_entered` and
`GovernedHelperChildIssuance::from_entered`.

#### `rkat resume` and `meerkat_resume` refuse mob members' sessions

They refuse a session built as a mob member's when no mob in their own process
owns it (`SESSION_UNSUPPORTED`).

**Do:** deliver to the member through its mob, which wakes it.

### Wrappers and decorators

Forward the new provided methods; their defaults do less:

- a `RuntimeStore` decorator: `list_runtimes_with_recovery_work` (without it,
  every start materializes every member);
- a `CommsRuntime` wrapper: `close_inproc_route` and `reopen_inproc_route`;
- a `SessionAgentBuilder` or `MobSessionService` wrapper:
  `recorded_auth_binding`;
- a `WorkAuthorization` wrapper: `run_entered_if_current_within` (without it,
  every further step of an entered governed operation is refused).

### Host store authors

A realm now asks `list_heads` for 2048 heads per call, not 256, when it opens
and when a stopped writer acquires the fence again, so one answer of typical
runtime heads is several MiB.

**Do:** if your backend or transport caps an answer below that, answer the
heads that fit and set `HeadPage::next`, as the SPI requires. A store that
sets `next` only after a full page of `limit` heads ends the listing early,
and the realm opens without the scopes it was not given.

### Thread stacks of Core's process-wide runtimes

`RKAT_WORKER_STACK_BYTES` now also sets the stack of the threads of
`meerkat-machine-cleanup` and `meerkat-runtime-serving`, the two process-wide
runtimes that run session and mob work. Without it they take 8 MiB, or
`RUST_MIN_STACK` when that asks for more; with neither set nothing changes.

**Do:** correct an invalid `RKAT_WORKER_STACK_BYTES` before you upgrade: it
now fails every operation that needs these runtimes. Through 0.9.8 the turns
of runtime-backed mob members run on the cleanup runtime's two workers, so
keep member tools non-blocking there. From 0.9.9 they run on the host's
runtime, the runtime of the task that provisions the member (see the 0.9.9
changelog).

### Consent on stock governed realms

On a stock governed realm, an approved consent's notice is now admitted as a
resume of the run that parked it, and the consent moves into the resumed run.
Before, the notice stayed pending forever. The resume is refused, and the
notice records `Failed`, for work an earlier process admitted (the stock
originals ledger is process memory), for a requester no longer admitted, and,
on any governed composition, once the session no longer keeps the
registration that ran the parked run or a later governed prompt has moved
its destination; the parked consent is then withdrawn. After a stock session
is closed and reopened in the same process, the notice stays owed until the
session's destination is next bound, and then fails.

**Do:** expect `Failed` notices in those cases where notices used to stay
pending, and treat them as final for that consent.

### Downgrading to 0.9.6

Starting 0.9.6 on a state root that 0.9.7 used is safe: 0.9.6 restores every
member at start again, and reads the journal rows and runtime heads 0.9.7
wrote. Three things do not carry back:

- **The 12-hour prompt-cache TTL.** 0.9.6 does not know `12h`: a session whose
  stored provider parameters carry it panics when 0.9.6 decodes its metadata,
  and a profile or mob definition that carries it fails its parse. Remove the
  setting on 0.9.7 before a downgrade.
- **A rotated member's owed kickoff.** 0.9.6 ignores the kickoff prompt 0.9.7
  stores for a member rotated with `MobHandle::rotate_member`, so a rotated
  member whose kickoff has not run yet does not run it under 0.9.6.
- **A fresh seat that never woke.** A member seated fresh by
  `MobHandle::seat_dormant_members`, or a rotation's next incarnation, has no
  session until its first wake. 0.9.6 restores such a member as broken, with
  a missing session, and ignores the build inputs 0.9.7 stored for its first
  build. Wake those members on 0.9.7 before a downgrade, or re-create them
  after it.

A downgrade also brings back the 0.9.6 behaviour that 0.9.7 changes, the
eager start included. To undo everything 0.9.7 wrote, restore the backup
instead.

a durable profile on a mob whose member sessions do not outlive the process
(`MobSessionService::keeps_durable_member_sessions`) is refused with the new
`MobError::NonDurableService { member_id, profile }` (wire code
`CAPABILITY_UNAVAILABLE`, data kind `mob_non_durable_service`). A
session-service wrapper should forward `keeps_durable_member_sessions`.

**Do:** pass `durable: false` where you build these with struct literals, and
set `durable = true` only on mobs over persistent sessions, once every host
that reads the profile runs 0.9.5. See
[Mobs: durable workers](/guides/mobs#durable-workers).

#### Identity adoption needs a persistent runtime

`adopt_member_identity_declaration` (`MobHandle`, `mob/adopt_member_identity_declaration`
and REST `POST /mob/{id}/members/{agent_identity}/identity-adoption`) refuses a
mob whose runtime has no runtime store (an in-memory store counts) with the new
`MobError::IdentityAdoptionRequiresPersistentRuntime { member_id }` (wire
code `CAPABILITY_UNAVAILABLE`, `-32020` over JSON-RPC and `501` over REST,
data kind `mob_identity_adoption_requires_persistent_runtime`), before
anything is recorded. Before 0.9.5 such an adoption was accepted, and
reconciliation then retired the member and could not resume it: the identity
stayed `RepairBlocked`. Every mob on an `EphemeralSessionService` runs on such
a runtime.

**Do:** adopt members only on mobs over the persistent session service,
whatever its stores (a `memory` realm works), and handle the new refusal where
you call adoption. See
[Mobs: cold resume and cancellation](/guides/mobs#cold-resume-and-cancellation).

#### Dedupe key on pending callback calls

A pending callback call carries the call's dedupe key (see Other behaviour
changes below):

- `meerkat-core`: `PendingCallbackToolCall` gains
  `dedupe_key: Option<ToolCallDedupeKey>`, the struct variant
  `AgentError::CallbackPending` gains
  `dedupe_key: Option<Box<ToolCallDedupeKey>>`, and
  `CoreApplyTerminal::CallbackPending` gains
  `dedupe_key: Option<ToolCallDedupeKey>`;
- `meerkat-runtime`: `CompletionOutcome::CallbackPending` gains
  `dedupe_key: Option<ToolCallDedupeKey>`;
- `meerkat-mob`: the struct variants `MobError::CallbackPending` and
  `BoundedTurnFailure::CallbackPending` gain
  `dedupe_key: Option<Box<ToolCallDedupeKey>>`;
- `meerkat-contracts`: `WirePendingToolCall` gains
  `dedupe_key: Option<ToolCallDedupeKey>`, and `WireCallbackPending::single`
  takes the key as its eighth argument.

On the wire the field is optional and omitted when absent, so readers that
ignore unknown fields are unaffected.

A pending callback call stored with a dedupe key cannot be finalized after
a downgrade to a runtime without the field, such as 0.9.4: its stored digest
no longer verifies there. A call stored without a key keeps its bytes (see
[Downgrading to 0.9.4](#downgrading-to-0-9-4)).

**Do:** name the field (`dedupe_key: None` for a call outside an agent-loop
round) where you build these with struct literals, add it or `..` to
patterns that list every field, and pass the key to
`WireCallbackPending::single`.

#### Orphaned drains in a quiescent close

`meerkat-runtime`: `RuntimeSessionQuiescentClose` is now `#[non_exhaustive]`
and gains `ClosedOrphanedDrain`.
`MeerkatMachine::unregister_session_registration_until_terminal_if_quiescent`
returns it after it completes an orphaned drain or a pending finalization,
which may abandon held inputs with reason `Stopped`. `Closed` now means only
a genuinely quiescent close.

**Do:** handle `ClosedOrphanedDrain` and add a wildcard arm where you match
`RuntimeSessionQuiescentClose`. Where you need a close that interrupted
nothing, do not treat `ClosedOrphanedDrain` as `Closed`.

#### WebRTC to mob members

`meerkat-rpc`: the session-scoped `live/open` refuses a mob member's session
with `INVALID_PARAMS` (-32602) and data kind
`mob_member_session_addressed_by_id`. A member's channel, WebRTC included,
opens through its mob with `mob/member_live_open`: the mob checks the member
first, and the member's own live host serves the transport or refuses it
typed. With `transport: "webrtc"`, answer the offer with `live/webrtc/answer`
on the same server. For a gpt-live-1 voice channel, pass the same
`execution_identity` as on `live/open` (the member must be local to the
server).

**Do:** open a member's live channel, WebSocket or WebRTC, with
`mob/member_live_open` instead of `live/open` by the member's session id.

#### Live open advisories

- `meerkat-contracts`: `LiveOpenResult` gains the field
  `advisories: Vec<WireLiveOpenAdvisory>`, left out of the wire when empty.
  It lists what a successful `live/open` went ahead without: today
  `staged_prompt_refused`, when a run-start hook refused the session's staged
  create-time prompt (the prompt stays staged for the first text turn). The
  vocabulary may grow: `WireLiveOpenAdvisory` has an `Unknown(String)` variant
  for a value this version does not know, and the Python and TypeScript SDKs
  keep such a value as the string the server sent instead of failing the open.

**Do:** set `advisories: Vec::new()` where you build `LiveOpenResult` with a
struct literal, and treat an advisory you do not know as informational.

### Other behaviour changes

- **An earlier incarnation's open run no longer blocks its session's next
  owner:** when the session's exclusive write authority is proven by the
  store (the session's cross-process hosting claim on the built-in SQLite
  realm, or the realm fence a host store's open took after waiting out the
  superseded lease), the run a dead or fenced-out incarnation left open no
  longer refuses the recovery. A resume, an actor's materialization or a
  cold attach continues the run as a restart does, so a host deploy killed
  in the middle of its suspend resumes every run. A store-only
  `append_system_context` on a session no runtime of yours hosts first
  commits that run as interrupted (an ambiguous tail fails the write with
  `SessionError::DurableTailHeldForRecovery`), then lands; it takes the session's
  hosting claim before it reads anything, so a session another runtime
  owner hosts refuses it at once with `ServedElsewhere` and keeps its run.
  Without that proof (or while your own runtime has the session
  registered) the earlier rules hold: an earlier incarnation's row still
  refuses the recovery, and the write fails with
  `SessionError::DurableTailRecoveryRefused`, or with
  `SessionError::DurableTailHeldForRecovery` when the run is one its next
  host resumes. A host store cannot tell a dead holder from a live one it fenced
  out: a superseded holder may still be finishing a tool call it dispatched
  before its fence window closed, which the interrupted commit answers as
  outcome unknown.
- **A Broken member no longer stops a mob start:** when a member whose
  restore already failed at a start cannot have its custody restored because
  another runtime owner hosts its session, its hosting claim cannot be taken,
  or its durable tail could not be proven, the start defers that restore and
  the mob runs. The member stays Broken, its status shows `custody_deferred`,
  and a respawn, retire or destroy of it answers
  `MobError::MemberCustodyDeferred` until the restore succeeds. 0.9.4 stopped
  the whole mob. See [Mobs](/guides/mobs).
- **Crash recovery of scheduled deliveries:** a delivery whose executor died
  after an earlier attempt recorded its dispatch is reclaimed, also past its
  misfire deadline (up to five attempts), and redelivered without a fresh
  admission: it ends with the admitted input's outcome, or `misfired` when
  only the dispatch start was recorded and the target never admitted it. A
  reclaim with no recorded dispatch still follows the misfire policy, and a
  target still busy with the admitted input does not end the redelivery
  under `skip_if_running`. This lifts the 0.9.4 known limitation (see
  "Upgrading to 0.9.4" below): a `catch_up_within` window longer than the
  lease is no longer needed to keep that recovery. A host runnable keeps no
  admission record and runs again, so for host runnables the guarantee is
  at-least-once: deduplicate on `delivery_idempotency_key`. See
  [Executor Lease And Crash Recovery](/guides/scheduling#executor-lease-and-crash-recovery).

- **Queued prompts kept across a graceful stop:** a mob Shutdown
  with `ShutdownOptions::with_queued_inputs(QueuedInputsOnShutdown::Requeue(max_age))`
  (or an unregister with `UnregisterQueuedInputs::Requeue { max_age }`) keeps
  each input still queued behind the running turn that is a durable prompt
  in the queue lane, neither directed nor bound to an objective (so never a
  member's kickoff). Its waiter ends with
  `RequeuedAcrossStop`, and the next start runs it once, before new work.
  JSON-RPC answers such a wait `-32003` and REST `409` `SESSION_NOT_RUNNING`,
  both with `kind` `requeued_across_stop`. A
  kept input older than `max_age` when a start finds it still queued ends as
  `RequeueExpired` without running; every start that finds it queued checks
  again. A graceful shutdown that does not choose now uses this option, with
  a 15 minute max age, for sessions with per-round commits: `rkat-rpc`'s and
  the REST server's own shutdowns, and a mob Shutdown without
  `with_queued_inputs` (the new default
  `QueuedInputsOnShutdown::RequeueDurable`). Choose `Stop` explicitly to keep
  the 0.9.4 behaviour.
  A kept input's row is written as stored input state version 8 until its
  run starts, and an unregister in progress with the requeue disposition as
  machine lifecycle record version 6; every other row and record keeps
  version 7 and version 5. 0.9.4 refuses a version 8 row with a stop mark,
  and a version 6 record, with its typed unsupported-version error, and fails
  to read a version 8 row that ended `RequeueExpired`, whose abandon reason it
  does not know. While a kept input is still queued, a store written by a
  requeue Shutdown does not open in 0.9.4, whose recovery reads every
  non-terminal row. Once every kept input has run or expired, the store
  opens in 0.9.4, but each read that decodes an expired input's row, or the
  row of a kept queued prompt that 0.9.5 itself ran (0.9.5 left the stop's
  mark on it), still fails: the input's status, a same-key lookup that finds
  it, and a batch compare-and-swap over it. See [Mobs](/guides/mobs).
- **Runs continue after a crash:** a run in a durable session (`sqlite`,
  `jsonl` or host-store realm) commits every tool round twice and, after a
  crash, kill or restart, continues under the same run id from its last
  committed round when its session is opened again, announced by
  `run_resumed`. 0.9.4 ran the input again or closed the run as interrupted.
  There is no switch. A call dispatched again carries the same dedupe key,
  and a call whose effect may already have happened gets an
  `outcome_uncertain` tool error instead. See
  [Durable Runs](/guides/durable-runs).
- **Write volume on WholeBlob realms:** a `jsonl` or host-store realm writes
  the whole session document at each round commit, twice per tool round; a
  `sqlite` realm writes only the round's rows. Long, tool-heavy runs on
  `jsonl` write much more than in 0.9.4. See
  [Storage Operations](/guides/storage-operations#write-volume-of-per-round-commits).
- **Dedupe key for tools outside the process:** MCP `tools/call` requests
  carry the call's dedupe key in `_meta` under
  `io.meerkat/tool_call_dedupe_key`, and callback requests and pending
  callback calls carry it as `dedupe_key`; the SDKs pass it to callback
  handlers. A host `McpCallContextProvider` whose metadata uses that name is
  refused with `McpCallContextError::Denied`. See
  [Durable Runs: the dedupe key](/guides/durable-runs#the-dedupe-key).
- **A requeue stop keeps a durable run in flight:** an unregister with
  `UnregisterQueuedInputs::Requeue`, or a mob Shutdown with
  `QueuedInputsOnShutdown::Requeue`, now suspends the run in flight of a
  session with per-round commits instead of cancelling it: the run continues
  from its last committed round at the next start, or, past the max age, its
  inputs end as `RequeueExpired` and the run is closed as interrupted with
  its committed rounds kept. A mob Shutdown keeps an autonomous member's
  running turn the same way, with its kickoff open, unless the member is
  retiring or host-placed. Because a graceful shutdown that does not choose
  uses Requeue for such sessions, a deploy no longer cancels their runs in
  flight. A REST request that waits on a run the shutdown suspends is
  answered `409` `SESSION_NOT_RUNNING` with `kind` `requeued_across_stop`.
  See
  [Durable Runs: graceful stops and deploys](/guides/durable-runs#graceful-stops-and-deploys).
- **An operator path for a held durable tail:** a session held as
  `SESSION_DURABLE_TAIL_HELD_FOR_RECOVERY` with ambiguous evidence, such as a
  transcript that ends in a tool call without its result, can be resolved
  with
  `rkat session resolve-held-tail <id> [--apply] [--runtime-store <FILE>] [--json]`
  or `meerkat_runtime::recovery::resolve_held_durable_tail`. The dry run is
  the default; applied, it commits the tail as interrupted with every row
  kept and each call without a result answered `outcome_uncertain`, once
  every host of the session is stopped. 0.9.4 had no path out of such a
  hold. The same command resolves an interrupted tail held beside inputs
  another run left staged or queued (a shape only pre-release builds of
  0.9.5, or a store fault, leave): it requeues those inputs. See
  [Storage Operations](/guides/storage-operations#resolve-a-durable-tail-held-for-recovery).
- **Host stores:** a host can keep a realm's durable state in its own
  database through the host store SPI (`meerkat_core::host_store`), checked
  by the host store chapter of `meerkat-store-conformance`. See the
  [Host Store SPI reference](/reference/host-store-spi).

### Downgrading to 0.9.4

Some state that 0.9.5 writes does not carry back to 0.9.4:

- **Runs in flight.** 0.9.4 never continues a run. It closes a run that was
  in flight when 0.9.5 last stopped (a crash or a kill) as interrupted, and
  ends the run's inputs without running them again. Some of these sessions,
  such as one whose run stopped in its first round or right after a
  compaction, do not open in 0.9.4 at all until 0.9.5 has settled the run.
- **Kept inputs.** 0.9.4 cannot open a store while an input that a
  requeue stop kept is still queued, and cannot read an expired input's row,
  or a kept queued prompt's row that 0.9.5 ran, after that (see Other
  behaviour changes above). This includes the inputs of a run that a requeue
  stop kept: 0.9.4 cannot read them, so it neither continues nor closes that
  run.
- **Unfinished requeue stops.** A requeue stop that was killed while it
  drained, such as a default graceful shutdown of a session with per-round
  commits, leaves the session's lifecycle record at version 6, which 0.9.4
  refuses when it opens that session. So does a rollback of a registration
  refused before it served, which keeps the inputs the registration
  recovered, when it is killed before it finishes. Opening the session on
  0.9.5 finishes that stop and rewrites the record in a version 0.9.4 reads.
- **Pending callback calls.** 0.9.4 cannot finalize a pending callback
  call stored with a dedupe key: its stored digest no longer verifies there.

Before you start 0.9.4 on a state root that 0.9.5 used:

1. On 0.9.5, open each session that had a run in flight at the last stop,
   and each session whose shutdown did not finish, and let any run end.
   Deliver the results of its pending callback calls, or cancel the run.
2. Shut down with an explicit `Stop` (an unregister with
   `UnregisterQueuedInputs::Stop`, or a mob Shutdown with
   `with_queued_inputs(QueuedInputsOnShutdown::Stop)`), so that no run and
   no queued input is kept. For `rkat-rpc` and the REST server, whose own
   shutdown keeps the work of sessions with per-round commits, stop sending
   work, let every run and queued input finish before you stop them, and
   let their shutdown finish.
3. Then start 0.9.4.

## Upgrading to 0.9.4

This section is for systems running 0.9.3. The full list of changes is in
the CHANGELOG under `## [0.9.4]`. This guide has no sections for 0.9.0 to
0.9.3: on 0.8.x, read their CHANGELOG sections as well.

### Before you upgrade

- **There is no downgrade to 0.9.3 once 0.9.4 has written to a runtime
  store.** 0.9.4 writes stored input state at version 7, including any input
  row it read at an older version, and a 0.9.3 or older binary refuses a
  version 7 row (it leaves the stored bytes in place). 0.9.4 still reads rows
  that 0.9.0 to 0.9.3 wrote (version 6).
- **Other records 0.9.3 cannot read back:**
  - a session event log that holds a content-filtered `run_failed` event
    (see [Refusals and content filters](#refusals-and-content-filters));
  - an authorization grant journal that holds an owner-scoped resource-domain
    restriction (0.9.3 refuses to restore that grant owner with
    `RestartRequired`);
  - a session transcript that holds a tool-configuration notice 0.9.4 wrote
    (a tool-scope, deferred-catalog or failed-closed notice; see
    [Tool configuration events](#tool-configuration-events));
  - a session that recorded a failed realtime response (realtime sidecar
    event schema 4; 0.9.3 refuses it with "unsupported realtime event schema
    4"; see [Realtime responses that fail](#realtime-responses-that-fail));
  - a temporary council record that holds a participant refused by the fork
    instruction policy (see
    [Forks and activated host instructions](#forks-and-activated-host-instructions));
  - a mob store: 0.9.4 migrates each mob's SQLite store to schema version 12
    (its creation record) when it opens it, and 0.9.3 refuses that version.
    Keep a copy of the mob stores from before the upgrade to roll back;
  - a persisted member delivery scope written at version 2, and a delivery
    addressed to a member in the new `rt:mob-member:` form (see
    [Mob incarnations](#mob-incarnations)).
- **Upgrade the SDKs with `rkat-rpc`.** The 0.9.3 Python and TypeScript SDKs
  fail on every `tool_config_changed` event a 0.9.4 `rkat-rpc` builds. An SDK
  downloads its own matching `rkat-rpc` only when you supply none, so this
  happens when it runs a binary you supply: `MEERKAT_BIN_PATH`, an explicit
  path, or an `rkat-rpc` on `PATH` (for example one Homebrew upgraded).
  SDKs older than 0.9.4 also do not know the `turn_failed` live observation
  or the `assistant_turn_failed` transcript event.
- **Upgrade every process that shares a runtime store together:** stop them
  all, back up the state root, then start 0.9.4 on all of them (steps 1, 2
  and 5 of [How to upgrade](#how-to-upgrade)).
- **Peers and member hosts on other versions:** a 0.9.3 peer that checks
  signatures (the default) drops a `reply_to_peer` reply from 0.9.4, and the
  sender's `reply_to_peer` reports an ambiguous delivery outcome; other
  message kinds are unchanged (see
  [Peer steers and replies](#peer-steers-and-replies)). For mobs placed on
  member hosts, upgrade the member hosts before their controller (see
  [Forks and activated host instructions](#forks-and-activated-host-instructions)).

### Breaking changes and what to do

#### Skill frontmatter

`SKILL.md` frontmatter is parsed by a new YAML parser (serde-saphyr), which
refuses frontmatter the old parser accepted:

- a key given twice, at any level (a top-level extension key or a `metadata`
  key; the old parser kept the last value);
- a null `description`, or a null value under `metadata` (`~` or an empty
  value);
- an unrecognized tag such as `!custom`, anywhere;
- nesting deeper than 64 levels, or 100 or more aliases that outnumber their
  anchors more than ten to one;
- a `...` document end marker line.

**Do:** remove duplicate keys, give `description` and every `metadata` key a
value, drop custom tags and `...` lines. A block scalar (`|`, `>`) that ends
the frontmatter now keeps its final line break.

Extension values read back through `SkillDocument.extensions` are rendered by
the new parser. A structured value's YAML uses double quotes where a string
needs quoting (`'1.10'` is now `"1.10"`), and some unquoted scalars now
resolve as YAML values: `1_000` is `1000`, `017` is `17.0`, `tRUE` is
`true`, an integer past u64 is a float, `1e999` is `.inf`, and a `!!binary`
value is decoded. **Do:** quote a value that must stay text, such as a file
mode with leading zeros (`'0755'`; unquoted it reads as `755.0`).

#### Mobs

- **`MobHandle::shutdown` now closes the mob's admission** before its
  teardown, as its contract says. From the moment a Shutdown is admitted, a
  spawn, respawn, work submission, flow run, wiring change, host bind, live
  commit, resume, reset, reload or owner lease is refused with
  `MobError::AdmissionClosed` (reason `shutdown`). If the Shutdown later
  fails, those commands stay refused for the actor's life; Stop, Shutdown and
  Destroy stay available.
- **Other requests during a Shutdown's drain** (Stop, Destroy, Complete, a
  read, a status probe) get the new `MobError::ShutdownInProgress` instead of
  `MobError::ActorCommandChannelClosed`. It is retryable, with the authority
  retained (wire code `SessionBusy`). `ActorCommandChannelClosed` now means
  the actor has exited or is exiting.
- **Owner leases end with the mob.** `MobHandle::acquire_owner` is refused
  with `MobError::AdmissionClosed` once a destroy is admitted (reason
  `destroyed`), after a durability fail-stop (`durability fail-stop`), after
  the actor task is lost (`actor lost`), and after a composition dispatch
  failure stops the actor (`dispatch failure`). A mob restored with a durable
  destroy marker starts with admission closed.
- **Do:** treat `AdmissionClosed` as final for that mob and retry
  `ShutdownInProgress` later. `MobError` is now `#[non_exhaustive]`: add a
  wildcard arm to any exhaustive match on it. `MobAdmissionCloseReason` gains
  `Shutdown`, `Destroyed`, `DurabilityFailStop`, `ActorLost` and
  `DispatchFailed`.
- **Child tool bundle opt-in** (Rust hosts): the new
  `ChildToolBundleAvailability::ChildOffered` offers a bundle to child mobs
  without supplying it. A child mob's inline profile mounts it by naming it in
  `tools.bundles`; a name the host does not offer is refused with the new
  `MobError::ToolBundleNotOffered`. `ChildToolBundleAvailability` and
  `ChildMcpServerRegistrationError` are now `#[non_exhaustive]` (add a
  wildcard arm), and `ToolConfig` and the wire `MobToolConfigInput` gain
  `bundles` (set it in struct literals, or build `ToolConfig` with
  `..ToolConfig::default()`).
- **A member unregister a Shutdown left pending can be followed:**
  `MemberShutdownOutcome::UnregisterPending` carries a `settlement`
  (`MemberUnregisterSettlement`) and is `#[non_exhaustive]`; match it with
  `{ stage, .. }`. `settlement.try_state()` reads where the unregister stands
  and `settle_within(deadline)` waits for it, also after the actor exited
  (`MemberUnregisterState`: `Settled`, `Pending`, `Failed`, or `HandedOver`
  when a later owner took the registration over).
- **A host's refusal of a restored member's registration** (at
  `select_destination`, `select_agent_mandate`, `prepare_member_surface` or
  `verify_member_surface`) now removes that registration through the
  canonical unregister, terminating the inputs the session still held, and
  leaves the member Broken with the new `MobError::MemberRegistrationRefused`
  (RPC data kind `mob_member_registration_refused`) until an explicit repair;
  `MobMemberSnapshot::registration_refusal` and the wire
  `MobMemberStatusResult::registration_refusal` show it (set the field in
  struct literals). A refused member can be retired, respawned or destroyed.
  A member `MobBuilder::resume` recreates on a fresh session is isolated the
  same way when its host refuses it, and the other members resume; 0.9.3
  failed the whole resume.
- **A respawned member keeps the restrictions it was spawned under:**
  `MobHandle::respawn` and the `mob_respawn` tool give the successor the
  predecessor's launch tool access policy and inherited visibility ceiling, as
  its session recorded them, intersected with the successor's own and never
  widened. It keeps the recorded auth binding only when its own spec names
  none and its profile resolves to that binding's provider. 0.9.3 built the
  successor from the profile alone, so a member spawned under its spawner's
  tool ceiling came back without it. A respawn whose predecessor's
  restrictions cannot be established (including a Broken member whose session
  was lost, which 0.9.3 respawned), whose successor profile cannot be resolved
  or whose member changes meanwhile is refused before anything is retired,
  with the new `MobError::RespawnPredecessorRestrictionsUnavailable` (no
  dedicated wire code; its message is
  `respawn of member <id> refused: <reason>`). **Do:** retire such a member
  and spawn a fresh one; a custom `MobSessionService` that wraps a Meerkat
  session service delegates the new `predecessor_tool_restrictions` (its
  default, `Unsupported`, refuses the respawns of its members). See
  [Preserve restrictions across respawn](/guides/authorization-integration#preserve-restrictions-across-respawn).
- **Stop and Shutdown of a member whose registration needs a durability
  reload** report its run and run starts as `ReloadRequired` (the new
  `MemberStopRun::ReloadRequired` and `MemberRunStarts::ReloadRequired`, wire
  `reload_required`) instead of failing or waiting on it, and a Shutdown holds
  every member's run starts and reports the first failure in roster order. An
  autonomous member whose registration degrades after the stop held its run
  starts reports its run `ReloadRequired` and its starts `Held` (the cancel
  of its current run was not dispatched). A Resume refuses with
  `MobError::MemberReloadRequired`, naming the member, while a local member
  needs a durability reload, before anything moves; until its reload such a
  member starts no run, requests to it are refused the same way, and its
  member status and member list entry carry an error naming the reload. A
  reload while the mob is Stopped answers
  `MemberReloadDisposition::Discarded`, and the next Resume completes the
  member's revival. **Do:** reload the member with
  `MobHandle::reload_member_registration`, then Resume.
  Known limitation: in a multi-host mob, a remote member that needs a reload
  still makes a Stop fail with `MobError::BridgeCommandRejected` (cause
  `internal`), and a Shutdown too when that member is `AutonomousHost`; a
  failed Stop rolls back and the mob stays Running, and a failed Shutdown
  keeps every member and can be retried. Reload the member on its host, then
  retry.
- **A runtime that did not install the destination its host selected** now
  answers `MobError::MemberDestinationNotInstalled` (RPC data kind
  `mob_member_destination_not_installed`, not retryable), where it answered
  `MobError::WiringError`; its failure class is `RuntimeRejected`, so
  schedule delivery records `runtime_rejected` instead of `mob_rejected`. A
  host's re-selection for a kept registration must advance
  `context_generation`.
- **`force_cancel_member` and `cancel_all_work` on a member whose runtime
  needs a durability reload** answer `MobError::MemberReloadRequired` at once
  (`MEMBER_RELOAD_REQUIRED`: JSON-RPC -32029, HTTP 409,
  `rkat mob force-cancel` exit 49) instead of `MobError::Internal`. **Do:**
  reload the member with `MobHandle::reload_member_registration`, then cancel
  again.

#### Tool configuration events

- The lifecycle bit of tool configuration changes is named `settled`, not
  `persisted`: `tool_config_changed` event payloads, stored `tool_config`
  notices and `mcp` notice blocks that 0.9.4 builds carry `settled`. Rows and
  events stored by 0.9.3 and earlier keep `persisted` when they are read back,
  replayed or served in history. The bit says whether the change is a settled
  lifecycle fact; whether a configuration write happened is still the
  `persisted` of `mcp/add`, `mcp/remove` and `mcp/reload`, which keep their
  name.
- The tool-scope, deferred-catalog and failed-closed events and the MCP
  restore-refusal delta now report `settled: true` where they reported
  `persisted: false`: each is a change that has already applied or failed.
- **Do:** accept either key when you read stored notices. The Python and
  TypeScript SDKs expose `ToolConfigChangedPayload.settled` (it was
  `persisted`) and derive it from `status_info`. In Rust, read
  `ToolConfigChangedPayload::settled()`, `ExternalToolDelta::settled()` and
  `SystemNoticeBlock::lifecycle_settled()`; `ToolConfigChangedPayload::new`
  takes no lifecycle argument, `SystemNoticeBlock::Mcp` carries
  `lifecycle_bit`, and `meerkat-mcp`'s
  `ExternalToolSurfaceEffect::EmitExternalToolDelta` carries `settled`.

#### Refusals and content filters

- **A provider refusal or content filter now fails the run as
  `content_filtered`**, with the stop the provider ended on (`refusal` or
  `content_filter`) and the provider's own detail when it sent one. An OpenAI
  refusal is no longer committed as the answer, an Anthropic refusal carries
  its `stop_details`, and a Gemini prompt blocked before any candidate fails
  after one call instead of being retried.
- **Wire change:** `error_report.reason` of a content-filtered `run_failed`
  event is now
  `{"reason_type": "content_filtered", "stop": ..., "detail": ...}` (it was
  `null`; `detail` is omitted when the provider sent none).
  SDKs older than 0.9.4 keep it as an unknown, raw reason.
- **`web_search`:** a search the provider refused or filtered, one that filled
  its context window and a cancelled one now come back `failed`, naming the
  stop reason, with no answer. A search cut at its output cap (`max_tokens`)
  or paused by the provider (`pause_turn`) keeps its status and answer, and
  its `error` now says the answer may be incomplete.
- **Do (Rust):** build `LlmDoneOutcome::Success` with
  `LlmDoneOutcome::success(stop_reason)` or `success_with_detail(..)` and match
  it with `Success { stop_reason, .. }`. `AgentError::ContentFiltered` gains
  `stop` and `detail` (a pattern that names `turn` without `..` needs them),
  and `AgentErrorReason`, an exhaustive enum, gains
  `ContentFiltered { stop, detail }`: add the arm to every `match` on it.

#### Realtime responses that fail

- **A realtime response the provider ends without completing it** (OpenAI
  `response.done` with status `failed` or `in_progress`, or `incomplete` for
  a reason other than `max_output_tokens` or `content_filter`) now arrives as
  the `turn_failed` live observation with its typed `failure.status`. 0.9.3
  reported it as a completed turn and committed its partial text as an
  ordinary reply, and a failed response without usage closed the channel.
- It is not terminal: the channel stays open, nothing of the response is
  committed (the transcript records `assistant_turn_failed`), a WebRTC peer
  stops its queued audio, and Meerkat neither cancels nor retries it. Usage
  the provider reported is charged; otherwise the session event stream
  carries `turn_usage_accounting_unmeasured`.
- **Do:** route on `failure.status` (`failed`, `incomplete`, `in_progress`,
  or `{"unknown": {"debug": ...}}`), treat the provider's `reason`, `code`
  and `message` as diagnostics, and decide in the client whether to ask
  again. Upgrade the SDKs with the server.
- **Do (Rust):** `RealtimeSessionEvent` gains
  `TurnFailed { response_id, failure, accounting }`,
  `RealtimeTranscriptEvent` gains `AssistantTurnFailed { response_id }` and
  `RealtimeTranscriptStopReasonKind` gains `Failed`; all are exhaustive, so
  add the arms. `LiveProjectionSink` gains the required method
  `signal_turn_failed(session_id, response_id, failure, accounting)`.

#### Forks and activated host instructions

- **Forks whose copied prefix carries activated host instructions:** under
  the default fork instruction policy, `require_explicit_activation`, the
  forks that start the child's first turn themselves are refused before
  anything is committed: `fork_off`, `MobHandle::fork_member_then_run_bounded`
  and `fork_member_then_run_detached`, `fork_member_at_turn_boundary` (and so
  the live delegation's durable fork), council participants, and the RPC
  forks `session/fork_at` and `session/fork_replace`. The error is
  `FORK_INSTRUCTION_REFUSED` (JSON-RPC -32037, HTTP 422, CLI exit 57). 0.9.3
  committed such a child, and its first turn failed. `fork_member` keeps the
  host's activation window, and forks of sources without activation rows are
  unchanged.
- **Do:** a host that wants such forks to carry the activations sets
  `reactivate_inherited` with `MobBuilder::with_fork_instruction_policy` or
  `MobMcpState::with_fork_instruction_policy`; an RPC client passes
  `"inherited_instructions": "reactivate_inherited"` to the fork call, whose
  result reports `reactivated_instruction_count`.
- **Mixed versions:** a 0.9.3 member host does not know the policy. Upgrade
  member hosts before their controller: until then a 0.9.3 member host forks
  participants without the policy, and a participant whose source has
  activated host instructions fails its first turn. A controller set to
  `reactivate_inherited` gets the typed refusal cause
  `member_host_unsupported` from a 0.9.3 member host.
- **Do (Rust):** `SessionError` gains `ForkInstructionRefused` and `MobError`
  gains `ForkInstructionRefused { source_member_id, refusal }` (exhaustive
  matches need the arms). `SessionForkAtRequest`, `SessionForkReplaceRequest`,
  `DurableSessionForkTarget`, `PlannedForkRequest` and
  `BridgeCreateForkedParticipantPayload` gain `inherited_instructions`, and
  `SessionForkResult` gains `reactivated_instruction_count` (set them in
  struct literals). `TemporaryCouncilExitReason` gains
  `ParticipantForkInstructionRefused` and `TemporaryCouncilAcquisition` gains
  `Refused`. A turn refused because a fork child never activated its
  inherited instruction keys fails with `AgentError::InstructionActivation`
  instead of `AgentError::ConfigError`.

#### Peer steers and replies

- **In-turn steers are durable:** every content steer admitted while a turn
  runs (a prompt, a peer message, request or lifecycle notice, an external
  event, a local flow step) is now written into the running turn's
  transcript at a model boundary, one per boundary in arrival order, or taken
  by exactly one follow-up turn. 0.9.3 showed peer and text-only prompt
  steers to one model request and never stored them. History now holds their
  rows, `boundary_append_applied` reports them, and each incoming comms
  notice publishes one `peer_content_ingested`.
- **Replies name what they answer:** the model's peer message notice gains a
  `Delivery ID: <id>` line and, for a reply, an `In reply to: <id>` line.
  `reply_to_peer` can answer a message that joined the running turn.
- **Mixed versions:** a 0.9.3 receiver that checks signatures refuses a
  `reply_to_peer` reply from 0.9.4 (it does not know `in_reply_to`), and the
  sender sees an ambiguous delivery outcome. `send_message` and every other
  message kind still reach a 0.9.3 peer. Upgrade peers together.
- **Do (Rust):** `SystemNoticeBlock::Comms` and
  `AgentEvent::PeerContentIngested` gain `delivery_id`;
  `CommsCommand::PeerMessage`, `InteractionContent::Message` and
  `SystemNoticeBlock::Comms` gain
  `in_reply_to`, as do `meerkat-comms`'s `MessageKind::Message` and
  `meerkat-runtime`'s `PeerInput`. Struct literals and exhaustive patterns
  name them.

#### Mob incarnations

- **A mob keeps its incarnation across resume.** Its create mints the
  `MobIncarnationId` once and stores it in a creation record; every resume
  reads it back, where 0.9.3 minted a new one at each runtime start. Only a
  destroy and a create under the same id start a new incarnation, so a mob
  operator grant bound to a mob still reaches it after a resume. A mob created
  before 0.9.4 gets its incarnation at its first resume (provenance
  `Unrecorded`). After a restart, the session that created a mob with the
  agent mob tools manages it again (the grant is re-derived from the creation
  record); a member that created a mob and was then reset to a later
  generation over the same session does not (known limitation; an operator
  grant restores manage).
- **Member delivery scopes name the incarnation** and are written at version
  2. A version-1 scope still decodes and is honoured only by a mob whose
  incarnation was assigned to a store from before 0.9.4; 0.9.3 refuses a
  version-2 scope. A scoped submit with a scope from another incarnation is
  refused first, with the new `MobError::IncarnationMismatch`, where it
  failed as `StaleDeliveryScope`, and so is `retire_at_scope` before any
  step; `recover_bounded_work_at_scope` answers
  `ScopedRecoveryUnresolved::IncarnationNotHosted`.
- **Member delivery addresses name the incarnation** too
  (`rt:mob-member:{mob}:{incarnation}:{identity}:{generation}`), so a
  continuation or detached-job delivery owed to a member of a destroyed mob no
  longer reaches the member of the same identity in a mob created again under
  the same id: it strands (`Stranded`, `OwnerRetired`), and a handle kept from
  the destroyed mob submits nothing. A 0.9.3 build does not read the new form
  and does not deliver rows addressed to one; addresses minted before 0.9.4
  are still read. Known limitation: with in-memory mob storage every start
  creates each mob again as a new incarnation, so deliveries still owed to the
  earlier incarnation strand. **Do (Rust):** `meerkat::member_delivery_address`
  takes the mob incarnation as its second argument (`handle.incarnation()`),
  and `MemberDeliveryAddress` gains `incarnation` (set it in struct
  literals).
- **Stores that disagree:** a mob store whose creation record and event log
  disagree is not resumed (`MobError::IncarnationInconsistent`), and one that
  holds a finished destroy whose files are not removed yet answers
  `MobError::IncarnationDestroyed` (the finished destroy failed as
  `Internal`). Such a mob no longer
  fails the whole restore of `MobMcpState`: it is left unrestored, listed by
  `MobMcpState::unrestored_mobs`, and a lookup of its id answers the refusal;
  the other mobs restore.
- **Creates record their provenance:** a `MobMcpState` create for a caller
  session (the agent mob tools, temporary council seating,
  `mob_create_definition_with_owner_bridge_session`) is refused with
  `MobError::ProvenanceUnavailable` while the state's mob set is not
  restored. **Do:** a host that restores mobs by inserting handles calls
  `declare_mob_set_restored`, and inserts a mob's handle before its members
  run turns.
- **Do (Rust):** the mob operator grant functions
  (`grant_manage_mob`, `grant_spawn_profile_in_mob`,
  `grant_spawn_profiles_in_mob`, `mint_mob_operator_authority_from_facts`)
  take a `LiveMobIncarnation` witness: pass `handle.live_incarnation()` where
  you passed `handle.incarnation()`. The scope readers still take a
  `MobIncarnationId`: pass the live mob's `handle.incarnation()`, never an id
  decoded from input. `MobIncarnationId` now serializes as its UUID.
  `MobError` gains `IncarnationMismatch`, `IncarnationInconsistent`,
  `IncarnationDestroyed` and `ProvenanceUnavailable`, and `MobStoreError`
  gains `IncarnationInconsistent` (exhaustive matches need the arms).

### Other behaviour changes

- **Compaction is sized for the model that writes the summary.** The summary
  source may take two bytes per token of that model's context window left
  after `max_summary_tokens` (capped by a declared input ceiling, at least
  4 KiB), instead of a quarter of the compaction threshold. With the default
  threshold that is about ten times more, so a summary call can cost more
  input tokens on a large window; it never costs more than the history being
  compacted plus the compaction prompt.
- **Compaction no longer pays for a summary at every boundary** when no
  rewrite can get the history under the threshold (for example when the
  System rows alone exceed an explicit `auto_compact_threshold`). It waits for
  its cadence and logs a warning that names the remedies.
- The `compaction_completed` event reports the summary's source
  (`summary_source`) and the estimated history left
  (`estimated_history_tokens_after`).
- **Multiprocess hosting** no longer refuses a runtime store whose file
  notifications cannot be registered (an inotify watch limit, for example):
  the store watch's sweep is the cross-process wake.
- **Fenced runtime-store writes under contention:** an intent-managed
  identity on SQLite mob storage no longer stays in `Backoff` on a host with
  slow disk writes. The SQLite runtime store now waits up to 2 seconds for
  the mob database's write lock inside the identity fence, through the new
  defaulted `RuntimeStoreWriteFence::execute_if_current_blocking` (for a
  caller on a blocking thread; the default calls `execute_if_current`). A
  fenced write whose fence answers `Backoff` while the writer holds an async
  lock (the in-memory runtime store's fenced writes, and `MeerkatMachine`'s
  publication of a registered session) is tried again for up to 2 seconds,
  with the lock released between attempts, instead of reporting the first
  `Backoff` at once. **Do:** a fence caller in your own crate that holds an
  async lock retries a `Backoff` the same way, since `execute_if_current`
  never waits beyond its own I/O; a fence decorator that forwards fenced
  calls may forward `execute_if_current_blocking` as well. A fence
  implementation needs nothing new.
- **Known limitation, adopted identities after a restart:** an adopted
  identity runs again only once the previous process's identity lease
  expires, at most 30 seconds after that process last renewed it
  (`IDENTITY_LEASE_MAX_TTL_MS`), whether that process stopped gracefully or
  not: no runtime path releases the lease at shutdown. Until then the
  identity's convergence status reads decision `await_lease` (condition
  `suspended`).
- **Work that names an original its source owner has not settled yet** is
  reported not ready (`ControllerReadinessUnavailable` with
  `original_admission_pending`) and stays retryable, instead of being refused
  as malformed or denied.
- **Fixed known issue:** stores no longer refuse to open with "schema domain
  ... has no ledger row but already owns objects" when another process
  creates the same schema domain at that moment.
- **macOS:** starting a SQLite change watch no longer waits for FSEvents
  registration, which held the first mob storage open for over 30 seconds.
- **Governed tool refusals tell the model whether the tool ran:** the
  `operation_refused` tool result carries `data`
  `{"kind": ..., "tool_invoked": false | "unknown"}`. Neither field grants
  anything; a new call is a new operation. A mob member upcall refusal with
  no known kind now reads as `operation_authorization_unavailable`, not
  `operation_refused` with `malformed_facts`.
- **Governed realms and environment keys:** in a governed realm, input of a
  host whose model key comes from the environment (`OPENAI_API_KEY`,
  `ANTHROPIC_API_KEY` and the other provider and `RKAT_*` keys, with no realm
  binding configured, or none that resolves) now reaches controller
  authorization. 0.9.3 refused every such input at admission, before any
  model request, with `controller credential is not currently usable`.
  Governed admission holds no credential lease for that route, and every
  other governed check still applies. The route has a route key of its own
  (the key covers the binding and the credential), so a stock controller
  grant admits it only if one of its `--route` keys names that route;
  otherwise the input is refused with a typed policy refusal. That includes
  the build-time fallback to the environment key when a session names no
  binding and the configured one does not resolve (for example a logged-out
  OAuth binding). **Do:** to run governed work on an environment key, grant
  that route's key
  (`rkat realm grant <REALM_ID> --controller --route <ROUTE_KEY>`); a host
  with its own controller policy decides there.
- **SQLite session store:** a whole-blob session compacted more often than
  `history_retained_rewrites` (default 4) is laid out instead of refused.
- **Public GPT Live:** a delegation result held behind the user's unanswered
  question first sends a finished notice, so the voice model no longer says
  the work is still in progress.
- **Session forks:** a child of `session/fork_at` or `session/fork_replace`
  now gets a build state derived from its source's and can run a turn. It
  carries the source's session configuration, without the source's
  `shell_env`, MCP attachments or mob operator authority (see
  [What a fork child inherits](/api/rpc#what-a-fork-child-inherits)). A
  source with session metadata but no build state is refused before anything
  is committed (`INVALID_PARAMS`, data kind
  `fork_source_build_state_missing`). A child forked by 0.9.3 that never ran
  a turn still fails `turn/start` with "missing session build state": fork
  its source again.
- **`@rkat/sdk`:** a Node process that calls `MeerkatClient.close()` exits as
  soon as it has nothing else to do, instead of about 5 seconds later.
- **SDK clients and a child that exits:** the TypeScript and Python clients
  settle on the `rkat-rpc` child's exit, not on its output pipes closing, so
  requests to a child that exited by itself fail within about a second
  (`PROCESS_EXITED` in TypeScript, `CONNECTION_CLOSED` in Python) and
  `close()` returns once the child has exited.
- **SQLite lock profile:** the release binaries are built with the bundled
  SQLite's three process-wide locks off, so concurrent sessions in one host
  no longer queue on each other. A build outside the repository
  (`cargo install rkat`, an application that embeds Meerkat) does not get
  that setting: **Do:** set `LIBSQLITE3_FLAGS` to the value in
  [SQLite Lock Profile](/guides/deploying#sqlite-lock-profile) for that
  build, and in an embedding application call
  `meerkat_sqlite::disable_memory_statistics_at_process_start()` (an
  `unsafe fn`) in an `unsafe` block as the first statement of `main`, before
  any other thread or SQLite connection exists. `rkat storage doctor` reports
  the profile and warns with `sqlite-lock-profile` when a lock is on.
- **Presence locks:** a connection a store keeps open between operations
  holds a presence lock (`<file>.mpresence` next to the database), and
  maintenance such as `rkat storage migrate --apply` waits for kept
  connections to close; `rkat storage doctor` lists the files as
  `maintenance-fence-lock` findings.
- **Scheduled occurrences end with their input's own outcome:** a reclaim
  whose redelivery the target deduplicated waits for the original input's
  outcome instead of recording `completed` at admission, and a delivery whose
  completion wait fails with `BoundaryRolledBack` or `DurableOutcomeUnknown`
  re-reads the input's outcome for up to 5 lease periods (5 minutes at the
  default 60 s lease) before it ends `delivery_failed` with
  `runtime_completion_authority_unavailable`. A scheduled mob delivery whose
  redelivery finds the delivery already failed records `delivery_failed`
  (0.9.3: `completed`). **Do:** a custom `ScheduleTargetDelivery` resolves a
  deduplicated replay's completion from the original input's outcome.
  Known limitation: a delivery whose executor crashes after the target
  admitted its input is reclaimed only inside the occurrence's misfire
  window. Under the default `skip` policy (a 30 s grace) and the hosts' 60 s
  claim lease the reclaim comes too late, so the occurrence ends `misfired`
  although its admitted input ran (nothing runs twice). To keep crash
  recovery, use the `catch_up_within` misfire policy with a `window_seconds`
  comfortably longer than the lease (the claim's own delay and a driver tick
  count too).
- **macOS stdio MCP servers close as soon as they exit**, as on Linux; 0.9.3
  waited about 8 s per stdio server (the EOF grace, SIGTERM, the TERM grace,
  SIGKILL) at every close, removal, reload, session end and shutdown.
- **RPC transcript edits after a restart:** `session/fork_at`,
  `session/fork_replace`, `session/rewrite_transcript`,
  `session/update_system_prompt` and `session/restore_transcript_revision` on
  an idle persisted session no longer answer `SESSION_BUSY` after the RPC
  server restarts. A session with a running turn or pending input still gets
  `SESSION_BUSY`; one that needs a durability reload answers the runtime's
  typed refusal instead, and one another process hosts answers its typed
  hosting refusal (`SESSION_BUSY` with data kind `session_served_elsewhere`).
- **A resume finishes an interrupted Stop or Complete** (waiting up to 5 s
  for its first attempt) before it hands the mob back, so the handle reads
  Stopped or Completed; 0.9.3 resumed it as Running and finished the Stop in
  the background. An attempt still running after 5 s (held on a member or a
  placed completion) goes on in the background; wait for `MobStopped`.
- **Sessions stuck at a compaction in 0.9.2 or 0.9.3:** a session whose last
  turn an earlier release committed but never finalized now finalizes it at
  its next start and accepts work again, where every start failed with
  "terminal completion finalization lost the exact durable CAS".
- **WebSocket and WebRTC voice** no longer pauses while another turn runs on
  the session: transcript rows wait in an ordered queue off the media path,
  observations are forwarded as they arrive (a transcript frame can reach the
  client before its row commits), and a refused row closes the channel with
  `projection_error` (see the [realtime guide](/guides/realtime)).
- **GPT Live transcript rows** the transport holds when a member turn ends
  all commit at that turn's boundary, before the next queued member turn, so
  the stored transcript no longer falls behind while member turns run back to
  back.
- **Published crates:** `cargo test` in an unpacked published Meerkat crate
  passes (`meerkat`, `meerkat-runtime` and `meerkat-mob` with the features
  and the 8 MiB test stack, `RUST_MIN_STACK=8388608`, that their README
  prints), and `rkat` builds without its default features.

### Upgrade checklist

1. Stop every 0.9.3 process that shares a runtime store.
2. Back up the realm state root; there is no downgrade to 0.9.3 after 0.9.4
   writes to it.
3. Upgrade the binaries, the Python and TypeScript SDKs and the Rust crates
   together, then start 0.9.4 on all of those processes.
4. Fix `SKILL.md` frontmatter the new parser refuses (duplicate keys, null
   values, custom tags, `...` lines), and quote extension values that must
   stay text (`'0755'`).
5. Handle `MobError::AdmissionClosed` and `MobError::ShutdownInProgress`, and
   add wildcard arms for the non-exhaustive mob errors.
6. Read `content_filtered` run failures with their typed reason, and stop
   treating refusal text as an answer.
7. Move model changes on a running session to `hot_swap_llm_identity`.
8. Update custom compactors for the new `prepare_for_summarization`.
9. Governed hosts: bind host-reported outcomes with `bind_host_outcome`, do
   not treat a review attempt retired as `ContextChanged` as the call's final
   outcome, and grant an environment key's controller route by its route key
   if governed work should run on it.
10. Read tool configuration changes by `settled` (accepting `persisted` on
    rows stored before 0.9.4).
11. Realtime clients: handle the `turn_failed` observation, and add the new
    arms and `signal_turn_failed` in Rust.
12. Forks: handle `FORK_INSTRUCTION_REFUSED`, and set or pass
    `reactivate_inherited` where a fork must carry activated host
    instructions; upgrade member hosts before their controller.
13. Comms: upgrade peers together (a 0.9.3 peer drops `reply_to_peer`
    replies), and expect in-turn steers in history.
14. Mobs: back up the mob stores (schema 12 has no downgrade), pass
    `live_incarnation()` to the operator grant functions, and call
    `declare_mob_set_restored` if your host restores mobs by inserting
    handles.

## Upgrading to 0.8.51

This section is for systems running 0.8.50. The full list of changes is in
the CHANGELOG under `## [0.8.51]`.

### Before you upgrade

- **The upgrade is one-way.** 0.8.51 migrates these stores forward the first
  time it opens them, and 0.8.50 binaries refuse the migrated files:
  - SQLite session store: schema v5 (transcript retirements);
  - WorkGraph: schema v4 (keyed admissions);
  - semantic memory: schema v3 (purges empty-text rows).
- **Upgrade every process that shares a store at the same time.** A 0.8.50
  process left running against a store a 0.8.51 process has migrated will be
  refused on its next open.
- **Take a backup first** (step 2 of [How to upgrade](#how-to-upgrade)),
  since there is no downgrade path for migrated files.

### SQLite sessions that 0.8.50 could no longer load

SQLite sessions written by 0.8.50 or earlier that went through more than 32
compaction rewrites could reach a state where every cold load fails with
`Store(Corrupted(<session id>))`. Writes kept succeeding and no rows were
lost.

- **Do not delete or recreate such a session. Upgrade the host to 0.8.51.**
- 0.8.51 loads these sessions again with no action needed. Cold load replays
  them from the edge their rotated anchor sealed, but only after verifying
  that the edge's result, extended by the anchor's own tail rows, reproduces
  the anchor exactly. The session's next compaction rewrite then re-mints the
  anchor.
- New sessions are not affected.

### Session envelope status

- **No envelope migration.** The persisted session envelope stays at version
  3 (`SESSION_VERSION`), stored input state at version 5, and session
  metadata schema at version 2, the same as 0.8.50. Session documents
  written by 0.8.50 load unchanged.
- **Transcript history is now bounded.** After each compaction, a session
  keeps the bodies of only the most recent
  `[compaction] history_retained_rewrites` rewrites (default 4). Existing
  documents re-anchor on their next compaction. The SQLite store deletes the
  rewrite rows below the same cut.
- **Old revisions can be retired.** Fork, rewind, restore and revision reads
  of a revision older than the retention window fail with the typed
  `TranscriptRevisionRetired`, naming the oldest retained revision. Raise
  `history_retained_rewrites` if you need to reach further back. Code that
  walks `commits()` and projects each commit's parent must skip commits
  before the cut.

### Breaking changes and what to do

#### Hosts that serve application tool policies

- Agent `mob_create`, agent `delegate` and spawns into existing child mobs
  are refused (`policy_denied`, code `child_tool_policy_required`) until you
  choose a child application tool policy.
- **Do:** call `MobMcpState::with_child_application_tool_policy(binding)`
  with the policy child members should run under, or pass
  `ApplicationToolPolicyBinding::Unmanaged` to opt out explicitly.
- `delegate` helpers now run as a child mob under that policy. Host-created
  mobs, same-mob `mob_spawn_member` and `fork_off`, and temporary councils are
  unaffected. Hosts without a tool-policy registry see no change.
- Host tool bundles reach child mobs only if you mark them `ChildAvailable`
  with `MobMcpState::with_child_tool_bundles`.

#### Agent-facing mob tool inputs

- Model-supplied mob definitions and profiles that name internal-only fields
  (`mcp_servers`, `rust_bundles`, `is_implicit`, `session_cleanup_policy`,
  ...) are refused with `InvalidArguments`. On the agent surface, host
  filesystem skill paths, images by `blob_id` and videos by `uri` are refused
  too.
- **Do:** keep MCP servers and Rust bundles in host-defined profiles, and
  have agents reference those profiles by name. Host-facing surfaces (RPC,
  REST, SDK, CLI) are unchanged.

#### MCP OAuth

- Meerkat no longer opens a browser or binds a callback listener itself.
- **Do:**
  - drive login with `McpOAuthAuthority::login_start`, `login_complete` and
    `login_cancel`, the `HostAuthService::mcp_login_*` methods, the
    `auth/login/*` RPC and REST methods with an MCP target, or
    `rkat mcp login` (see [Authentication](/guides/auth));
  - give each server that needs interactive login an account selection:
    `oauth_account`, or `oauth_account_selection = "discover"` or
    `"unverified"` (`rkat mcp add --oauth-account` or
    `--oauth-account-selection`);
  - update `McpOAuthAuthority::new(persistence, auth_lease)` and
    `with_http(persistence, http, auth_lease)` calls, which no longer take a
    browser;
  - set `AgentBuildConfig::mcp_auth_resolver` (use `None` to keep the old
    behaviour);
  - replace `BrowserOpener`, `SystemBrowserOpener` and
    `McpOAuthAuthority::interactive_login`, which are removed.
- RPC, REST and the MCP server now install interactive MCP auth by default.
  A missing credential surfaces as the typed `AuthorizationRequired` host
  status.

#### Auth wire (`auth/login/*`, `auth/status/get`)

- Login params take a `target` (a provider or an MCP server). The Rust
  `LoginStartParams`, `LoginCompleteParams`, `WireLoginStart` and
  `WireLoginReady` replace their provider fields with `target`.
- Provider login params now refuse unknown fields.
- **Do:** in Python, build requests through the client wrappers; the
  generated types are unions and no longer constructible dataclasses.
  Provider JSON payloads themselves are unchanged.

#### Per-profile tool deny lists

- `[profiles.<name>.tools] deny = [...]` is new. A name that is not a known
  tool (or a tool of a declared MCP server's mapped list) fails the member's
  build with `DeclaredToolUnknown`.
- A profile's `read_only` now travels as `declared_tool_restriction` and no
  longer appears in `AgentBuildConfig::tool_access_policy`. The effective
  gate is unchanged.
- **Do:** if you read `tool_access_policy` off a built config, read
  `declared_tool_restriction` too. Members persisted before 0.8.51 keep their
  old restriction until respawned.

#### Mob Stop and Shutdown

- `MobHandle::stop` returns `Result<MobStopReport, MobError>`.
  `MobMcpState::mob_stop` returns the report, and `mob_lifecycle_action`
  returns `MobLifecycleReports`.
- **Shutdown cancels members' in-flight runs immediately.** Use Stop if runs
  should finish first. `shutdown_with_report(ShutdownOptions)` reports
  per-member outcomes, and `ShutdownOptions::with_deadline` bounds every wait
  by your own deadline (for example below a Kubernetes termination grace
  period).
- While a Shutdown runs, commands other than a second Shutdown get
  `ActorCommandChannelClosed`. Treat it as "mob shutting down". (0.9.4
  changes these answers; see [Mobs](#mobs) under Upgrading to 0.9.4.)
- A retirement that started and failed answers `MemberRetirementStuck`.
  **Do:** call `MobHandle::redrive_retirement` or resume the mob.
- A spawn that completes into a Stopped mob leaves it Stopped and holds the
  new member. Call Resume to run it. `Reset` also releases a Stop's holds.
- `MobBuilder::with_runtime_adapter` must be passed the session service's
  own `MeerkatMachine` (a clone of it). A different machine over the same
  store is refused with `MobError::RuntimeOwnerConflict`.

#### Live (GPT Live and WebRTC clients)

- `WireLiveAdapterStatus::Closed` is now a struct variant,
  `Closed { reason, reopen_recommended }`. **Do:** match `Closed { .. }` (or
  use `is_closed()`) and build it with `WireLiveAdapterStatus::closed()`. A
  plain close still serializes as `{"status":"closed"}`.
- `AgentEvent::LiveChannelClosed` is published on every committed close.
  **Do:** handle it in event consumers that match exhaustively on event
  types.
- WebRTC clients should answer `live/media_health_requested` with
  `live/media_health`, and may apply `live/assistant_playback_hint`
  (`duck`/`restore`) to their playback. The TypeScript and Python SDKs now
  deliver `live/*` notifications through `onLiveNotification` and
  `on_live_notification`.
- Hosts that forward observations receive playback hints only if they
  override `ExperimentalLivePublicObservationPublisher::publish_playback_hint`.

#### Other behaviour changes

- **rkat-rpc over TCP:** a session's callback tools route only to the
  connection that created it. `SessionRuntime::set_callback_channel` is
  deprecated. **Do:** use `init_callback_channel` for the single-client
  default route.
- **MCP stdio servers** are killed as soon as their stdin closes. A server
  that must flush state on EOF can no longer rely on a grace period.
- **Shell tool commands** read EOF from stdin immediately (`/dev/null`).
- **Mob kickoff status notices** (`mob.kickoff_*`) are one-way lifecycle
  notices. Receivers no longer get a peer request to answer.
- **SQLite database paths** that are hard links or not regular files are
  refused (`UnsupportedDatabaseFile`). **Do:** point stores at a single
  regular file.
- **Semantic memory:** empty-text rows are purged on first open, and empty
  queries return no hits.

#### Rust API

Struct literals and exhaustive matches need updating for the new fields and
variants listed under `### Breaking` in the CHANGELOG. The most common are:

- `LlmRequest.tool_choice`, `TurnToolOverlay.tool_choice_plan`, and
  `CompactionConfig.history_retained_rewrites` (default 4);
- `MemoryIndexExclusion::EmptyText`,
  `TranscriptEditError::TranscriptRevisionRetired`,
  `LlmError::ToolChoiceUnsupported` and `MobError::RuntimeOwnerConflict`;
- `SessionRuntimeLlmReconfigureHost::service` is now a `Weak` (build it with
  `Arc::downgrade`).

### Upgrade checklist

1. Back up stores you might need to roll back.
2. Stop every 0.8.50 process that shares a store, then start 0.8.51 on all of
   them together.
3. If you serve application tool policies, set a child application tool
   policy.
4. Move host-only MCP servers and Rust bundles out of agent-created profiles.
5. Update MCP OAuth hosts to the start/complete/cancel flow.
6. Review Shutdown callers: use Stop to let runs finish, and set a
   `ShutdownOptions` deadline that fits your termination grace period.
7. Update live clients for `Closed { .. }`, `LiveChannelClosed`, and the
   media-health and playback-hint notifications.
8. Leave any SQLite session that 0.8.50 reported as `Corrupted` in place.
   0.8.51 loads it.
