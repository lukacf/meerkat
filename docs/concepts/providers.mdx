Meerkat keeps one session and runtime model across Anthropic, OpenAI, Gemini,
and configured self-hosted servers. Provider independence does not erase model
differences: the selected catalog profile controls context limits, output
limits, multimodal input, reasoning options, realtime support, provider-native
tools, and the effective tool surface.

Query the effective catalog instead of inferring capabilities from a model
name:

```bash
rkat models
```

The same catalog is available through JSON-RPC `models/catalog`, REST
`GET /models/catalog`, and MCP `meerkat_models_catalog`. Configured
self-hosted aliases appear beside built-in models.

## Current Defaults

| Provider | Catalog default |
|----------|-----------------|
| Anthropic | `claude-opus-5-5` |
| OpenAI | `gpt-6-astra` |
| Gemini | `gemini-4-argon` |
| Global catalog default | `gpt-6-astra` |

<Warning>
A catalog entry describes Meerkat's supported capability contract, not the
entitlement of a particular API organization, ChatGPT workspace, cloud
deployment, or OAuth account. If `gpt-6-astra` is unavailable to the active
OpenAI account, explicitly select `gpt-5.5` or set a compatible binding
`default_model`. `gemini-4-argon` is served only on paid Gemini API tiers; on
the free tier, select `gemini-3.8-flash` explicitly (`--model
gemini-3.8-flash`) or keep it as the Gemini default with
`[models] gemini = "gemini-3.8-flash"` in config.
Catalog-default changes alone do not rewrite configured models, binding
defaults, or the model an existing session recorded (a resumed session keeps
its recorded model). The CLI has a separate, narrow built-in OAuth repair.
</Warning>

During interactive login, or read preparation when a matching stored token
exists, the CLI can replace a built-in OAuth binding's `default_model` with
the login route's current default: the provider's catalog default, except
`google_oauth` (the Google Code Assist route), which uses `gemini-3.8-flash`
because the catalog's Gemini default is not verified on Code Assist. A new
`rkat auth login google` binding also starts on `gemini-3.8-flash`, as does
the `copilot_gemini` route binding that `rkat auth login copilot` creates. This
applies only to the following reserved `global` binding/backend/auth profile
IDs and frozen legacy values:

| Binding | Backend profile | Auth profile | Legacy `default_model` values repaired |
|---------|-----------------|--------------|----------------------------------------|
| `anthropic_oauth` | `anthropic_api` | `anthropic_oauth` | `claude-opus-4-6`, `claude-opus-4-7`, `claude-sonnet-4-6` |
| `openai_oauth` | `openai_chatgpt` | `openai_oauth` | `gpt-5.4` |
| `google_oauth` | `google_code_assist` | `google_oauth` | `gemini-3.1-flash-lite` |

This is not a generic catalog migration: other binding IDs and other pins,
including `gpt-5.5`, are not rewritten by this repair. A matching legacy value
has no provenance marker distinguishing an old CLI sample from an operator
pin. The replacement still requires account entitlement.

## GPT-6 Astra: Initial Responses Support

Meerkat supports ordinary Astra Responses requests: text/image input, text
output, application function calls, and the existing provider-native web-search
path. Its 1,050,000-token context has a distinct 922,000-token input ceiling
and a 128,000-token output ceiling (including reasoning). Context-budget
projections apply the input ceiling in addition to the output reserve;
estimated context pressure is not exact provider token accounting.

Supported reasoning efforts are `low`, `medium`, `high`, `xhigh`, and `max`.
`none`, `temperature`, `top_p`, and log-probability controls are unsupported.
Astra does not support the Realtime endpoint; it cannot back `live/*`.
For compatibility, existing OpenAI `temperature` and generic `top_p` settings
remain omitted from provider requests rather than gaining a new rejection
policy. Unsupported reasoning efforts and log-probability fields fail the
existing typed validation.

`store: false` remains the default. Assistant-item `commentary` and
`final_answer` phases, supported output order, and terminal encrypted
reasoning associated with assistant output survive transcript persistence and
input replay. The existing orphan-only compatibility rule remains: replay
strips reasoning from an assistant message with no replayable text, assistant
item, or tool output, even if that reasoning is encrypted. An empty identified
assistant item still counts as output. Provider response and item IDs are
continuity metadata, never Meerkat session identity.
`misalignment_policy_violation` is a typed terminal policy stop, not an
authentication error: Meerkat does not refresh credentials, retry, switch
providers, or reset the conversation to evade it.

This integration does not enable async/pending provider tools, early tool
dispatch, Responses WebSocket steering, `configuration_update`, tool search,
programmatic calling, new hosted tools/MCP/connectors, provider multi-agent
orchestration, provider compaction/conversations, or background responses.
Unsupported output execution semantics fail explicitly; additive inert
metadata does not disable established behavior. Direct OpenAI support does not
establish Astra availability on Azure, Copilot, ChatGPT OAuth, or a custom
endpoint.

See OpenAI's [model contract](https://developers.openai.com/api/docs/models/gpt-6-astra),
[reasoning and phase guidance](https://developers.openai.com/api/docs/guides/reasoning),
and [misalignment monitoring](https://developers.openai.com/api/docs/guides/safety-checks/misalignment-monitoring).

## Environment Credential Precedence

`RKAT_*` variables let Meerkat use dedicated credentials without taking over
keys used by other tools.

| Provider | Resolution order |
|----------|------------------|
| Anthropic | `RKAT_ANTHROPIC_API_KEY`, `ANTHROPIC_API_KEY` |
| Public OpenAI | `RKAT_OPENAI_API_KEY`, `OPENAI_API_KEY` |
| Gemini | `RKAT_GEMINI_API_KEY`, `GEMINI_API_KEY`, `RKAT_GOOGLE_API_KEY`, `GOOGLE_API_KEY` |
| Azure OpenAI | `RKAT_AZURE_OPENAI_API_KEY` plus `RKAT_AZURE_OPENAI_ENDPOINT`, then unprefixed equivalents |

If public OpenAI and only unprefixed Azure variables are both present, public
OpenAI wins. Setting either prefixed Azure selector makes a complete Azure
key/endpoint pair the OpenAI environment default.

Environment credentials are synthesized as a typed ephemeral binding and go
through the same provider runtime resolver as configured bindings.

## Public OpenAI API Versus ChatGPT OAuth

OpenAI has separate backend/auth pairs:

| Backend | Auth | Account surface |
|---------|------|-----------------|
| `openai_api` | `api_key`, `static_bearer`, or host authorizer | Public OpenAI API organization/project |
| `chatgpt_backend` | `managed_chatgpt_oauth` or host-supplied ChatGPT tokens | ChatGPT/Codex subscription and workspace |
| `azure_openai` | `azure_api_key` | Azure deployment |
| `copilot` | `github_copilot_oauth` | GitHub Copilot account |

These are not interchangeable credential paths. A model ID available to an API
organization may be unavailable to a ChatGPT workspace, and vice versa.
`rkat models` reports the Meerkat catalog, not account entitlement. Keep a
binding's backend, auth method, and default model aligned.

Copilot is also available beneath the Anthropic and Gemini provider families.
Those routes share one account-scoped credential while preserving the model's
provider identity and selecting the account-advertised wire dialect. Model
entitlement is therefore an account observation, never a fixed property of the
Meerkat model registry.

See [Auth](/guides/auth) for the full backend/auth compatibility matrix.

## Model And Provider Resolution

The effective model registry is the built-in catalog plus configured custom
and self-hosted entries. Provider resolution uses exact registry ownership, not
name prefixes.

- An explicit model wins.
- An explicit provider constrains every omitted-model choice.
- An explicit binding infers and validates its provider; its
  `default_model` wins when the model is omitted.
- Otherwise Meerkat checks compatible configured defaults and then the
  provider/global catalog default.
- A known provider/model mismatch fails before agent construction.
- An uncataloged model needs an explicit typed provider/binding owner; a name
  that merely begins with `gpt-` or `claude-` is never guessed.

All public session-creation surfaces use the same resolver. Inherited bindings
retain the realm that owns their config.

Rust applications can select only the provider adapters they use:

<CodeGroup>

```toml Anthropic-only feature selection
meerkat = { version = "=0.9.8", default-features = false, features = ["anthropic", "jsonl-store"] }
```

```toml All providers
meerkat = { version = "=0.9.8", features = ["all-providers", "jsonl-store"] }
```

</CodeGroup>

Cargo features are additive across the dependency graph; another dependency
can still enable additional provider features.

## Capability-Gated Projection

The durable session transcript remains provider-neutral and ordered. Each
adapter projects that transcript and the effective tool surface to its wire
format:

- unsupported multimodal blocks or tools are rejected or hidden according to
  the model profile;
- system instructions remain ordered, and a limited provider projection fails
  when it cannot represent their positions without changing meaning;
- a model switch or fallback recomputes context/output limits and tool
  visibility from the newly selected catalog profile.

The transcript itself is not rewritten merely because a different provider
wire has stricter placement rules.

## Provider Parameters

Use `--param` for common top-level parameters such as `temperature`. Use the
typed `provider_params.provider_tag` envelope for provider-specific fields:

<Tabs>
  <Tab title="Anthropic">
    ```bash
    rkat run --model claude-sonnet-4-6 --params-json \
      '{"provider_tag":{"provider":"anthropic","thinking_budget_tokens":10000,"cache_control":"disabled"}}' \
      "Solve this problem"
    ```

    Thinking is typed per model: `{"type": "adaptive"}`,
    `{"type": "enabled", "budget_tokens": N}`, or, on Claude Sonnet 5.5,
    `{"type": "between_tools"}`, which turns off up-front thinking and is
    accepted only at `high` effort or below. `{"type": "disabled"}` turns
    thinking off on the models that accept it: Claude Opus 4.8, Opus 4.7,
    Sonnet 5, Sonnet 4.6, Sonnet 4.5, Haiku 4.5 and Opus 4.5 at any effort,
    and Claude Opus 5 and Haiku 5.5 at `high` effort or below; Claude
    Fable 5.1, Fable 5, Opus 5.5 and Sonnet 5.5 refuse it. A thinking type or
    budget (`thinking_budget_tokens`) the model does not accept, `top_k` on a
    model without top-k support, and `between_tools` or a capped `disabled`
    above `high` effort are refused when the agent is built and again before
    each request, never sent to Anthropic. A generic `temperature` is omitted
    for models that reject sampling parameters.

    Anthropic also supports `top_k` and the prompt-cache policies `automatic`
    (the default on the Anthropic API, Vertex, and Foundry), `system_prefix`,
    `system_and_conversation`, and `disabled`, plus `cache_ttl` (`5m`, the
    default, or `1h`). Bedrock and Copilot do not accept automatic caching:
    they default to `disabled` and reject an explicit `automatic` locally. In a
    mob profile or `AgentBuildConfig` the same knobs nest under
    `provider_tag`:

    ```toml
    provider_params = { provider_tag = { provider = "anthropic", cache_control = "disabled" } }
    ```

    A flat `provider_params = { cache_control = "disabled" }` fails the whole
    definition parse: `ProviderParamsOverride` and `AnthropicProviderTag` are
    both `deny_unknown_fields`, so the misplaced key is rejected before the
    agent boots.

    Under `automatic` and `system_and_conversation`, Meerkat also keeps one
    explicit breakpoint at the end of the previous run's output on every
    request of a run. The run's first request writes that entry even on a
    cold cache and later requests refresh it, so a `fork_off` child, whose
    first request is the forker's transcript up to its previous turn end,
    reads the shared prefix from cache.
  </Tab>
  <Tab title="OpenAI">
    ```bash
    rkat run --model gpt-5.6-terra --params-json \
      '{"provider_tag":{"provider":"open_ai","reasoning_effort":"max","reasoning_mode":"pro","reasoning_context":"all_turns","text_verbosity":"high"}}' \
      "Prove this theorem"
    ```

    The catalog validates each model's reasoning-effort subset. GPT-5.6 and
    the GPT-6 family also support `prompt_cache_enabled`, `prompt_cache_key`,
    and `prompt_cache_options` (`implicit` or `explicit`, with an optional
    `30m` or `12h` TTL). On the OpenAI API Meerkat defaults GPT-5.6 to
    `explicit` and GPT-6 to `implicit`, both with the `30m` TTL. Use `max`,
    not `ultra`, as the public provider effort.

    The TTL is a minimum cache lifetime. `30m` is OpenAI's default and
    Meerkat's; `12h` is only ever an explicit choice. Choose `12h` for a
    long-lived agent with a stable prefix (system prompt, tools, reference
    material) that responds every few hours, so the prefix stays cached
    between its turns. A `12h` cache write costs 2.5x the uncached input
    rate, against 1.25x for `30m`; cache reads cost the same, and OpenAI may
    keep a `12h` entry for up to 24 hours. Set it per agent or profile, or
    per turn:

    ```json
    {"provider_tag": {"provider": "open_ai", "prompt_cache_options": {"ttl": "12h"}}}
    ```

    Meerkat's breakpoints carry no lifetime of their own, so the request's
    TTL applies to every breakpoint: a request with `12h` makes every cache
    write of that request a 12-hour write at 2.5x, the conversation tail
    included, not only the stable prefix. Weigh that against rewriting the
    prefix after 30 minutes. On the public OpenAI API, models without
    GPT-5.6-and-later prompt caching (`gpt-5.5`, `gpt-5.5-pro` and earlier)
    refuse a TTL with a typed error when the agent is built (a per-turn
    override, before its request is sent); they set their lifetime with
    `prompt_cache_retention` instead. The ChatGPT backend, Azure OpenAI and
    Copilot drop the prompt-cache fields, so a TTL there is not sent and not
    refused.

    Explicit mode marks every input item, so the last input before the
    previous run's output always carries a breakpoint. In `implicit` mode on
    those models Meerkat adds one explicit breakpoint there and lowers inputs
    as content parts, so a run that starts on a cold cache still writes an
    entry a `fork_off` child cut at the previous turn end can read.
    `prompt_cache_retention = "in_memory"` is refused for these models when
    the agent is built; set the lifetime with `prompt_cache_options.ttl`.

    Meerkat's default `prompt_cache_key` is one key per model
    (`meerkat:profile:openai:<model>`), shared across sessions so identical
    system and tool prefixes can reuse OpenAI's prefix cache. The key only
    routes requests; it never proves a cache hit, and OpenAI still needs a
    byte-identical prefix. A caller-supplied key wins. Sharing maximises
    cross-session reuse of the static prefix, while very high aggregate request
    rates on one model can overflow OpenAI's routing for a single key; see
    [Rust SDK advanced](/rust/advanced#provider-parameters).
  </Tab>
  <Tab title="Gemini">
    ```bash
    rkat run --model gemini-3.8-flash --params-json \
      '{"provider_tag":{"provider":"gemini","thinking_level":"medium"}}' \
      "Analyze this data"
    ```

    Consult `rkat models` for the selected model's effective parameter schema.
    The catalog records the thinking levels each model accepts. A level the
    selected model refuses, such as `minimal` on `gemini-4-argon`,
    `gemini-3.8-flash` or `gemini-3.1-pro-preview`, is refused with a typed
    error before any request is sent (when the agent is built, for build
    parameters).
  </Tab>

Provider-native web search is enabled by default for catalog models that
support it. Disable the relevant `provider_tools.<provider>` toggle in config
or use `rkat run --no-web-search` for one run.

### What later steps see of a search

A provider-native search runs inside one model step. What the next steps of
the same turn, and later turns, still see of it depends on the provider:

- **OpenAI** (Responses, stateless with `store: false`, the default): on the
  public OpenAI API, a request with the hosted search tool asks for the
  sources each search consulted (`include: ["web_search_call.action.sources"]`).
  Later steps replay the search call with its query and those sources, and
  the answer with its `url_citation` annotations, plus the encrypted
  reasoning when reasoning is on. The text of the pages never comes back: a
  later step can name and search the sources again, but cannot quote what it
  read. The ChatGPT backend, Azure OpenAI and GitHub Copilot Responses wires
  replay the search call without its sources and the answer without its
  citations.
- **Anthropic**: later steps replay the search results themselves, with their
  encrypted content.
- **Gemini**: grounding metadata has no place in a request, so later steps see
  only the model's text.

For full continuity on OpenAI, set `store: true` in the OpenAI provider
params: OpenAI then keeps each response and the next step continues from it
(`previous_response_id`), which is a retention choice. The Meerkat
`web_search` fallback tool returns its results as an ordinary tool result,
which every later step sees.

## Refusals and Content Filters

Since 0.9.4, when a provider refuses a response or its content filter blocks
it, the response ends with a typed stop instead of answer text. Meerkat
commits nothing of that turn and runs none of its tool calls, and the run
fails with class `content_filtered`. The `run_failed` event's
`error_report.reason` names the stop and carries the provider's own account
when it sent one:

```json
{
  "reason_type": "content_filtered",
  "stop": "refusal",
  "detail": {"provider": "open_ai", "reason": "refusal", "refusal": "I can't help with that."}
}
```

`stop` is `refusal` or `content_filter`. `detail` is tagged by `provider` and
omitted when the provider sent none:

| `provider` | `detail` fields |
|------------|-----------------|
| `anthropic` | `category` (the policy category, for example `cyber`) and `explanation` (display text, not stable), from the refusal's `stop_details` |
| `open_ai` | `reason` (`refusal`, or the raw filter reason of a Responses, Chat Completions or realtime turn) and `refusal` (the refusal text) |
| `gemini` | `stage` (`prompt` or `candidate`), `reason` (`promptFeedback.blockReason` or the candidate's `finishReason`) and `blocked_categories` (the safety categories marked blocked) |

Each text field is capped at 4 KiB. Evidence of an unexpected shape reads as
absent and never turns the stop into a stream error. Branch on `stop`; use
`detail` for display and diagnostics.

- **OpenAI**: a Responses `refusal` output part, streamed
  (`response.refusal.delta` / `.done`) or in the terminal response, and a Chat
  Completions `delta.refusal` end the response as a refusal. The refusal wins
  over text and tool calls in the same response, and its text travels only as
  the detail. A Responses `incomplete_details.reason` or a Chat
  `finish_reason` of `content_filter` ends it as a content filter.
  OpenAI-compatible self-hosted servers are read the same way.
- **Anthropic**: a `refusal` stop carries its `stop_details` wherever the
  stream puts it (inside or beside the `message_delta` delta, or on
  `message_stop`); the `message_delta` value wins. A refusal whose stream is
  cut after the stop still ends as a refusal.
- **Gemini**: a prompt blocked before any candidate
  (`promptFeedback.blockReason`, every reason including `OTHER`) fails the
  run after one provider call. It is not retried, because the same prompt is
  blocked again. A candidate that finishes with `SAFETY`, `RECITATION`,
  `BLOCKLIST`, `PROHIBITED_CONTENT`, `SPII`, `IMAGE_SAFETY`,
  `IMAGE_PROHIBITED_CONTENT`, `IMAGE_RECITATION` or `LANGUAGE` is a content
  filter; `OTHER`, `MALFORMED_FUNCTION_CALL` and unknown reasons are retried
  as an incomplete response.

The `web_search` fallback tool reads its native search call's stop the same
way; see [Built-in tools](/reference/builtin-tools#web-search-fallback-tool).

In 0.9.3 and earlier the reason was `null`, an OpenAI refusal could be
committed as the answer, and a Gemini prompt block was retried as an
incomplete response. A 0.9.3 binary cannot read a session event log that
holds a 0.9.4 content-filtered `run_failed` line.

## Model Fallback

Runtime model fallback is disabled by default. Operators must explicitly enable
it and provide a non-empty ordered chain; catalog defaults are never a chain:

```toml
[model_fallback]
enabled = true

[model_fallback.policy]
cross_provider = true

[[model_fallback.chain]]
model = "claude-opus-4-8"
provider = "anthropic"

[[model_fallback.chain]]
model = "gpt-5.5"
provider = "openai"
auth_binding = { realm = "global", binding = "openai_oauth" }
```

Fallback activates only when generated recovery authority classifies the
failure as recoverable and the core loop determines that switching is
pre-stream safe. The default triggers are capacity and provider unavailability,
after three failed attempts. Transport and empty output do not migrate by
default, and a switch is suppressed after visible text or reasoning.

An accepted switch is sticky for later turns and recovery. Meerkat re-resolves
credentials, output limits, context limits, provider parameters, and tool
visibility for the target. Actual materialized context, output reserve,
tool/modality/structured-output parity, and credential authority must pass both
selection and precommit admission. Cross-provider targets without opt-in and
targets with unavailable credentials are typed skips, not fatal configuration
errors; malformed configuration and credential-store faults still surface.

New fallback-origin unsafe resumes require explicit reconfiguration. Older
sticky routes have no proven fallback provenance and are not automatically
healed. See [fallback configuration](/concepts/configuration#model-fallback-settings)
for precedence and deferred migration boundaries.

Ordinary same-model retry is separate. Genuinely unknown provider failures now
consume the existing bounded retry budget, while explicit terminal classes
remain non-retryable.

## Image Generation

The `generate_image` builtin routes independently of the active chat model:

| Provider | Default image target |
|----------|----------------------|
| OpenAI | `gpt-image-2` |
| Gemini | `gemini-nano-banana-2.1` |

Generated bytes are stored as realm blobs and can be fetched through CLI,
RPC, MCP, or SDK blob methods. REST responses carry blob references but the
current REST router does not expose a blob-byte fetch route. See
[Image generation](/guides/image-generation) for the request shape.

## Rust Provider Features

```toml
# Exactly pin the pre-1.0 Meerkat crate family.
meerkat = { version = "=0.9.8", features = ["sqlite-store", "session-store"] }
```

The `meerkat` facade enables `anthropic`, `openai`, and `gemini` by
default. Use `all-providers` as a convenience alias or disable default
features and select only the provider/storage capabilities your embedded build
needs. Shipped CLI/RPC/REST/MCP binaries use product feature sets rather than
the minimal library profile.
