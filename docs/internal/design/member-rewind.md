# Same-identity member rewind

Status: draft for review. This note supplies the design note that the disposition of #2117 asked for before same-identity rewind is built. It recommends one option, but that recommendation is open to change: the maintainers own the decision. It is docs only: no API, wire type or test changes yet, and `a_member_session_forks_at_a_message_boundary` in `crates/meerkat-rpc/tests/member_session_fork_at_boundary.rs` stays `#[ignore]`d until the decision.

Source baseline: Meerkat `main` at `ad31c1fd31517c0c1908084fae459758808cfd2d`. Paths and names below describe that baseline.

## Problem

A host that runs an interactive agent as a durable mob member wants "rewind": the user picks an earlier message, and the member's own conversation continues from that boundary. The continuation must have the exact context (the prefix byte for byte, including the copied system prompt), keep the same identity, and record where it came from.

Today none of the member surfaces gives that:

- `mob/fork_member` (`MobHandle::fork_member`) copies the exact prefix, but seats it under a **new** identity. A fork onto the source identity is refused before anything is forked: `admit_fork_member` returns `MobError::MemberAlreadyExists` when `member.identity == source_identity` (pinned over RPC by `mob_fork_member_onto_a_seated_identity_commits_nothing`: "mob member already exists").
- `session/fork_at` refuses a member's session with `INVALID_PARAMS`, "mob-owned session transcripts cannot be edited through the generic session surface" (`session_fork_at_refuses_a_member_session`). The same refusal covers `session/fork_replace`, `session/rewrite_transcript` and `session/restore_transcript_revision`.
- Re-seating the identity on a fork child's session is refused. After the child and `main` are retired, `mob/spawn` of `main` with `launch_mode = resume` on the child's session returns `INVALID_PARAMS` with `data.kind = resume_session_bound_to_another_member`, naming the session and the member it is bound to (`main_cannot_be_reseated_on_another_members_session`). The fork child's session is durably bound to the child's identity at fork commit, and `crates/meerkat-mob/src/build.rs` refuses a resume whose current identity does not match the stored binding. Its sibling check, "persisted mob member binding ... contradicts persisted comms_name", fires only when a session's own records disagree with each other. A re-seat does not reach that check.

The consumer is rkat-tui's `/rewind` in attach mode: one durable host-root member `main` per workspace, driven over the daemon (see rkat-tui `docs/mob-split.md`). The user picks an earlier message, and `main` continues from that boundary.

## Requirements

From the rkat-tui regression list and #2117:

1. **Exact prefix.** The continued transcript is the source's messages before `message_index`, including the copied system prompt (`assert_exact_prefix`).
2. **Same identity continues.** After the rewind, `main` is the member that answers. `mob/member_status` and every member-targeted method resolve `main` to the rewound conversation.
3. **Lineage recorded.** The source session and boundary are durable and readable.
4. **Inherited restrictions.** The member keeps its tool access policy, dispatch admission and instruction policy. A deny list in force before the rewind is in force after it.
5. **Idle source only.** A member that owes work is refused with the typed cause (`SESSION_BUSY`, `fork_source_unavailable` / `running`). Nothing is committed, seated or rebound.
6. **Durable.** After a process restart, the member resumes on the rewound conversation, and replay never seats it on the old one.
7. **Redo.** The previous tail stays readable (for example through `session/history` of the retired session), and the host can continue the member from it again ("redo").

## Options

### (A) Re-seat the identity on a prefix fork

`mob/fork_member` into a staging identity, retire `main`, then seat `main` on the staging child's session by rewriting the child's persisted binding (and so its comms name) to `main`.

- Mechanics: needs a binding rewrite on an existing session, which is exactly what `ResumedIdentityRejection::bound_to_another_member` refuses today, plus a retire of the staging identity.
- Trade-offs: the binding check guards identity integrity across restarts, and a rewrite path weakens it for every caller. The operation spans two identities and three journal facts (staging spawn, retire, re-seat). A crash between them leaves `main` unseated, or two sessions claiming it. It is also unnecessary: `DurableSessionForkTarget::member_binding` can already bind the child to any identity at commit (see (B)).

### (B) Prefix fork as a new session of the same identity

A mob-owned method forks the member's own session at the boundary into a new session that is **born bound to the same identity**, then moves the identity's seat onto it in one journal fact.

- Mechanics: reuse the durable prefix fork (`SessionService::fork_persisted_session`) with `DurableSessionForkTarget::member_binding` set to the member's existing binding (same mob, role and member). No staging identity, no binding rewrite. The new session is seated as a new generation of the same identity, as `MemberReset` does: new fence token and `AgentRuntimeId`, same `AgentIdentity`. Lifting the `member.identity == source_identity` guard is **not** enough on its own: `fork_source_session` would still resolve a `ForkBuildInheritance` and `apply_to` would set `spec.fork_source` to the member's own old session (see **Lineage** and **Split of the fork path** below).
- Trade-offs: a new seat transition in MobMachine ("rebind a seated identity to a committed fork of its own session") and a new journal fact. In exchange, no window exists in which two sessions claim the identity, and the binding/comms-name invariant is untouched: the new session's binding proves the same comms name.

### (C) New identity, host follows

Use `mob/fork_member` as merged and let the host switch to `main-2`.

- Trade-offs: identity churn becomes visible to every surface: the spawn customizer (keyed by identity), admission and grants, operator methods, wiring, `mob/member_status` consumers, and rkat-tui's conversation model, which names one durable `main` per workspace. The maintainers chose this shape for forks, and it is right for forks. It does not meet "same identity".

### (D) Same-session rewind through the transcript revision graph

The engine already has a same-session, append-only edit: `session/rewrite_transcript` (`SessionService::rewrite_session_transcript`) commits a rewrite and keeps the parent revision, and `session/restore_transcript_revision` restores it. A mob-owned variant could cut the tail `[message_index, end)` and record reason kind `rewind`. Redo would then be a restore.

- Mechanics: route the rewrite through the mob, under an owner's authority. `crates/meerkat-mob/src/control_policy.rs` lists a `RewriteTranscript` control scope as deferred to v2.
- Trade-offs: no seat change, no new session id, and lineage comes from the revision graph. Before this could be chosen, these must be settled: whether an ordinary edit may have an empty replacement (a pure tail cut); how live mob state keyed to that session's messages reacts to a rewrite (instruction activation rows in the cut tail, fork jobs' `prefix_message_count`, children whose `fork_source` names this session at a later boundary); and the new control scope. It also fails requirement 3 as the ignored test states it (a new `session_id`, `fork_source`). Recorded here so the decision is made against it, not by default.

### Recommendation

**(B).** It reuses the durable prefix fork, its typed refusals and its admission lineage. It keeps the binding invariant, and it makes the switch a single journal fact. (A) is not needed as a fallback: the seat path can already bind an identity at creation through `DurableSessionForkTarget::member_binding`. (D) is the alternative to weigh if the maintainers would rather extend the revision graph than add a seat transition.

## Proposed contract for (B)

**Method:** `mob/rewind_member`. It replaces the ignored test's stand-in call.

```
MobRewindMemberParams  { mob_id, agent_identity, message_index, source_session_id?, inherited_instructions? }
MobRewindMemberResult  { agent_identity, member_ref, session_id, source_session_id, message_count, generation }
```

`message_index` has its `session/fork_at` meaning: the new transcript is the source's messages before it. The source is the member's current session unless `source_session_id` names another session of the identity's own rewind chain (see **Redo**). If `inherited_instructions` is absent, the path uses the mob builder's `ForkInstructionPolicy` with `ActivationWindow::HostDriven`, as `mob/fork_member` does: the host drives the next turn.

**Owner:** `MobHandle::rewind_member` in `crates/meerkat-mob/src/runtime/handle.rs`, admitted under control scope `SendCommand`, like `fork_member`.

**Atomicity: an identity-scoped admission hold.** The fork path's busy check is point-in-time. `refuse_fork_source_with_admitted_work` reads the runtime state and the input ledger once, out of band, and `mob/turn_start` resolves its target (`mob_turn_start_target`) and then calls `turn/start` on that session id with nothing held in between. A turn can therefore be admitted after the check, or after the fork commits but before the switch. The rewind closes that window with parts that exist today:

- *Run-start hold.* MeerkatMachine's `RunStartHoldReason` holds a session registration's run starts. Add a mob-owned reason `MemberRewind`, staged and released only by the mob, as `HostPreparation` is (a host's `release_member_run_starts` refuses it).
- *Rewind pending.* A MobMachine field `member_rewind_pending[identity] = { generation, fence_token, session_id }`, set and cleared only by the rewind's own actor commands. While it is set, every input admission the mob gates for that identity (`admit_member_host_door` / `SubmitWork` for `mob/turn_start`, `mob/member_send`, kickoff and flow steps) is refused `SESSION_BUSY` with `data.kind = member_rewinding`, retryable. It is not journaled: a crash drops it with the process, and the restart sees no rewind.
- *Generation-validated target.* `MemberDeliveryScope` (`crates/meerkat-mob/src/runtime/delivery_scope.rs`) already pins generation, fence and session, and scope-bound submits are refused as `StaleFenceToken` or `StaleDeliveryScope` "before any admission effect", never retargeted. `mob_turn_start_target` captures a scope in the same actor-gated step it resolves the session in, and `mob/turn_start` admits through the scope-bound submit instead of a bare `turn/start` on the session id.

Sequence:

1. **Begin** (one actor command): resolve the source and current session `S0`, refuse a placed or unseated member, refuse a second rewind of the same identity (`member_rewinding`), set `member_rewind_pending`, stage the `MemberRewind` hold on `S0`, then re-run `refuse_fork_source_with_admitted_work` **under the hold**. If `S0` is running or its ledger holds a non-terminal input, clear the pending state, release the hold and refuse `SESSION_BUSY` (`fork_source_unavailable`, `running`). A hold that cannot be staged (the registration is unregistering, the mob is stopping) refuses the same way. Nothing has been forked yet.
2. **Fork** (outside the actor): observe the dispatch lineage, then `fork_persisted_session` of the source at `message_index` with the member's own binding. **The child `S1` is committed here, after every refusal that promises "nothing committed".** A refusal from the fork owner (`SessionError::Busy`, a bad boundary) still commits nothing.
3. **Build** the member's runtime on `S1` under the next generation, without routing anything to it. The build goes through the ordinary resume pipeline, so it returns the pipeline's `PendingProvision` guard (`crates/meerkat-mob/src/runtime/provision_guard.rs`) for `S1`: origin `ProvisionSessionOrigin::ResumedDurable` with its `ResumedMemberRollbackAuthority`, and `RollbackOrigin::RevivalOrRebuild`, so a rollback never touches the roster entry, which still names `S0`. The guard is the custody of everything Build provisioned (the runtime, its session registration, the comms endpoint). It is not dropped or committed before step 4 decides.
4. **Commit** (one actor command, carrying the guard): check that `member_rewind_pending` still names the generation, fence and `S0` it set (a retire, destroy or Stop in between clears it, and the commit then fails like a seat failure, going to Abort with the guard still unconsumed). Only when the check passes: `PendingProvision::commit` the guard, journal `MemberRewound`, move the binding to `S1` with the new generation and fence, clear the pending state, and retire `S0`'s registration, which drops the hold with it. Any input that still reached `S0`'s ledger is abandoned runlessly (`InputAbandonReason::Retired`). It cannot have run, because the hold stood.
5. **Abort** (one actor command, on any failure or cancellation after Begin): if Build produced a guard, roll it back first with `rollback_retaining_custody`, which detaches `S1`'s runtime and restores `S1` to durable idle (the resumed-session rollback, not the fresh-session retire), so no unjournaled `S1` runtime or endpoint is left beside the old seat. Then clear the pending state if it is still this rewind's, and release the hold if `S0` still has one. The durable child `S1`, the prefix fork, is kept: it is not archived or deleted, and the refusal names it (`ForkMemberProvisionFailed { fork_session_id }`). A rollback that fails keeps its `RetainedProvisionCustody`, and the rewind stays in Abort retrying the exact owner cleanup instead of reporting a settled outcome. A cancelled rewind task (the client went away, a crash-stop aborted the actor's tasks) reaches the same Abort through the guard's in-flight handling: the guard is never dropped unconsumed. If the commit lost the race to a Stop or retire, `S0` is gone by that owner's doing, not the rewind's. Otherwise `S0` stays seated and continues.

The failure rule for racing turns: a turn whose target was resolved before Begin and admitted before the re-check makes the rewind `SESSION_BUSY`. One admitted between Begin and Commit is refused `member_rewinding`. One admitted after Commit against the old generation is refused `StaleFenceToken` (wire `StaleFence`), because the scope it captured names the retired fence and session. Every case is typed, and none is retargeted silently. The client re-resolves `main` and retries.

**Split of the fork path.** The rewind reuses the durable prefix fork, but not `ForkBuildInheritance`:

- `admit_fork_member` becomes a shared `admit_durable_fork_source` (control scope, placement, the source's bridge session, building `DurableSessionForkTarget` from a given `MobMemberBinding`) plus the fork-only checks it keeps (`MemberAlreadyExists` for `member.identity == source_identity`, the approval-branch reservation, the `fork_build_inheritance` refusal). The rewind calls the shared part with the member's own binding.
- `fork_source_session` becomes a shared `commit_durable_fork` (the `fork_persisted_session` call and its `Busy` → `ForkSourceUnavailable { Running }` mapping) and the fork path's inheritance step (`resolve_fork_build_inheritance`, `ForkBuildInheritance::apply_to`, `resolve_seat_dispatch_admission`). The rewind does what `fork_member_at_turn_boundary` already does: `observe_fork_source_dispatch_lineage` on its own identity and session, then `resolve_seat_dispatch_admission`, and never constructs a `ForkBuildInheritance`. Its build inputs are its own: the roster entry's labels, role and definition wiring, the identity's retained overlay (`per_spawn_external_tools` is keyed by identity), its tool access policy, and the application context the fork copies verbatim with the build state. Its existing `fork_source`, if it is itself a fork child, is kept unchanged.
- `seat_forked_member` stays fork-only (it spawns a new identity). The rewind seats with a new `reseat_member_on_rewind`, the generation advance of steps 3–4.

**Typed refusals** (nothing committed, seated or rebound unless stated):

| Case | Refusal |
| --- | --- |
| Member owes work at Begin (turn in flight, admitted input, unanswered boundary) | `SESSION_BUSY`, `data.kind = fork_source_unavailable`, `cause = running` (the re-check under the hold, then the durable owner's `SessionError::Busy`) |
| Another rewind of the identity in progress, or the hold cannot be staged | `SESSION_BUSY`, `data.kind = member_rewinding` |
| Member seated without a session | `fork_source_unavailable`, `cause = no_session` |
| Unknown or retired identity | `MobError::MemberNotFound`, mapped as other member-targeted methods map it. Today `fork_member` reports an unseated source as `no_session` because `resolve_bridge_session_id` finds nothing. A rewind should name the missing member instead |
| `source_session_id` not in the identity's rewind chain | `INVALID_PARAMS`, `data.kind = rewind_source_not_in_lineage`, naming the session and identity |
| `message_index` beyond the committed end, or not a message boundary the durable fork accepts | the durable fork owner's refusal, mapped as `session/fork_at` maps it (`INVALID_PARAMS`) |
| Fork committed, build or commit failed | `ForkMemberProvisionFailed { fork_session_id }` after Abort has rolled back `S1`'s provisioning. The **old seat stays bound** (unless the commit lost to a concurrent retire or Stop, which removed it). The durable orphan carries the identity's binding, but no runtime is attached to it, no roster fact names it and it is not in the rewind chain. A client that sent a turn while the rewind was pending got `SESSION_BUSY` / `member_rewinding` and retries against `S0`: it never sees a switch, and no `MemberSessionReplaced` is emitted |

**What is persisted:** the fork commit, written by the session store with the member's own binding. Then one mob journal fact, `MemberRewound { agent_identity, previous_generation, new_generation, fence_token, agent_runtime_id, session_id, source_session_id, message_count }` (the name is illustrative). Replay feeds it to MobMachine as a seat rebind and updates the roster's bridge session. Because it is a single row, a crash leaves either the old seat (fact absent) or the new one (fact present), never neither.

**Lineage:** record it on the rewind fact and project it on the roster entry as `rewound_from { source_session_id, message_count }`, and only there. **Do not** put it in `fork_source`. `fork_source` means "built with the source's `ForkBuildInheritance`", and the split above never applies one. A self-referential `fork_source` would send `fork_overlay_rule` through `follow_fork_link` to the member itself, now bound to another session, so every rebuild would hit `ForkLinkBroken::OtherSession` and warn.

**Observation by an attached client.** `mob/events` (`handle_events`) is a bounded cursor query that answers only when called. `mob/stream_open` forwards `AttributedEvent`s that the event router (`subscribe_mob_events`, `runtime/event_router.rs`) merges from per-member session streams, not journal facts. So the journal fact alone reaches no waiting client. The router already follows structural `MemberSpawned` / `MemberRetired` facts to attach and detach member streams, and it follows `MemberRewound` the same way. On the fact it detaches `S0`'s stream, forwards one synthesized `AttributedEvent` for the member whose envelope carries a new `AgentEvent::MemberSessionReplaced { previous_session_id, session_id, message_count, generation }`, attributed to the new runtime id and fence, and then attaches `S1`'s stream. A mob-wide `mob/stream_open` subscriber therefore sees the switch before any event of the new session, without polling.

That covers only the mob-wide form. `mob/stream_open` with `agent_identity` does not go through the router: `handle_mob_stream_open` (`crates/meerkat-rpc/src/router.rs`) calls `subscribe_member_events_resuming` and forwards that one session's raw envelopes, and the stream ends when `S0`'s registration retires. The contract covers the per-member form too, and does not narrow to mob-wide streams, because rkat-tui's attach client opens the per-member form for `main`. The per-member subscription follows the rebind: the member's event subscription (`subscribe_agent_events_from`) watches the identity's seat, and on `MemberRewound` it ends `S0`'s source after `S0`'s last event, yields the same `MemberSessionReplaced` envelope, then subscribes to `S1` from its earliest event and keeps forwarding on the same `stream_id`. It does not end the stream. Events from `S1` carry `S1`'s own sequence-space epoch, so the stream's epoch changes at the replacement. A client that reattaches with a cursor from the old epoch gets the existing behaviour of `subscribe_member_events_resuming`: the cursor is rejected for the current space and the stream replays `S1` from its earliest retained event, whose first item is the `MemberSessionReplaced` envelope, so the reattached client learns of the switch from the replay. This rebind-following lives in the mob's member-event subscription, not in the RPC forwarder, so every per-member consumer gets it. The fallback is explicit: a client with no open stream, or one that missed the event (a lagging or reconnected stream), learns of the switch from `mob/member_status` (`current_session_id`, generation, `rewound_from`) or from `mob/events`, both by polling. A turn it sends against the stale target is refused `StaleFenceToken`, never run on the retired session.

**Recovery:** restart restore resumes the identity on the session the latest seat fact names, as for any member. The retired session is a plain durable session that no seat names. It is not disposed, and `session/history` (a read, not one of the refused transcript edits) still reads its tail.

**Redo.** After a rewind the current session holds only the prefix, so `{agent_identity, message_index}` alone cannot reach the discarded tail, and the generic transcript edit surfaces refuse mob-owned sessions. Redo is defined in this contract as `mob/rewind_member` with `source_session_id` set to a retired session of the identity's rewind chain, and `message_index` at that session's committed end (a full redo) or at any earlier boundary of it (a partial redo). It runs the same sequence: the hold and the idle check are on the current session `S0`, which is the one being replaced, and the fork source is the retired session, which has no runtime.

- Authorization is by lineage, scoped to the **current membership** of the identity. The source must be a session that a `MemberRewound` fact of this identity, in this mob, names as `source_session_id` or `session_id`, recorded since the latest `MemberSpawned` of the identity, and it must not be the current one (pass no `source_session_id` for that). The check folds the mob's own durable member history the way delivery-scope recovery's `JournalFold` (`crates/meerkat-mob/src/runtime/delivery_scope.rs`) does: every `MemberSpawned` starts the identity's next membership there, and the rewind chain is part of that membership's head. So the fold resets the identity's chain to empty on `MemberSpawned` (and on `MobReset`, which ends every membership), appends on `MemberRewound` only while that membership is live, and freezes it at `MemberRetired` of the exact generation. `MemberReset` carries the live membership on, so it keeps the chain. A retired-then-recreated identity therefore starts with no chain, and its predecessor's sessions, though bound to the same identity, are refused. Any other session (another member's, another mob's, an earlier membership's, a failed rewind's orphan) is refused `rewind_source_not_in_lineage` before Begin.
- Listing the chain: `mob/member_status` carries `rewind_lineage`, newest first: `[{ session_id, source_session_id, message_count, generation }]`, a projection of the same journal facts the authorization reads, for the current membership only. A host does not walk `session/history` metadata, because session metadata is not the authority for mob seats. `session/history` on a listed session reads its transcript, to show what redo would restore.
- Recommended over a separate `mob/redo_member` that re-seats the identity on a retired session as-is. Both pass the binding check, since the retired session is bound to the same identity. But re-seating would bind one session to the identity in two generations, which `MemberBindingHistory` and the delivery-scope proofs would then have to tell apart, and it would add a second seat transition. The `source_session_id` form always produces a fresh session, so one transition and one fact cover rewind and redo, and a retired session is never seated again.

**Afterwards:** `mob/member_status` shows the same `member_ref`, a new `current_session_id`, the advanced generation, `rewound_from` and `rewind_lineage`. `mob/stream_open` subscribers, mob-wide and per-member, receive `MemberSessionReplaced`, and a per-member stream continues with `S1`'s events. `mob/events` carries the journal fact for cursor readers.

**Mapping onto the ignored test:** the stand-in call becomes `mob/rewind_member`. Its assertions hold as written: `session_id != source`, `source_session_id`, `message_count == BOUNDARY`, exact prefix, the source history unchanged, `member_session(MAIN) == child`, the deny list kept, and `SESSION_BUSY` with nothing rebound while a turn is held. One exception: the lineage assertion reads `rewound_from` instead of `fork_source`. The stale doc-comment reference in that test is fixed when it is un-ignored.

- `a_member_session_forks_at_a_message_boundary`: un-ignored, the stand-in replaced by `mob/rewind_member`.
- A restart test: rewind, drop the runtime, restore over the same stores, and `main` resumes on the rewound session with the prefix plus later turns. The old session is still readable.
- A two-client test, run for both stream forms: client B has `mob/stream_open` open on the same mob before client A rewinds `main`, once mob-wide and once per-member with `agent_identity = main`. B receives `MemberSessionReplaced` naming the old and new sessions, with no `mob/events` or `mob/member_status` call, and before any event of the new session. On the per-member stream the same `stream_id` stays open and then carries a turn's events from the new session under its new epoch. A reattach of the per-member form with a cursor from the old epoch replays the new session from its earliest event, starting with `MemberSessionReplaced`. B's next `mob/turn_start` for `main` lands on the new session. A variant without a stream sees the switch through `mob/member_status`.
- Admission races (`crates/meerkat-mob` runtime tests, with the test pause hook `fork_source_session` already has): a `mob/turn_start` resolved before Begin and admitted after the re-check is refused `member_rewinding`; one whose scope was captured before Commit and submitted after it is refused `StaleFenceToken`; in both cases `S0`'s transcript is unchanged and nothing ran on it.
- Running refusal: a held turn, then a rewind, gives `SESSION_BUSY`. Roster, session list and binding are unchanged (already in the ignored test). Add an admitted-but-queued input case, as `fork_member` pins.
- Lineage and restrictions: `rewound_from` and `rewind_lineage` survive a restart. A member seated under a host dispatch admission keeps it (the #2112 lineage case: a `crates/meerkat-mob-mcp/tests/fork_dispatch_admission_lineage.rs` sibling). A rebuild after a rewind emits no fork-source warning, and the roster's `fork_source` is unchanged.
- Redo: rewind, then `mob/rewind_member` with `source_session_id` = the retired session at its end restores the full transcript as a new session. A `source_session_id` of another member's session, or of a failed rewind's orphan, is refused `rewind_source_not_in_lineage` with nothing committed. Retire then recreate: rewind `main`, retire it, spawn `main` again; `mob/member_status` shows an empty `rewind_lineage`, and `mob/rewind_member` with `source_session_id` = either session of the old chain is refused `rewind_source_not_in_lineage`, with nothing committed. The same holds after a restart, since the fold is over the journal.
- Seat failure: an injected failure after the fork commit gives `ForkMemberProvisionFailed`, `main` is still seated on the old session, and the hold is released (a turn then runs).
- Commit lost to a retire (`crates/meerkat-mob` runtime test, paused between Build and Commit): retire `main` while paused, resume. The rewind is refused `ForkMemberProvisionFailed`, no `MemberRewound` is journaled, the guard was rolled back (no runtime, registration or comms endpoint for the new session remains), and the new session is still readable through `session/history` as a durable idle session. A cancellation at the same pause point leaves the same state.

## Consumers

- rkat-tui `/rewind` in attach mode: the motivating case. It needs requirements 1-7, and redo needs 7.
- An interactive host runtime (for example Meta's) that offers rewind on a durable member.
- `rkat mob` CLI could expose it as `rkat mob rewind <member> --at <index>`.
