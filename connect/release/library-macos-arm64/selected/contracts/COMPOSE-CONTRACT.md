# Canonical Compose contract

Draft implementation contract, schema version 1. The adjacent `request.example.json` is the exact CLI input shape. Its tool/image pins and endpoint are illustrative placeholders, not execution evidence. The separately formatted package, manifest and profile examples show the corresponding string contents; the request hashes bind the compact strings, not the formatted example files.

`toolkit-compose-plan` reads one JSON object on stdin and writes one JSON object plus a newline. It does no filesystem or Docker work. Input is at most 2 MiB; each package, manifest and profile string is at most 256 KiB. All JSON parsing rejects duplicate keys, and typed records reject unknown fields. Failure is a fixed code on stderr and a nonzero exit.

## Request and profile

Request fields are `schema_version`, `package_json`, `manifest_json`, `profile_json`, `profile_sha256`, `configuration`, `policy` and `files`. The first three document values are exact JSON strings. Configuration and policy are exact UTF-8 strings whose SHA-256 values must match the manifest references. Files is a map from safe relative names to exact UTF-8 strings; each must match the profile's `files` digest map. Each content string is at most 64 KiB and cannot contain NUL. Whitespace is retained.

The profile contains `schema_version`, `owner`, `placement`, `host`, `project`, `engine`, `components`, `volumes` and `files`:

- `host` is the existing canonical HostCapabilities declaration. Existing manifest validation and host compatibility remain authoritative.
- `engine` contains explicit `endpoint` (`unix:///...`), opaque observed `id`, and `docker` and `compose` objects, each with absolute `path` and exact `sha256`. Runtime verifies these declarations before effects; preparation alone proves none of them.
- Optional `engine.bind_source_prefix` is a host-declared `{local_root,engine_root}` spelling map for bind sources reported by that engine. Absent or null retains exact identity matching and is omitted from prepared engine serialization. Both roots must be normalized non-root absolute ASCII paths, at most 256 characters after the initial slash, with only alphanumeric, `.`, `_`, `-` and `/` characters, no empty, `.` or `..` segments. Equal or ancestor-overlapping roots are refused. For example, `/private/tmp` to `/host_mnt/private/tmp` is valid. The runtime may accept a selected bind's exact host path or the exact mapped suffix under these roots, at path-segment boundaries; unrelated paths and named volumes are unaffected. This does not rewrite the generated Compose file or infer a platform mapping. The exact profile bytes and prepared engine declaration bind the map into the plan digest. The host owns the declaration and the engine's actual filesystem relationship.
- `components` is keyed by exactly the selected canonical component IDs. Each value has `service`, `image_id`, `platform`, `user`, `environment`, `mounts`, `resources`, and optional `healthcheck` (null is equivalent to absent).
- `image_id` is `sha256:<64 lowercase hex>`, the exact image object observed from the bound Docker engine/platform, not necessarily an OCI config digest. `platform` is `linux/arm64` or `linux/amd64`. `user` is explicit numeric `uid:gid`.
- `resources` has positive `cpu_millis`, `memory_bytes`, and `pids_limit`. The supported bounds are 1-32000 CPU milliseconds, 8 MiB-8 GiB memory, and 16-4096 PIDs. There is no implicit resource default.
- `environment` is an explicit literal string map. Dollar interpolation and control characters are refused. For example, `POSTGRES_PASSWORD_FILE=/run/config/db-password` is permitted; the referenced file remains separately pinned configuration, not a native credential grant.
- A file mount is `{kind:"file",source:"configuration"|"policy"|"files/<name>",target:"/absolute/path"}`. All file mounts are read-only, and source creation is disabled.
- A volume mount is `{kind:"volume",source:"<state namespace>",target:"/absolute/path",read_only:true|false}`. Each volume has exactly one canonical component owner. Other components may mount it read-only only if they transitively depend on that owner. Every volume requires an owner-writable mount. Duplicate/overlapping targets and lexical executable-path shadowing are refused. This does not inspect symlinks inside an image; the host must review its actual image filesystem and mount paths.
- `volumes` has exactly the canonical state namespaces, each with one unique physical `name` prefixed by `<project>-`. Local volume storage is selected explicitly. No migration, adoption or deletion is implied.
- `healthcheck` is null for canonical readiness check `running`, or an explicit object for readiness check `healthy`: `argv`, `interval_ms`, `timeout_ms`, `retries`, `start_period_ms`. Docker receives `CMD` plus the argv, never an implicitly added shell. This is backend health, not domain role readiness.

The selected components must be independent container artifacts. Deployment and request lifetimes are supported; all dependency targets must have deployment lifetime. Request components are placed in the `request` Compose profile. State requires deployment lifetime and no migration. Lifecycle owner must equal the profile owner, shutdown operation must be `stop` with `preserve_uncertainty` and a whole-second 1000-120000 ms maximum, and rollback must be owner reconciliation operation `reconcile`. Unsupported host services, extra runtime contracts, frontend exports, event exports and portable MCP entries are refused rather than silently discarded.

Artifact image forms are explicit. HTTPS `https://<registry>/v2/<repository>/manifests/sha256:<digest>` uses the existing GitOps image validator and lowers to `<registry>/<repository>@sha256:<digest>`. The digest must match the artifact content digest. The container-only local form `docker-image:///sha256/<digest>` must match both content digest and profile image ID and lowers to `sha256:<digest>`. It names an already-present object in the selected engine. It does not assert registry provenance, import an archive, or infer a relationship between a saved archive and an image. Runtime never pulls or loads images through this contract.

## Prepared output

The output is `{schema_version:1,status:"prepared",plan_sha256,plan}`. `plan_sha256` hashes the existing canonical JSON serialization of `plan` without a trailing newline. It is not an approval or completion receipt.

Plan has exact request/source digests, canonical `manifest_sha256`, `host_owner`, `project`, `network`, `engine`, `compose_json`, `files`, `components`, `volumes`, `initialization_order`, `shutdown_order`, `deployment_order` and `request_components`. `request_sha256` hashes the exact entire stdin bytes. `package_sha256`, `manifest_source_sha256` and `profile_sha256` hash exact source strings. Configuration and policy digest fields bind their exact contents.

`files` maps fixed workspace-relative paths to `{sha256,contents,mode}`: `inputs/configuration`, `inputs/policy`, and `inputs/files/<name>` use decimal mode 292 (0444); `compose.json` uses 384 (0600). `compose_json` equals the contents of that exact file, including its final newline. No caller-chosen output path is introduced.

Prepared components have `service`, `lifetime`, `image`, `image_id`, `platform`, `user`, `entrypoint`, `command`, `environment`, `resources`, `mounts`, `dependencies`, `deployment_dependencies`, `readiness`, and `stop_timeout_ms`. `deployment_dependencies` is the canonical transitive dependency set in initialization order, so the runtime need not derive graph meaning. Prepared mount sources are fixed workspace-relative file paths or exact physical volume names. Prepared volumes are keyed by canonical namespace and contain `name`, owning `component`, canonical state `owner` and `format`.

The network is exactly `<project>-network`, internal bridge with no host ports. Compose uses explicit literal argv/user/resources, `pull_policy:never`, no restart policy, disabled inherited healthchecks when unselected, exact generated labels, fixed bind paths and named volumes. Label values bind manifest, profile and request digests. They identify expected objects but are not sufficient authorization to mutate them. Runtime must verify the actual IDs/configuration and current observation before stop/removal.

This supports selected component deployment and request-container launch without changing portable MCP restrictions or introducing another native admission/runtime owner.
