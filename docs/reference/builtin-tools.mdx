runtime-composed memory, comms, schedule, WorkGraph, mob, image-generation,
and web-search surfaces. Each family remains the source of truth for its own
tool names, schemas, execution contract, mutation class, and gates.

## Enabling and disabling tools

<Accordion title="Factory-level flags">
`AgentFactory` controls which tool categories are available via builder methods:

| Flag | Builder Method | Default | Controls |
|------|---------------|---------|----------|
| `enable_builtins` | `.builtins(bool)` | `false` | Task tools, utility tools (`datetime`, `apply_patch`, `view_image`), and blob file tools when a blob store is wired |
| `enable_shell` | `.shell(bool)` | `false` | Standard shell tools (`shell`, `shell_jobs`, `shell_job_status`, `shell_job_cancel`); `monitor_start` remains an explicit high-trust policy decision |
| `enable_memory` | `.memory(bool)` | `false` | `memory_search` (requires `memory-store-session` feature) |
| `enable_schedule` | `.schedule(bool)` | `false` | Scheduler tools (`meerkat_schedule_*`) |
| `enable_workgraph` | `.workgraph(bool)` | `false` | WorkGraph tools (`workgraph_*`) |
| `enable_comms` | `.comms(bool)` | `false` | All comms tools (requires `comms` feature) |
| `enable_mob` | `.mob(bool)` | `false` | Mob orchestration tools (`mob_*`, `meerkat_*`) |

`AgentFactory` is the only place tool categories are composed. The public `meerkat::AgentBuilder` delegates to the factory path with explicit client/tool/store overrides. The lower-level `meerkat_core::AgentBuilder` is not re-exported by the facade and is not a public standalone embedding API. See [AgentBuilder vs AgentFactory](/rust/advanced#agentbuilder-vs-agentfactory).

**Source:** `crates/meerkat/src/factory.rs` -- `AgentFactory` struct and builder methods.
</Accordion>

<Accordion title="Per-build overrides">
Each `AgentBuildConfig` can override factory-level flags for a single agent build:

| Override Field | Type | Effect |
|---------------|------|--------|
| `override_builtins` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_shell` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_memory` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_schedule` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_workgraph` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_mob` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_comms` | `ToolCategoryOverride` | Explicit `enable`, `disable`, or `inherit` |
| `override_image_generation` | `ToolCategoryOverride` | Controls assistant image-generation visibility independently from general builtins |
| `override_web_search` | `ToolCategoryOverride` | Controls provider-native search or the Meerkat fallback independently from general builtins |

All default to `inherit`. The categories backed by factory flags inherit those
flags. Image generation treats `inherit` as visible once its session-owned
substrate is wired into the normal composite dispatcher. The minimal
no-builtins/no-shell early return requires an explicit image enable to create
that dispatcher. The Meerkat-owned web-search fallback is different: it treats
`inherit` as hidden and requires an explicit `enable`. An explicit enable fails
closed if its runtime dependencies cannot be provisioned. Enabling either
category does not enable general builtins.

**Source:** `crates/meerkat/src/factory.rs` -- `AgentBuildConfig` struct.
</Accordion>

<Accordion title="ToolPolicyLayer">
Individual tools can be enabled or disabled via `ToolPolicyLayer` in
`BuiltinToolConfig`, but policy can only select tools from a category that was
actually composed. When shell is enabled, the factory applies a policy that
activates the four standard shell tools (which have `default_enabled: false`).
The high-trust `monitor_start` and all five skill tools also default off and
require an explicit policy enable in a custom dispatcher build.
</Accordion>

<Accordion title="Execution contracts and mutation classes">
Every dispatcher exposes a `ToolExecutionContract` per tool. The default is
`Fast`; tools may additionally support `Streaming` or `Detached`. Streaming
contracts own progress/cancellation policy. Detached contracts declare runner
identity, submission idempotency, restart class, and a bounded submission
deadline. The resolved deadline is the narrowest contribution in the call's
deadline chain.

`RestartClass` values are `Adoptable`, `CheckpointResumable`, `Replayable`, and
`NonResumable`. A tool can advertise only the classes its runner can honor.

Separately, every dispatcher reports `ToolMutationClass::ReadOnly`,
`Mutating`, or `Unknown`. Unknown is fail-closed uncertainty for third-party or
undeclared tools, not an assertion that the call is harmless.
</Accordion>

<Accordion title="Capability registrations">
Capabilities are registered via the `inventory` crate in `crates/meerkat-tools/src/lib.rs`:

- **Builtins** (`CapabilityId::Builtins`): `task_list`, `task_create`, `task_get`, `task_update`, `datetime`, `apply_patch`, `view_image`, and runtime-backed `blob_save_file`/`blob_load_file`/`blob_inspect` when a blob store is available. Controlled by `config.tools.builtins_enabled`.
- **Shell** (`CapabilityId::Shell`): `shell`, `shell_jobs`, `shell_job_status`, `shell_job_cancel`, plus opt-in `monitor_start`. Controlled by `config.tools.shell_enabled` and per-tool policy.
- **Image generation**: runtime-owned `generate_image`, controlled by `override_image_generation` after runtime capability resolution.
- **Web search**: provider-native search when the active model owns it, otherwise the Meerkat-owned `web_search` fallback; controlled by `override_web_search`.
- **Schedule** (`CapabilityId::Schedule`): `meerkat_schedule_*`. Controlled by `config.tools.schedule_enabled`.
- **WorkGraph** (`CapabilityId::WorkGraph`): `workgraph_*`. Controlled by `config.tools.workgraph_enabled`.
</Accordion>

## Runtime tool scoping

Beyond static factory flags and per-build overrides, tool visibility can be changed at runtime during a live session. See [Tool scoping](/concepts/tools#tool-scoping) for the conceptual overview.

<Accordion title="ToolScope lifecycle">
`ToolScope` (in `meerkat-core`) manages runtime tool visibility. It holds the base tool set from the dispatcher, an active external filter, and an optional per-turn overlay.

**Staging:** External callers stage filter updates via `ToolScopeHandle::stage_external_filter(filter)`. The staged filter is NOT applied immediately — the current turn is unaffected.

**Boundary apply:** At the start of each `CallingLlm` loop iteration, `tool_scope.apply_staged(dispatcher_tools)` atomically promotes the staged filter to active, prunes stale tool names, and returns the visible tool set. A `ToolConfigChanged` event is emitted and a typed `tool_config` system notice is recorded in the conversation.

**Filter types:**
- `ToolFilter::All` — no restriction (default)
- `ToolFilter::Allow(set)` — only listed tools are visible
- `ToolFilter::Deny(set)` — listed tools are hidden

**Composition:** Most-restrictive wins. Multiple allow-lists intersect, multiple deny-lists union, deny beats allow.

**Persistence:** The active external filter is stored in session metadata under `tool_scope_external_filter` and restored on session resume.

**Source:** `crates/meerkat-core/src/tool_scope.rs`
</Accordion>

<Accordion title="Live MCP server mutation">
MCP servers can be added or removed from a running session. Operations are staged on the `McpRouter` and applied at the next turn boundary.

| Surface | Method | Status |
|---------|--------|--------|
| JSON-RPC | `mcp/add`, `mcp/remove`, `mcp/reload` | Fully wired (staged) |
| REST | `POST /sessions/{id}/mcp/add\|remove\|reload` | Fully wired |
| CLI | `rkat mcp add/remove/list/get` | Config surface; start or resume a session to load config |
| MCP server | `meerkat_mcp_add`, `meerkat_mcp_remove`, `meerkat_mcp_reload` | Fully wired |

Servers being removed transition through `Active → Removing (draining) → Removed` to allow in-flight tool calls to complete before finalization.

**Source:** `crates/meerkat-mcp/src/router.rs`, `crates/meerkat-rpc/src/handlers/mcp.rs`
</Accordion>

<Accordion title="Per-turn tool overlay">
Mob flow steps can restrict tools for a single turn via `TurnToolOverlay`:

```rust
let overlay = TurnToolOverlay {
    allowed_tools: Some(vec!["shell".into()]),
    blocked_tools: Some(vec!["task_create".into()]),
    ..Default::default()
};
```

The native allow/deny fields are `Option<Vec<ToolName>>`; `.into()` converts
the names above. The default supplies an empty host-only `dispatch_context`.
Set the overlay on `StartTurnRequest.runtime.turn_tool_overlay` by the flow
engine or another trusted per-turn producer. It is ephemeral — cleared after
the turn completes — and composes with the external filter using
most-restrictive semantics.

Public wire requests use the caller-safe `PublicTurnToolOverlay` shape:
`allowed_tools` and `blocked_tools` contain string names. They do not accept
the internal `dispatch_context` field.

**Source:** `crates/meerkat-core/src/service/mod.rs`, `crates/meerkat-mob/src/runtime/flow.rs`
</Accordion>

## Deferred tool catalog control plane

An exact dispatcher can keep eligible session tools out of the LLM's inline
schema set and expose two always-inline control tools instead. The adaptive
selector enters deferred mode when a source is still pending, at least two
eligible tools exist, or their combined name, description, and schema volume
reaches 160 bytes. These tools are not part of the general builtins gate.

<Accordion title="tool_catalog_search">
Search deferred-eligible session tools without loading them.

<ParamField body="query" type="String">
  Optional case-insensitive substring search over canonical name and
  description.
</ParamField>

<ParamField body="limit" type="usize" default="10">
  Result limit, clamped to `1-50`.
</ParamField>

The response contains `catalog_exact`, `total_matches`, `results`, optional
`pending_sources`, and optional `empty_result_status`. Each result reports
`name`, `description`, `currently_callable`, and `visibility_status`:
`loaded`, `deferred`, `blocked_by_filter`, or `temporarily_unavailable`.
`pending_source` is used only as the empty-result status while a catalog source
is pending.

**Source:** `crates/meerkat-tools/src/control_plane.rs`
</Accordion>

<Accordion title="tool_catalog_load">
Stage one or more canonical deferred tool names for the next tool boundary.
The control plane consults the bound `ToolScope` and fails closed when it has no
authoritative visibility state.

<ParamField body="names" type="String[]" required>
  One or more canonical tool names.
</ParamField>

The response contains `catalog_exact`, `accepted_names`, `noop_names`, and one
resolution per requested name. Rejection reasons are `unknown_key`,
`not_deferred_eligible`, `not_filterable`, or `temporarily_unavailable`.
Already staged or visible names are successful no-ops. Accepted loads take
effect at the next boundary, not during the current tool call.

**Source:** `crates/meerkat-tools/src/control_plane.rs`,
`crates/meerkat-core/src/tool_catalog.rs`
</Accordion>

## Model-switch tool

`brain_swap` is available only when the host can realize committed model
handoffs, more than one distinct model is reachable, and tool policy permits
it. Its required `target_model` argument selects from that reachable set.

The tool returns `staged` or `already_staged`; it does not change the model
during the current run. A clean run completion commits the request, which the
runtime attempts to realize before processing the next input. Failed,
interrupted, or hook-denied runs do not commit the switch, and later
realization can still be denied or held. A staging result is not proof that
the model has changed.

**Source:** `crates/meerkat-tools/src/builtin/brain_swap.rs`,
`crates/meerkat-tools/src/builtin/composite.rs`,
`crates/meerkat-core/src/agent/state.rs`, `crates/meerkat-runtime/src/service_ext.rs`

## Mob tools

`AgentMobToolSurface` is composed only for sessions with generated MobMachine
authority. It defines the 13 core tools in the inventory above, including
`fork_off` for durable transcript-forked work and `council` for bounded
discussion among temporary forks of existing members. Realm
profile storage adds five profile CRUD tools; a parent-owned snapshot provider
also adds `mob_profile_list_sources`. Admission is then checked again at each
dispatch against the current typed mob, spawn, profile-mutation, or objective
scope. See [Mob tools](/guides/mobs#agent-tools-vs-host-apis) for argument shapes
and workflows.

### `fork_off` and `council` delivery

`fork_off` forks the calling member's committed transcript into a durable child
member, commits the task (and any `expected_output` guidance) as the child's
input, and admits the child's one turn. The child runs turn-driven whatever
its role's default runtime mode, like a `delegate` helper. What happens next
depends on whether the host can deliver a completion after the call returns.

**Detached.** A call runs detached when three things hold: the host declares
it can deliver later, it has a runtime to admit the completion, and the caller
can be made live again to receive it. A host built with a runtime adapter
declares delivery by default (the JSON-RPC, REST, and MCP servers and
MobKit), and so do `rkat run --keep-alive` and `rkat mob deploy --surface
rpc`. The caller can be revived when it is a member of a mob the host manages
(its mob revives it) or when the host installs a `DetachedOwnerHost` (the
JSON-RPC host does). A `fork_off` caller is always a mob member. There
`fork_off` returns without waiting for the child's turn:

```json
{
  "status": "running",
  "mob_id": "research",
  "source_member_id": "planner",
  "agent_identity": "planner-ledger-fork",
  "member_ref": "...",
  "fork_session_id": "...",
  "cache_inheritance": { "...": "..." },
  "job_id": "...",
  "note": "Running in the background. The result will be added to your conversation later as \"Background fork_off job ... finished\". ..."
}
```

When the child's turn ends, its outcome names the child (`agent_identity`,
`member_ref`) and carries a `status`:

| `status` | Meaning |
|----------|---------|
| `completed` | The turn completed. Carries `bounded_result` (the child's final text under `max_text_bytes`, with explicit truncation), `usage`, `turns`, and `tool_calls`. The child stays seated. |
| `failed` | The turn failed. Carries `error`. The child was retired. |
| `max_run_elapsed` | The opt-in `max_run_secs` elapsed. The run was cancelled and the child retired; `retirement_error` reports a failed retirement. The notice status is `terminated`. |
| `supervisor_stopped` | The runtime supervising the child stopped (mob shutdown) before the turn ended. |
| `restart_interrupted` | The host restarted while the child ran and the child's turn did not survive the restart. The child stays seated for its forker. |

The outcome is recorded once, durably, in the forker's own transcript as a
`BackgroundJob` system notice. Its body is the header "Background fork_off job
`<job_id>` finished (`<status>`):", where the status is `completed`,
`terminated` for a `max_run_secs` autokill, or `failed` for every other
outcome. Its typed block, `SystemNoticeBlock::BackgroundJob`, carries the
`job_id`, the tool name, that status, the outcome JSON as `detail` (stored only
there), and `persisted: true`, which marks it as a durable completion record
rather than a progress notice that is refreshed at each model call
(`SystemNoticeMessage::persisted_background_job_id` finds it). The model sees
the header followed by the outcome, once.
It stays in the transcript across later model calls, turns, and reloads, and it
remains readable after the child is retired: in the transcript the model sees,
and through the forker's session history (`session/history` over JSON-RPC,
`GET /sessions/{id}/history` over REST).

The record is delivered to the forker's session as a runtime input with steer
handling and the idempotency key `fork_off:<job_id>`, so it is written exactly
once however often delivery runs:

- a forker in the middle of a turn sees it in that same turn: the notice is
  written into the running turn at its next model call (after that point's
  tool results), every later model call of the turn sees it, and it commits
  with the turn, with no second turn. Only when the turn ends before another
  model call (the model answered without a further tool call) does the forker
  get exactly one follow-up turn that sees it;
- an idle forker runs exactly one wake turn that sees the outcome, and the
  notice is committed with that turn;
- a forker that is no longer live (the runtime retired its idle executor, or
  the host restarted) is revived through its mob first.

**Blocking.** A one-shot host may exit when the turn ends and so cannot deliver
a later completion. The `rkat` CLI is one-shot unless it stays alive: `rkat
run` without `--keep-alive` and the other one-shot `rkat mob` commands. There
`fork_off` waits for the child and returns the completed result as its tool
result (`bounded_result`, `usage`, `turns`, `tool_calls`, and the child's
identity and sessions). A child that does not complete is a tool error whose
text carries the same outcome. A blocking result names why it blocked in
`blocked_because`: `host_declared_unavailable`; `no_runtime_adapter` for a
host that declares detached delivery but has no runtime (which also logs an
error); or `no_owner_revival_host` for a caller that is a plain session on a
host without a `DetachedOwnerHost`. A blocking call leaves no detached job
owed, so no result can be lost.

Neither form has a default deadline: the child runs for as long as its task
needs. The agent loop's default tool deadline does not cut a blocking call. An
operator's explicit `tools.tool_timeouts.fork_off` entry still bounds it, as
does a deadline the host itself imposes on tool calls. `max_run_secs` is an
opt-in autokill, honored in both forms, that cancels the child's run and
retires the child once it has run that long; omit it for no limit. `fork_off`
rejects arguments it does not define, so a misspelled or invented field is an
argument error instead of a silently ignored intent.

**Across a restart.** A detached child carries a durable job record (job id,
forker session, start time, opt-in limit, fork prefix length, and result bound)
on its spawn event and roster entry. When a host restores its mobs, or inserts
a restored mob handle as MobKit does, a one-time re-link pass settles every
child whose job began in a previous process:

- a child whose reply to the job is already in its durable transcript has that
  reply delivered, however late the restart landed, and stays seated;
- a child still running is observed until its turn ends, with `max_run_secs`
  measured from the original start (an elapsed limit autokills it and its
  descendants);
- otherwise `restart_interrupted` is delivered and the child stays seated.

Delivery uses the same record and idempotency key, so an outcome recorded
before the restart is never recorded twice, and an idle forker is woken to see
it. A job whose completion was already admitted is finished: the pass leaves
it and its child alone (no limit, no cancel, no second record), and a
respawned child carries no job, although its ownership still follows the
identity. A job whose forker no longer exists is reported as owner gone
instead of retried. A forker that cannot be revived yet, because its mob is
not running (for example restored Stopped after a clean shutdown) or is still
being revived, is reported as awaiting, and delivery is retried when the mob
starts running or after a bounded backoff. `MobMcpState::relink_restored_fork_children` runs the pass
explicitly.

`council` follows the same split. Detached, it returns `status: "running"`,
the `council_id`, a `job_id`, and a `note`, and the sealed outcome (`result`,
`cleanup`, `replayed`) is recorded and delivered the same way, as a
"Background council job `<job_id>` finished" notice with the idempotency key
`council:<job_id>`. A council that fails after the call returned is recorded
with `{"error": ...}` as its outcome and status `failed`, and so is a sealed
council whose exit reason is a failure (`participant_seating_failed`,
`wiring_incomplete`, `exchange_failed`, `coordinator_interrupted`), whose
record keeps the full sealed outcome. A detached council also survives a
restart: its custody record carries the convener's job, and the post-restore
recovery sweep delivers the council's sealed result, or
`coordinator_interrupted` once the dead coordinator's claim lease has expired
(councils are never re-executed). The sweep runs on every host whose council
store is durable and whose `MobMcpState` was built with `into_shared()` (a
state wrapped in a plain `Arc::new` never runs it), and it retries after the
earliest observed lease expiry;
`MobMcpState::relink_detached_councils` runs the re-link explicitly. Blocking, `council` returns the sealed outcome as its tool
result, with `blocked_because`. A detached convener that is not live is
revived first: through its mob when it is a mob member, or through the host's
`DetachedOwnerHost` when it is a plain session. A plain-session convener on a
host without that hook (a top-level REST, MCP-server, or `rkat run
--keep-alive` session) is not given the detached route at all: its council
runs in the call and returns with `blocked_because: "no_owner_revival_host"`.
`MobMcpState::detached_delivery_blocked_because_for(owner)` reports the route
for a given caller. Its own `timeout_seconds` bounds it in both
forms, and the agent loop's default tool deadline does not. See
[Temporary Councils](/guides/temporary-councils#agent-tool).

An embedding host declares the capability on its `MobMcpState`
(`with_detached_completion_delivery` / `set_detached_completion_delivery` with
`DetachedCompletionDelivery::Available` or `Unavailable`). The default follows
the presence of a runtime adapter, and `detached_delivery_blocked_because`
reports why the tools would block. A host whose detached-job owners can be
plain sessions installs a `DetachedOwnerHost` (`with_detached_owner_host` /
`set_detached_owner_host`) so their results are delivered, live and by the
restart re-link, after the runtime retired an idle executor. Install it before
inserting restored mob handles: `mob_insert_handle` reads it at insert.
`compose_rpc_mob_state` does this for the JSON-RPC host.

### Forked children belong to their forker

Ownership follows the process tree. A child created by `fork_off` belongs to
the member that forked it, and so does every member that child forks in turn;
ownership never flows upward. The spawner is recorded durably when the child is
seated, survives resume and respawn (including a respawn with a successor
spec), and is checked against the caller's own session binding, never against
tool arguments. Without manage scope over the mob, the forker can still:

- read any of its descendants with `mob_check_member`, which answers at once
  even while the member's turn runs (`progress.run_state` is `run_open`, the
  output preview and token count are from its last completed turn, and a
  `note` says so);
- retire any of its descendants with `mob_retire_member`;
- list its descendants, and only those, with `mob_list_members`.

A profile's member operator tools (`member_status`, `retire_member`,
`force_cancel_member`, `list_members`) apply the same rule. With manage scope,
all of these tools reach every member, as before.

Retirement cascades like a process tree. Retiring a member retires every member
it transitively spawned, deepest first, then the member itself, each through
the same exact-incarnation retire; every retirement is attempted and the first
failure is reported, so a retry converges. The cascade lives in the core
retire, so every path takes it: `mob_retire_member`, `retire_member`, the
`max_run_secs` autokill, the retirement of a child whose turn failed,
host-side retirement (`mob/retire` over JSON-RPC, `meerkat_mob_retire` over
MCP), and `MobHandle::retire` itself, which MobKit's retire paths and idle
sweep use. A descendant forked while its subtree is being retired is retired
with it.

A child whose own turn fails is retired automatically. A child whose turn
completes stays seated, for inspection or further work, until its forker
retires it. Meerkat adds no retention limit of its own; a host can apply one
(MobKit's `idle_retire_secs`, for example).

Host/operator surfaces for placement, binding, grants, observation, live
member sessions, and hard cancellation are control-plane APIs, not agent
builtins, so they are intentionally excluded from this inventory.

**Source:** `crates/meerkat-mob-mcp/src/agent_tools.rs`

## Shell tools

Shell tools execute commands and manage background jobs. They are all
`default_enabled: false`. The effective shell category must first be composed;
the factory then uses `ToolPolicyLayer` to activate the four standard shell
tools. A policy cannot create an absent shell category, and `monitor_start`
still requires its own explicit policy enable.

<Warning>
`background: true` is available only when the session has a persistent realm
job store and blob store. Submission, status, result references, cancellation,
and terminal delivery are durable. The shell worker itself is
`non_resumable`: if its process is lost across restart, the committed attempt
becomes `worker_lost` after its existing lease expires and is never silently
replayed.
</Warning>

`command: "some-command &"` and `background: true` are different contracts.
An ampersand is only syntax interpreted by the selected shell. Meerkat still
executes that shell invocation through the foreground tool path, returns the
ordinary foreground result, and does not create a job ID or a record visible to
`shell_jobs`, `shell_job_status`, or `shell_job_cancel`. Any child the shell
leaves running is unmanaged and its lifetime is not guaranteed.

Use `background: true` when the command must be managed as a Meerkat shell job.
It commits and returns a stable job ID and enables durable status/list/cancel
operations. This does not claim that the subprocess survives a host restart:
the durable record survives and reports the non-resumable worker loss.

### Timeout hierarchy

Tool execution has layered deadlines; the narrowest applicable layer wins.

| Layer | Default/current contract | Meaning |
|---|---:|---|
| Foreground shell command | 30 seconds | Shell-internal command deadline |
| SDK/builder `ToolDispatcher` | 30 seconds | Enforced dispatcher-layer deadline when this wrapper is composed |
| Schedule occurrence lease | 60 seconds | Scheduling/redelivery ownership lease; not a long-job execution deadline |
| Normal Meerkat tool batch | 600 seconds | Agent-loop outer deadline; per-tool overrides may narrow it |
| MobKit provider callback | 120 seconds | Public host-callback work window |
| MobKit Python/TypeScript callback cancellation | 125 seconds | Host cancellation margin, not extra work time |
| MobKit gateway callback wire | 130 seconds | Transport margin, not extra work time |
| LLM stream inactivity | 300 seconds | Provider-stream watchdog; unrelated to tool callbacks |

Changing the normal Meerkat tool timeout cannot extend a narrower shell,
SDK/builder `ToolDispatcher`, or MobKit callback deadline. The foreground shell
and dispatcher deadlines are distinct enforced layers, even though both
defaults currently come from `ToolTimeoutPolicy`. Background shell submission
returns within the normal tool call, but the spawned command keeps its own shell
timeout. The command runs under one fenced non-resumable attempt; terminal state
is committed before runtime notification delivery.

A foreground result reaches the model as compact text: one status line, then
stdout as is, then stderr under a `[stderr]` line only when it is non-empty.
Flags such as invalid UTF-8 appear only when set. Transcripts, tool events and
every surface carry this text as a `Text` content block. Only code that calls
the tool directly (`BuiltinTool::call`) gets the typed `ShellOutput` through
`ToolOutput::into_json`.

stdout is capped at `[shell] max_output_chars` characters (default 40000, about
10K tokens), and stderr at half of that. The cap applies to foreground calls
and background jobs alike. Longer output keeps up to half the cap from its
start and the rest from its end. A cut moves to a line boundary when the line
it lands in fits the cap. The marker between the two sides names the omitted
lines, the line where the head ends and the line where the tail starts, and a
`sed -n` range that pages exactly the omitted lines:

```text
[... lines 153-4900 of 5000 omitted (4748 lines, 22893 of 23893 characters); the head ends at line 152 and the tail starts at line 4901. To see them, re-run the command piped through `sed -n '153,4900p'`, or narrow it with `grep -n`. ...]
```

When a line is longer than the cap, the cut falls inside it and the marker says
which lines were cut and suggests narrowing the command instead.

```text Returns (foreground)
...stdout...
[stderr]
...stderr...
```


</CodeGroup>

</Note>

A pure rename is not supported: a move must include at least one update hunk.
Multi-file patches are applied in order and are not transactional, so an error
after an earlier operation can leave that earlier operation applied.

The JSON result reports `status: "success"` plus `added_files`,
`modified_files`, and `deleted_files`.

**Source:** `crates/meerkat-tools/src/builtin/utility/apply_patch.rs`
</Accordion>

<Accordion title="view_image">
Read an image file from the project directory and return its contents as a base64-encoded `ContentBlock::Image`. This enables vision-capable models to analyze images from disk during tool use.

**Default enabled:** Yes (when builtins are on and the model supports image tool results)

<ParamField body="path" type="String" required>
  Path to the image file, relative to the project root.
</ParamField>

**Supported formats:** PNG, JPEG, GIF, WebP, SVG.

**Size limit:** 5 MB. Files exceeding this limit return an error.

**Capability gating:** `view_image` is currently hidden via `ToolScope` when the active model does not support image content in tool results (`ModelProfile.image_tool_results == false`).

**Returns:** A content-block result containing a single `ContentBlock::Image` with the base64-encoded image data and detected media type.

**Source:** `crates/meerkat-tools/src/builtin/utility/view_image.rs`
</Accordion>

<Accordion title="blob_save_file">
Save decoded bytes from the session blob store to a file inside the project root. This is the model-facing equivalent of materializing a blob with `rkat blob get`, but it remains sandboxed to the active project.

**Default enabled:** Yes when builtins are on and the runtime-backed session has a blob store.

<ParamField body="blob_id" type="String" required>
  Blob ID to save.
</ParamField>

<ParamField body="path" type="String" required>
  Destination path, relative to the project root or absolute within the project root.
</ParamField>

<ParamField body="overwrite" type="Boolean" default="false">
  Whether to replace an existing file.
</ParamField>

**Returns:** JSON metadata: `blob_id`, `media_type`, `path`, and `bytes_written`. Raw bytes are never returned in the tool result.

**Source:** `crates/meerkat-tools/src/builtin/utility/blob_file.rs`
</Accordion>

<Accordion title="blob_load_file">
Read a file inside the project root and store its bytes in the realm blob store.

**Default enabled:** Yes when builtins are on and the runtime-backed session has a blob store.

<ParamField body="path" type="String" required>
  Source path, relative to the project root or absolute within the project root.
</ParamField>

<ParamField body="media_type" type="String" default="inferred from extension">

<Accordion title="blob_inspect">

**Default enabled:** Yes when builtins are on and the runtime-backed session has a blob store.

<ParamField body="blob_id" type="String" required>
  Blob ID to inspect.
</ParamField>

**Returns:** JSON metadata: `blob_id`, `media_type`, and decoded `size_bytes`.

**Source:** `crates/meerkat-tools/src/builtin/utility/blob_file.rs`
</Accordion>

<Accordion title="generate_image">
Generate or edit an assistant-owned image through the session image-generation substrate. Generated bytes are committed to the realm blob store and returned as durable `AssistantImageRef` values.

**Tool policy default:** Yes after the category has been composed. **Factory
category default:** `Inherit`, which is visible in the normal composite when
the image-generation machine, executor, planner, session identity, and blob
store are wired. A minimal no-builtins/no-shell composition needs explicit
`Enable`; Mob profiles and in-process builds can use that override without
opening general builtins. See the guide for the current surface matrix.

<ParamField body="request" type="Object" required>
  Image generation request. The simple shape supports `intent`, `prompt`, `instruction`, `source_images`, `reference_images`, `size`, `quality`, `format`, `count`/`n`, `target`, `provider`, `model`, and `provider_params`.
</ParamField>

**Common request:**

```json
{
  "request": {
    "intent": "generate",
    "prompt": "a cozy tabby cat by a sunlit window",
    "size": "1024x1024",
    "quality": "auto",
    "format": "png",
    "count": 1,
    "provider": "openai"
  }
}
```

**Targets:** `auto` uses the current provider's image profile when available. Use `provider: "openai"` or `provider: "gemini"` to force a provider default. Use `provider` plus `model` to force a provider-owned image model.

**Supported universal options:** `size` accepts `auto`, `1024x1024`, `1024x1536`, `1536x1024`, or `WIDTHxHEIGHT`; `quality` accepts `auto`, `low`, `medium`, `high`; `format` accepts `auto`, `png`, `jpeg`, `jpg`, `webp`; `count` is currently limited to `1`.

**Provider params:** Use top-level `size`, `quality`, `format`, and `intent` for normal requests; these are Meerkat fields, not raw provider params. For the current `gpt-image-2` default, OpenAI `provider_params` should normally be limited to `background`, `output_compression`, `moderation`, hosted-tool-only `action`, hosted-tool-only `reasoning_effort`, and hosted-tool-only `web_search`; `background` is `auto` or `opaque` only, `output_compression` applies when `format` is `jpeg`/`webp`, `moderation` is `auto` or `low`, `action` is usually omitted in favor of top-level `intent`, and `input_fidelity` is not accepted by Meerkat. Gemini accepts `aspect_ratio` and `image_size`.

**Returns:** `ImageGenerationToolResult` JSON containing `operation_id`, `terminal`, `images`, `provider_text`, `revised_prompt`, `native_metadata`, and `warnings`. Each generated image includes `blob_ref.blob_id`, which can be saved from inside the session with `blob_save_file` or fetched externally with `rkat blob get <blob_id> --output image.png`.

**Source:** `crates/meerkat-tools/src/builtin/image_generation.rs`

See [Image generation](/guides/image-generation) for provider behavior, examples, and troubleshooting.
</Accordion>

## Web search fallback tool

The active model may receive provider-native web search directly in its
provider request. When the active model lacks native search and web search is
explicitly enabled, `AgentFactory` can instead compose the Meerkat-owned
`web_search` fallback against a configured OpenAI, Gemini, or Anthropic search
executor. The explicit enable fails closed if no executor can be provisioned.

<Accordion title="web_search">
<ParamField body="query" type="String" required>
  Non-empty natural-language search or research query.
</ParamField>

<ParamField body="provider" type="String">
  Optional assertion: `openai`, `gemini`, or `anthropic`. When present it must
  match the fallback provider selected for the session.
</ParamField>

<ParamField body="context" type="String">
  Optional brief conversation context used to disambiguate the query.
</ParamField>

The result is `WebSearchResult`: `status`, `query`, optional `provider` and
`model`, optional `answer`, typed `evidence`, provider-observed
`native_events`, optional `error`, and `checked_at`. Native events are evidence
from the provider, not Meerkat-owned truth.

This tool is classified read-only. Visibility is controlled by
`override_web_search`, independently from general builtins.

**Source:** `crates/meerkat-tools/src/builtin/web_search.rs`
</Accordion>

## Comms tools

Comms tools enable inter-agent communication. They require the `comms` Cargo feature (`dep:meerkat-comms`) and the factory-level `enable_comms` flag. Unlike other tool categories, comms tools are provided as a separate `CommsToolSurface` dispatcher (implementing `AgentToolDispatcher`) and composed via `DynamicToolComposite`, NOT bundled into `CompositeDispatcher`.

Tool availability is reported per tool through the catalog
(`comms_tool_unavailable_reason`): `send_message`, `reply_to_peer`, and `peers` are advertised
even before any peers are configured, while `send_request` and `send_response`
require a runtime-bound command authority and are otherwise marked unavailable
with the typed reason `RuntimeCommandAuthorityUnavailable`.

Tool definitions (name, description, input schema) are dynamically loaded from `meerkat_comms::tools_list()`.

<Accordion title="send_message">
Send a fire-and-forget collaboration message to a trusted peer.

**Default enabled:** Yes (when comms is active)

<ParamField body="peer_id" type="String" required>
  Canonical peer ID from the `peers` tool.
</ParamField>

<ParamField body="display_name" type="String">
  Optional display name, retained only for diagnostics.
</ParamField>

<ParamField body="body" type="String" required>
  Message content.
</ParamField>

<ParamField body="blocks" type="Array">
  Optional multimodal blocks: text entries or `image_ref` entries (`source: "current_turn"` with `index`, or `source: "blob"` with `blob_id` and `media_type`).
</ParamField>

<ParamField body="handling_mode" type="String" required>
  Use `"queue"` for ordinary delivery or `"steer"` for immediate steer processing on runtime-backed sessions.
</ParamField>

```json
{ "status": "sent", "kind": "peer_message", "receipt": { ... } }
```

**Source:** `crates/meerkat-comms/src/mcp/tools.rs`
</Accordion>

<Accordion title="reply_to_peer">
Reply to the peer message that triggered the current turn. This tool is
pre-addressed by a turn-scoped reply capability, so it deliberately has no
`peer_id` argument.

**Default enabled:** Yes when comms is active. It does not require runtime
request/response command authority.

<ParamField body="body" type="String" required>
  Reply text.
</ParamField>

<ParamField body="blocks" type="Array">
  Optional multimodal text or `image_ref` blocks.
</ParamField>

<ParamField body="handling_mode" type="String" required>
  `queue` for ordinary delivery or `steer` for urgent immediate processing.
</ParamField>

<ParamField body="reply_to" type="String">
  Delivery ID selector. Omit when exactly one peer message triggered the turn.
  When several arrived, retry with one ID listed by `ambiguous_reply`.
</ParamField>

```json
{
  "body": "Acknowledged. The migration is complete.",
  "handling_mode": "queue"
}
```

Typed failures include `no_reply_capability`, `ambiguous_reply`, and
`unknown_reply_to`. Trust is revalidated at dispatch time, so revoking a peer
after turn admission invalidates the previously minted reply capability.

**Source:** `crates/meerkat-comms/src/mcp/tools.rs`
</Accordion>

<Accordion title="send_request">
Send a structured request to a trusted peer. Use when you want explicit `intent + params` and a correlated response via `send_response`. Requires a runtime-bound command authority.

**Default enabled:** Yes (when comms is active and runtime command authority is attached)

<ParamField body="peer_id" type="String" required>

</ParamField>

<ParamField body="display_name" type="String">

</ParamField>

<ParamField body="intent" type="String" required>

</ParamField>

<ParamField body="params" type="Object" required>
  Request parameters, validated against the selected intent.
</ParamField>

<ParamField body="blocks" type="Array">
  Optional multimodal blocks (text and `image_ref` entries).
</ParamField>

<ParamField body="handling_mode" type="String" required>
  Use `"queue"` for ordinary delivery or `"steer"` for immediate steer processing on runtime-backed sessions.
</ParamField>


<Accordion title="send_response">

**Default enabled:** Yes (when comms is active and runtime command authority is attached)

## Skill tools

The five skill tools are registered only when a `SkillRuntime` is present.
Each has `default_enabled: false`, so an embedding that constructs the builtin
dispatcher must explicitly enable the desired names in `BuiltinToolConfig`.
Current factory-built CLI, REST, and JSON-RPC sessions register the set but do
not add that policy enable; preload and typed `skill_refs` still work, but the
interactive skill tools are not advertised there.

Every skill identity is a typed pair of `source_uuid` and `skill_name`. The
runtime canonicalizes source-lineage remaps before reading or invoking it.

<Accordion title="browse_skills and load_skill">
`browse_skills` accepts optional `query` and `source_uuid` filters and returns
active skills as `{source_uuid, skill_name, name, description}` entries.

`load_skill` requires `source_uuid` and `skill_name`. It resolves and renders
the skill, returning the canonical identity, display `name`, rendered `body`,
and `byte_size`.

**Source:** `crates/meerkat-tools/src/builtin/skills/browse.rs`,
`crates/meerkat-tools/src/builtin/skills/load.rs`
</Accordion>

<Accordion title="Skill resources and functions">
`skill_list_resources` takes `source_uuid` and `skill_name` and returns the
skill's artifact descriptors. `skill_read_resource` adds a required `path` and
returns that artifact's content.

`skill_invoke_function` takes `source_uuid`, `skill_name`, `function_name`, and
optional JSON-object `arguments`. Its success response echoes the canonical
identity and function name and carries the skill function's wire-opaque JSON in
`output`.

**Source:** `crates/meerkat-tools/src/builtin/skills/resources.rs`,
`crates/meerkat-tools/src/builtin/skills/functions.rs`
</Accordion>

## Cargo feature gates

Tool availability depends on compile-time features in the `meerkat-tools` crate:

| Feature | Default | Dependencies | Tools unlocked |
|---------|---------|-------------|----------------|
| `comms` | Yes | `dep:meerkat-comms` | `send_message`, `reply_to_peer`, `send_request`, `send_response`, `peers` |
| `mcp` | Yes | `dep:meerkat-mcp` | External MCP tool routing (not builtin tools) |
| `skills` | Yes | skill runtime types | The five policy-opt-in skill tool implementations |

The `memory_search` tool is gated by the `memory-store-session` feature on the `meerkat` facade crate (not `meerkat-tools`), since `MemorySearchDispatcher` lives in `meerkat-memory`.

**Source:** `crates/meerkat-tools/Cargo.toml`
