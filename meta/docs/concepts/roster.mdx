The mob roster is the operational view of the members known to a mob. Roster
reads return lightweight `MobMemberListEntry` projections. Deep execution
inspection is a separate operation that returns `MobMemberSnapshot`.

<Warning>
Member lifecycle is dual-plane. Use the worker plane for ephemeral, disposable
members such as helpers spawned by a parent agent and reaped by an idle-retire
policy. Durable members, including per-user agents and long-lived coordinators,
belong on the identity plane: declare them in an identity roster and reconcile
them. The gateway profile changes the default behavior of
`meta/ensure_member`; see the profile-specific contract below.
</Warning>

## Profiles are templates and members are declared

A `[profiles.<name>]` entry in `mob.toml` is a role template: model, tool
posture, skills, runtime mode, peer description. It produces no member. A
member exists only when something names it:

- the identity roster: the `RosterProvider` callback on `rpc_gateway`
  (Python `.roster(provider)`, TypeScript `.rosterProvider(provider)`), or the
  `identity_roster` top-level `meta/init` param on `meta_gateway` (a list
  of `DurableAgentSpec` objects, restored at boot and extended at runtime by
  `meta/ensure_member`);
- a Rust `Discovery` implementation on `UnifiedRuntimeBuilder` (classic,
  non-identity boot only; neither gateway binary wires one);
- an explicit `meta/ensure_member`.

Nothing derives one member per profile, and neither does meerkat: a mob
definition's `orchestrator` names a profile, not a member. The only automatic
spawn anywhere is `meta_gateway`'s no-config fallback, which ensures a single
`alpha` member of its built-in definition when no `config/mob.toml` or
`definition.json` exists; a workspace definition with an empty
`identity_roster` boots with no members at all.

On `rpc_gateway`, `callback/roster_provider/roster` supplies the serialized
`RosterContext` under `params.context`. Both SDKs pass a typed context to
`roster(context)`: read `context.mob_definition` in Python or
`context.mobDefinition` in TypeScript for the booted mob's compiled definition.
Its `id`, `orchestrator`, and `profiles` are top-level fields, unlike the
`[mob]` nesting in the source TOML. Prior-identity context is call-site-dependent;
an empty list does not establish that no identities are registered. See
[Roster provider context](#roster-provider-context) for the field contract.

A host may instead derive a profile-shaped crew from its own parsed `mob.toml`
as an explicit policy choice, not as a workaround for a missing callback
definition. This example uses the same text passed to `.mob_inline(MOB_TOML)`
and intentionally ignores `context`:

```python
import tomllib

from meerkat_meta import DurableAgentSpec

DEFINITION = tomllib.loads(MOB_TOML)  # the text passed to .mob_inline(MOB_TOML)


def orchestrator_profile(definition):
    # `[mob] orchestrator = "lead"` or `[mob.orchestrator] profile = "lead"`
    orchestrator = definition["mob"].get("orchestrator")
    return orchestrator.get("profile") if isinstance(orchestrator, dict) else orchestrator


class ProfileShapedRoster:
    # One durable identity per profile; the orchestrator is addressable.
    async def roster(self, context):
        orchestrator = orchestrator_profile(DEFINITION)
        return [
            DurableAgentSpec(
                identity=f"{profile_name}:main",
                profile=profile_name,
                addressability=(
                    "addressable" if profile_name == orchestrator else "internal_only"
                ),
            )
            for profile_name in DEFINITION.get("profiles", {})
        ]
```

Profile-to-member is not one-to-one in general (a per-user profile may back
hundreds of identities), which is why this stays a host decision rather than a
default.

### When to call `reconcile_edges`

Declared definition wiring (`[wiring] auto_wire_orchestrator = true` or
`role_wiring` rules) is applied by meerkat only at spawn time and, for the
orchestrator rule, only from the non-orchestrator side, so the result depends on
bring-up order. Meta installs the definition's wiring as a reconcilable edge
policy and converges it with `meta/reconcile_edges` (Python
`handle.reconcile_edges()`, TypeScript `handle.reconcileEdges()`).

- `meta/ensure_member` already runs that reconcile after every successful
  ensure, on both the worker plane and the console identity plane. Calling
  `reconcile_edges` after `ensure_member` is redundant.
- `meta/reconcile_identity` (Python `runtime.reconcile()`) and the
  identity-first gateway boot do not: the gateway reconciles definition edges
  before the roster is materialized. When the definition declares wiring, call
  `reconcile_edges` once after boot and after each `runtime.reconcile()`.
- Without declared wiring there is no definition edge policy; the call returns
  an empty report. Edges from a host `TopologyProvider` converge on every
  identity restore and reconcile on their own.
- With a `TopologyProvider`, the provider (plus operator topology intent) owns
  the identities' edges: reconcile unwires every live edge between two
  identities that neither the provider nor the definition's wiring declares,
  including one wired before a restart. Declare an edge in your provider to
  keep it. Without a provider, reconcile unwires only the edges it wired
  itself.

## Roster operations

All operations are available through the gateway's JSON-RPC interface.

| Method | Result | Description |
|--------|--------|-------------|
| `meta/list_members` | `MobMemberListEntry[]` | List operationally visible members, including retiring members |
| `meta/get_member` | `MobMemberListEntry` | Get one lightweight roster entry by member ID |
| `meta/find_members` | `MobMemberListEntry[]` | Find lightweight roster entries by a label key-value pair |
| `meta/ensure_member` | Gateway-profile dependent | Ensure a durable identity or an ephemeral worker as described below |
| `meta/member_status` | `MobMemberSnapshot` | Inspect one member's deep execution and connectivity state |
| `meta/retire_member` | Acceptance acknowledgement | Retire a member |
| `meta/respawn_member` | Acceptance acknowledgement | Replace a member with a fresh runtime incarnation (identity-first: resets the identity onto a fresh session at a new generation) |
| `meta/reload_member` | `{reloaded, disposition, session_id, generation}` | Non-destructive cold reload: same identity, same durable session, same generation (identity-first only) |
| `meta/member_health` | `MemberHealthReport` | Lifecycle and delivery health from in-process reads; answers while the mob actor loop is stalled |

## `ensure_member` gateway profiles

The same method name has different ownership and result contracts across the
two gateway profiles:

| Gateway profile | Behavior | Result |
|-----------------|----------|--------|
| SDK-facing `rpc_gateway` (`StdioRpc`) | Calls `MobHandle::ensure_member` on the ephemeral worker plane | `MobMemberListEntry`, or `null` if the post-ensure roster lookup finds no entry |
| Console/admin `meta_gateway` with identity-first runtime and roster | By default, upserts a durable identity into the desired roster and reconciles it through the identity runtime | Identity receipt with `agent_identity`, `role`, `identity_first: true`, `outcome`, and `state` |
| Identity-first console/admin request with `plane: "worker"` | Explicitly uses `MobHandle::ensure_member` on the ephemeral worker plane | `MobMemberListEntry`, or `null` if the post-ensure roster lookup finds no entry |

<Warning>
To create an ephemeral worker through an identity-first console/admin gateway,
you must pass `plane: "worker"`. Omitting it creates or retains a durable
identity and returns an identity receipt, not a `MobMemberListEntry`.
</Warning>

The identity receipt's `outcome` is `created`, `resumed`, `dormant`,
`refused` or `unchanged`. The other roster operations keep the contracts shown in the
operation table.

## Lightweight roster entries

`list_members`, `get_member`, and `find_members` project Meerkat's
`MobMemberListEntry`. `ensure_member` projects the same type only on the
worker-plane paths described above. A raw Meta worker-plane response has this
shape:

```json
{
  "agent_identity": "agent-1",
  "role": "worker",
  "runtime_mode": "turn_driven",
  "wired_to": ["agent-2", "agent-3"],
  "labels": {"owner": "user-123"},
  "status": "active",
  "state": "active",
  "is_final": false
}
```

| Field | Type | Description |
|-------|------|-------------|
| `agent_identity` | `string` | Canonical public identity used to address the member |
| `role` | `string` | Role or profile name used to build the member |
| `runtime_mode` | `string` | `autonomous_host` or `turn_driven`; see [Runtime modes](#runtime-modes) for the default and its consequences |
| `wired_to` | `string[]` | Canonical identities of currently wired peers |
| `labels` | `object` | String key-value metadata |
| `status` | `string` | Machine-projected lifecycle status |
| `error` | `string`, optional | Machine-recorded member restore failure; omitted when absent |
| `is_final` | `boolean` | Whether the member has reached a terminal state |
| `kickoff` | `object`, optional | Initial autonomous-turn kickoff state, when present |
| `state` | `string` | Meta compatibility alias of `status`; this is not a field on the Rust `MobMemberListEntry` |

The lightweight entry deliberately omits session IDs and live connectivity
fanout. Use `meta/member_status` when those details are required.

### Runtime modes

`runtime_mode` comes from the profile (`[profiles.<name>] runtime_mode`), or
from a per-spawn override where a surface offers one. `autonomous_host` is
meerkat's default when a profile omits the key, and it is the mode most hosts
end up on without choosing it. The two modes differ in ways that show up on
the roster and on every send:

- A fresh `autonomous_host` member runs one kickoff turn as soon as it is
  spawned, on its `initial_message` if the spawn carried one, otherwise on
  meerkat's fallback prompt (`You have been spawned as '<identity>' (role:
  <role>) in mob '<mob>'.`). The `kickoff` field on the roster entry reports
  that turn. Later sends are ordinary durable inputs that queue behind it;
  nothing is dropped, but the member answers in order.
- Autonomous inbox delivery carries no user-channel work boundary, so meerkat
  refuses injected context and completion-bearing sends on that path. Meta
  therefore skips ambient per-turn agent-memory recall for `autonomous_host`
  members with the typed reason `runtime_mode_autonomous_host` (the turn still
  runs, without memory). Ambient per-turn memory requires
  `runtime_mode = "turn_driven"` until meerkat's carrier change lands; the
  Unreleased entry in the repository `CHANGELOG.md` records this.
- `turn_driven` members run exactly one turn per delivered input and sit idle
  between inputs. It is the mode meerkat's tracked, completion-bearing turn
  carriers support; on `autonomous_host` those are refused with `tracked turn
  completion is not supported by autonomous inbox delivery`.

Pin `runtime_mode = "turn_driven"` explicitly on every profile that hosts a
durable, addressable identity unless the member is meant to run its own inbox
loop.

Operational list projections retain `active`, `retiring`, and `broken` rows as
applicable. They filter terminal `completed` and `unknown` rows, even though
those values remain part of the status vocabulary.

## Durable workers

A profile can declare `durable = true` (meerkat 0.9.5):

```toml
[profiles.worker]
model = "gpt-5.5"
runtime_mode = "turn_driven"
durable = true
```

The flag belongs to the profile alone. `DurableAgentSpec`, `meta/ensure_member`
and the SDKs take no durable argument, and an omitted key means an ordinary
profile.

- Meerkat spawns the profile's members with a durable identity, keyed by the
  member's identity, so a host can list and re-attach them after a restart.
  Every identity-first member is already spawned that way, so for an identity
  the flag changes nothing in how Meta creates, wakes or resets it.
- A durable profile needs a mob whose member sessions outlive the process:
  a runtime built with `persistent_state` or a storage provider. On any other
  mob Meerkat refuses the spawn before anything is created, whether the
  profile is inline or a realm profile:
  `MobError::NonDurableService`, code `CAPABILITY_UNAVAILABLE` (`-32020`),
  `data.kind = "mob_non_durable_service"` with the `member_id` and the
  `profile`. That includes Meta's default composition: without
  `persistent_state` or a storage provider its member sessions live in
  memory, so it answers Meerkat's `keeps_durable_member_sessions` false.
  - On the identity plane the refusal is a deterministic build refusal. The
    wake answers `HostRejectedBuild` with a reason that names the remedy: run
    the mob on a persistent realm, or drop `durable` from the profile. Nothing
    retries it and nothing is recorded; every wake answers it again.
  - On the worker plane, `meta/ensure_member` answers Meerkat's own code and
    `data` instead of the generic `-32602`.
- The mobpack editor document carries the flag as the member key `durable`,
  present only when true. The export writes `durable = true` back into the
  profile, and `update_member` accepts a boolean `durable` patch. Validation
  refuses a member whose `durable` disagrees with `mob.toml`
  (`editor_profile_durable_mismatch`) or is not a boolean (`invalid_durable`).

### Resuming a durable worker's run

Meerkat rebuilds a durable worker on its session after a crash, kill or
restart, and continues the run it was in from its last committed round.
Meerkat keeps no WorkGraph claim alive while the worker is down, so a worker
that was down longer than its lease can come back to work that has moved on.
Before such a run continues, Meerkat asks the mob's resume check. It asks for
every member spawned with a durable identity: the members of a
`durable = true` profile, and every identity-first member, whose spawn always
carries one. When the mob runtime is composed with a WorkGraph service, Meta
answers the check from that WorkGraph:

- A run dispatched for an item (its input carries the WorkGraph attention
  projection) continues only while the item lives in the mob's realm and is
  live, unclaimed or claimed by the worker under a lease that has not lapsed,
  and while its attention binding is active or paused and still targets the
  worker.
- A run that named no item continues unless a claim the worker holds has
  lapsed. A worker that holds no claim continues.
- Otherwise the run is superseded. Meerkat settles it the way a stop does:
  its bound inputs are abandoned as refused resumes, the run ends failed with
  the check's reason, and it never resumes. A lapsed lease is committed
  first, with the WorkGraph's lease-expiry observation, so the item can be
  claimed again, and every later attempt of the same resume answers
  superseded too.
- When the WorkGraph cannot be read, or the run's attention projection does
  not decode, the check answers unavailable. Meerkat asks again, up to three
  attempts, then settles the run the same way.

The check knows the worker by its member owner key
(`agent:mob/<mob_id>/agent/<identity>`) and by its session (`session:<id>`);
a claim under any other key belongs to another owner. Two limits apply. A
run that named no item, whose lapsed claim another worker took while it was
down, holds no claim any more, so the check cannot see the move and the run
continues; its later WorkGraph writes are revision-checked and conflict. And
the mobs that agents create through the mob tools have no check: their
durable workers continue unchecked.

## Deep member status

`meta/member_status` serializes Meerkat's `MobMemberSnapshot`. It is a deep
inspection result, not the type returned by roster list operations. Its core
fields are `status`, `output_preview`, `error`, `tokens_used`, `is_final`, and
`current_session_id`. It can also include peer connectivity, kickoff,
external-member observations, resolved model capabilities, execution progress,
placement, reachability, freshness, and lifecycle-capability diagnostics.
When Meerkat could not observe the member's session for the status (meerkat
0.8.45+), `preview_unavailable` names why (`observation_deadline`,
`read_failed`, `session_absent`, `not_observed_while_retiring`), and a missing
`output_preview` then does not mean an empty member. `meta/inspect_identity`
and the console's per-member progress carry the same marker.

The snapshot's Rust `agent_identity` is bridge-internal and skipped during
serialization. The requested member ID identifies the result on the Meta RPC
surface. The snapshot also does not carry the roster entry's `role`,
`runtime_mode`, `wired_to`, or `labels` fields.

## Member statuses

The known `MobMemberStatus` values are:

| Status | SDK constant | Meaning |
|--------|--------------|---------|
| `active` | `MEMBER_STATE_ACTIVE` | Active and potentially running |
| `retiring` | `MEMBER_STATE_RETIRING` | Retirement is in progress |
| `broken` | `MEMBER_STATE_BROKEN` | Durable session restore failed and the member needs repair |
| `completed` | `MEMBER_STATE_COMPLETED` | The session was archived or not found |
| `unknown` | `MEMBER_STATE_UNKNOWN` | The member is not in the roster |

<Note>
`MobMemberStatus` is non-exhaustive. Branch on the known values and tolerate
new status strings. Do not reduce lifecycle handling to only `active` and
`retiring`. The Rust `MobMemberSnapshot` structure is also non-exhaustive.
</Note>

`retiring` can be transient. At the Meerkat Rust layer, a successful
`MobHandle::retire` is the terminal lifecycle barrier and returns unit, so a
later roster read can show the member as absent rather than retiring.

## Role migration

A durable member's role is part of its durable identity, not a configuration
knob: the stored role, the member's comms name, and its mob-member binding are
one fact. A resume that targets a different role than the durable predecessor is
therefore a restamp of identity, and Meerkat refuses it with
`MobError::MemberRoleMigrationRequired` unless that exact resume declares the
migration. If a durable member stopped resuming after a role or profile rename,
this is the refusal to look for.

Migration authority is supplied by the activation, per exact identity, as a
top-level `meta/init` param. It is not a `runtime_options` field:

```json
"role_migrations": [{"identity": "domain:automation", "from_role": "domain"}]
```

Python hosts declare the same thing on the builder, with
`RoleMigrationDeclaration` dataclasses or plain
`{"identity": ..., "from_role": ...}` dicts:

```python
from meerkat_meta import RoleMigrationDeclaration

builder.role_migrations([
    RoleMigrationDeclaration(identity="domain:automation", from_role="domain"),
])
```

The declaration is boot-scoped and never persisted. It is installed on the
session bridge, which lives for exactly one boot, so dropping it from the next
boot payload is how the authority goes away. Lookup is an exact identity match:
no prefix, suffix, or case variant of a declared identity inherits authority.
Meta only carries the declared predecessor role into the resume request.
Meerkat re-verifies it against durable state and refuses with
`MobError::MemberRoleMigrationRejected` on mismatch, so a mistyped `from_role`
cannot authorize an unintended restamp, and Meta never retries a resume that
Meerkat refused. Once the durable and requested roles agree, Meerkat returns
before it reads the declaration at all, so a declaration left in place after the
migration landed is inert rather than a repeated restamp. That is why an
identical repeated declaration is accepted on purpose, while one identity
declared twice with conflicting predecessor roles is refused.

On a restart the mob restores every durable member under its stored role
before the identity plane resumes it, so a declared migration first meets the
member still on its old role. Meta then applies it or refuses it, and never
adopts the member as it is:

- When the identity plane has repair custody (no Meerkat identity intent, or
  an Absent one), Meta retires the restored member to absence, after proving
  the session it will resume exists and carrying its queued input, and resumes
  the same session under the declared role. Meerkat re-verifies the
  predecessor role, and Meta checks that the member runs the declared role.
- When the restored member's role is not the declared `from_role`, the
  declaration does not describe it, and Meta refuses before retiring
  anything.
- When a Present Meerkat identity intent (from
  `mob/adopt_member_identity_declaration`) owns the member, the intent pins
  its profile and MobMachine owns its materialization, so Meta refuses
  rather than retire it. Declare the new profile in the identity intent.

A refusal holds the identity's wake with the typed kind
`identity_role_migration_refused` (`-32603`): the identity reads `dormant`,
its `wake_refusal` names the remedy `resolve_role_migration`, and the
`meta/init` result reports it under `identity_bootstrap` (restore stage
`refused` with that kind), so a refused migration is visible at boot. The
hold stands for the roster spec it was refused against: nothing retries it,
and no later restore or reconcile pass retires the member the refusal
kept. Change the declaration (next boot) or the member's roster
spec to try again.

<Warning>
A malformed or self-contradicting `role_migrations` payload refuses the boot
rather than arming nothing, and the two gateway binaries refuse differently.
`rpc_gateway` parses and checks the key at init scope and answers both refusals
with `-32602` on the request id. `meta_gateway` answers with a null `id` in
both cases: `-32602` when its typed init params fail to deserialize, and
`-32603` from the conflict check that sits inside its identity-first block.
Under `identity_first: false` that block never runs, so a self-contradicting
payload is then not refused at all; `identity_first` defaults to true. The
Python builder raises `ValueError` on a conflicting pair before any of this
reaches a gateway.
</Warning>

Only the identity plane carries migration authority. Every mob-plane resume path
passes no declared predecessor role, so a role change reached through the worker
plane still fails closed. Which declarations arm also depends on the binary:
`rpc_gateway` installs them inside its roster-provider branch, `meta_gateway`
inside its identity-first block. Declarations that reach neither arm nothing,
because there is no identity plane to migrate on.

## Peer identity and comms names

A member's comms (peer) name is `{mob_id}/{role}/{member}` (meerkat's
`MemberCommsName`): the mob definition `id`, the profile name, and the
mob-roster member id. That is the string peers see in the `peers` tool and in
`Peer message from ...` projections; the routing key underneath is the
pubkey-derived peer id.

Identity-first members are registered under an encoded roster id, because a
durable identity such as `domain:security` contains `:` and a comms-name
component may only contain ASCII letters, digits, `-`, and `_`. Meta's
`mk--` codec escapes it (`domain:security` becomes `mk--domain_csecurity`), so
the peer-facing name is `home/domain/mk--domain_csecurity`. Console, RPC, and
SDK surfaces decode the id back to the public identity; the model-facing
projections do not.

The mob id is part of every member's name, so renaming a mob (changing the
definition `id`) re-mints every peer name in it. Nothing rewrites records that
already hold the old strings: identity-keyed agent memory lives in the host
realm, survives the rename, and can recall `{old_mob}/...` names into a later
prompt. Renaming a member's role is a different case and is refused unless
declared, as the previous section describes.

## Mutation results

The underlying Meerkat Rust operations have different success types:

- `MobHandle::retire` returns `Result<(), MobError>`.
- `MobHandle::respawn` returns
  `Result<MemberRespawnReceipt, MobRespawnError>`. The receipt identifies the
  respawned member.

The domain `MemberRespawnReceipt` publicly serializes only `identity`; its
runtime and fence atoms are internal. Meerkat's typed `mob/respawn` surface
wraps that outcome as `status` (`completed` or `topology_restore_failed`), a
`receipt` containing `identity` and an opaque `member_ref`, and optional
`failed_peer_ids`.

Meta's compatibility RPC consumes the worker-plane respawn receipt and
projects both mutations as acceptance acknowledgements. Identity-owned targets
can add identity-first receipt fields such as a session ID and generation for
respawn. The Python and TypeScript SDK wrappers
discard these acknowledgement objects and return `None` or `void`. Re-read the
member when the caller needs the resulting roster or execution state.

## SDK projections

The SDK type named `MemberSnapshot` wraps the lightweight roster response. It
currently exposes `agent_identity`, `role`, `state`, `wired_to`, and `labels`.
It does not expose every field present in the raw `MobMemberListEntry` JSON.
The separate `RichMemberSnapshot` type wraps `meta/member_status`.

    from meerkat_meta import (
        MEMBER_STATE_ACTIVE,
        MEMBER_STATE_BROKEN,
        MEMBER_STATE_COMPLETED,

        MEMBER_STATE_ACTIVE,

    for member in members:

## Reconciliation

Reconciliation compares the desired member set with the current roster and
spawns, retains, or retires members to converge. See the
[unified runtime guide](/guides/unified-runtime) for the complete flow.

### Roster provider context

Every time the identity runtime derives the desired roster it calls the
host's roster provider with a `RosterContext`. Behind the SDK gateway that is
the `callback/roster_provider/roster` request, whose params nest the context
under `context` (the same envelope the topology and customizer callbacks use):

```json
{
  "context": {
    "mob_definition": { "id": "team", "profiles": { "...": {} } },
    "previous_identities": ["identity:luka", "triage:main"]
  }
}
```

| Field | Meaning |
|-------|---------|
| `mob_definition` | The booted mob's compiled definition. Always present behind the bundled `rpc_gateway`; `null` only when an in-process Rust embedder or test harness resolves a roster without a mob definition. |
| `previous_identities` | Call-site-dependent prior-identity context, not an authoritative membership snapshot on every callback. Topology-query and edge-reconciliation snapshots supply currently registered identities. Bootstrap, full roster refresh/reconcile, and reset-time spec adoption currently pass an empty list; an empty list does not establish that no identities are registered. |

The Python SDK delivers this as `RosterContext` from
`meerkat_meta.identity_first_models`; the TypeScript SDK as the exported
`RosterContext` interface (`mobDefinition`, `previousIdentities`). Use
`context.mob_definition` / `context.previous_identities` in Python and
`context.mobDefinition` / `context.previousIdentities` in TypeScript; the
prior-identity field has the same call-site qualification in both SDKs.
