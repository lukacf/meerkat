Fixes #404 (reported by the OB3 operator on 0.8.31): after `retire_member`, the identity stayed in `Retiring` and the roster reconciler (`reconcile_roster_remove`), `embody_identity` and `send` all refused it as "in progress", so a retired identity could neither be removed from the roster nor re-materialized.

Root cause: `Retiring` is both the transient in-transaction marker and the terminal form `retire_locked` leaves behind, and every lock-holding door treated it as in-progress. Since every lifecycle mutation runs under the identity's lifecycle lock, lock-holders can only observe the terminal form, so the refusal protected nothing.

Design: keep `Retiring` as the retired terminal state (console `retired`, `reset_all` LeavingFleet, the delegate sweeper and existing tests read it that way; a `Dormant` end state would make retired identities addressable and reset-able) and make the lock-holding doors accept it: the reconciler can remove or replace it; an operation ADDRESSED to the identity (`send`, `dispatch`, `materialize`, `reload_member`) revives it onto the same session id and continuity generation; indirect hydration (a peer hand-off's `materialize_reachable_peers`, fleet `materialize_all`, the background warm) still refuses it typed through a `retired_terminal_refusal` guard, paging `IdentityMaterializationFailure` exactly as OB3 observed, so a stale hand-off cannot silently resurrect a member an operator retired. `respawn_member` is unchanged.

Tests: `identity_first_retired_identity_is_removed_by_topology_refresh` (OB3's sequence, twice), `retired_identity_send_rematerializes_the_same_session`, `retired_identity_profile_change_is_adopted_by_the_reconciler`, `retired_peer_is_refused_typed_by_hand_off_hydration` (a<->b, a<->c with b retired: b refused typed and paged with initiator a, c completes, b stays Retiring; `materialize_all` skips b; a direct `send(b)` revives it with one resume).
