The TypeScript SDK (`@rkat/meta-sdk`) provides type-safe access to the Meta JSON-RPC gateway from Node.js.

## Installation

```bash
npm install @rkat/meta-sdk
```

<Note>
  The npm package is client-only and does not contain `rpc_gateway`. Download
  `meta-rpc-gateway-<version>-<target>.tar.gz` for Unix or macOS, or
  `meta-rpc-gateway-<version>-<target>.zip` for Windows, and extract its
  `rpc_gateway` binary (`rpc_gateway.exe` on Windows). Alternatively, follow the
  [source-build instructions](/quickstart#prepare-a-matching-sdk-and-gateway). Pass that binary's path to
  `.gateway(...)`. Linux x86_64 and aarch64 and macOS arm64 archives are
  published with the release and listed in `index.json` and `checksums.sha256`;
  macOS x86_64 and Windows archives may arrive later, listed in
  `index-trailing.json` and `checksums-trailing.sha256`.
</Note>

## Quick start

In a fresh project directory, install the SDK and make the project an ES
module (the program below uses top-level `await`):

```bash
npm install @rkat/meta-sdk
npm pkg set type=module
```

Then create `config/mob.toml`:

```toml
[mob]
id = "typescript-quickstart"

[profiles.worker]
model = "gpt-6.2-astra"
runtime_mode = "turn_driven"
external_addressable = true

[profiles.worker.tools]
comms = true
```

Set `OPENAI_API_KEY` in your environment for the model above, or choose a
supported model and its matching provider credentials. Save the following
as `main.ts` in that directory, replacing `/path/to/rpc_gateway` with the
binary you installed, and run it, for example with `npx tsx main.ts`.
Profiles are templates, not pre-created members: the roster names the agent
the program sends to.

```typescript
import { Meta } from "@rkat/meta-sdk";
import type { DurableAgentSpec, RosterProvider } from "@rkat/meta-sdk";

// The roster names the agents of this application.
const roster: RosterProvider = {
  async roster(): Promise<DurableAgentSpec[]> {
    return [
      {
        identity: "assistant",
        profile: "worker",
        addressability: "addressable",
        displayName: "Assistant",
        labels: {},
        context: null,
        additionalInstructions: ["Answer in one short sentence."],
      },
    ];
  },
};

const rt = await Meta.builder()
  .mob("config/mob.toml")
  .persistentState(".meta/state")
  .rosterProvider(roster)
  .gateway("/path/to/rpc_gateway")
  .build();

try {
  const status = await rt.mobHandle().status();
  console.log("Running:", status.running);

  // Send a message and wait for the answer of that turn.
  const answer = await rt.sendAndWait("assistant", "What is a meerkat?");
  console.log(answer);
} finally {
  await rt.shutdown();
}
```

The program prints `Running: true` and the answer, and shuts the gateway
down. The gateway writes its log to the standard error of the program.
`sendAndWait` addresses an agent of the roster and returns the text of the
turn it started (see [Waiting for a turn](#waiting-for-a-turn)); a build
without a roster provider refuses it with
`identity-first runtime not configured`. Run again, the program reuses
the state under `.meta/state`.

The same program as a project to copy is
[`008-typescript-quickstart`](https://github.com/lukacf/meerkat/tree/main/meta/examples/008-typescript-quickstart).
It sends twice, the second time with `sendAndWaitOutcome`, and run twice it
shows that the agent kept what the first run told it.

### Knowledge memory and a Console config

The builder also takes the knowledge memory backend and the path of a Console
config:

```typescript
import { Meta, memory } from "@rkat/meta-sdk";

const rt = await Meta.builder()
  .mob("config/mob.toml")
  .memory(memory.localJson())
  .persistentState(".meta/state")
  .consoleConfig("config/console.toml")
  .gateway("/path/to/rpc_gateway")
  .build();

const results = await rt.mobHandle().memoryQuery({
  entity: "identity:ops",
  topic: "deployment",
  store: "knowledge_graph",
});

await rt.shutdown();
```

The file `consoleConfig` names must exist when the gateway starts. A missing
file refuses the start
(`runtime_options.console_config_path is invalid: I/O error: failed to read config/console.toml: ...`);
an empty file is accepted. On a store with no knowledge yet, `memoryQuery`
answers `{"assertions":[],"conflicts":[],"results":[]}`.

## Host runnables

Run deterministic application code when a durable schedule fires:
`MetaBuilder.hostRunnables(names)` declares the names and
`MetaBuilder.onScheduleFire(name, handler)` installs handlers before the
initial connection. `MetaRuntime.onScheduleFire(name, handler)` registers
or replaces handlers on a runtime you already have. Declaration and runtime
dispatch match Python's `host_runnables` and `on_schedule_fire`; builder
registration also covers schedules that fire during startup. These use the
existing `runtime_options.host_runnables` and `callback/schedule_fire`
gateway contract. Handler functions stay in the host process.

Every member that holds the schedule tools and is not private to a person
can create a schedule that fires any runnable the host registers, with
parameters of its choosing (the handler reads them as the occurrence's
`payload`). The fire does not tell the handler who wrote the schedule.
Register only runnables that any such member may fire, and check the payload
in the handler.

Install handlers before `build()` connects, on every boot:

```typescript
import { Meta, type ScheduleFireHandler } from "@rkat/meta-sdk";

const collect: ScheduleFireHandler = async (occurrence) => {
  console.log(occurrence.schedule_id, occurrence.occurrence_id);
  console.log(occurrence.due_at, occurrence.payload);
};

const runtime = await Meta.builder()
  .mob("config/mob.toml")
  .gateway("/path/to/rpc_gateway")
  .persistentState(".meta/collector")
  .hostRunnables(["local.collect"])
  .onScheduleFire("local.collect", collect)
  .build();
```

The handler receives the raw occurrence with `schedule_id`, `occurrence_id`,
`due_at` and optional `payload`. It may return synchronously or asynchronously;
throwing or rejecting fails the occurrence attempt. A handler returning
nothing acknowledges completion with JSON `null`. Return values cross the
callback bridge but are not stored as schedule results. Use `occurrence_id`
to deduplicate external side effects.

Declaring a name creates no schedule. A schedule targeting
`{target_kind: "host_runnable", runnable: "local.collect"}` must exist on
the persistent gateway's schedule service. An
[announcement source runner](/reference/configuration#mob-announcement-source-runners)
creates such a schedule through `announcementSourcePut` with
`runner: {host_runnable: "local.collect", every_seconds: 60}`. The
[runnable example](https://github.com/lukacf/meerkat/tree/main/meta/sdk/typescript/examples)
declares a source, receives its scheduled callback and ends the source,
without a provider key or an LLM turn.

`build()` returns a connected runtime: a stored schedule may fire before
that promise resolves. Each runtime copies the builder's handlers before
connecting. Later handler registrations on the builder do not affect it. Calling
`runtime.onScheduleFire` replaces that runtime's handler, and the replacement
survives `shutdown()` followed by `connect()` on the same object; reconnect
does not reinstall builder defaults. A fresh process must register on its
builder again. Declaration and handler registration are separate requirements.

Builder registration and declaration can appear in either order, but
`build()` refuses a builder handler whose exact name is absent from
`hostRunnables`, naming it before any gateway transport starts. Declaring
a name without a handler is allowed. Runtime registration remains
independent of declarations and can add or replace a handler after connection;
it does not add a gateway target.

| State when the source runner fires | SDK behavior | Durable gateway outcome |
| --- | --- | --- |
| Name declared, no handler registered | Returns `no schedule-fire handler registered for runnable: <name>` through the callback bridge | `delivery_failed`, with failure class `runtime_rejected` |
| Name undeclared, even if registered through `runtime.onScheduleFire` | Receives no callback | `misfired`, with failure class `target_missing`, under the source runner's default `mark_misfired` policy |

Such an occurrence ends after its one attempt: it is not delivered later
when a handler is registered. The interval schedule stays active and its
later occurrences stay pending.

### Upgrading a host

These TypeScript methods are in the SDK from 0.9.18.
They work with Meta gateways 0.9.15 and 0.9.16; compatibility with earlier
gateway versions is not established. At the next start, an occurrence that
came due while the gateway was stopped is delivered to the handler the
builder registered if it remains eligible under the schedule's misfire
policy. This exposes an existing gateway
contract: existing callers, stored schedules and wire schemas do not need
migration. Omitting `hostRunnables`, or passing an empty list, sends no
declaration and changes no default. The gateway continues to validate
duplicate and reserved names. On every restart, declare the names used by
stored schedules and call the builder's `onScheduleFire` before `build()`;
upgrading alone supplies neither declaration nor handler. Waiting until
`build()` returns to register on the runtime leaves a startup gap for stored
schedules.

## Operator instructions

Standing instructions for the members of the gateway's mob: the host writes
one body per slot (a `namespace` it owns and a `key`) at a revision, for
every member, the members of one profile, or one identity. Each member it
selects applies the instruction at its next run start, never inside a run.
Host methods only: no agent tool sets, revokes or reads them.

```typescript
const receipt = await rt.setInstruction("app.example", "tone", 1, "Answer formally.", {
  kind: "profile",
  profile: "worker",
});
await rt.setInstruction("app.example", "persona", 1, "You review releases.", {
  kind: "member",
  identity: "triage:main",
});
const status = await rt.instructionStatus({ identity: "triage:main" });
await rt.revokeInstruction("app.example", "tone", 2);
```

A write resolves once the record is durable (`disposition` `"committed"`, or
`"duplicate"` for an exact repeat); a refusal rejects with an RPC error whose
`data.instruction_set_code` names it (for example `stale_revision`). A
member target is for that member alone. From 0.9.15 Meerkat has
`include_forks`, a record for a member and its forks: `setInstruction`
refuses a target that carries it, and such a record is written by a Rust
host that embeds Meta, through the mob handle's `set_operator_instruction`
(`instructionStatus` shows it). The
status read never wakes a member and names each member by its `identity`;
its advisory values (a pending or blocked `reason`, `residency`) may be new
to this SDK, so keep them as they are. These replace
`activateMemberInstruction` (`meta/member_activate_instruction`, deprecated
since 0.9.11). See [Operator instructions](/api/rpc#operator-instructions).

## Compacting a member's conversation

From 0.9.15. `compactMember` compacts a member's conversation now: the member
runs one maintenance turn in which the older turns are summarized and the
most recent ones are kept. It costs one model turn and two in-place rebuilds
of the member, one before that turn and one after it, on the same
conversation.
A `meta/compact_member` call that is admitted rebuilds the identity, whether
it then compacts, compacts nothing or fails. On a 0.9.15 gateway a completed
call keeps an identity's listing and management of the mobs it created with
its own tools (one run; a call that times out, or completes without
compacting, rebuilds by the same step: read from the source, not run), unless
the same-session step does not serve its member (see Known limitations in
Meta's changelog, the entry on the loss of an identity's mobs after a
respawn); against a gateway on 0.9.9 through 0.9.14 the call costs it that,
and upgrading does not give it back (see the `meta/compact_member` section of
the RPC reference). Where the cost applies, have the identity destroy a mob
it created before the call if it must not be left running unmanaged.
Call it against a 0.9.15 gateway: on 0.9.9 through 0.9.14 a call that fails
leaves the agent with the call's low compaction threshold.
It is a host method only (`meta/compact_member`): the Console's RPC route
does not forward it.

```typescript
const result = await rt.compactMember("triage:main");
result.compaction_applied; // check it: false means not compacted
result.messages_before, result.messages_after;

// A lower threshold for a shorter conversation, a longer watch for a long turn.
// A conversation of only a few turns may not get smaller whatever the floor,
// and the call can then fail with compact_member_completion_failed.
await rt.compactMember("triage:main", { floorTokens: 256, timeoutMs: 180_000 });
```

A changed instruction that waits for a compaction takes effect with it: an
update whose `instructions` outcome is `applies_after_compaction`, because
the member's model takes a system instruction only ahead of the
conversation.

`floorTokens` is the member's compaction threshold for that one turn (gateway
default 1024 tokens). A conversation shorter than the floor is left as it is,
so always check the result's `compaction_applied`: `false` means the
conversation holds no fewer messages than before the call. `timeoutMs`
(gateway default 60000) is how long the gateway watches the maintenance turn;
past it the call rejects even if the compaction completes later. The gateway
holds the call for longer than `timeoutMs`, so the call waits for the reply
for `timeoutMs` plus 30 seconds, whatever the transport's own request timeout
is.

The result is the gateway's, as it is: `identity`, `session_id`,
`floor_tokens`, `messages_before`, `messages_after`, `compaction_applied`,
`head_revision` and `last_rewrite_reason`. A failure rejects with an RPC
error whose `data.kind` names it, for example `compact_member_busy`,
`compact_member_timeout` or `compact_member_completion_failed`, with
`data.stage` and `data.operation_id`. See
[`meta/compact_member`](/api/rpc#meta%2Fcompact_member).

## Fork instruction policy

A member forked with `fork_off`, a delegation fork or a council does not run
the instructions its source activated (`meta/member_activate_instruction`,
skill bodies activated that way included) unless the gateway's fork instruction
policy says so. Under the default, `"require_explicit_activation"`, such a fork
is refused with `fork_instruction_refused` before anything is committed. Set
the policy on the builder; it is sent as
`runtime_options.fork_instruction_policy`:

```typescript
import { Meta } from "@rkat/meta-sdk";

const rt = await Meta.builder()
  .mob("config/mob.toml")
  .forkInstructionPolicy("reactivate_inherited")
  .build();
```

`forkInstructionPolicy` takes a `ForkInstructionPolicy`:
`"require_explicit_activation"`, `"reactivate_inherited"` or `"refuse"`;
another value throws `RangeError`. Unset, nothing is sent and the gateway
default applies. The setting applies to every fork of the gateway's mob and
cannot be chosen per fork. See
[Fork instruction policy](/reference/configuration#fork-instruction-policy)
for what each value does and what `reactivate_inherited` trusts.

## Durable decisions

`MobHandle` calls the [durable decision methods](/api/rpc#durable-decision-methods)
of the stdio gateway: `decisionsList({kind, phase, approverId, requester,
after, limit})`, `decisionsGet(decisionId, {includeRequest})`,
`decisionsRendering(decisionId, {maxPartBytes})`,
`decisionsPresent(decisionId, presentation)`, `decisionsWithdraw(decisionId)`
and `decisionsDecide(decisionId, {approve, presentedDigest, reason,
attestation})`. Each resolves to the gateway's result object.

```typescript
import { Meta } from "@rkat/meta-sdk";

const rt = await Meta.builder()
  .mob("config/mob.toml")
  .persistentState("./state")
  .accessControl("config/access.toml")
  .decisionIngresses([{ ingress: "chat", attests: "person", maxClockSkewMs: 5000 }])
  .build();
const mob = rt.mobHandle();

// The methods answer the gateway's result object, untyped.
type OpenDecision = { decision_id: string; subject_digest: string; approver_id: string };

rt.onDecisionNotice((notice) => console.log(notice.event, notice.decision_id));
const page = await mob.decisionsList({ phase: "open" }); // notices are written before the answer
const decision = (page.decisions as OpenDecision[])[0];
const decisionId = decision.decision_id;
const subjectDigest = decision.subject_digest;

// Show the person the whole text of the rendering.
const rendering = await mob.decisionsRendering(decisionId);
// ... post rendering.rendering to the chat ...
const shownAtMs = Date.now(); // once the post has succeeded
// ... wait for the answer ...
const observedAtMs = Date.now(); // the time of the answer's event

await mob.decisionsDecide(decisionId, {
  approve: true,
  presentedDigest: subjectDigest,
  attestation: {
    ingress: "chat",
    subject: "U123",
    scope: "chat-session-1",
    eventRef: "chat:event-1",
    observedAtMs,
    presentation: {
      audience: { kind: "approver", approver_id: decision.approver_id },
      subject_digest: subjectDigest,
      parts_shown: rendering.parts,
      channel_ref: "chat:owners",
      message_ref: "chat:message-1",
      at_ms: shownAtMs,
    },
  },
});
```

The approver map of `config/access.toml` lists `U123` on the `chat` ingress
for the decision's approver id. An attested decide is accepted only for a
decision that was presented to its approver: by the `presentation` the
attestation carries, as here; by one recorded before with
`decisionsPresent(decisionId, presentation)`, which takes the same object;
or by the gateway's own showing to the stdio operator (its `presented`
notice), where the approver map lists the operator for that approver id.
With none of these, the decide is refused `presentation_incomplete`. The
keys of a presentation are the gateway's own (snake_case) and are listed
under [`meta/decisions/decide`](/api/rpc#meta%2Fdecisions%2Fdecide).

`decisionIngresses` declares the ingresses as `runtime_options.decisions`.
`MetaRuntime.onDecisionNotice(handler)` receives each `meta/decisions/notice`.
The gateway writes a notice when a decision opens, once when the connection
starts for a decision already open, and before a list answers; a handler may
still be running after `decisionsList` resolves. A `held` notice that arrives
before a handler is registered is kept (one per decision, the newest 1024
decisions) and handed to the handler when it registers; an older one comes
again at the host's own list. Without an `attestation` the stdio
operator decides, eligible only for a decision presented to it on this
connection. A decide called while the SDK serves a host tool callback rejects
with `DecideInsideToolCallbackError` (`kind = "decide_inside_tool_callback"`)
and sends nothing: an agent's tool call never decides.

A notice of `kind` `ask_user.questions` names a question set that is open in
the store: read it with `handle.gatingQuestions()` and answer it with
`handle.gatingAnswer()`. That works on a launch with a roster
(`.rosterProvider(...)`): a gateway serves its agents' questions only there.
On a launch without a roster the handler is still called for a set the store
already holds, and `decisionsList()` returns it, but `gatingQuestions()`
returns no set and `gatingAnswer()` rejects with `RpcError` (`-32602`: the
`pending_id` was not found). Such a notice is genuine and is not a readable
question: do not treat it as one.

## Member restore

Every roster identity is a member of the gateway's mob from ready, and is
materialized when work reaches it. `memberRestore` sets what the mob
materializes when it starts; it is sent as `runtime_options.member_restore`:

```typescript
const rt = await Meta.builder()
  .mob("config/mob.toml")
  .rosterProvider(roster)
  .memberRestore("on_demand_verified")
  .build();
```

`"on_demand"` (the gateway default when unset) materializes only the members
that must be live, such as those that hold work (the full set is under
`member_restore` in
[Configuration](/reference/configuration#sdk-and-gateway-runtime-options)); `"on_demand_verified"` also checks every other member once,
read-only, before ready, so a member whose session cannot be resumed reads
broken at ready; `"eager"` materializes every member. Another value throws
`RangeError`. A read never materializes a member:
`rt.mobHandle().identityResolvedToolsDetail(identity)` answers a member that
is not materialized from its last recorded build (`toolsSource` says which),
and `rt.mobHandle().identityWarm(identity)` builds a member without a turn
and records its tools. A tool record's `recordRevision` counts its writes
and is not the identity's generation.

## Waiting for a turn

The recommended completion barrier is a tracked delivery plus its ticket:
`sendAndWait(identity, content)`, or `send(identity, content, { trackTurn:
true })` followed by `waitForTurn(identity, result.turnTicket)`. It reads only
the ticket ledger and returns that turn's own output.

`sendAndWaitOutcome` and `dispatchAndWaitOutcome` resolve the typed
`AwaitedTurn` (`text`, `attributed`, `admission`, `ticket`, `outputStatus`,
`untrackedCode`); `sendAndWait` / `dispatchAndWait` resolve its `text`. When
the delivery returns no ticket (any delivered `turnUnavailable.code`, such
as `autonomous_host`, the default mode, or a gateway predating turn tickets),
the call waits on the identity-wide completion cursor with a
`TurnTrackingUnavailableWarning` naming the code: `attributed` is `false`
because another delivery's turn may have produced the text, and
`untrackedCode` carries the code. `requireAttribution: true` throws
`TurnTrackingUnavailableError` (carrying `admission`) in every untracked case
instead. `not_delivered` (nothing ran) throws `TurnNotDeliveredError`.

The delivery is never repeated. A transport or RPC failure of the
exact-ticket wait is retried for that ticket only until `timeoutMs`, then
throws `PostAdmissionObservationError` with `admission`, `ticket` and the
last failure as `cause`. Every error an `*AndWait` call throws after
admission keeps its type and carries `admission` (and `ticket`, `null` when
untracked): `TurnFailedError`, `TurnUnknownError`, `WaitEndedError`,
`TurnWaitTimeoutError` (a turn still pending at the deadline), and on the
identity-wide wait its deadline, missing-baseline and superseded-incarnation
errors and a raw transport error. A tracked `WaitEndedError` carries the
top-level `ticket` too. The one exception is a thrown value that cannot carry
fields (a non-object, or a frozen object thrown by custom code), which still
propagates unchanged.

`waitForCompletion(identity, baseline)` and `waitUntilReady(identities)` are
identity-wide: any completion on the identity satisfies them.

Every wait is server-side and event-driven: `waitForTurn` is one
`meta/wait_for_turn` request, and `waitForCompletion` / `waitUntilReady` are
one `meta/wait_for_completion` request per identity. The gateway answers
when the ticket settles or a completion is recorded, so nothing polls, and the
member's output is read once, at completion. `timeoutMs` is only the deadline;
`pollIntervalMs` applies only against a gateway that predates the server-side
waits. `completionCursor(identity)` is a one-shot cursor read that never
touches the member session. `inspectIdentity` does read the member session, so
do not poll it.

A wait that ends before a completion (a failed or cancelled run, a broken,
retiring or deleted identity, or gateway shutdown) rejects with the typed
`WaitEndedError`, whose `outcome` names why.

## Scope-bound dispatch

Capture the identity's scope from `status()`, persist it, and dispatch
against it. A moved scope throws `StaleScopeError` with nothing submitted; a
lost reply is recovered from the scope's original session.

```typescript
import { deliveryScopeToDict, parseDeliveryScope, StaleScopeError } from "@rkat/meta-sdk";

const status = await runtime.status("domain:calendar");
if (!status.deliveryScope) throw new Error(status.deliveryScopeUnavailable?.reason);
const saved = deliveryScopeToDict(status.deliveryScope); // persist byte-exact

try {
  const { receipt } = await runtime.dispatch(
    "domain:calendar",
    { content: "occurrence 42", origin: "system", idempotencyKey: "occ-42", correlationId },
    { expectedScope: parseDeliveryScope(saved) },
  );
  receipt.stage; // "ingress_accepted": not a durable-input claim
} catch (error) {
  if (error instanceof StaleScopeError) error.mismatch; // nothing was submitted
}

const recovery = await runtime.recoverDelivery("domain:calendar", parseDeliveryScope(saved), {
  idempotencyKey: "occ-42",
  correlationId,
});
// recovery.state: "absent" is a point-in-time miss, never permission to retry
```

`expectedScope` needs both keys, does not combine with `trackTurn`, and
applies no delivery preparation. `parseDeliveryScope` throws
`ContractMismatchError` for an unknown scope `version`; `status()` then
leaves `deliveryScope` `null` and the rest usable. An unknown recovery state
reads as `unresolved`, never `absent`. See
[Scope-bound dispatch](/api/rpc#scope-bound-dispatch).

## Scoped tool grants

A profile's `tools.grant_gated` mounts tools closed on every build of its
members; a grant to an identity opens one for a fixed window, across the
member's respawns and the gateway's restarts. The grant wakes nothing and
applies at the member's next model request.

```typescript
import { ToolGrantRequestRefusedError } from "@rkat/meta-sdk";

const granted = await runtime.grantTool("agent-a", {
  tool: "datetime",
  durationMs: 600_000,
  decisionRef: "approval-7", // your own record of the decision
});
const grantId = (granted.grant as { grant_id: string }).grant_id;
granted.applies; // "now", "not_mounted" or "at_next_build"
const listed = await runtime.listToolGrants("agent-a", { includeEnded: true });
listed.gate; // { running, next_build }
await runtime.toolGrantAudit("agent-a", { limit: 50 });
await runtime.revokeToolGrant(grantId, { reason: "done" });

try {
  await runtime.grantTool("agent-a", { family: "shell", durationMs: 600_000 });
} catch (error) {
  if (error instanceof ToolGrantRequestRefusedError) {
    error.refusalKind; // "target_not_gated", ...
  }
}
```

Name exactly one of `tool` and `family`, and exactly one of `durationMs` and
`expiresAtMs`. A grant answers `applies`, whether it applies to the member's
running build, and a list answers the member's `gate` (none for a retired
identity); both are advisory. Every refusal rejects with
`ToolGrantRequestRefusedError`; its kinds are
`TOOL_GRANT_REQUEST_REFUSAL_KINDS`. See
[Scoped tool grants](/api/rpc#scoped-tool-grants).

## Long-term agents

`runtime.identities` reads and changes the mob's long-term agents, one call
per `meta/identity/*` host method. Every agent is read and changed the same
way, whoever asked for it and by whatever route it came to exist. The
[guide](/guides/long-term-agents) walks through adopting an agent your
configuration declares.

```typescript
import { IdentityRefusedError } from "@rkat/meta-sdk";

const identities = runtime.identities;

const record = await identities.get("scout"); // AgentRecord
const page = await identities.list({ includeArchived: true }); // { agents, next }
try {
  const outcome = await identities.adopt("scout", {
    expectedSpecDigest: record.specDigest,
    requestId: "adopt-scout-1",
  });
  outcome.outcome; // "done", "pending_decision" or "pending_preparation"
} catch (error) {
  if (error instanceof IdentityRefusedError) {
    error.kind, error.field, error.detail, error.retryable, error.details;
  }
}

const state = await identities.operation({ requestId: "adopt-scout-1" });
```

| Call | Sends | Resolves |
| --- | --- | --- |
| `create(agents, { requestId, proposer?, sourceEvidence? })` | `agents`: `AgentSpec[]` (`name`, `profile`, `displayName`, `instructions`, `context`, `labels`, `firstMessage`, `peers`, `addressability`, `runtimeModeOverride`) | outcome |
| `update(name, { expectedSpecDigest, requestId, set?, peersAdd?, peersRemove? })` | `set`: `AgentSet` (`displayName`, `instructions`, `context`, `labels`, `labelsRemove`, `profile`, `addressability`, `runtimeModeOverride`) | outcome |
| `archive`, `unarchive`, `remove`, `adopt` `(name, { expectedSpecDigest, requestId })` | the agent and the spec digest you read | outcome |
| `settlePreparation(name, { requestId })` | the agent your host has prepared | outcome |
| `withdraw({ requestId } \| { operationId })` | exactly one of the two | `IdentityWithdrawn` |
| `changesHold(held, { reason? })` | | `IdentityChangesHold` |
| `list({ profile?, includeArchived?, after? })` | | `AgentPage` of `AgentSummary` |
| `get(name)` | | `AgentRecord` |
| `operation({ requestId } \| { operationId })` | exactly one of the two | `IdentityOperation` |
| `directory({ query?, after? })` | | `AgentDirectoryPage` |
| `plan(change, request)` | `change` and a `CreateAgents`, `UpdateAgent` or `AgentRef` | `IdentityChangePlan` |

An `archive` or a `remove` of an agent that still owns mobs it created is
refused `owns_mobs`: have the agent destroy them first (see
[`meta/identity/archive`](/api/rpc#meta%2Fidentity%2Farchive-meta%2Fidentity%2Funarchive-meta%2Fidentity%2Fremove-meta%2Fidentity%2Fadopt)).

Options and answers are camelCase; the SDK spells the wire's names. A change
needs your `requestId`: the same id and request return the same state and
commit at most once. `expectedSpecDigest` is the agent's `specDigest` as you
read it. There is one spec digest on every surface: the same value in `list`,
`get`, an outcome and `stale_spec`'s `current_digest`.

An outcome is a union discriminated by `outcome`: `done` (`operationId`,
`agents`), `pending_decision` (`operationId`, `decisionId`, `deadlineMs`) or
`pending_preparation`. A held decision is a normal answer. The SDK does not
poll: read `operation` when you want the state; it also resolves `refused`
(the operation ended refused) and `unknown`. Each `AgentOutcome` carries the
agent's `specDigest` afterwards, a create's `seat` (`seated` or `owed`) and
an update's `instructions` (`applies_at_next_run`,
`applies_after_compaction`, `applies_at_next_session` with a `reason`, or
`unchanged`). `applies_after_compaction` is a change that waits: the
agent's model takes a system instruction only ahead of the conversation, and
a short conversation may never reach the compaction that brings it into
effect. `rt.reset(name)` does, and gives the agent's conversation up.
`rt.instructionStatus` is the authority for whether a change is in
effect; see
[Changing an agent's instructions](/concepts/roster#changing-an-agent%E2%80%99s-instructions).

The first answer of an `archive`, an `unarchive` and a `remove` also carries
the agent's `schedules` (`SchedulesFollowed`: `effect`, `count`,
`schedules` of `{ scheduleId, name }`, `incomplete`): how the agent's
schedules stand after the change; `null` otherwise. After an archive the
list is the schedules paused for the agent; after an unarchive, its
schedules that are active after the call (one somebody resumed by name
meanwhile included); after a removal, the ended ones. The gateway gives
your host the list; a caller that is not given it (an agent that asks for
the change, a Console caller without `runtime.admin`) is told the `effect`
and the `count` only, and such an answer reads as an empty `schedules` with
its `count` kept. A
replay of the request and an `operation` read state none, so compare a
retry by `operationId` and each agent's `state` and `specDigest`, not
whole. `IdentityChangePlan.schedules` carries the list a planned change
would answer.

`AgentSpec` and `AgentSet` take `addressability` (`addressable`,
`internal_only`) and `runtimeModeOverride` (`autonomous_host`,
`turn_driven`), the members and values of a roster row; `AgentSummary` and
`AgentRecord` read both back, each `null` when it is the default.

A create of an agent of a profile whose preparation the policy names
`required` resolves `pending_preparation`: prepare what the agent needs,
then `settlePreparation(name, { requestId })` seats it. An agent that
awaits none refuses `preparation_not_pending`.

`IdentityStatus.rosterListingSuperseded` (`runtime.status(name)`) is `true`
when the host's roster lists a name whose agent is served from its record,
an adopted agent your roster still lists for one: the roster's entry is not
applied. `get`, `list`, the directory and the plan of a change of such an
agent read the same member (`AgentSummary`, `AgentRecord`, `DirectoryPeer`,
`IdentityChangePlan`). `IdentityStatus.archived` is `true` while the agent
is archived,
and `IdentityStatus.preparationPending` while it waits for its host's
preparation; the gateway writes each only when it is so. An agent's spec
digest, provenance and `openOperations` are read with `get` and `list`:
`openOperations` names its create while it waits for its host, and each
change of it that is held or approved and not yet carried out, and is
empty when nothing is open.

Every refusal of every call rejects with `IdentityRefusedError` (`-32058`);
its kinds are the closed vocabulary `IDENTITY_REFUSAL_KINDS`
(`IdentityRefusalKind`). A kind newer than the SDK is the same error with
`knownKind` false. Only `operation` resolves a refusal as a value. An
`archive` or a `remove` of an agent that still owns mobs it created is
refused `owns_mobs`, and nothing is changed: `details` holds `count` (how
many mobs) and `mobs` (their ids, given to this host), and the remedy is to
have the agent destroy its mobs first, or to keep the agent. A
candidate launch refuses a change with the gateway-wide
`AnnouncementRefusedError` (`kind` `candidate_launch`). `field` and the keys
of `details` are in the wire's names (`agents[1].name`, `current_digest`).
Advisory values (`readiness`, a change's `state`, provenance, directory
verdicts) are kept as the gateway sent them.

The gateway changes agents only under the host's policy:
`MetaBuilder.identityCreation(policy)` sends it as
`runtime_options.identity_creation`, in wire form. Without one every change
is refused `change_denied`. The outcomes of this release are `allow`,
`require_approval` and `deny`; a policy that names `notify` or `review` is
refused at init. See the [policy reference](/reference/identity-policy) and,
for the methods themselves, [Agent changes](/api/rpc#agent-changes).

A 0.9.15 client against a 0.9.14 gateway was exercised in one keyless run
only (the Meta Python SDK's own tests that start a real gateway without a
provider key, against a gateway built at the 0.9.14 commit); no other client
and no 0.9.14 runtime was exercised. Of the tests in that run that start a
real gateway, the five that existed at 0.9.14 and need no provider key
passed; the failures were in tests new in 0.9.15 (the identity methods and
cross-mob delivery between gateways) or in tests that need a provider key.
The methods for agents created at run time (meta/identity) need a 0.9.15
gateway: upgrade the gateway before the SDKs that call them.

## Realm MCP administration

The stdio gateway lets its host administer the installation realm's own MCP
servers and the secret values of their stdio servers' `secret_env` slots,
kept in the launch's provider credential store:

```typescript
import { RealmMcpRefusedError } from "@rkat/meta-sdk";

const listed = await runtime.realmMcpServers(); // {servers, generation}
const server = { name: "search", command: "search-mcp", secret_env: ["SEARCH_API_KEY"] };
await runtime.realmMcpInstall(server, { expectedGeneration: listed.generation as number });
await runtime.realmMcpSetSecret(server, "SEARCH_API_KEY", apiKey);
try {
  await runtime.realmMcpInstall(server, { expectedGeneration: listed.generation as number });
} catch (error) {
  if (error instanceof RealmMcpRefusedError) {
    error.refusalKind; // "generation_conflict"
  }
}
await runtime.realmMcpRemoveSecret(server, "SEARCH_API_KEY");
```

The value is sent once, in the `set_secret` request, and never appears in an
answer or an error. A launch whose credential store did not open rejects the
secret methods with `RealmMcpUnavailableError`; a write whose result is
unknown rejects with `RealmMcpOutcomeUnknownError`. See
[Realm MCP administration](/api/rpc#realm-mcp-administration-stdio-gateway).

## Durable detached tools

Long-running host work must declare detached execution rather than keeping a
tool callback open:

```typescript
import { DetachedJobExecution, DetachedJobResult, Meta } from "@rkat/meta-sdk";

const runtime = await Meta.builder()
  .persistentState("state/meta")
  .jobCredentials(resolveProfileCredentials)
  .sessionService({
    async buildAgent(draft) {
      draft.registerTool(
        "security_scan",
        async () => ({ error: "detached owner required" }),
        {
          description: "Run a durable security scan",
          execution: new DetachedJobExecution({
            runner: "example.security_scan",
            version: "v1",
            restartClass: "checkpoint_resumable",
            idempotencyScope: "interaction_and_arguments",
            submissionTimeoutMs: 30_000,
            credentialScopes: ["unifi.read"],
            handler: async (ctx) => {
              await ctx.progress(1, "scan started");
              const resultRef = await performScan(ctx.arguments, ctx.credentials);
              return new DetachedJobResult(resultRef);
            },
          }),
        },
      );
    },
  })
  .gateway("/path/to/rpc_gateway")
  .build();

const job = await runtime.jobs.get(jobId);
await runtime.jobs.cancel(jobId);
```

The gateway durably accepts the job and returns a receipt; host work runs
outside the agent turn. Start, reconcile, and cancel remain short callbacks
inside the 120-second public contract (125-second host and 130-second wire
margins). Reconnect offers the exact committed attempt, fence, lease,
checkpoint, and runner handle. Reopening never mints a fence; only a
machine-authorized claim or retry does. Credentials are resolved per attempt
and never serialized into durable job state. `ctx.requester` is the requester
of the run that submitted the job (see below), recorded with the job, or
`undefined` when that run had none.

## Who a tool call serves

A tool handler's optional second argument is the original requester of the
run the call serves (`ToolCallRequester`): its `principal` (`kind`, `id`, and
`trustDomainId` when it is qualified) and `carried`, true when the run's work
reached the agent through another actor, such as a peer hop. A person the
Meta console authenticated appears with `trustDomainId` `oidc-issuer:`
followed by the token's issuer; a run without a requester
passes `undefined`. The runtime sets it, never the arguments, so a tool that
acts in one person's name can refuse everyone else:

```typescript
draft.registerTool("read_mail", async (args, requester) => {
  if (
    requester === undefined ||
    requester.carried ||
    requester.principal.kind !== "human" ||
    requester.principal.id !== OWNER_SUB ||
    requester.principal.trustDomainId !== OWNER_DOMAIN
  ) {
    throw new Error("this mailbox serves its owner only");
  }
  return readMail(args);
});
```

For identity-first builds with a `rosterProvider`, `.agentMemory()` enables optional identity-scoped hot memory injection from `<persistentState>/agent-memory` with contextual recall by default. Options include `realm`, `selection`, `maxEntries`, `recallTimeoutMs`, `recallFailurePolicy`, and `instructionHeader`; automatic injection defaults to a 500 ms timeout and skips the memory block if recall fails. Write records with `handle.rememberAgentMemory(identity, { title, body, tags, realm })`, read them with `handle.recallAgentMemory(identity, { realm, selection, queryText, queryTerms, maxEntries })`, and withdraw them from the agent with `handle.forgetAgentMemory(identity, memoryId, { realm })`; new records are available on the next identity-first send and during later materialize/resume/respawn/reset flows. Forgetting a record removes it from future recall/injection, but does not erase text already delivered into an active model context, and it is not an erasure of the record: the bundled store keeps its text (see [`meta/agent_memory/forget`](/api/rpc#meta%2Fagent_memory%2Fforget)).

`recallAgentMemory` selects records and does not list them: `"contextual"`
(the default) returns the active records that match the query, `"always"`
the most recently updated ones, and either returns at most `maxEntries`
(8 by default, 64 at most) with no cursor (see
[Reading agent memory](/concepts/memory#reading-agent-memory)). To see
everything an identity holds, read its manifest with the full tier.
`handle.manifestAgentMemory(identity, { tier, k, realm })` returns metadata
and never bodies; `handle.updateAgentMemory(identity, memoryId, { title,
body, tags, realm })` replaces an active record and returns the new
record's `memoryId` and the id it `supersedes`.

```typescript
const handle = runtime.mobHandle();

// Every active record of the identity: metadata only, no bodies.
const all = await handle.manifestAgentMemory("scout", { tier: "full" });
for (const meta of all) {
  console.log(meta.id, meta.title, meta.ageDays);
}

// The most recently updated records with their bodies: at most 64 a call.
const newest = await handle.recallAgentMemory("scout", {
  selection: "always",
  maxEntries: 64,
});
```

## Type definitions

The SDK exports camelCase result types. Its wire parsers translate snake_case
gateway JSON into these shapes:

```typescript
export interface EventEnvelope {
  readonly eventId: string;
  readonly source: string;
  readonly timestampMs: number;
  readonly event: unknown;
}

export interface UnifiedAgentEvent {
  readonly kind: "agent";
  readonly agentId: string;
  readonly eventType: string;
  readonly payload?: Record<string, unknown> | null;
}

export interface UnifiedModuleEvent {
  readonly kind: "module";
  readonly module: string;
  readonly eventType: string;
  readonly payload: Record<string, unknown>;
}

export type UnifiedEvent = UnifiedAgentEvent | UnifiedModuleEvent;
```

`handle.gatingDecide(...)` returns the decision plus `approverId`, `outcome`,
`decidedAtMs`, `reason`, and `nextPendingId`. These added fields are optional for
compatibility with existing TypeScript objects; parsed responses use `null` when
a field is absent or malformed. Unknown outcome strings are preserved.
`nextPendingId` identifies an escalation successor; the SDK does not automatically
retry or execute the action. See [Gating](/concepts/gating) for decision semantics.
`gatingDecide` reads the result of a gated action. From 0.9.15
`meta/gating/decide` answers a question set's `pending_id` with another
result, which carries `kind: "question_set"` and no `action_id`: decide a
question set with `gatingAnswer` or `gatingDismiss`, which read it.

`handle.gatingWithdraw(pendingId, reason?)` withdraws a pending request this host
minted, with no decision: it returns `pendingId`, `actionId`, `actorId`,
`outcome` (`safe_draft`), `withdrawnAtMs`, `withdrawnBy` and `reason`. A request
that was already decided, timed out or withdrawn is refused as an unknown id.

From 0.9.15. `handle.gatingQuestions()` lists the open
[question sets](/concepts/gating#question-sets) agents asked with `ask_user`
(they are not part of `gatingPending()`). Each `GatingQuestionSet` carries the
`pendingId` a decision takes, the asking agent as `origin`, a `title` (or
`null`), its `questions` (`id`, `prompt`, `choices`, `allowFreeText`,
`recommended`), `createdAtMs`, `deadlineAtMs` and the `subjectDigest` a
decision sends back. Both decisions go through `meta/gating/decide`, so the
host names the approver:

```ts
for (const set of await handle.gatingQuestions()) {
  const result = await handle.gatingAnswer(set.pendingId, {
    approverId: "operator",
    presentedDigest: set.subjectDigest,
    answers: [
      { questionId: "region", answer: { kind: "choice", choiceId: "eu" } },
      { questionId: "start", answer: { kind: "free_text", text: "After the 16:00 freeze" } },
    ],
  });
  // result.outcome === "answered"
}
```

At least one answer is needed (`gatingAnswer` throws otherwise, before
anything is sent); a question left out reaches the agent as `unanswered`, and
free text is allowed only where the question sets `allowFreeText`.
`handle.gatingDismiss(pendingId, { approverId, presentedDigest })` tells the
agent no answer is coming. Both return a `GatingQuestionSetResult`
(`pendingId`, `kind`, `outcome`: `answered` or `dismissed`, `decidedAtMs`). The
gateway refuses an invalid answer set as invalid params (`-32602`). A set that
itself refuses the decide (it is no longer open, or `presentedDigest` is not
its digest) is refused `-32602` with the typed refusal in the error's data:
`data.kind = "decision_refused"` and `data.decision_refusal.kind` (`not_open`,
`subject_changed`, `expired` or `not_eligible`); see
[Answering a question set](/api/rpc#answering-a-question-set).

There is no Meta SDK for the browser: the browser client of these methods is
the Console's own `@console-core` package (`normalizeQuestionSet`,
`createQuestionSetResource` and the `listQuestionSets` command), and the Core
Web SDK (`@rkat/web`) has no Meta surface.

`ModuleConfig` is not a public TypeScript SDK export. Pass module declaration
objects to `.modules(...)`, whose public parameter type is `unknown[]`.

An identity-first `RosterProvider.roster(context)` receives a typed
`RosterContext`, a one-to-one mirror of the Rust struct the gateway sends
under `params.context`:

```typescript
export interface RosterContext {
  /**
   * The booted mob's compiled definition as JSON (`id`, `profiles`, ...).
   * Always present behind the bundled `rpc_gateway`; `null` only for in-process
   * Rust embedders and test harnesses that resolve a roster without one.
   */
  readonly mobDefinition: Record<string, unknown> | null;
  /**
   * Call-site-dependent prior-identity context, not an authoritative membership
   * snapshot on every callback. Topology queries and edge reconciliation supply
   * currently registered identities. Bootstrap, full roster refresh/reconcile,
   * and reset-time spec adoption currently pass an empty list; an empty list
   * does not imply that no identities are registered.
   */
  readonly previousIdentities: readonly string[];
}
```

## More than one mob on a gateway

A gateway hosts the mob its launch names and can host more. `rt.mobHandle()`
is the handle of the launch's own mob. `rt.mob(mobId)` is the same
`MobHandle` for a mob named by its id, and `rt.mobs` creates, lists and reads
the mobs of the host, and stops, resumes, redefines and destroys them.

```typescript
import { readFileSync } from "node:fs";

const entry = await rt.mobs.create(readFileSync("research.toml", "utf8"));
for (const mob of await rt.mobs.list()) {
  console.log(mob.mobId, mob.default, mob.state);
}

const research = rt.mob(entry.mobId);            // sends nothing
const members = await research.listMembers();    // every call carries mob_id
await research.send(members[0].agentIdentity, "Review PR #42");
```

**The hosting calls.** `rt.mobs` has six calls, and each asks the gateway
every time: the SDK keeps no list of mobs and no state of one.

| Call | Wire method | Resolves |
|------|-------------|----------|
| `mobs.create(mobConfig)` | `meta/mobs/create` | the new mob's `HostedMob`; `mobConfig` is the mob definition as TOML text, and the mob's id is the definition's `[mob] id` |
| `mobs.list()` | `meta/mobs/list` | `HostedMob[]`, the launch's own mob first; loads no mob |
| `mobs.get(mobId)` | `meta/mobs/get` | one `HostedMob`; loads the mob when the host created it and it is not loaded |
| `mobs.lifecycle(mobId, action)` | `meta/mobs/lifecycle` | `MobLifecycleResult`: the mob's entry (`mob`) and, for a stop, its stop report (`stopReport`); `action` is `"stop"` or `"resume"` |
| `mobs.redefine(mobId, mobConfig, expectedRevision)` | `meta/mobs/redefine` | `MobRedefineResult`: the mob's entry and the update's `receipt` (`MobRedefineReceipt`: `previousRevision`, `committedRevision`, `projectionRevision`, `eventCursor`, `declaredFields`); `expectedRevision` is the mob's `revision` (below) |
| `mobs.destroy(mobId)` | `meta/mobs/destroy` | `MobDestroyResult`: `mobId` and the `destroyReport`; removes the mob's storage |

A `HostedMob` has `mobId`, `default` (true for the mob the launch names) and
`state`, and when the gateway sent them `provenance`, `failure`,
`quarantine` and `revision` (`null` otherwise). `state` says where the mob
stands. `creating`, `running`, `completed` and `destroyed` are the lifecycle
of a loaded mob. `stopped` is the mob's own stop and holds whether the host
has the mob loaded or not: the host's records keep it, across a restart too.
`dormant` says that the host knows the mob, has not loaded it and does not
know it as stopped. `quarantined` says that its store could not be opened or
restored, and `held` that a mob one of the host's agents created waits for
its owner. The list
(`HOSTED_MOB_STATES`, `HostedMobState`) is open: a state newer than this SDK
is kept as its text and `knownState` is false, so read `state` as advice.
`provenance` (the kind of the mob's creation record: `host`, `member` or
another kind) is `null` for a quarantined or held mob, and for a mob that is
not loaded and whose store the host has not read yet: for a short time after
a start such a mob reads `dormant`, a stopped one too, until the host has
read its store, which it does by itself.

`mobs.list` loads nothing: it answers from the host's records. `mobs.get`
loads the mob it names when the host created it and it is not loaded, as its
store has it: a stopped mob loads stopped, no agent of it runs and nothing is
started. A mob one of the host's agents created is answered from the records
and is not loaded by a `get`. A load that fails rejects with what a
`lifecycle` of that mob would reject with, unless the host's records show
what became of the mob: a store that cannot be opened is kept quarantined,
and the entry says so.

`revision` is the revision of the mob's definition: a whole number that every
committed redefinition advances. A mob that was never redefined reports the
revision its create recorded. `mobs.get` carries it for a loaded mob, which a
mob the host created is after a `get`, and so does the entry in a `create`,
`lifecycle` or `redefine` answer; an entry of `mobs.list` never carries it,
and a `quarantined` or `held` mob has `null`.

```typescript
await rt.mobs.lifecycle("research", "stop");
const entry = await rt.mobs.get("research");
if (entry.revision !== null) {
  await rt.mobs.redefine("research", readFileSync("research.toml", "utf8"), entry.revision);
  await rt.mobs.lifecycle("research", "resume");
}
```

Read `(await mobs.get(mobId)).revision` before a `redefine` and pass it as
`expectedRevision`: the `get` loads a mob the host created, so its entry
carries the revision. A `quarantined` or `held` mob has none.

The calls need the gateway's `hosted_mobs` feature capability
(`supportsHostedMobs`). Their own refusals reject with
`MobHostingRefusedError` (code `-32059`) with `kind`, `mobId`, `retryable`
and `detail`. The kinds (`MOB_HOSTING_REFUSAL_KINDS`,
`MobHostingRefusalKind`) are a closed list: `mob_exists` (a create under an
id a mob of the host has, loaded or not), `invalid_mob_id`, `default_mob`
(a destroy, a redefinition, a stop or a resume of the mob the launch
names), `mob_not_stopped` (a
redefinition of a mob that is not stopped: stop the mob, redefine it, resume
it) and `mob_busy` (a redefinition of a stopped mob that still holds
something: the one kind with `retryable` true; its `detail` ends with
`held: ` and one closed word for each thing held, `work`, `roster` or
`owner`, or the word `unanswered`). A kind newer than this SDK is still
this error, with `knownKind` false.

`lifecycle`, `redefine` and `destroy` name their mob themselves: there is no
default, so none of them can reach the launch's own mob by omission. A stop
and a resume are the mob's own. The launch's own mob is not stopped or
resumed through `lifecycle` (`default_mob`): its host stops it by its own
means. A
storage refusal with code `-32014` rejects with `StorageResolutionError`, even
when it carries no structured `data`; the error keeps its message and code.
These answers remain plain `RpcError` with their data: a mob the host does
not have (`foreign_mob_target`), a mob whose store did not load
(`mob_quarantined`; such a mob cannot be destroyed through `destroy`). A
call that lacks what the wire requires (an id or a definition that is not
text, another action, a revision that is not
a whole number or is negative) is refused before anything is sent, with a
`TypeError`. An answer the SDK cannot read rejects with
`ContractMismatchError` instead, so the two are told apart: the request was
sent and the gateway acted on it. That is an answer without its entry, its
id or a member of its receipt, a stop answered without its stop report, and
a report that is not an object.

**A handle for a named mob.** Obtaining `rt.mob(mobId)` sends nothing and
loads nothing, and it does not say whether the host has such a mob. Every
call of the handle then carries `mob_id`: in each JSON-RPC request, in the
multipart upload of `send` with attachments and `uploadBlob`, and as
`?mob_id=` on the streams of `subscribeAgent` and `subscribeMob`. A call on a
mob the host does not have rejects with a plain `RpcError` (`-32602`, data
`kind` `foreign_mob_target`). `handle.mobId` is the id, and `null` on the
handle of the launch's own mob, whose requests name no mob, as before.

A method with a `mobId` of its own keeps it: the announcement methods that
take `mobId` (`announce`, `announcementGet`, `announcementAuditList` and the
`announcementSource*` methods) and an event query's `mobId` (`queryEvents`,
`queryMobEvents`, `subscribeMobEvents`) send the value you pass, and the
handle's id when you pass none.

The agent memory calls of a handle send `realm` beside the mob when you give
one, as you gave it, and leave it out otherwise: the gateway then takes the
memory realm of the mob the request names.

A gateway of an earlier release ignores `mob_id` and answers for its own mob.
So a named handle first reads the gateway's `mob_addressing` feature
capability (`supportsMobAddressing`), once per started gateway, and without
it every call rejects with `CapabilityUnavailableError` and nothing else is
sent. The handle of the launch's own mob reads it before one call only, a
`queryEvents` whose query names a mob, and refuses that query without it:
such a gateway would answer the query without an error and for its own mob.

`rt.jobs`, `rt.monitors` and the realm MCP calls are the host's whichever mob
is named; they stay on the runtime.

**Providers under a host with more than one mob.** The three callbacks that
build a member name the member's mob: `customizeBuild`'s
`AgentBuildContext.mobId`, `afterCreate`'s context (`mobId`), and the
`context` a topology provider's `computeEdges` is given (`mob_id`, in the
wire's spelling as the rest of that object). A host that names none serves
its own mob only, and the contexts then have no `mobId` (no `mob_id` in the
topology context): they are whole as they were before a host could name a
mob. A `mob_id` that is not text is refused: the callback answers an error
(`ContractMismatchError`) and the customizer or the provider is not asked.
The callback tools a customizer registers with `draft.registerTool` are kept
per mob and identity, so a build of `analyst` in one mob leaves the tools of
`analyst` in another in place. An SDK older than this one keeps them per
identity name alone: under a host with two mobs, a build of a member in one
mob releases the callback tools of the member with the same name in the
other. A mob created under the id of a destroyed mob starts with none of that
mob's callback tools: the gateway names each mob's incarnation with the build
(`mob_incarnation` beside `mob_id`), and the first member build of the later
mob releases every tool kept under that mob id.

## Mob announcements

A `member` is a parsed `AnnouncementMember` or the wire form
`{ mob_id, identity }`. The [method reference](/api/rpc#mob-announcement-sources)
describes every field. A collector step reads the source, then advances it
from the position it read; a step that lost a race throws with the current
position:

```typescript
import {
  SourceStaleRevisionError,
  SourceVersionConflictError,
  supportsAnnouncementSources,
} from "@rkat/meta-sdk";

const handle = runtime.mobHandle();
if (!supportsAnnouncementSources(await handle.capabilities())) {
  throw new Error("this gateway does not serve announcement sources");
}
const { source } = await handle.announcementSourceGet("mail");
if (source === null) throw new Error("declare the source first");
const { items, nextCursor } = await readProvider(source.cursor.token); // your adapter
try {
  await handle.announcementSourceAdvance(
    `${runId}:v${source.cursor.version}`,
    "mail",
    source.revision,
    source.cursor.version,
    principal,
    nextCursor,
    { items, observed: { kind: "delta" } },
  );
} catch (err) {
  if (!(err instanceof SourceStaleRevisionError || err instanceof SourceVersionConflictError)) {
    throw err;
  }
  // another step or a configuration change moved the source: read it again
}
```

The refusals are typed: `MobAnnouncementsUnavailableError` (`-32044`),
`AnnouncementConflictError` (`-32045`; `SourceStaleRevisionError` and
`SourceVersionConflictError` carry the source's `currentVersion`, `cursor`
and revision), `AnnouncementFrontierError` (`-32046`),
`AnnouncementRefusedError` (`-32047`) and `AnnouncementNotFoundError`
(`-32048`), each with the refusal's `kind` (a kind this SDK does not know
keeps its code's class). `parseAnnouncementRpcError(code, message, ...)` is
the reifier the runtime uses. A source method on a gateway without sources
rejects with an `RpcError` `-32601` whose message says "Meta does not
support sources". `CapabilitiesResult.mobAnnouncements` reads
`meta/capabilities.mob_announcements`, `null` when they are disabled.

A batch's `handling` and an observation's `handling`
(`AnnouncementBatchHandling`: `state`, `cause`, `redelivered`, `held`,
`dismissed`, `readAtMs`) say what became of the turn
([Delivery handling](/api/rpc#delivery-handling)). Each is `null` until
the batch is admitted. A batch that holds nothing for an operator
rejects `announcementDeliveryRedeliver` and
`announcementDeliveryDismiss` with `AnnouncementRefusedError` `not_held`.
An `AnnouncementAuditEntry` for a plain announcement has `sourceId` and
`generation` `null`.

Escalations ([Mob announcement health](/api/rpc#mob-announcement-health))
reach `.onError(callback)` as `mob_announcement_escalated` and
`mob_announcement_escalation_resolved`, each with its event `cursor` in
`context`. After a reconnect, read the events you missed:

```typescript
const page = await handle.announcementEscalationsList({ after: lastCursor });
for (const event of page.events ?? []) {
  record(event.escalationId, event.event, event.cause); // your own
}
lastCursor = page.next;
```

`StatusResult.mobAnnouncements` (`MobAnnouncementsStatus`: `sources`,
`members`, `handling`, `openEscalations`, `lastEventCursor`) reads
`meta/status.mob_announcements`. It is absent when mob announcements are
disabled, and `null` when their database could not be read. A source's
`health` adds
`escalations`, `quietMonitoring`, `emptyCoverageMonitoring` and
`runnerScheduledHere`. Each `AnnouncementEscalation` keeps its `cause` and
its `subject` (a wire object, with its kind as `subjectKind`) as sent.

A role template ([Role templates](/api/rpc#role-templates)) subscribes
every member of a mob with a role:

```typescript
const template = await handle.announcementRoleTemplatePut(
  "op-reviewers",
  "reviewers",
  { mob_id: "mob-a", role: "reviewer" },
  ["ops.alert"],
);
const change = await handle.announcementSubscriptionPause("op-pause", "reviewers", template.revision);
// change.subscription is null; change.template and change.children carry the template
```

The subscription verbs answer a template with its `children`, and
`announcementSubscriptionGet` reads it as `template`.
`announcementDeclarationsApply(declarations)` applies declared sources and
subscriptions in wire form, with `revision` defaulting to
`declarations.revision` ([Mob announcement declarations](/api/rpc#mob-announcement-declarations)).
Called without declarations, it asks a gateway with a declarations sidecar
to read the file again. Each `AnnouncementDeclarationRecord` keeps its
`kind`, `status` and `collection` as open unions, with `refusalKind` and
`deliveryKind` read from their objects. The refusals
`declaration_rollback`, `declaration_digest_conflict`,
`role_template_limit` and `subscription_id_taken` are
`AnnouncementRefusedError`s with their data. The builder passes
`declarations` or `declarations_path` in `mobAnnouncements({...})`
unchanged.

over `instanceof`**:

  } else if (isRpcError(err)) {

## Rust parity notes

The TypeScript SDK targets the JSON-RPC gateway. Rust also exposes lower-level native builder options for in-process embedding; those remain Rust-native and are not mirrored one-for-one in the gateway SDKs.

Identities and their sessions live in Core's stores under `persistentState(path)`: Core's mob machine holds each identity's session and generation, and a host supplies no continuity storage and holds no leases. The external identity providers of Meta 0.9.3 are removed; see [Upgrading to Meta 0.9.4](/guides/upgrading-to-0-9-4) to move a deployment that used them.

Raw gateway memory config accepts `{ backend: "local_json", health_check_endpoint: url }`, with `health_check_endpoint` optional; `local_json` is the only backend. The TypeScript helper is `memory.localJson({ healthCheckEndpoint: url })`; it translates that option to the snake_case wire key. The predecessor's backend helper was removed in 0.9 with no alias, and the gateway refuses its backend value at init. Gateway auth config supports JWT validation; Google/OIDC helpers are model objects, not accepted by `meta/init` today.

The builder exposes no `roleMigrations(...)` setter and sends no `role_migrations` init param, so a TypeScript host cannot authorize a role-migrating resume: a durable member whose role changed keeps refusing to resume with `MobError::MemberRoleMigrationRequired`. Declaring the migration currently requires the Python builder's `.role_migrations([...])` or a hand-built `meta/init` payload; see the [configuration reference](/reference/configuration#member-role-migrations).

The builder forwards `consoleConfig(path)` as `runtime_options.console_config_path`, which lets the bundled console consume the same `console_config` contract projected by `/console/experience`. The console default is fail-closed: with neither `auth(...)` nor `consoleAuthRequired(false)` the gateway trusts no signing key and refuses every console request with 401 (it logs a startup warning naming this). `consoleAuthRequired(false)` is the explicit opt-out; use it only for a local or host-protected console. The Python twin is `.console_auth_required(False)`.

`DurableAgentSpec` carries the two per-identity knobs the Rust type deserializes: `runtimeModeOverride` (`"autonomous_host"` or `"turn_driven"`; `null` defers to the profile's `runtime_mode`, whose meerkat default is `autonomous_host`) and `initialMessage` (the first turn a fresh `autonomous_host` member runs on: a string or `DispatchContentBlock[]`, Rust `ContentInput`; `null` leaves meerkat's fallback spawn prompt). Both are omitted from the roster payload when unset. `durableAgentSpecToDict` and `parseDurableAgentSpec` translate them (`runtime_mode_override`, `initial_message`). The Python twins are `runtime_mode_override` and `initial_message` on `DurableAgentSpec`.

The gateway binds `127.0.0.1` on an ephemeral port by default. `httpListen("0.0.0.0:8080")`, `allowRemote()` and `httpPublicBaseUrl(url)` are the exposure knobs (`runtime_options.http_listen`, `allow_remote`, `http_public_base_url`): a non-loopback bind is refused at init unless `auth(...)` enforces console auth or `allowRemote()` acknowledges the exposure, and the advertised base is read back as `runtime.rustHttpPublicBaseUrl` while `runtime.rustHttpBaseUrl` stays the same-host form the SDK itself dials. See [Deployment](/guides/deployment).

`meerkatConfig(path)` forwards a Meerkat host `config.toml` as `runtime_options.meerkat_config_path`, the only door for the `[self_hosted]` and `[realm]` tables Meerkat keeps out of `mob.toml` (a host-config `[models]` table reaches the factory too, but a profile's `model` must be catalogued, provider-annotated or defined under `mob.toml`'s own `[models.<id>]` to pass the init model check); a missing, malformed or non-validating file refuses init rather than building agents from the default config, and a top-level `[self_hosted]` or `[realm]` table inside `mob.toml` is refused at init with a message naming this option. The Python twin is `.meerkat_config(path)`. See [Self-hosted models and the Meerkat host config](/reference/configuration#self-hosted-models-and-the-meerkat-host-config).

`memberCommsTcp(address = "127.0.0.1:0")` gives the locally hosted mob members signed TCP comms endpoints (`runtime_options.member_comms_address`): each member binds a port on `address`. From 0.9.15 `MobHandle.peerInfo` reports it as `dialable_address`, and the rest of this note, on wiring members of two gateways and on what a wire survives, applies from 0.9.15. `MobHandle.wireCrossMob(localMemberId, remoteMemberId, remoteHandle)` wires a member of this mob and a member of another mob to each other, so the two agents can send each other ordinary peer messages. Every runtime starts its own gateway process, so two mob handles are normally two processes: call `memberCommsTcp()` on both builders. `peerInfo` answers `member_id`, `mob_id`, `comms_name`, `peer_id`, `address` (the in-process address), `pubkey_b64` (the member's own transport key) and, only for a member with a socket endpoint, `dialable_address`. When both answers carry `dialable_address`, each side is wired to the other by that address and the member's key (never the gateway key of `peerPubkey()`); otherwise each side is wired by the in-process address with no key, which works when one process hosts both mobs, and a member that process does not have is refused in plain words with nothing wired. A refused second side undoes the first, unless that side was wired before the call. Calling the helper again for a pair that is already wired with the same endpoints changes nothing. A wire is never replaced: when a side is already wired to that peer with another endpoint (another address, or another key after a respawn), its `wireLocal` is refused in plain words and nothing changes; call `unwireLocal` on both sides, each with the other member's current `peerInfo`, then wire again. A member of a stopped mob still accepts a message through a wire and is handed it when its mob resumes. The Python twins are `.member_comms_tcp(address)` and `wire_cross_mob(...)`.

Between two gateways, a wire survives a gateway restart on persistent state only when each wired member's `dialable_address` is the same after the restart. With `memberCommsTcp()`'s default address (port `0`, a port the system picks at each start) it is not: the restarted member binds another port, is restored `broken`, and its wires are dead. Give a mob with persistent state a fixed address (`memberCommsTcp("host:port")`). To wire a member again after its address changed: `respawnMember` the broken member (it comes back active with its new address, and on a fresh conversation: a respawn starts the member on a new session); `unwireLocal` on the other gateway, with the respawned member's current `peerInfo`; `unwireLocal` on the restarted gateway, with the other member's current `peerInfo`; then `wireCrossMob` again. With member socket endpoints, run one member per gateway today.

`providerCredentialsRoot(path)` forwards a provider credentials directory as `runtime_options.provider_credentials_root`: every agent the gateway builds resolves and persists provider logins and tokens there instead of the process default `<config dir>/meerkat/credentials`, which every process of the OS user shares. The path is absolute: the gateway opens it once at init, creating it when missing, and a relative path or a root it cannot open refuses init rather than falling back to the default. Give each user their own root, and pass the same root on every reopen of that user's state; a host moving off a per-process `XDG_CONFIG_HOME=<C>` passes `<C>/meerkat/credentials` to keep existing logins. See [Provider credentials](/reference/configuration#provider-credentials).

`nativeRealm({realmId, contextRoot, stateRoot, userConfigRoot})` forwards a native realm as `runtime_options.native_realm`: the gateway reads that realm's effective configuration once at init with Meerkat's own native reader, copying and writing nothing, and every agent it builds starts from it in place of `meerkatConfig(path)` (the two are refused together). Each root is an absolute path; a realm the state root does not hold, or a configuration that cannot be read or does not validate, refuses init, never falling back to the default configuration, and the realm's whole configuration applies to every member. `memberAuthBinding({realm, binding, profile?, origin?})` forwards the binding every member is built with as `runtime_options.member_auth_binding`; `origin` is absent or `"configured"`. The gateway refuses at init a binding the members' configuration does not define, a definition profile the binding does not serve, and an automatic spawn policy, a model fallback target off the binding, image generation or the agent memory engines, in the definition, a realm profile it references or a stored child mob, and an identity declaration an earlier launch adopted that was sealed with no binding or another one; every member it builds then uses exactly this binding, or its build is refused (roster members, helpers and forks, later spawns, respawns and resets, members rebuilt after a restart, child mobs' members), never a default one, and a member Meerkat rebuilds from its own records (a fork seated before the launch named the binding) that recorded another binding or none is refused at its rebuild and must be re-created; a spawn that names another binding, an agent's child mob that would leave it, identity adoption, and an attach of a session whose live actor runs another binding are refused, and a running gateway is never rebound. `nativeRealm` requires `memberAuthBinding`. The Python twins are `.native_realm(...)` and `.member_auth_binding(AuthBindingRef(...))`. See [Native realm and member auth binding](/reference/configuration#native-realm-and-member-auth-binding).

## Storage durability declarations

The gateway is fail-closed about durable storage: a store that cannot open
is a startup error, never a silent in-memory fallback. The `runtimeStore`
and `eventLog` config modules produce the explicit declarations:

```typescript
import { Meta, eventLog, runtimeStore } from "@rkat/meta-sdk";

const runtime = await Meta.builder()
  .mob("config/mob.toml")
  .persistentState("state/meta")
  // Declare an in-memory runtime store (sessions do not survive restart).
  .runtimeStore(runtimeStore.memory())
  // Declare a queryable in-process event log (it has no size limit) — or eventLog.nullStore().
  .eventLog(eventLog.memory({ batchSize: 64 }))
  .gateway("/path/to/rpc_gateway")
  .build();
```

`handle.queryEvents(query)` reads the declared event log. A gateway with no
event log configured reads as an empty list through the SDK: an empty result
does not show that no event happened.

The resolved picture is the typed storage census: `StatusResult.storage` /
`CapabilitiesResult.storage` parse the gateway's `storage` object into
`StorageSummary` (blob durability, the H2 incremental probe, and the
per-slot `StorageSlotSummary` census with `domain`, `durabilityClass`,
`resolution`, `backend`, `degraded`, `detail`); apply `parseStorageSummary`
to the raw `storage` record of `meta/storage/doctor`. A fail-closed
startup refusal — file-name twins, a store that failed to open — surfaces
as the typed `StorageResolutionError` (code `-32014`,
`STORAGE_RESOLUTION_CODE`), not a `TransportError`; its message names the
remediation (`meta/storage/doctor`, or the explicit ephemeral
declaration). Blob-store durability has no wire declaration today — it is
declared by Rust embedders via `ephemeral_blobs(true)` /
`binary_blob_store(...)` and reported read-only in the census.

A composition provenance refusal surfaces as the typed
`CompositionProvenanceError` (code `-32019`, `COMPOSITION_PROVENANCE_CODE`).
The gateway raises it when the persistent mob storage's recorded composition
cannot be proven to match this launch, for example a `mob.toml` edited since
the persistent mob storage was created. Its `kind` names the refusal
(`"divergent"`, `"created_by_rehearsal"`, the manifest kinds, and
`"candidate_divergent"` from gateways launched as a candidate) and `fields`
lists the diverged definition fields as dotted paths, so a host can show what
changed without parsing the message.

If a gateway that the TypeScript SDK starts accepts init, reports a refusal
and exits:

- In 0.9.15 and 0.9.16, Node can exit on an unhandled `write EPIPE` even if
  `build()` is inside a `try`/`catch`. See the [0.9.16 limitation and workaround](https://github.com/lukacf/meerkat/blob/v0.9.17/meta/CHANGELOG.md#L793).
  When `build()` does reject, the refusal is the `startupError` of
  `GatewayStartupCleanupError`, a transport error.
- From 0.9.17, `builder.build()` rejects with the refusal itself when it
  reads the failed settlement. If it writes a host callback reply after the
  gateway exits but before it reads the settlement, cleanup also fails.
  `build()` then rejects with `GatewayStartupCleanupError`; its `startupError`
  is `InitOutcomeUnknownError` (source reading, not a run).

This distinction does not describe a failure before acceptance or a gateway
that exits without reporting a settlement.

To support both forms, check for the underlying refusal as below. Do not
retry a start just because a typed refusal arrived inside a transport error.

```typescript
import { CompositionProvenanceError, GatewayStartupCleanupError } from "@rkat/meta-sdk";

try {
  const runtime = await builder.build();
} catch (err) {
  const refusal = err instanceof GatewayStartupCleanupError ? err.startupError : err;
  if (refusal instanceof CompositionProvenanceError && refusal.kind === "divergent") {
    console.error("mob.toml differs from the stored definition in", refusal.fields);
  }
  throw err;
}
```

The comparison is over the parsed definition, so a profile key the TOML parse
warns about and ignores (for example `tools.mob_tasks` in a config written for
an earlier release) is never one of the `fields`: removing it to act on the
warning, or adding it, does not cause this refusal.

## Gateway logging (stderr)

The persistent gateway reports tracing lines, panic hooks, and storage
migration progress on its stderr. By default the SDK **inherits** the host
process's stderr, so those lines are visible where your application logs.
Two environment variables adjust this (same shape as the Python SDK):

| Variable | Effect |
|----------|--------|
| `META_GATEWAY_STDERR_FILE=<path>` | Append gateway stderr to a file |
| `META_GATEWAY_STDERR=devnull` | Discard gateway stderr entirely |

Discarding is the legacy pre-0.8.9 default and is not recommended: it hides
panic output and makes a slow-but-working storage migration indistinguishable
from a hang.

### Error hook (`onError`)

| Builder call | Effect |
|--------------|--------|
| `.onError(callback)` | Registers an `ErrorCallback` (`(event: ErrorEvent) => void`, or a promise of it). The gateway forwards every runtime `ErrorEvent` as the `meta/on_error` notification; the SDK parses it into `{ category, message, context }` and awaits your callback. |

`category` is one of the `ErrorCategory` constants (`spawn_failure`,
`reconcile_incomplete`, `checkpoint_failure`,
`compaction_persistence_rejected`, `actor_loop_stalled`,
`actor_loop_recovered`, `actor_loop_terminated`, `host_loop_crash`, `rediscover_failure`,
`event_log_flush_failure`, `identity_materialization_failure`,
`mob_stop_proceeded_without_interrupt`, `retired_member_release_failed`,
`lifecycle_effect_failed`, `lifecycle_projection_off`,
`mob_announcement_escalated`, `mob_announcement_escalation_resolved`). The SDK source constants are kept
in lockstep with the Rust enum by `tests/sdk_error_category_parity.rs`;
`context` carries the variant's fields (`member_id`, `error`, and so on).
`actor_loop_terminated` is a terminal actor failure requiring a process restart,
not a recovery notification like `actor_loop_recovered`. The hook is
fire-and-forget: a rejected promise is swallowed, and with no callback registered the
notification is dropped. The gateway's own stderr line for the same event
(ERROR, or INFO for `actor_loop_recovered` and
`mob_announcement_escalation_resolved`) is written either way, so the hook
adds alerting, not logging. Use `isResolutionErrorEvent(event)` to tell a
failure ending (`actor_loop_recovered`,
`mob_announcement_escalation_resolved`) from one starting before paging on
it. The Python
twin is `.on_error(callback)`.

## Startup: no built-in total deadline

`connect()` runs `meta/init` as accepted-then-settled. The gateway accepts
the init at once, reports each startup phase, and then settles it `ready` or
`failed`. The SDK has **no built-in total deadline** for that wait. Startup
legitimately includes provider callbacks (each bounded at 130 s by the
gateway) and the native identity restore, which is deliberately unbounded
and can run for minutes on a large roster. Any fixed SDK timer
would sooner or later abort a healthy restore. `gatewayTimeoutMs` still
bounds the wait for the `accepted` answer, and for an older gateway's single
init response.

The wait ends only when one of these happens:

- the init settles `ready` (connected);
- the init settles `failed`. You get the typed error, for example
  `StorageResolutionError`, with `err.data.durable_effects`: `"none"` when
  nothing durable was touched, otherwise `"possible"`;
- the gateway exits, or the transport reader fails. You get
  `InitOutcomeUnknownError`;
- your own deadline runs out. Set it with
  `Meta.builder().initDeadline(ms)`, and running out also throws
  `InitOutcomeUnknownError`.

`InitOutcomeUnknownError` carries `initId`, `lastPhase` (the last
`meta/init_progress` phase seen, such as `"roster"` or `"restore"`) and
`reason`. That makes a stuck or interrupted init diagnosable. The gateway may
already have changed native state, so the SDK never retries it automatically
and asks the gateway to shut down.

Provider callbacks that run during startup must not call ordinary runtime
RPCs on the same runtime. Ordinary dispatch starts only after init settles,
and the gateway refuses an earlier request at once with `InitInProgressError`
(`-32018`, exported as `INIT_IN_PROGRESS_CODE`).

## HTTP transport timeout

`createJsonRpcHttpTransport` defaults to a 60-second timeout (via
`AbortController`) so a server that accepts but never replies cannot
hang the caller's `await` forever. Override per-call:

```typescript
import { createJsonRpcHttpTransport } from "@rkat/meta-sdk";

const transport = createJsonRpcHttpTransport(endpoint, {
  timeoutMs: 5_000,
});
```
