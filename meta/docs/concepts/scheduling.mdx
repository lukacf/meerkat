Meta uses Meerkat's durable `ScheduleService` as its only scheduling
authority. Schedule definitions live in the schedule store, every firing is
claimed as an occurrence, and the firing host records the outcome before it
advances.

<Warning>
The stateless `meta/scheduling/evaluate` and
`meta/scheduling/dispatch` methods were removed in contract 0.5.0.
`runtime_options.scheduling_files` is also rejected. Static TOML evaluation
never owned durable firing authority.
</Warning>

## Enable schedule tools

Enable schedule tools on the member profile:

```toml
[profiles.operator.tools]
schedule = true
```

The gateway binds the member's
`meerkat_schedule_{create,get,list,update,pause,resume,delete,occurrences}`
tools and the firing host to the same `ScheduleService` and store.

To read those tools' definitions (names, descriptions and JSON input schemas)
from a running gateway, call
[`meta/schedule/tools`](/api/rpc#meta%2Fschedule%2Ftools), or
`MobHandle.schedule_tools()` in Python and `MobHandle.scheduleTools()` in
TypeScript. It returns Meerkat's base definitions without touching the
schedule store. Inside a member's session, `meerkat_schedule_create` and
`meerkat_schedule_update` also accept a `current_session` session target.

## Durable ownership

A persistent gateway stores schedules under its state directory. The firing
pipeline has four parts:

1. `ScheduleService` owns definitions and occurrence state.
2. The schedule host resolves due occurrences.
3. The host claims each occurrence before target delivery.
4. The terminal firing result is written back to the same store.

This makes restart recovery and duplicate suppression properties of the
schedule domain itself. Callers do not poll a tick oracle or keep a second
schedule registry.

## Targets

Schedules can target:

- a session
- a mob member
- a named host runnable

An agent schedules for itself, or for an agent of its own mob that it is
wired to. A schedule
an agent's own schedule tools write for any other target that names an
agent is refused as a policy denial (`schedule_target_not_a_peer`), in the
same words whether the name is an agent it is not wired to, an agent of
another mob or a name no agent holds. Schedules the host writes, and the
Console's schedules, are not judged this way.

A schedule can also have the gateway create something when it fires: a
fresh session (a session target of type `materialize_on_demand_session`) or
a helper (a mob target of type `spawn_helper` or `fork_helper`). The fresh
session is built as the gateway builds a session by default, and the helper
from the role the schedule names, so these are not every agent's to write.
On a stock gateway every agent is a mob member: an agent's create, update
or resume of a schedule that creates a session is refused as a policy
denial (`schedule_session_creation_not_allowed`), and a schedule that
creates a helper is taken only from an agent whose profile holds the mob
tools as well as the schedule tools (`tools.mob` and `tools.schedule`); the
helper is then held to that agent's tool access policy, so give an agent
both only if it may hold the tools of every role it can name. An agent can
still read, pause and delete such a schedule. A gateway whose Meerkat host
configuration sets `agent_schedules_may_create_sessions = true` under
`[tools]` takes both kinds from every agent that holds the schedule tools;
the host configuration is the file
[`meerkat_config_path`](/reference/configuration#sdk-and-gateway-runtime-options)
names. Schedules the host writes are not judged, and a schedule stored
earlier fires as before.

Python applications register deterministic host runnables with
`MetaBuilder.host_runnables(...)` and handle
`callback/schedule_fire` through `MetaRuntime.on_schedule_fire(...)`.
TypeScript applications use `MetaBuilder.hostRunnables(...)` and
`MetaBuilder.onScheduleFire(...)`, or `MetaRuntime.onScheduleFire(...)` on a
runtime they already have; see [Host runnables](/sdks/typescript#host-runnables).
The callback is delivery for a durable occurrence, not a substitute scheduler.
A handler for a schedule that can be due when the gateway starts belongs on
the builder: `MetaBuilder.on_schedule_fire(name, handler)` in Python or
`MetaBuilder.onScheduleFire(name, handler)` in TypeScript. The gateway can
fire such a schedule before `build()` returns the runtime, and a fire that
finds no handler ends that occurrence as `delivery_failed`. A handler given
to the builder can run before `build()` returns, so it must not need the
runtime object. Python releases 0.7.32 to 0.9.16 have no handler on the builder:
a program that uses `build()` there cannot have its handler in place for such
a fire, see
[Schedule callbacks that arrive during startup](/sdks/python#schedule-callbacks-that-arrive-during-startup).

Every member that holds the schedule tools and is not private to a person
can create a schedule that fires any runnable the host registers, with
parameters of its choosing (the handler reads them as the occurrence's
`payload`). The fire does not tell the handler who wrote the schedule.
Register only runnables that any such member may fire, and check the payload
in the handler.

## Console schedules

The Console keeps an agent's **console schedules** in the same store:
messages a Console caller defines in the agent's details pane and the Console
sends to the agent later. Each is a durable schedule whose target is the host
runnable `meta.console.scheduled_send`, which the gateway reserves: an
application cannot register a host runnable or callback under that name, an
agent's schedule tools cannot create a schedule that names it, and those tools
neither list nor change console schedules. Each fire is a Console send by the
caller who defined the schedule, judged when it fires: the Console admits that
caller as it would admit a live request by them, then sends as a live send by
them is sent. A refused send fails that occurrence, and the schedule keeps its
later times. See [Schedules](/guides/console#schedules) for
the Console and [Console schedules](/api/rpc#console-schedules-console) for the
methods.

The memory steward's scheduled pass is reserved in the same way. A gateway
with the steward enabled keeps one schedule whose target is the host
runnable `meta.memory.steward.dream` and retimes it itself: an application
cannot register a host runnable or callback under that name, an agent's
schedule tools cannot create or retarget a schedule that names it, and those
tools neither list nor change the host's steward schedule.

The gateway's own steward schedule carries the label
`meta.memory.steward.schedule`, which an agent's schedule tools refuse on a
create or an update. At each start the gateway keeps that schedule, resumes
it if it is paused, sets it to the configured interval, and deletes any
other schedule that names the steward's runnable. A store written by an
earlier version holds no schedule with the label: the first start after an
upgrade deletes the schedules that name the runnable and creates the
gateway's own, so the steward's first pass after an upgrade comes one
interval after that start.

## Rust embedding

Rust embedders can supply a schedule store and attach both schedule tools and
the firing host through `meerkat_meta::schedule_wiring`. Keep those two
surfaces on one `ScheduleService`; using separate stores would split
authoring from firing authority.

## Migration from static scheduling

1. Remove `.scheduling(...)` from Python and TypeScript builders.
2. Remove `runtime_options.scheduling_files`.
3. Create schedules through the `meerkat_schedule_create` tool or
   `ScheduleService`.
4. Bind deterministic application work as a host runnable when needed.
5. Inspect occurrences through `meerkat_schedule_occurrences`.

Unknown `runtime_options.scheduling_files` fails `meta/init` with
`-32602`. Calls to either removed `meta/scheduling/*` method return the
standard `-32601` method-not-found error.
