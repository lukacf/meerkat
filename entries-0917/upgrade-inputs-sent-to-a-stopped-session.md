- A session that an earlier release stopped after a peer response without a result (see Fixed, "Peer requests: a response to a peer request without a result no longer stops the requester"): what was sent to it while it was stopped. At the first start on this release, as at any start on 0.9.15 and 0.9.16, an input that was queued behind the stop is ended as abandoned and is not run, however soon that start comes: send it again; new work runs (by the source a stop ends every queued input except a durable prompt that a graceful stop keeps for the next start, and has ended them at least since 0.5.2). The exception seen: a message that a Meta gateway took with an idempotency key (`meta/send` with `idempotency_key`) is run at that start, once, and sending it again under the same key makes no second input and answers the session and input ids (by the source a keyed send is admitted as a durable prompt, which a graceful stop keeps for the next start, and an unkeyed send to a member in the default mode is an event, which a stop ends; the stores of the runs show the two kinds so). A kept prompt has a time limit of fifteen minutes, counted from the stop that kept it. In these states the earlier release's stop of the stopped session had not finished (its stores show no stop mark and an unfinished unregister with that limit), so it is finished at the next start and the limit counts from that start: the keyed send ran sixteen minutes after the stop for that reason (read from the source and from the stores before the start). After a stop that did finish, a kept prompt is ended as `requeue_expired` at a start more than fifteen minutes later (read from the source; not run here). No log line and no event reports an abandoned input to a host; a program that embeds Meerkat and waits on the input in the same process is given its end (read from the source). Where the caller holds the input's id its status can be asked (`session/input_status`; `meta/send_status` on a Meta gateway) and reads `abandoned` without a reason; a `meta/send` without a key answers no input id. (Shown by runs on the published 0.9.15 and 0.9.16 and on a candidate build of this release: abandoned at starts from under one second to six hours after the stop; the keyed send run at starts 7 seconds, 57 seconds and 16 minutes after it, on the published 0.9.16 gateway and on the candidate's.)
