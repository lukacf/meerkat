---
title: "Set up an agent frontend"
description: "Connect a chat or device interface to an agent through your application."
icon: "comments"
---

A frontend lets people talk to an agent through Slack, Telegram, a web app or a device. The application runs the interface and owns participant identity, conversation routing and reply delivery.

For service operations such as reading Slack history, use [service setup](/guides/request-an-integration). To let people send messages to an agent through that service, follow the frontend flow below.

## Start the setup conversation

Follow the [CLI quickstart](/quickstart#standalone-cli), choose a realm and
describe the frontend you want at `You:`. There is no separate frontend mode to
select. Keep the application that will run the frontend running; the local realm
holds the setup conversation, while that application owns the frontend.

When the agent requests host selection, use the protected terminal prompts:

- **the paired host:** select the running host and complete device pairing. Choose
  whether to remember the pairing or keep it only for this process. The optional
  `--paired-host <origin>` startup flag selects the host before the conversation.
- **Forge application:** enter its actual Console origin in the form
  `http://127.0.0.1:PORT`, then its Console password. Sign-in is kept only in memory
  for this process. Use the port shown by the running application, not a guessed port.

Keep host addresses and credentials out of chat. Enter pairing codes and
passwords only in those protected prompts. The selected application must provide
frontend management; a package listing alone does not supply it. In an integrated
application, use that application's setup entrypoint instead.

## Choose the host and conversation

Select a persistent application that supports the interface. A realm supplies native configuration and storage; the application supplies the listener, routing and delivery lifecycle.

Describe the interaction you want:

```text
Let the approved Support group talk to the existing Work Assistant
in our support channel. Keep each admitted thread separate and send
replies into that same thread.
```

## Configure the interaction

| Setting | Choose |
| --- | --- |
| Interface | Provider installation, endpoint and account |
| Participants | People or groups allowed to send, view and control |
| Target | The existing agent or routing policy |
| Conversations | How provider channels and threads map to agent context |
| Replies | Permitted destinations and visible output |
| Service access | Operations the agent may perform for those participants |
| Lifetime | Persistent or time-limited exposure |

Use the host's protected controls for provider credentials. Sign in to the application separately from connecting the provider account.

Choose from the settings the selected host actually offers. The paired host channel
frontends route messages to each sender's own agent, so that flow has no separate
destination-agent choice.

## Review and activate

Review the exact package, configuration, participants and requested service authority. Apply executable or deployment changes through the application's deployment workflow.

Read the host's result before treating the frontend as active. A submitted or
queued request may still need an operator review, build or activation. The paired host
submission creates an operator review request; it does not itself start the
frontend.

After activation, send a message from an admitted identity. Confirm that it reaches the intended agent and that its reply returns to the permitted conversation. Check an excluded participant as part of the application's access validation.

## Keep the application running

The application owns the frontend after setup ends. Its process lifecycle is separate from the setup conversation. Use its current status to inspect connection, routing and delivery health.

## Pause or remove

Review what happens to accepted work and queued replies before pausing or disabling the frontend. The application can drain that work or cancel it according to its policy. Remove a shared daemon or credential only after checking the other integrations that use it.

## Build the adapter

The [frontend authoring guide](/guides/agent-frontends) describes provider verification, principal admission and delivery contracts. The [Python frontend SDK](/sdks/python-frontends) supplies transport and durable egress components.
