- Behaviour-only (not measured by the gate): a persistent `meta_gateway` (`persistent_sessions: true`) with no mob definition file (`config/mob.toml` or `<workspace>/definition.json`) is now served on a state directory that holds a built-in default mob in cases where its start was refused before. The built-in default mob's id was derived from the launch, so a start was refused (`the supplied mob definition diverges from the canonical definition in this storage, in: id`, answered as `-32603` `failed to bootstrap local runtime`) whenever one of these launch inputs differed from the launch that created the mob: the workspace path, `store_path` as the launch spells it, the realm, the isolation setting, the runtime profile, the Console's read-only setting, the runtime, project and context roots, the compaction policy, the HTTP listen address and public base URL, the control listener, the host configuration file, the workspace's configuration files, `manifest.toml` and every file under `skills/`, `hooks/`, `mcp/` and `config/`, `auth_config` and `console_voice`, the flow editor's host deploy switch, and the release version. The gateway now takes the mob id the state directory records, so such a start serves that mob under any of them, from any workspace, with one exception that another check of this release makes: a launch whose project root (the workspace root when it names none) is, or lies inside, the state directory, the gateway home or the provider credentials root is refused with `-32602` on the request's `id`. A state directory created under a sign-in configuration and started again without `auth_config` is served on a Console that identifies nobody, where that start was refused before. A mob with a definition file always behaved so, because its id never depended on the launch. Before a start, check that `store_path` names the state directory of the mob you mean to run and that the launch carries the `auth_config` its Console needs. Meta 0.9.9, the oldest release looked at, through 0.9.16 refused such a start.
