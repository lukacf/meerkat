Meerkat's tool system is trait-based. You implement `AgentToolDispatcher`, and the engine handles dispatch, parallel execution, and result injection. MCP servers are first-class -- register them and their tools appear alongside your custom tools with no code changes.

## Mental model

At the concept level, tools answer one question: **how does the agent act on the world?**

The important conceptual layers are:

- custom tools you own
- built-in tools Meerkat can compose
- MCP-provided external tools
- runtime visibility/scoping rules

The Rust trait example below is an implementation detail of that model, not the model itself.

## Custom tools

Implement the `AgentToolDispatcher` trait:

```rust
struct MathTools;

#[async_trait]
impl AgentToolDispatcher for MathTools {
    fn tools(&self) -> Arc<[Arc<ToolDef>]> {
        vec![Arc::new(ToolDef::new(
            "add",
            "Add two numbers",
            json!({
                "type": "object",
                "properties": {
                    "a": {"type": "number"},
                    "b": {"type": "number"}
                },
                "required": ["a", "b"]
            }),
        ))].into()
    }

    async fn dispatch(&self, call: ToolCallView<'_>) -> Result<ToolDispatchOutcome, ToolError> {
        match call.name {
            "add" => {
                let args: AddArgs = call.parse_args()
                    .map_err(|e| ToolError::invalid_arguments(call.name, e.to_string()))?;
                Ok(ToolResult::new(call.id.to_string(), format!("{}", args.a + args.b), false).into())
            }
            _ => Err(ToolError::not_found(call.name)),
        }
    }
}
```

`ToolCallView` is a zero-allocation borrowed view (`{ id: &str, name: &str, args: &RawValue }`). When the model requests multiple tool calls, Meerkat dispatches them in parallel.

## MCP servers

Register any MCP server and its tools automatically appear in the agent's tool set:

```bash
rkat mcp add filesystem -- npx -y @modelcontextprotocol/server-filesystem /tmp
rkat mcp add api --url https://mcp.example.com/api
rkat mcp add --transport http knowledge https://mcp.example.com/v1
```

Config is stored in `.rkat/mcp.toml` (project) or `~/.rkat/mcp.toml` (user). Supports stdio, streamable HTTP, and SSE transports. OAuth-protected HTTP servers discover auth at connect time; use `rkat mcp login <name>` or `rkat run --mcp-auth interactive` when browser login is needed. See the [MCP reference](/api/mcp) for full details.

## MCP Apps in UI hosts

A host with an isolated MCP Apps renderer can opt in with
`AgentFactory::mcp_apps(true)`. Its MCP connections advertise
`io.modelcontextprotocol/ui` and capture the original tool definition,
arguments, full `CallToolResult` and available UI resource before model
projection. Headless factories leave this capability disabled.

App authors use standard `_meta.ui.resourceUri`, `ui://` resources and
`text/html;profile=mcp-app`. UI-only result `_meta` remains in native session
persistence, outside model requests and public transcript projection. Resource
reads do not require the resource to appear in `resources/list`.

`ToolAudience` separates model and app visibility while retaining normal tool
scope and policy checks. MCP tools default to both audiences; explicit
`_meta.ui.visibility` narrows them. An app-only tool is unavailable to model
selection and deferred catalog search/load. Visibility is not authorization:
every app action still enters the current member's native tool policy.

UI hosts submit `ToolApplicationControlRequest` through `SessionService` with a
trusted, revalidatable ingress and an exact session/tool-call locator. Governed
hosts must implement fresh tool-application authorization through their native
work-policy owner. The prior agent run's authorization is never reused. Resource
context providers implement `prepare_resource` separately from tool-call
credential preparation.

Native session-service App IO can run while the model turn continues. Each
request uses an executor minted by the original Agent with its current tool
scope and configured hooks and review. Results without session effects or hook
notices return without loading or saving the accumulated transcript. Actual
effects and notices wait for that exact actor to apply them; persistent services
commit them before response delivery. This decision uses the collected outcome,
not `readOnlyHint`; a post-hook error or a disconnected caller does not cancel
required settlement. Custom `SessionAgent` implementations that do not provide
this executor keep serialized execution.

The runtime binds live operations to the originating physical MCP connection.
Retained views can replay without re-executing the tool; retirement, replacement
or process restart refuses new IO against the old binding. App code cannot pick
another server by supplying a name. Developer panels belong to the embedding
product's Console integration. An MCP App can use its own renderer for a
versioned generated UI document without another host authoring contract.

## Built-in tools

Meerkat ships with tool categories resolved per agent. Factory category flags
default off; product surfaces may apply their own explicit preset (for example,
the CLI defaults to `--tools safe`).

| Category | Tools | Enable with |
|----------|-------|-------------|
| Builtins | `task_create`, `task_list`, `task_get`, `task_update`, `datetime`, `apply_patch`, `view_image`, `blob_save_file`, `blob_load_file`, `blob_inspect` | `enable_builtins` |
| Image generation | `generate_image` | inherited visibility when the normal runtime substrate is wired; explicit `override_image_generation` for independent minimal composition |
| Web search | provider-native search or the Meerkat-owned `web_search` fallback | `override_web_search` (or a surface convenience flag) |
| Shell | `shell`, `shell_jobs`, `shell_job_status`, `shell_job_cancel`; high-trust `monitor_start` is opt-in | `enable_shell` plus tool policy |
| Memory | `memory_search` | `enable_memory` |
| Scheduler | `meerkat_schedule_*` | `enable_schedule` |
| WorkGraph | `workgraph_*` | `enable_workgraph` |
| Comms | `send_message`, `reply_to_peer`, `send_request`, `send_response`, `peers` | `enable_comms` |
| Mob orchestration | `delegate`, `conclude_objective`, `mob_*` | `enable_mob` |

Shell tools support allow/deny list security policies. Runtime tool visibility can also be shaped with mob overlays and turn-boundary tool-scope updates. See the [built-in tools reference](/reference/builtin-tools) for parameter details.

Image generation and web search are independent category decisions. Enabling
either one does not implicitly expose general builtins. Conversely, disabling
general builtins does not prevent a runtime-backed build from explicitly
enabling one of those capabilities. Explicit enables fail closed when the
selected runtime cannot provision the requested capability.

The current direct `rkat run`, REST, and JSON-RPC session builders leave image
generation at `inherit`. In a normal composite dispatcher, that can expose
`generate_image` when the session identity, image machine, executor, planner,
and blob store are wired and tool visibility policy permits it. The minimal
no-builtins/no-shell path instead needs an explicit image-generation `Enable`
to avoid the factory's early return. These direct surfaces do not expose that
enable switch. `--allow-tool generate_image` only narrows an already composed
surface; it cannot provision missing dependencies or enable the category.

For nontrivial Meerkat-owned tool families, companion skills provide the agent
instruction manual. Tool descriptions stay short and schema-oriented; skills
such as `workgraph-workflow`, `schedule-workflow`, `task-workflow`, and
`shell-patterns` explain the operating posture for the tool family.

## Execution contracts

Tool visibility and tool execution are separate decisions. A visible tool has
an execution contract that declares the modes it supports:

- fast execution for ordinary request/response calls
- streaming execution with progress and cancellation policy
- detached execution backed by a durable job record

The runtime resolves a call to one supported mode, applies the narrowest
deadline in the chain, and supervises progress or cancellation through the
same tool gateway. Detached execution records its restart class explicitly.
For example, a background shell command is `non_resumable`: its durable job
truth survives a host restart, but a lost subprocess becomes `worker_lost` and
is never silently replayed.

Tool definitions also carry source provenance, and dispatchers classify calls
as read-only, mutating, or unknown. Hooks and policy layers receive those typed
facts rather than inferring authority from a tool name.

## Tool scoping

Tool visibility can change during a session without restarting the agent. Changes are **staged** then **atomically applied** at the turn boundary — the LLM never sees a tool list change mid-stream.

**External filters.** Callers can stage an allow-list or deny-list filter programmatically through `ToolScopeHandle`. This is distinct from MCP server lifecycle management.

**Per-turn overlays.** Mob flow steps can restrict tools for a single turn via `TurnToolOverlay` (allow + deny). The overlay is ephemeral — it's cleared after the turn completes.

**Live MCP mutation.** MCP servers can be added or removed from a running session. Additions connect the server and register its tools; removals drain in-flight calls before finalizing. Both are staged and applied at the next turn boundary.

**Composition rule:** Most-restrictive wins. Multiple allow-lists intersect, multiple deny-lists union, and deny always beats allow. The conversation records a typed `tool_config` system notice when the tool set changes, and a `tool_config_changed` event is emitted to the event stream.

### Live MCP controls

MCP servers can be added, removed, or reloaded on a running session via JSON-RPC, REST, MCP-server tools, or SDK helpers:

```json
{"jsonrpc":"2.0","id":1,"method":"mcp/add","params":{
  "session_id":"...",
  "server_config":{"name":"my-tools","command":"npx","args":["-y","@my/server"]},
  "persisted":false
}}
```

| RPC Method | Effect |
|------------|--------|
| `mcp/add` | Connect a new MCP server, register its tools |
| `mcp/remove` | Drain in-flight calls, disconnect server, remove tools |
| `mcp/reload` | Reconnect one or all servers (picks up config changes) |

All mutations are staged and applied at the next turn boundary. Set `persisted: true` to write the change to disk config so it survives restart. See the [RPC reference](/api/rpc#mcp-methods) for full parameter details.

Since 0.9.4 the `tool_config_changed` event that reports the outcome carries `settled`, which says whether the change is a settled lifecycle fact rather than a pending or draining step; it never said whether anything was written to config. Events and notices stored by 0.9.3 and earlier carry `persisted` in its place, so a reader should accept either key. The `persisted` field of `mcp/add`, `mcp/remove` and `mcp/reload` keeps its name and meaning.

### Surface availability

| Surface | Live MCP | External tool filter |
|---------|----------|---------------------|
| JSON-RPC | `mcp/add`, `mcp/remove`, `mcp/reload` | Via in-process `ToolScopeHandle` on the session runtime |
| CLI | `rkat mcp add/remove/list/get` edits project/user config; start or resume a session to load it | No standalone public CLI filter surface today |
| REST | `POST /sessions/{id}/mcp/add`, `remove`, `reload` | No standalone public REST filter surface today |
| MCP server | `meerkat_mcp_add`, `meerkat_mcp_remove`, `meerkat_mcp_reload` | No standalone public MCP filter surface today |

### Scoped tool grants

A build can mark built-in tool families and individual tool names
**grant-gated**. A gated name is mounted, a gated family as if it were enabled,
but it stays hidden from the model and is refused at dispatch until a live
scoped tool grant that covers it is admitted. A grant never widens a session
past its build: it opens only names the build gated, and the static tool
policy, the application tool policy, governed authority, review and
confinement all still apply to every call it opens.

- **Gating a build.** In Rust, set `grant_gated_tools` on
  `SessionBuildOptions` or `AgentBuildConfig`, for example
  `GrantGatedTools::default().with_family("shell").with_tool("deploy")`. The
  session records its gate, and a resume that names none restores it. The
  factory refuses a gate that no grant could honour with
  `BuildAgentError::GrantGate`: an unknown family, a gated family the build
  disables, a gated family none of whose tools the build mounts (comms tools
  mount only with a comms runtime), a gated name the build does not mount (a
  name a still connecting MCP server may provide is gated from the moment it
  appears), a name the build's tool policy refuses, and a build without the
  runtime's grant service. A gate that covers `web_search`, by name or through
  its family, disables the provider's native tools for the session, including
  native search that the session's or a turn's provider params ask for, so the
  gated tool is the only search path.
- **Granting.** `MeerkatMachine::grant_tool` issues a grant for a subject (a
  session), a target (one tool name, or a built-in family with the names it
  provides, which `meerkat::tool_family_names` answers) and a window of at most
  the host policy's maximum lifetime, 24 hours by default.
  `revoke_tool_grant`, `list_tool_grants` and `read_tool_grant_audit` complete
  the Rust API; `ToolGrantService` offers the same operations over any
  `RuntimeStore`.
- **Adjudication.** Every model-request boundary opens the gated names a live
  grant admits at that moment, and every gated call is adjudicated again
  immediately before it is handed to its tool, so a call at or after the
  deadline is refused even when the boundary that showed the tool ran before
  it. A refusal is an ordinary `policy_denied` tool error with the code
  `tool_grant_required`, `tool_grant_expired`, `tool_grant_revoked` or
  `tool_grant_unavailable`. When the grants cannot be read, the gate stays
  closed and the session records a warning notice.
- **Lifecycle.** The canonical `ToolGrantLifecycleMachine` owns each grant:
  issued, then expired at its fixed deadline or revoked before it. Expired and
  revoked grants stay ended across restarts and host clock rollbacks. The
  runtime's deadline timer expires a served session's grants on time, and a
  list or audit read settles the due grants of any session without loading
  it; nothing about a grant wakes a dormant member. Grants live in the runtime
  store, on SQLite in the `runtime-tool-grants` schema domain that the first
  write of a grant or audit row creates (a refused call's audit row is one).
  With the in-memory store, Web/WASM included, they last only for the
  process.
- **Audit.** Each subject's grants append to one audit log: `granted`,
  `expired` (with the driver that observed the expiry), `revoked` and
  `refused` rows. A lifecycle row commits with the grant's change; a failed
  refusal row never admits the call.
- **Limits.** The dispatch gate is the authority; what the model is shown
  follows it at the next model-request boundary. A live session keeps the
  tool surface its live bridge opened with, so a name a grant opened stays
  visible there after the grant ends, and the dispatch gate refuses each call. A control-plane
  tool, such as the deferred catalog's search and load tools, is never hidden
  by a gate; a gated one is refused at dispatch until a grant opens it. A
  grant row this binary cannot read (written by a newer binary, or damaged)
  opens nothing and blocks none of its subject's other grants; a list reports
  it. A binary older than scoped tool grants does not know a session's gate:
  it resumes a gated session with its gated tools ungated, so upgrade every
  host that serves gated sessions before relying on a gate.

A scoped tool grant confers no authority of its own: it only opens, for a
bounded time, names the build gated. Governed authority grants
([Agent authorization](/concepts/authorization)) decide whether an operation
may run at all, and an application tool policy's member tool grants
(`CompiledMemberToolGrant`) decide which tools a member may use and with what
consequence. Both still apply to a call a scoped grant opened.

## Multimodal tool results

Tools can return rich content beyond plain text. The injected runtime shape is `ToolResult.content: Vec<ContentBlock>`, with helper constructors for text-only or multimodal output.

- **`ToolResult::new(...)`** -- the standard text-only path. The string becomes a single text content block.
- **`ToolResult::with_blocks(...)`** -- returns one or more content blocks directly, including images and video.
- Built-in tools that expose richer output may internally use `ToolOutput::Blocks(...)`, but the persisted/runtime-facing result shape is still `ToolResult.content`.

`ContentBlock` is non-exhaustive and currently has five variants:

- `ContentBlock::Text { text }` -- plain text content.
- `ContentBlock::Image { media_type, ... }` -- inline or blob-backed image content.
- `ContentBlock::Video { media_type, duration_ms, ... }` -- inline or URI-referenced video content. Video blocks are accepted only on Gemini user-message input paths and are rejected in tool results. Vertex Gemini can consume `gs://` references directly; Gemini API sessions can consume public or already-registered file URIs, and register `gs://` references first when the session has Google bearer auth.
- `ContentBlock::Structured { data }` -- canonical opaque JSON returned by a
  tool without first stringifying it into text.
- `ContentBlock::SkillContext { skill_key, text }` -- runtime-authored skill
  activation context with its canonical source identity preserved.

The built-in `view_image` tool reads an image file from disk and returns a result containing image content blocks. It supports PNG, JPEG, GIF, WebP, and SVG formats up to 5 MB. The tool is automatically hidden from models that lack vision support via capability-aware tool visibility.

The built-in `generate_image` tool is session-owned runtime dispatch. It lets a model request generated or edited images through universal fields plus provider-owned `provider_params`. Generated image bytes are stored as blobs and committed as `AssistantBlock::Image` transcript blocks, so every surface reads the same `image_id`/`blob_ref` history and fetches bytes through `blob/get` or model-facing `blob_save_file`.

The blob file bridge tools are registered only when the session has a blob store. `blob_save_file` writes decoded blob bytes to a file inside the project root, `blob_load_file` reads a project file into the blob store, and `blob_inspect` returns blob metadata without raw payload bytes. They do not expose blob listing or deletion.

Custom tools can return text, image, or structured content through
`ToolResult::with_blocks(...)`. Video tool results are rejected, and
`SkillContext` is reserved for the runtime skill-injection path.

## Image generation

`generate_image` is a session-owned tool for creating or editing assistant
images. It is registered when the runtime-backed surface supplies the
image-generation machine, provider executor, planner, and blob store. In the
normal composite dispatcher, `Inherit` is visible once that substrate is wired.
The category can also be enabled independently from general builtins through a
Mob profile or an in-process `override_image_generation: Enable`.

The tool accepts a typed request under `request`, routes it to OpenAI or Gemini image backends, stores generated image bytes in the realm blob store, and returns structured `ImageGenerationToolResult` JSON with durable `images[].blob_ref` values. A model can then call `blob_save_file` to materialize that blob as a project file, for example `top-news-infographic.png`.

For setup, provider parameters, result fields, and troubleshooting, see [Image generation](/guides/image-generation).

## Composition

Tools from different sources (custom, MCP, built-in) are composed into a single dispatcher. The agent sees one flat tool list regardless of where each tool comes from. Hooks can observe tool calls before and after execution, and guardrails can deny unsafe calls before dispatch.

## Mob tools (`meerkat-mob-mcp`)

Mob tools (`mob_*`) are provided by the `meerkat-mob-mcp` dispatcher and composed
through the late-bound `SessionBuildOptions.mob_tools` factory slot.

- CLI `run` composes this dispatcher when the `full` tool preset is selected (`--tools full` or `--yolo`).
- `rkat mob ...` remains the explicit direct lifecycle surface.
- Other session-driven surfaces can grant the same agent-side `mob_*` capability
  by installing `AgentMobToolSurfaceFactory` into their session build path.
- Public host APIs should not re-export that raw dispatcher. They use typed
  control planes instead: `mob/*` on RPC/SDK surfaces and `meerkat_mob_*` on
  public MCP surfaces.
