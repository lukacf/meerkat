- Peer requests: a response to a peer request without a result no longer stops the requester. On a host whose realm is on disk, a session that had sent a peer request stopped running once it had handled a response that carried no result (the agent tool `send_response`, or a host's or SDK caller's `peer_response`, with status `accepted`, `completed` or `failed`): the SQLite runtime store refused to record that run as finished, the log had ERROR `failed to durably publish directed interaction terminal ... terminal completion finalization lost the exact durable CAS` and WARN `runtime-loop exit teardown did not complete; the registration is detached ...`, and from then on every input to the session was accepted and never ran, or on some doors was refused, while the session still read active; on `rkat-rpc`, `runtime/health` read degraded under `session_runtime_loop` and `mob/destroy` answered `mob destroy incomplete`. Now the store's exact compare of an input row takes the stored bytes first and keeps the typed re-encoding as a second reading for rows of an older stamp, which alone ends the stop; and a peer response whose result is JSON null is admitted with no payload, at the comms ingress and at `session/peer_response_terminal`. No stored form and no wire form changes. Two rendered lines change in the process that received the response: a final response without a result is no longer shown to the receiving agent with a line `Result: null`, and a comms notice without a payload no longer with `Payload: null`; the instruction texts agents are shown do not change. What this does not do: a session that an earlier release stopped stays stopped while its host runs. After a restart of the host a stop caused by a final response is over, as it already was on 0.9.16, and the work queued behind it is abandoned at that start and not run, except a message that a Meta gateway took with an idempotency key, which is run (see Upgrade notes); a stop caused by a progress response (`accepted`) is the subject of the recovery entry of this release. One narrow case stays: a pending completion whose stored row has the current version stamp and a null payload, read after a restart, is still refused (read from the source, not run). A run whose structured output is JSON null was a separate defect: see the item after this one. Affected: 0.9.5 through 0.9.16 (by the source at the release tags; shown by runs on builds of the 0.9.5, 0.9.11 and 0.9.15 tags and on the published 0.9.14, 0.9.15 and 0.9.16; a build of the 0.9.4 tag did not stop). (Shown by tests that fail on the 0.9.16 code, and by runs with a real model on an `rkat-rpc` built from the store change alone: after a response with status `accepted` and no result, three of three, and with status `completed` and no result, three of three, the requester ran its next message, `runtime/health` read ok, `mob/destroy` completed and the log had neither line, where the published 0.9.16 stopped two of two each; a response with its typed result, one of one, as before. The ingress change, a `failed` response and the hosts other than `rkat-rpc`: by tests or read from the source.)
