## Known limitations

The known limitations of Meta 0.9.16 are in the release's own notes: section 0.9.16, Known limitations, of meta/CHANGELOG.md at this tag (https://github.com/lukacf/meerkat/blob/meta-v0.9.16/meta/CHANGELOG.md). Read the Upgrade section of the same file before you upgrade. One step was found after the release notes were written and is printed below; it will also be in the upgrade guide and in meta/CHANGELOG.md on main, where later entries are added too.

- Added 2026-11-17, after the release. Upgrade: a persistent `meta_gateway` on its built-in default definition does not start after the upgrade until its definition is given as a file. This is a `meta_gateway` launched with `persistent_sessions: true` in a workspace that has neither `config/mob.toml` nor a definition file. What you see: the gateway exits with code 1 and answers `meta/init` with `{"error":{"code":-32603,"message":"failed to bootstrap local runtime"},"id":null,"jsonrpc":"2.0"}`; the reason is only in the gateway's log: `the supplied mob definition diverges from the canonical definition in this storage, in: id`. Nothing is lost, and the 0.9.15 gateway still starts on that state. Do: copy the `definition` object from `<state directory>/event_log.sqlite3.composition.json` (by default the state directory is `<workspace>/state`) into a new file `<workspace>/definition.json`, then start the 0.9.16 gateway: it starts on the recorded mob, with its members and their sessions. You can do this before the upgrade or after the first refused start. This is not new in 0.9.16: it holds for every upgrade of such a gateway since Meta 0.9.9. The stdio gateway (`rpc_gateway`, which the SDKs start) is not affected. Shown by a run from the published 0.9.15 gateway to the 0.9.16 release candidate; that it holds since 0.9.9 and that the stdio gateway is not affected are read from the source.

- Added 2026-11-17, after the release. TypeScript SDK: when a gateway that the SDK started refuses the start after it has accepted the init request, and exits, the Node program can end with an unhandled `write EPIPE` error instead of `builder.build()` rejecting. In the maintainers' runs on Linux with Node 22 that happened in 5 of 8 starts (7 of 8 on 0.9.15); in the others `build()` rejected with `GatewayStartupCleanupError` as documented. A refusal that the gateway gives as its answer to the init request is not affected. Until it is fixed, install a `process.on("uncaughtException", ...)` handler before calling `build()` and remove it with `process.off` once `build()` has settled. In the handler, ignore only this error (`error.code === "EPIPE"` and `error.syscall === "write"`); for any other error, print it and exit with a non-zero code, as Node does without a handler; do not throw from the handler. The `EPIPE` then arrives in the handler and `build()` rejects with `GatewayStartupCleanupError` (in 10 of 10 starts on the published 0.9.16 on Linux with Node 22, where the refusal was a missing console configuration file; the `EPIPE` arrived in the handler in 8 of them; not run on macOS or on Windows). While it is installed the handler also swallows a `write EPIPE` on the program's own output. A fix is planned.

- Added 2026-11-17, after the release. Peer requests between mob members: on a host whose realm is on disk, a member that has sent a peer request (`send_request`) stops running when a response to that request arrives without a result. That is a `meta_gateway` or `rpc_gateway` that keeps persistent state in a state directory (the tell is the file `runtime.sqlite` in that directory), whatever the session format; for Core's own hosts see the entry of the same date on the Core 0.9.16 release page, https://github.com/lukacf/meerkat/releases/tag/v0.9.16 (read from the source). A response is what an agent's `send_response` sends, or a host's or SDK caller's `peer_response`; its `result` is optional. The documented `comms/send` call lists `result` as optional for a `peer_response`, and a call that leaves it out sends a response without a result (the Python and TypeScript SDKs' `send`, RPC, REST and the MCP tool `meerkat_comms_send`; read from the source, not run). An agent can send one, and the texts it is shown lead to it: the instruction a responding agent is shown with each request gives `completed` without a result as its example, and the built-in mob communication guidance names `accepted` as the status for progress. (In the maintainers' runs a model that was told nothing about how to answer a `checksum_token` request answered `completed` with the typed result, 3 of 3, and the requester kept running.) Messages (`send_message`, `reply_to_peer`) are not responses and are not affected, and the responses Meerkat itself sends always carry a result (read from the source). When the requesting member has handled such a response, the store refuses, at every try, to record that run as finished, and the member runs nothing further. No caller is told. The member's status still reads `active`, `idle` and `healthy`; a message sent to it afterwards is accepted and never runs (runtime mode `autonomous_host`, the default) or is refused with `session '<id>' has no committed runtime attachment; explicit create or resume is required (unregister_not_started)` (`turn_driven`); what is queued for it stays queued. The gateway's log shows it with the default settings: `ERROR meerkat_runtime::runtime_loop: failed to durably publish directed interaction terminal run_id=<id> error=... terminal completion finalization lost the exact durable CAS`, then `WARN meerkat_runtime::runtime_loop: runtime-loop exit teardown did not complete; the registration is detached until an explicit resume completes its unregister` (on this release that resume does not complete it; read from the source). A stop of the host then logs `failed to unregister runtime session <id> during mob teardown` and exits with status 0. A response that carries a result does not stop the requester (shown for `completed` and for `accepted`, each with a result). The tool takes only a typed result: for a `checksum_token` request `{"request_intent":"checksum_token","request_subject":"<subject>","token":"<token>"}`; any other object is refused by the tool (`data did not match any variant of untagged enum CommsPeerResponseResult`), and the contract names no result for a `failed` response to a `checksum_token` request (read from the source). Until the fix, on such a host, keep members from sending peer requests: add `send_request` to the `deny` list of the tools of every profile that has the comms tools (`[profiles.<name>.tools]` with `deny = ["send_request"]`, leaving `comms = true`); on a state directory that already holds the mob, declare the change with the one-shot mob definition update (`declare_spec_update`), because a start whose definition differs from the stored one is refused as `divergent`. Members then no longer have the tool and use `send_message` and `reply_to_peer` (shown by a run of the published 0.9.16 `rpc_gateway`: the member's model no longer lists the tool and does not call it, also a member that existed before the change, from the first start after the declared update; messages between the members work). It takes effect at a start of the host, so set it on a host on which no member has stopped. Helpers a member spawns take their tools from that member and lose `send_request` with it (read from the source); a profile used to spawn a member from a session that does not carry the entry wants the same entry. It does not stop a peer request that a host or an SDK caller sends itself, and `send_response` stays, so a member can still answer such a request without a result. A member that has stopped this way: nothing an operator can call brings it back on this release (read from the source, not run): a resume of the mob and a later message do not. DO NOT retire, respawn or rotate the member, and do not reset or destroy the mob. Do not restart the host on a guess: after a stop caused by an `accepted` response, a host that was ended and started again came up with the member's status `broken` (shown by restarts of the published `rpc_gateway` on copies of such states, 0.9.16 twice and 0.9.15 once, and once on a build of the release commit); the host's log then says `Recovery corruption: pending terminal owner <id> is absent from the live shell (settlement: Unproven)`, and a message to the member is refused with an error that carries `the member is Broken until retired or respawned (repair required: retire or respawn the member)`. After a stop caused by a `completed` response without a result, a restart brought the member back, and what had been queued for it was abandoned, not run: it has to be sent again (shown on copies of such states, 0.9.16 and 0.9.15, once each; `failed` not run). The log with its default settings does not say which kind of response stopped a member, and the member's status reads the same; its timeline does: in the answer of `meta/console/query_timeline` for the member, the last run that started has one frame of kind `peer_content_ingested` for every peer input it took, just before its `run_started` frame or after it: if any of them has `payload.kind` `response_progress`, do not restart; if all of them have `response_terminal`, a restart brings the member back; the `run_started` frame of a run that a peer response started carries the text `Peer response progress` or `Peer response terminal` (shown in the stopped host on the published 0.9.16: two stops by `accepted`, one by `completed`, each run with one response and its frame just before `run_started`; several inputs in one run, and a frame after `run_started`: read from the source). Read it before any restart and copy the state first, as said below; where no such frame is found, do not restart. In the `broken` state, do not follow the error's advice: `retire_member` and `respawn_member` are both refused with an error that carries `runtime_retire consumer refused bridge session <id> [composition_endpoint_unbound]`, the member is left `retiring`, and the next start of the host then fails for the whole mob (`Runtime bootstrap failed: failed to bootstrap mob runtime: mob actor reply channel closed`). `rotate_member`, `retire_all` and a retire of an ancestor with its descendants retire the member the same way (read from the source); whether a reset or a destroy of the mob does is not known, so leave those as well. A further restart and `force_cancel_member` change nothing. Leave the member as it is, send it nothing, and keep a copy of the state directory together with the members' comms identity directory, which is not inside it: by default, under the account that runs the host, `$XDG_STATE_HOME/meerkat/session_comms_identity` (else `~/.local/state/meerkat/session_comms_identity`) on Linux, `~/Library/Application Support/meerkat/session_comms_identity` on macOS and `%LOCALAPPDATA%\meerkat\session_comms_identity` on Windows, or `<root>/.rkat/session_comms_identity` where `session_identity_config_root` is set. A copy of the state directory started without it has every member refused with `cannot publish its comms endpoint: ... respawn the member to mint a new endpoint` (shown by a run); do not follow that advice here either. If a retire or respawn was already tried and the host no longer starts, keep the state directory untouched and report it. The member's history can still be read: `meta/console/query_timeline` and the Console's timeline answer for the member, the last answer of the interrupted run included. The `broken` state after a restart is older than the stop and has another way in: a host that ends, for any reason, while a member's run is unsettled leaves the member refused in the same way if that run was started by, or consumed, a peer's progress response to a request the member had sent (read from the source; shown by runs of the published 0.9.16 `rpc_gateway` and `meta_gateway` on the saved state of one such occurrence). Affected: the stop, 0.9.5 through 0.9.16 (by the source at the release tags, and shown by runs on builds of the 0.9.5, 0.9.11 and 0.9.15 tags and on the published 0.9.14, 0.9.15 and 0.9.16; a build of the 0.9.4 tag did not stop, 3 of 3); the `broken` state, 0.8.11 through 0.9.16 (by the source at the release tags). A gateway without persistent state does not get the stop: its runtime state is in the in-memory store (read from the source, not run on a gateway). For Rust hosts see the Meerkat changelog's limitation of the same name: a memory realm and a realm kept through the host store interface do not get it; a runtime store of the host's own implementation was not read. (The stop is shown by runs of the published `rpc_gateway` with a real model on Linux, a mob of two members, one `checksum_token` request: 0.9.16: stopped in 5 of 5 with `accepted` without a result, in 3 of 3 with `completed` without a result, in 2 of 2 with a `turn_driven` requester; not stopped in 3 of 3 with `completed` with a result and in 3 of 3 with `accepted` with a result; 0.9.15: stopped in 3 of 3 with `accepted` and in 1 of 1 with `completed` without a result, not stopped in 2 of 2 with a result; 0.9.14: stopped in 1 of 1, not stopped in 1 of 1 with a result. On builds of the release commit and of the 0.9.15 tag also with `failed` without a result (6 of 6). Not run: `meta_gateway`; a mob with a roster; a host's or SDK caller's `peer_response`; releases before 0.9.14.) Fixes for the stop and for the `broken` state are being prepared.
