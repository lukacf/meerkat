- A configuration that defines `gpt-6.2-astra` or `gpt-6.2-sol` itself (a `[models."gpt-6.2-sol"]` entry, for example because you ran the model on 0.9.16 before the catalog listed it) must drop that entry when upgrading: the catalog now has both ids, and a second definition of a model id is refused with "model id '<id>' must be unique across built-in, custom, and self-hosted entries". The refusal comes when the configuration is loaded, not when the model is first used, so with such an entry the hosts do not start: `rkat-rpc` ends at its start with exit code 1, having served nothing, and its error line reads "rkat-rpc: invalid runtime config: Validation error: " and that message (an SDK sees only that the process closed); by the source every `rkat` command that loads the runtime configuration answers "Invalid runtime config: Validation error: " followed by that message, and the REST server and a Meta gateway refuse to start. An entry in a mob definition is refused when one of the mob's members is built. Two ways to take the entry out were run. Before the upgrade, on 0.9.16: the RPC `config/patch` with `{"models": {"gpt-6.2-sol": null}}` removes it (from then until the upgrade 0.9.16 does not resolve the model). After a refused start: remove the `[models."gpt-6.2-sol"]` table from the realm's `config.toml` by hand (in the run it lay under `.local/share/meerkat/realms/<realm>/` in the home directory). After either, this release starts and the catalog row serves the model with its own limits and reasoning effort levels (see Added). (Shown by runs with `gpt-6.2-sol` on a realm that the published `rkat-rpc` 0.9.16 wrote, where a turn through the entry had answered, and an `rkat-rpc` built from the source of this release's catalog change: the refused start, both ways out and a turn on the model after each. Read from the source, not run: `rkat`, the REST server, a Meta gateway and a mob definition's entry.)
