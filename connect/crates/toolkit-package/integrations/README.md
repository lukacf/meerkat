# Maintained integration recipes

`bundled_integration_library()` loads the retained versioned packages through `IntegrationBundle::parse`. The parser reads real Agent Plugins 1.0.0 plugin and MCP documents, validates their toolkit package namespace, and joins the source observations and typed recipes. No process, network request or credential access occurs while loading. Metadata from a failed or skipped portable import is rejected.

There are 14 retained package versions across 11 distinct publisher/name package identities. They contain 17 strategy recipes: six remote service recipes and eleven guidance-only recipes. Exactly one recipe is an agent frontend. Gmail, Slack and Google Calendar each retain both `0.1.0` and `0.2.0`; retaining another version does not add another service. No live service operation or frontend deployment is certified by this inventory. All current assessments are experimental. These counts are neither operation counts nor supported-service counts.

The Toolkit metadata is MIT OR Apache-2.0. Each `recipes.json` records observed source-byte hashes, commit/release where available, and the narrower upstream license scope. Documentation hashes identify inspected bytes, not deployed servers. Source/license observations do not clear transitive dependency licenses. Newcomer account, OAuth, administrator and host prerequisites are typed alongside each recipe. Registration-dependent or artifact-dependent recipes remain usable investigation guidance without becoming executable selections.

## Using the library

Agents inspect `library.catalog()` or `DiscoveryTools::from_library(&library)`, then make their own integration choice. The existing list/read discovery tools return package identity and digest plus a separate `library_digest` for complete retained inputs. A read of library-backed metadata requires both digests. Pagination snapshots include configuration and prerequisites. Plain `DiscoveryTools::new(&catalog)` remains compatible with metadata-only catalogs. There is no fuzzy matcher, ranking policy or automatic integration selection.

Call `library.get(&identity, &library_digest)` for the exact retained bundle. Selection never upgrades a prior version or switches strategy after denial. Gmail and Google Calendar `0.2.0` expose concrete preview endpoints while their REST operation libraries remain guidance until the host supplies the missing activation/authentication binding. Calendar's preview guide advertises write tools but its sample read/freebusy scopes do not grant mutation authority. An endpoint recipe is not a usable-account or readiness receipt. Slack `0.2.0` keeps both strategies guidance-only: the documented MCP endpoint and private Python read-operation proof do not supply host registration, credentials or an activated export. A setup agent can inspect `servers()` for the portable endpoint and `recipes()` for prerequisites and source observations. `validate_selection(&library_digest, manifest, &host_capabilities)` constrains a concrete `ActivationManifest` to that recipe, then delegates to the existing manifest validator and host capability checker. It rejects endpoint/publisher substitution, missing authentication declarations, unsupported export roles, guidance-only strategies and missing host capabilities. The provider-documented read-only variants also reject declared writes. This metadata check does not certify an operation's classification.

The caller must supply actual selected configuration and policy references, current observed MCP schema/contract, bounded operations, credential-owner binding and lifecycle owner contracts. The library does not invent these values. The configuration revision in the remote component must equal the selected configuration revision. Successful validation returns the existing `ValidatedManifest`; activation, grants, authentication, effect classification and readiness remain their existing owners' work. A separately investigated endpoint requires its own explicit package recipe rather than substitution into an existing version.

## Conformance and maintenance

Offline conformance exercises retained bundle imports, complete discovery reads, exact digests, manifest validation, host capability gaps and refusal paths. It neither contacts a provider nor establishes a usable account. Before promoting a service/deployment combination, retain owner evidence for authentication, actual account/resource scope, live tools/schemas, pagination/result limits, denial/revocation, cancellation/cleanup and effects. Frontend promotion additionally needs multi-user isolation, replay, audience restrictions, admission and uncertain-delivery evidence. Those acceptance obligations remain open.

Maintainers revise a package version whenever instructions, prerequisites, endpoint configuration or source observations change. Duplicate identity with changed bundle content is rejected. Retain prior versions for explicit migration/replacement decisions. Refresh provider observations and verify endpoint/schema drift before live activation; an old successful support assessment cannot override current policy. Local and private libraries can use the same byte parser and exact insertion API without automatic publication.
