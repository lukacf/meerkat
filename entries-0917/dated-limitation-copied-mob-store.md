- Added 2026-11-17, after the release. Mobs: a copy of a mob's store file that is left in the mob root can become the file the mob runs on, and what the mob does then is lost when the copy is removed. A host that restores its mobs from disk takes for a mob's store every regular file directly in `<persistent storage root>/mobs` whose name begins with `mob--` and whose extension is exactly `db`; nothing between is looked at, and the mob's id is read from the records in the file, not from its name. Taken: `mob--x-copy.db`, `mob--x (copy).db`, `mob--x.bak.db`. Not taken: `mob--x.db.bak`, `mob--x.bak`, `mob--x.db.orig`, `mob--x.DB`, `copy-of-mob--x.db` and any file in a subdirectory. Where two taken files hold the same mob id, the mob is served from whichever of the two the directory lists first, which can be the copy; the other is refused at its resume and kept as it was found, and the rest of the restore goes on. From then on the mob's changes (a member added, for one) go into the file it is served from; where that is the copy and the copy is removed later, the next start serves the original and those changes are gone, with no error. The only sign is one line in the host's log at each start while both files are there, which names the mob id and not the file: it begins `WARN meerkat_mob_mcp: quarantining a persisted mob store: the rest of the restore goes on mob_id=<id> class=resume_refused error=participant name '<id>/__mob_supervisor__' already has a live route`; the inventory's list of quarantined stores stays empty for it. To avoid it, keep a backup of a store file outside the mob root or under a name that is not taken: a copy kept as `mob--<id>.db.bak` in the mob root was left alone, byte-identical, with no warning, over four starts. Where the line is in the log, find which of the two files the mob runs on before removing either: `sqlite3 -readonly <file> "select count(*) from mob_events;"` on each, with the host running or stopped; the file with more rows is the one the mob runs on (in both orders in the runs: 4 against 3). A modification time alone is not a safe sign: a fresh copy is newer than the original until the original is written again. Reading a store file in place left a `-shm` file and an empty `-wal` file beside it (the `.db` file stayed byte-identical); run the count on copies made elsewhere to leave nothing there. Affected as described: 0.9.9 through 0.9.16 (run on a build of the 0.9.16 tag, ten passes in both orders, on Linux ext4; read at 0.9.9; the releases between by a search of all tags by content). Earlier releases differ, read from the source and not run: in 0.8.24 through 0.9.3 (read at both) a refused second file fails the whole restore, every mob access answers the error and nothing is destroyed; 0.9.4 through 0.9.8 leave the second file unrestored with another warning (not traced further); before 0.8.24 the mob resumed second could be destroyed, and the first could be the copy: on those releases leave no copy in the mob root. Not run: taking the file the mob does not run on out of the mob root as a step of its own (removing the copy the mob ran on was run: the next start served the original); a second process on the same root; other platforms. Read from the source, not run: a taken file that holds no events is removed by the restore. Not read: which RPC or CLI calls answer from the inventory. No fix is in 0.9.17.
