Correction to the operator guidance in the analyst report above: on MobKit 0.8.31, `mobkit/retire_member` followed by `send` does NOT re-materialize the member. Evidence from the MobKit implementation branch (meerkat-mobkit/src/identity_first/runtime.rs): retire leaves the identity in `Retiring` and nothing moves it to `Dormant` (the only `Dormant` setter applies to `Active | Suspended` on lease release); `embody_identity` refuses `Retiring` with `InvalidState { operation: "materialize" }` and `send_core` only materializes `Dormant | Uninitialized`. The continuity record itself is untouched by retire (same session id and generation; only the destructive `reset_*` behind `respawn_member` advances the generation), which is why the new `mobkit/reload_member` verb (0.8.32) = retire with memory hooks skipped, explicit `Retiring -> Dormant`, then re-embody the same session under one lifecycle lock, is non-destructive; tests assert session id and generation unchanged and no fresh session created. Until 0.8.32, the validated recovery for a repair-blocked member is a cold process restart (OB3 measured: complete recovery, nothing durable poisoned).
