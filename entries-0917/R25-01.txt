- Behaviour-only (not measured by the gate): the answer of `meta_gateway` (the Console gateway binary) to a `meta/init` whose runtime bootstrap is refused or fails. The answer is now on the request's `id`. A mob composition provenance refusal (the state directory holds a mob that the launch's definition does not match, or a composition manifest that cannot be judged) answers `-32019` with the refusal's `kind` and facts as `error.data` (for example `{"kind": "divergent", "fields": [...], "manifest": ...}`) and the message `Runtime bootstrap failed: failed to bootstrap mob runtime: <reason>`, as the stdio gateway answers it; before, it answered `-32603` with `id: null`, no data and the message `failed to bootstrap local runtime`, and the reason was on standard error only. Any other bootstrap failure keeps `-32603`, now on the request's `id` with the message `Runtime bootstrap failed: <reason>` (before: `id: null` and `failed to bootstrap local runtime`). A client that starts this binary and matched these refusals on `-32603`, on a null `id` or on that message must match `-32019`, the request's `id` and the new message. Meta 0.9.9, the oldest release looked at, through 0.9.16 answered the old way. No new code and no new kind: `-32019` and its kinds are the ones the SDKs' `CompositionProvenanceError` already carries, and the SDKs start the stdio gateway, which is unchanged. The gateway's own log line for such a start is the `meta/init refused` warning with the code and the reason, in place of the `gateway startup failed` error. A start that fails before its answer at one of the exits that fall to the binary's last catch still answers `-32603` with `id: null`; the other refusals of an init (a refused declaration, `-32602`; a storage refusal, `-32014`; a failed bind, `-32603`) are answered on the request's `id`, as before.
