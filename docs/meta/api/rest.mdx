Meta serves a REST API over HTTP using Axum. The API provides console access, runtime inspection, timeline replay, JSON-RPC ingress, legacy console send compatibility, multipart upload/send, and blob retrieval.

## Base URL

```
<http_base_url>
```

The console/admin `meta_gateway` and SDK-facing persistent `rpc_gateway`
bind an available loopback port and report the exact `http_base_url` in their
`meta/init` result. Use that value for every route on this page; do not
assume port 8080. A Rust library host chooses its own listener and must supply
that base URL to its clients.

## Console endpoints

### `GET /console`

Returns the admin console HTML page. The page is a self-contained single-page React application with no external dependencies.

**Response:** `text/html`

### `GET /console/assets/console-app.js`

Returns the console React bundle as JavaScript.

**Response:** `application/javascript`

### `GET /console/assets/console-app.css`

Returns the console stylesheet.

**Response:** `text/css`

## JSON API endpoints

### The mob of a request (`mob_id`)

A request to the Console names the mob it is for with `mob_id`. A request
without it is for the launch mob (the mob the gateway's launch names). Send
`mob_id` only to a gateway that lists the feature capability
`mob_addressing` in [`meta/capabilities`](/meta/api/rpc): an earlier gateway
ignores the parameter on the GET routes and on `POST /console/send`, and
refuses the body member on `POST /console/send/recover` and the
`/console/mcp-apps/*` routes.

| Routes | Where `mob_id` goes |
|--------|---------------------|
| `POST /console/rpc`, `POST /console/rpc/multipart` | a top-level member of the request's `params` |
| `GET /console/experience`, `/console/modules`, `/console/identities`, `/console/timeline`, `/console/timeline/stream`, `/console/identity/{identity}/stream`, `/console/gating/stream` | a query parameter |
| `POST /console/send`, `/console/send/recover`, `/console/mcp-apps/resolve`, `/console/mcp-apps/read-resource`, `/console/mcp-apps/call-tool` | a member of the JSON body |

- No `mob_id`, the launch mob's id, or `null` in a body or in `params`: the
  request is served as one that names no mob.
- Any other id, an empty one included: HTTP **404** with
  `{"error":"foreign_mob_target","requested_mob_id":"<id>"}` on a route, and
  on the request doors a JSON-RPC error `-32602` whose `data` is
  `{"kind":"foreign_mob_target","requested_mob_id":"<id>"}`. The answer is
  the same for an id no mob has and for a mob the caller may not address,
  and it names the requested id and no other mob. A Console that requires
  sign-in answers a request without valid credentials **401** first,
  whatever the request names.
- A body member `mob_id` that is neither a string nor `null`: HTTP **400**
  with `{"error":"invalid_request","message":"mob_id must be a string"}`
  (on the request doors `-32602`).

A caller may address a mob other than the launch mob when access control is
not enforced, when the caller is an administrator, or when an allow rule
that applies to the caller lists that mob in `mobs`. Every caller the
Console lets in addresses the launch mob.

The announcement methods that carry a `mob_id` of their own
(`meta/mob_announcements/announce`, `get`, `audit/list` and the
`sources/*` methods) name the mob they act on with it. That id is judged
with the caller in the same way: a mob other than the launch mob that the
caller may not address is answered the refusal above. So is the `mob_id`
of the four methods over the mobs of a host that act on one mob
(`meta/mobs/get`, `meta/mobs/lifecycle`, `meta/mobs/redefine` and
`meta/mobs/destroy`).

Of the twelve routes of the last two rows, the two send routes
(`POST /console/send`, `POST /console/send/recover`) serve the mob a
request names and the other ten serve the launch mob only in this
release. The request doors serve another mob on these methods only:
`meta/status`, `meta/find_members`, `meta/get_member`, `meta/list_members`,
`meta/stop_member_run`, `meta/delivery/history`, four `meta/console/*`
methods (`inspect_identity`, `query_timeline`, `send`, `recover_send`),
two `meta/mob_events/*` methods (`query`, `subscribe`; the address
`subscribe` hands back is of the named mob's stream), the six
`meta/schedule/*` methods of an agent's console schedules (`create`,
`delete`, `list`, `pause`, `resume`, `update`), the five
`meta/topology/*` methods (`query`, `plan`, `apply`, `operation/get`,
`audit/query`), thirteen `meta/identity/*` methods (`adopt`, `archive`,
`changes_hold`, `create`, `directory`, `get`, `list`, `operation`, `plan`,
`remove`, `unarchive`, `update`, `withdraw`) and twenty-five
`meta/workgraph/*` methods (`attention/break_glass_reassign`,
`attention/list`, `attention/pause`, `attention/prune`,
`attention/reassign`, `attention/resume`, `block`, `claim`, `close`,
`create`, `events`, `evidence/add`, `facts`, `get`, `goal/confirm`,
`goal/create`, `goal/request_close`, `goal/status`, `link`, `list`,
`policy/escalate`, `ready`, `release`, `snapshot`, `update`). A request on one of
those ten routes, or of any other method that is neither a method of the
host nor one whose own parameter names the mob it acts on (the voice
methods included), that names another mob is answered the refusal above
for every caller. A method of the host, such as `meta/console/whoami`,
takes no mob as a selector: an id beside it is judged with the caller as
on every method (a mob the caller may not address, and an id no mob has,
are answered the refusal above) and then selects nothing, so the request
is answered as one that names no mob. The methods whose own parameter
names the mob they act on are the announcement methods and the four
methods over the mobs of a host named above: that id is judged with the
caller. A client that works with
another mob sends `mob_id` on the listed methods and leaves it out
elsewhere.

A Console mounted without a runtime knows no mob by an id: it refuses every
`mob_id` a request names, its own mob's included, and does not list
`mob_addressing`. A client therefore does not send `mob_id` on every
request: it sends it to a gateway that lists the capability.

### `GET /console/experience`

Returns experience metadata describing the current runtime state. This is the primary data source for the console UI.

**Response:**

```json
{
  "agent_sidebar": {
    "title": "Agents",
    "live_snapshot": {
      "agents": [
        {
          "agent_id": "agent-001",
          "member_id": "lead-1",
          "label": "Team Lead",
          "kind": "autonomous_host",
          "mob_id": "ops-team"
        }
      ]
    }
  },
  "activity_feed": { "title": "Activity" },
  "chat_inspector": { "title": "Chat" },
  "topology": {
    "title": "Topology",
    "live_snapshot": {
      "nodes": [...],
      "node_count": 5,
      "mob_id": "ops-team",
      "mobs": [
        { "mob_id": "ops-team", "state": "running", "member_count": 4 },
        {
          "mob_id": "research",
          "parent_mob_id": "ops-team",
          "host_identity": "lead-1",
          "state": "running",
          "member_count": 1
        }
      ]
    }
  },
  "health_overview": {
    "title": "Health",
    "live_snapshot": {
      "loaded_modules": ["router", "delivery", "memory"],
      "loaded_module_count": 3,
      "running": true
    }
  }
}
```

When a Meerkat mob runtime is configured, the response includes live agent data from the mob. Without a mob runtime, only module-level information is returned. When console UI config is loaded, the response includes `console_config`, the view-level contract consumed by the bundled console.

An agent row in `agent_sidebar.live_snapshot.agents`, and its rows in
`identity_status` and `health_overview`, can carry `last_activity_ms`: the
newest time, in milliseconds since the epoch, that the console's frame log
recorded the agent acting (a live runtime event, a console send or a tool
application). Frames rebuilt from session history or synthesized by the
console do not count, and neither do lifecycle records (respawn, retire,
reset, delete), interaction failures and memory events, which record
something done to the agent. The field is advisory: a row without it has no
known activity, and reading it wakes no agent. A row answered pending (below)
keeps it, since the frame log answers it, not the read model.

The gateway reads each agent's newest acting frame from the log on the first
experience after it starts that lists the agent, 256 agents per store call,
and keeps the time in memory after that. At 10,000 agents that first read
takes about 56 ms in all when the agents' newest frames record them acting,
and longer when many of those frames do not (rebuilt history, for example),
at about 0.4 to 0.9 microseconds per such frame. A retire, a delete or a
clear made meanwhile waits for at most one such call, and so do the console
writes queued behind it.

`topology.live_snapshot.mob_id` is the id of the mob whose members the
topology shows, when one mob is known: a runtime's console reports its own
mob, and a shared console the mob of its one registered runtime. It is absent
on a shared console over several runtimes or none, and from a snapshot a host
builds without it. The console names the topology's team from it, never from
`runtime_id`.

After 0.9.17, `topology.live_snapshot.mobs` lists every mob a runtime's console shows the
caller: its own mob and each mob one of its members created (nested under
that member's mob, at any depth). A mob the host created is a mob of its
own, served by its own id: this list does not hold it, and a read over
every mob (`mobs=*`, below) lists it to a caller who may address it.
Each entry has:

| Field | Meaning |
|-------|---------|
| `mob_id` | The mob's id. A mob definition names no title, so the console puts the id in words. |
| `parent_mob_id` | The mob it is nested under: the mob of the member that created it or, when the caller is listed no member of that mob, the nearest mob above it the caller is listed. Absent for a top-level mob. |
| `host_identity` | The identity of the member that created the mob, as the experience lists that member. Absent when the experience does not list that member to the caller. |
| `state` | `running` or `stopped`; `unknown` when nothing observed it. Treat a value you do not know as `unknown`. |
| `member_count` | How many of its members the experience lists for the caller. Never zero. |

Every agent row and every topology node of such a console carries `mob_id`,
the mob it is a member of.

**Member identities.** A member of the console's own mob is named by its bare
name in `agent_id`, `member_id` and `identity`, as before. A member of any
other mob is named by its mob and its name in one string, `<mob id>/<name>`
(for example `research/analyst-1`), in those same fields, in a node's
`identity`, in `wired_to`, in `mobs[].host_identity`, in the identities read,
on its frames and in every request that names it: send that string back as you
read it. A mob's id never holds `/`, so the first `/` ends it; the name after
it may hold any character. A bare name names a member of the console's own
mob only, so two members with one name in two mobs never share an identity
and a request with a bare name never reaches a member of another mob. The
row's `label` is the member's display name, never the string that holds its
mob.

A member of a mob other than the console's own carries the labels
`source_mob_id` (its mob) and `group`, and `delegate_host_identity` (the member
that created its mob) while the experience lists that member to the caller.
The console writes these labels itself from the mob the member's roster row
belongs to and from the mob's creation record: a value a spawn wrote under
either name is discarded.

A mob is listed only through members the experience lists for the caller. A
mob in which the caller is listed no member is absent, also when a mob nested
under it is listed, and also for an access admin: nothing tells a caller that
a mob exists in which that caller sees no member. So a mob with no member at
all is listed to no one, and so is a mob whose members the console's
visibility policy hides, such as the mob the `delegate` tool runs its helpers
in on the stock console.

Which mobs a console can list comes from each mob's creation record: a mob a
member created (with its own `mob_create`, with `delegate`, or through a
create the host made for that member's session).
A mob created for a session that is no member's is not listed, and none of
its members is: a temporary council's mob is such a mob, and so is a mob a
session created with its own create capability while no roster named it, and
a mob from a store older than 0.9.4, whose creation was not recorded. The
list is absent from a console that lists no mob (a shared console over
several runtimes, or a snapshot a host builds without it). Reading it wakes
no member and loads no mob: a dormant member is listed from its mob's roster
like a live one.

`health_overview.live_snapshot.running` is the mob owner's answer when the
experience is read. A console served from the console aggregator answers for
its registered runtimes: `true` only while every registered runtime's mob is
creating or running, and `false` when at least one is not. Without a runtime
that can answer (no live mob runtime, or an aggregator with no registered
runtime), it is `null`, and the snapshot names it in an `unobserved` marker:
`{"reason": "not_observed", "fields": ["running"]}`.

An identity-first member's records take its session from the identity
runtime, never from a walk made under an earlier identity binding. When the
member's binding has moved (after a reset, retire or delete), a read collects
the member again first and waits at most 2 s. Past that bound, the member's
sidebar row answers with the identity runtime's session, the member's run
`progress` and state `unknown`, and offers no send or retire. Each record of
the member (the sidebar row, the `identity_status` and `health_overview`
rows, and the topology node) withholds the other facts the earlier walk
found and names them in an `unobserved` marker with reason
`refresh_pending`, for example
`{"reason": "refresh_pending", "fields": ["label", "role", "state", "wired_to", "addressable"]}`
on the topology node. Access and visibility still decide on the last
observed facts, so a label-scoped deny keeps such a member hidden.

### Every mob the caller may address (`mobs=*`)

A gateway that hosts more than one mob lists `mob_addressing` in the
feature capabilities of [`meta/capabilities`](/meta/api/rpc). Send `mobs` only
to such a gateway. Three reads take the query parameter `mobs=*`:
`GET /console/experience`, `GET /console/timeline/stream`, and
`GET /console/timeline` on a request without `identity`
(`meta/console/query_timeline` takes `"mobs": "*"` in its `params` the same
way). Without `mobs` each of them answers for the launch mob alone, as
before.

With `mobs=*` the experience lists, in `topology.live_snapshot.mobs`, the
launch mob and every other mob the gateway hosts that the caller may
address, loaded or not, each at the top level, with the mobs nested under
each. An entry:

| Field | Meaning |
|-------|---------|
| `mob_id` | The mob's id, unique on the gateway. |
| `parent_mob_id` | The nearest listed mob it is nested under. Absent for a top-level mob. |
| `host_identity` | The row key of the member that created it, while that member is listed to the caller. |
| `state` | `running`, `stopped`, `dormant` (known and not loaded: no member rows, no `member_count`; a request that names the mob loads it), `unavailable` (its store did not load) or `unknown`. Read a value you do not know as `unknown`. |
| `member_count` | How many of the mob's members the document lists to the caller. Absent for a mob that is not loaded. |
| `provenance` | `host` (the gateway's host created it: a top-level mob with a door of its own) or `member` (a member created it). An open list. |
| `default` | `true` for the launch mob. |
| `incarnation` | An opaque token of this creation of the mob. When it differs from the value last seen for the same `mob_id`, the mob was created again: drop what you kept under that id. |

A member row (`agent_sidebar.live_snapshot.agents[]`) is keyed by
`identity`, by the door it was read on: on the launch mob's door the
member's name as that door knows it (the bare name for a member of the
launch mob, `<nested mob id>/<name>` for a member of a mob nested under
it), and on the door of another hosted mob `<that mob's id>/<the name as
that door knows it>`. A row states three more things, the same on every
read of the experience: `mob_id` is the door (the launch mob's id on the
launch mob's door, never the member's own mob), `member_mob_id` is the mob
the member sits in, and `member_name` is its bare name there. Take a
member's own mob and name from these two members, never from the key: two
members of one door can spell one key (a member named
`<nested mob id>/<name>` beside the member `<name>` of that nested mob),
and the two differ in `member_mob_id` and `member_name` alone. In this
version a console that lists the members of nested mobs lists neither
member of such a pair as a row; `meta/console/list_identities` lists each
of the two to a caller it answers for that member.

A request for a member carries `mob_id` = its door (absent for the launch
mob's door) and names the member in one of two ways: by `member_mob_id`
and its bare name in the member word, which names the member of exactly
that mob; or by the one string its door knows it by. A request that names
by one string a spelling two members share, where its method would answer
the caller for both, is refused (`-32602`, `data.kind`
`member_mob_id_required`, with the string in `data.identity`) by a method
that takes `member_mob_id` and reads the name from `identity`; every other
method reads it for the member of the door's own mob. Four methods of this
contract take `member_mob_id`: `meta/console/inspect_identity`,
`meta/console/query_timeline`, `meta/console/send` and `meta/retire`. A
request that carries `member_mob_id` on a method that does not take it is
refused (`data.kind` `member_mob_id_not_accepted`, with `data.method`).
No route takes it: `POST /console/send`, `POST /console/send/recover`,
`GET /console/timeline`, `GET /console/timeline/stream` and
`GET /console/identity/{identity}/stream` refuse a request that carries it
(the two `POST` routes in the body, once it parses; the three `GET`
routes in the query) with HTTP 400 and `error`
`member_mob_id_not_accepted`; a body member that is `null` is read as no
member. Send `member_mob_id`
only to a gateway that lists `mob_addressing`.

Every name a member row carries of its own member (`identity`,
`member_id`, `agent_id`) is the row key; the bare name stands in
`member_name` alone. An
entry of a host list that names a member (a pending approval, an audit
record) names it by the pair a frame carries: `mob_id`, absent for the
launch mob, beside the member's name as that mob knows it.

The contract document lists, for each method, the member of `params` that
names a member (`member_params`: `identity` for most, `member_id` for
`meta/stop_member_run`, `source_member_id` for `meta/fork_member`, `name`
for the `meta/identity/*` changes). On a request to a hosted mob it carries
the member's name as that mob knows it. A method that serves one mob and
names no member takes `mob_id` alone. In the answer of a method served for
one mob every member it names, in any field, is named as that mob knows
it: turn it into a row key with the request's mob, as for a frame. A
method of the host takes no mob;
the one that names a member, `meta/access/preview`, takes the member's row
key in `identity` and is judged in that member's own mob.

There is no load request. An ordinary request that names `mob_id` loads a
mob that is not loaded, and a console opens a mob a person chose with
`meta/status` naming it; any caller who may address the mob may send it.
Send no request of your own accord (a periodic read, a gap repair) that
names a mob listed `dormant` or `unavailable`.

A member's own stream (`GET /console/identity/{identity}/stream`, and the
timeline stream or `GET /console/timeline` with `mob_id`) and the
`/console/mcp-apps/*` routes serve the launch mob's members only in this
release. Read another mob's member from the one stream with `mobs=*` and
from `meta/console/query_timeline` naming `mob_id` and `identity`.

The lists of the host that name members (`meta/gating/pending`,
`meta/gating/audit`, `meta/gating/questions`, `meta/console/attention`, and
the console audit read `meta/console/audit`) take `"mobs": "*"` too.
Without it a list answers, of the entries members made, those of the launch
mob's members alone, as before; with it the entries of every mob the caller
may address, each entry a member made naming its mob beside its member's
name. A request made
with no origin is no member's entry: with the selector and without it,
`meta/gating/pending` and `meta/gating/audit` serve it to the callers who
may address the mob it was made for, as a request of the mob that stands
under that mob's id. `meta/decisions/list` takes no
selector: a decision row names no member and no mob.

The two kinds of read differ in this. A list of the host that names
members answers the entries of another mob's members only to a request
that carries `"mobs": "*"`. The host's own records of its mobs, the storage doctor
(`meta/storage/doctor`) and the route list (`meta/routing/routes/list`),
take no selector. A request to either that names the launch mob's id is
served as one that names no mob, and one that names another mob's id is
refused for every caller. Which mobs' stores and routes a caller is
answered is the rule of each method's own entry in the
[method reference](/meta/api/rpc).

Limits of this release. Each of these serves the launch mob only, and a
request on it that names another mob is refused for every caller, unless
its item says how the request is answered:

- ten of the twelve console routes for `mob_id`,
  `GET /console/gating/stream` among them; the two send routes
  (`POST /console/send`, `POST /console/send/recover`) serve the mob a
  request names (another mob is reached through `POST /console/rpc`, the
  two send routes and the reads that take `mobs=*`);
- `GET /console/gating/stream` takes no selector: of the entries members
  made it signals a change only for an entry of the launch mob's members,
  and it signals a change of a request made with no origin to the callers
  `meta/gating/audit` serves that request's rows to;
- a member's own stream and `GET /console/timeline` with `mob_id`;
- the `/console/mcp-apps/*` routes (an interactive view of another mob's
  member is not loaded);
- the voice methods;
- every method of the request doors that the contract document gives the
  scope `launch_mob_only`: `meta/capabilities`, the identity list, a
  member's retire, respawn, reset and fork, the routes list, the memory
  panel and `meta/identity/settle_preparation`;
- every other method of the contract document that is neither of its
  scope `one_mob` nor a method of the host. The
  request doors serve another mob on the methods of that scope (a
  mob's status, its timeline, schedules, topology, delivery history, mob
  events and WorkGraph, a send to a member and its recovery, a member's
  stop, an identity's inspection, and thirteen
  methods of `meta/identity/`: `adopt`, `archive`, `changes_hold`,
  `create`, `directory`, `get`, `list`, `operation`, `plan`, `remove`,
  `unarchive`, `update` and `withdraw`) and on no other method of that
  document, of that prefix or any other. The doors serve further
  methods the document does not list, some of them for another mob: the
  list above names those;
- of a send to a member of another mob: a governed send and its recovery,
  on a gateway whose Console sends can be governed (refused with
  `foreign_mob_target` that carries `hosted: true`); a send on
  `POST /console/rpc/multipart`, with uploads or without; a member named
  by a runtime member id, or with `member_mob_id` in a mob nested under
  that mob (an unknown identity). A mob whose identity plane is not
  attached yet holds a send and its recovery (`-32004`, 503 on a route).

Reading with `mobs=*` loads no mob and is no use of a mob: a periodic read
never keeps a mob loaded. A mob the caller may not address is not listed,
its members are no rows, and no count includes it.

A timeline read with `mobs=*` (`GET /console/timeline`,
`meta/console/query_timeline` and the timeline stream) answers no frame of
a mob that is not loaded, and its cursor moves past that mob's stored
frames: following the cursor does not bring them once the mob is loaded. A
client that opens such a mob (the request that loads it) reads that mob's
timeline, or a member's, from no cursor with `meta/console/query_timeline`
naming `mob_id`.

`mobs` with any value but `*`, together with `mob_id`, together with
`identity` on the timeline read, or on any other route or `meta/*` method is
refused: HTTP **400** with `{"error":"invalid_request","message":"..."}` on
a route, `-32602` on the request doors. The announcement methods
(`meta/mob_announcements/*`) are apart: `mobs` is a member of their own
requests (the mobs a subscription or a declaration is for), and the mobs
it names are judged with the caller.

### `GET /console/modules`

Returns the configured module IDs from `RuntimeDecisionState`. This response
does not contain per-module health or startup state.

**Response:**

```json
{
  "contract_version": "0.6.0",
  "modules": [
    "router",
    "delivery",
    "memory"
  ]
}
```

### `GET /console/identities`

Returns visibility-filtered identities from the console aggregator, including
ordinary runtime/worker identities; an identity-first runtime is not required.
Without a console aggregator, this route returns `404` with
`error: "unavailable"`.

**Response:** `{identities: ConsoleIdentityRecord[]}`. Each record carries
`identity`, `display_name`, `runtime_key`, `runtime_member_id`, optional
`session_id`, optional `member_id` (Core's mob member id of the identity's
last binding, live or retired: the identity's roster member id, as Core's
member tokens name it, which is Meta's comms-safe encoding of the identity and
starts with `mk--` when the identity has a `:`; absent when Core holds no
binding of the identity and on records of raw runtime members),
`visibility`, `addressable`, `health`, `labels`, and
`topology_peers` when non-empty. `labels.role` is the member's role, and, from
0.9.15, for an identity with no live member its profile unless its declared
labels name a role. Address a member by `identity`: for a
member of a nested mob both `identity` and `runtime_member_id` are its mob
and name, `<mob id>/<name>` (see Member identities under `GET /console/experience`),
and an access rule `agents = ["<bare name>"]` matches a member of the
console's own mob only. Use
[`meta/console/inspect_identity`](/meta/api/rpc#meta%2Fconsole%2Finspect_identity)
for identity/peer inspection and `/console/experience` for affordances;
neither identities nor inspection records contain an affordances field.

### `GET /console/timeline`

Returns console timeline frames from the Meta console log store. This endpoint is the REST equivalent of `meta/console/query_timeline`.

| Param | Type | Required | Description |
|-------|------|----------|-------------|
| `identity` | `string` | no | Restrict results to one console identity. |
| `conversation_id` | `string` | no | Restrict results to one conversation. |
| `mode` | `"since"` or `"recent"` | no | `since` scans forward after `after`; `recent` returns the latest visible frames in display order. Defaults to `since` for compatibility. |
| `after` | `console:<seq>` | no | Exclusive lower cursor bound for continuation. |
| `before` | `console:<seq>` | no | Exclusive upper cursor bound, primarily for older-history paging with `recent`. |
| `limit` | `usize` | no | Visible frame limit, clamped by the server. |
</Accordion>

Response frames are visibility-filtered and returned in display order. `next_cursor` is safe to use as the next `after` cursor for `since` pagination; `latest_cursor` is the latest cursor for the target window and is useful for live continuation after a `recent` seed.

The log keeps a streamed block's `text_delta` and `reasoning_delta` frames until the block's `text_complete` or `reasoning_complete` frame is stored, then removes all of them but the first, which keeps the block's place in the timeline: a later read returns that first frame and the complete frame, whose text supersedes it, and live streams have already delivered each delta. A block that never completes keeps its deltas. Cursors are never renumbered, so the cursor of a removed frame still works as `after` or `before`.

```json
{
  "frames": [],
  "next_cursor": "console:240",
  "latest_cursor": "console:240",
  "exhausted": false
}
```

### `GET /console/timeline/stream`

Streams timeline replay followed by live console frames (`text/event-stream`).
It accepts the same query parameters as `GET /console/timeline`, but `limit`
does not bound the whole replay: `recent` produces one bounded seed page
(`limit` sizes it), while anchored `since` replays all retained matching
backlog, sent page by page as it is read, whatever `limit` says. Without
`after`, `since` switches to `recent`. A non-empty `Last-Event-ID` header
overrides the URL's `after` parameter. See the
[timeline SSE contract](/meta/api/sse#console-timeline-stream) for event envelopes
and snapshot markers.

If the requested cursor can no longer be replayed, the route returns HTTP **409** with `{"error":"replay_unavailable"}` and cursor context. Clients should refetch a recent page and resume from `latest_cursor`.

An anchored replay can also end after the stream opened: if the log no longer holds what follows the frames sent (it was cleared during the replay), the stream sends a `replay_unavailable` event and ends, to be handled as the `409`; if a later page cannot be read, the stream ends after the frames it sent, with no `snapshot_complete`, and the client reconnects with the last frame's cursor as `Last-Event-ID`.

### `GET /console/identity/{identity}/stream`

Identity-filtered convenience route for the same console timeline stream. It sets the `identity` filter from the path and accepts the remaining timeline query parameters.

### `POST /console/send`

Legacy console send route backed by the console aggregator. New clients should prefer `POST /console/rpc` with `meta/console/send`.

With `mob_id` in the body the send is for a member of the mob it names,
for a caller the checks of a send admit in that mob: the caller may
address the mob, may know of the member and holds `agent.send` on it
there. The send is recorded and recovered under that mob: one
idempotency key for the members of one name in two mobs is two sends.
For a member of a mob other than the launch mob:

- a governed send, on a gateway whose Console sends can be governed, is
  refused with HTTP **404** and
  `{"error":"foreign_mob_target","requested_mob_id":"<id>","hosted":true}`
  beside a `message` (on the request door `-32602` with `data.hosted`).
  The kind is the one of a mob the gateway does not serve to the caller:
  a client tells the two apart by `hosted`;
- every send on `POST /console/rpc/multipart` serves the launch mob only,
  with uploads or without, and one that names another mob is refused
  with `foreign_mob_target`;
- a member named by a runtime member id, and a member of a mob nested
  under that mob, is an unknown identity (HTTP **404**
  `{"error":"unknown_identity"}`, `-32001` on the request door);
- a mob whose identity plane is not attached yet holds the send: HTTP
  **503** `{"error":"unavailable"}` (`-32004` on the request door),
  and the client asks again.

A steer (`handling_mode` `steer`) to a member whose start has not
settled yet is refused, in every mob: HTTP **409**
`{"error":"host_human_input_refused"}` whose `data.kind` is
`host_human_input_unsupported` (`-32000` on the request door). Its frame
is marked `delivery_failed` under its mob; send the steer again once the
member has started.

### `POST /console/send/recover`

REST twin of [`meta/console/recover_send`](/meta/api/rpc):
the body is `{identity, origin, idempotency_key}`, with `mob_id` for the
send of a member of the mob it names, and the caller is the
request's authenticated principal. It runs the same gate as `/console/send`
(read-only and `agent.send` refusals), in the mob the request names: the
recovery acts on that mob's send of the key and on no other mob's, and
is served for another mob on both request doors too. The recovery of a
governed send, and a mob whose identity plane is not attached yet, are
answered as the send is. A send the caller does not own, or
never made, answers HTTP **404** with `{"error":"send_not_found"}`. A
candidate launch (`runtime_options.mob_composition.authority =
"candidate"`) settles no send and answers HTTP **409** with
`{"error":"candidate_launch"}`, as `/console/send` does: recover the send on
the authoritative launch. It waits for the runtime's admission evidence as
the RPC does: up to 45 seconds in all when the store is slow (after a restart,
reading the evidence loads the session the send recorded), so an HTTP client
whose timeout is shorter gives up first. `console_fetch_timeout_ms`, the bundled
console's fetch timeout, should stay above 45 seconds.

### `POST /console/rpc`

JSON-RPC 2.0 endpoint for console and runtime operations.

### `POST /console/rpc/multipart`

Multipart JSON-RPC endpoint. Supported methods:

| Method | Purpose |
|--------|---------|
| `meta/console/send` | Send console content with image upload placeholders. |
| `meta/blob/upload` | Store a single blob/image and return a blob ID. |

For `meta/blob/upload`, send a `payload` part containing this JSON-RPC
request, plus exactly one binary part named `file:upload-1` with
`Content-Type: image/png`:

```json
{
  "jsonrpc": "2.0",
  "id": "upload-1",
  "method": "meta/blob/upload",
  "params": {
    "upload": {
      "upload_id": "upload-1",
      "type": "image_upload",
      "media_type": "image/png"
    }
  }
}
```

The upload fields may instead be directly in `params`. `part_name` is an
alias for `upload_id`; both identify the suffix after `file:`, with
`upload_id` taking precedence if both are present. `type` is optional and,
when supplied as a string, must be `image_upload`. Optional `media_type`
must match the file part's MIME type. Supported types are `image/png`,
`image/jpeg`, `image/webp`, and `image/gif`, with a **25 MiB per-file** limit.
The result contains `blob_id`, `media_type`, and `size` in bytes, not `url`
or `content_type`. Fetch the bytes through `GET /blobs/{blob_id}`.
Console sends with image placeholders remain subject to the multipart
image-count and per-file byte limits.

### `GET /blobs/{blob_id}`

Returns blob/image content by ID when a blob store is configured.

## Authentication

The reference router keeps its frontend shell and bootstrap assets public:

- `/`, `/favicon.ico`, and `/healthz`
- `/console`, `/console/`, and `/console/assets/*`
- `/flow-editor`, `/flow-editor/`, and `/flow-editor/assets/*`

When `ConsolePolicy.require_app_auth` is `true`, the console JSON, JSON-RPC,
timeline, blob, Flow Editor RPC, and SSE surfaces require a valid JWT. Clients
may use either a bearer header:

```
Authorization: Bearer eyJhbGciOiJSUzI1NiIs...
```

or an exact query parameter:

```
?auth_token=<url-encoded-token>
```

Query values are percent-decoded. URL-encode reserved characters such as `=`,
`&`, `+`, and `%`. Prefer the header except for browser or SSE bootstrap cases.
The token is validated against the fixed trusted OIDC snapshot and configured
auth policy. See [authentication](/meta/guides/authentication) for details.

Meta's built-in console auth is bearer-token based and does not rely on
cookies. Deployments that add cookie-backed console auth at a reverse proxy must
also add CSRF/origin protection for mutating console routes.

Set `ConsolePolicy.read_only` to `true` to serve the console in view-only mode.
Read endpoints and streams remain available, while mutating JSON-RPC methods
such as `meta/console/send`, `meta/blob/upload`, lifecycle controls, gating
decisions, and metadata writes are omitted from `meta/capabilities` and return
a read-only error if called directly.

## Error responses

API errors return standard HTTP status codes with a JSON body:

```json
{
  "error": "unauthorized",
  "message": "Email not in allowlist"
}
```

| Status | Meaning |
|--------|---------|
| `200` | Success |
| `400` | Bad request (invalid parameters) |
| `401` | Unauthorized (missing or invalid token) |
| `403` | Forbidden (read-only policy or insufficient access grants) |
| `404` | Not found |
| `409` | Console timeline replay unavailable or console-send conflict/refusal |
| `429` | Console-send admission backlog full (`admission_backlog_full`) |
| `500` | Internal server error |
| `503` | Console-send actor probe unhealthy, reload refused, or a governed send held |
| `504` | Console-send admission or reload timed out, or a governed send's admission unresolved |

Structured `/console/send` admission failures carry `{error, message, data}`:
`429` uses `admission_backlog_full`, `503` uses `actor_probe_unhealthy`,
`reload_refused` or `governed_input_held` (every bind of the host's binder
answered "not now" until the door's wait budget ended: nothing was
submitted, so send it again under the same idempotency key), and `504` uses
`admission_timeout`, `reload_timed_out` or `governed_admission_unresolved`
(a governed send whose native admission's answer was lost: the input may
have run, so retry it only under the same idempotency key, or read it with
`POST /console/send/recover`, never as a new send; its frame stays
`submitted`, with a `delivery_unresolved` record, until the runtime's
evidence settles it). A governed send the host
refused is `409` `governed_input_refused`.
Preserve `data` when reporting these failures; a timeout does not by itself
establish execution fate or retryability. These REST status mappings are
distinct from the JSON-RPC policy codes documented in the
[RPC reference](/meta/api/rpc#meta-specific-error-codes).
