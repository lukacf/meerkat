- A structured output that is JSON null no longer leaves a record that cannot be read. When a run's output schema admits null at its root and the model answered null, the run completed and answered, and the stored record of its input could not be read again (one record per such run). With the SQLite runtime store that alone did no harm in runs on 0.9.16: the session and its history read whole, and a start does not read a finished record (it reads the inputs still open and those with a completion pending), so nothing is logged for it. But where the host process ended between such a run's commit and the finalization of its completion (typically 20 to 40 ms; 1 to 260 ms seen; over before the client has the answer), the session could not be registered at the next start (`failed to recover runtime driver during registration` with `pending terminal owner row read failed: Store read failed: terminal completion candidate digest mismatch`) and a new prompt was refused, through `rkat-rpc` with that same text; and on a realm kept in the host's own database through the host store interface, read from the source, any such finished run was enough: the session's state failed to load at its next use. Now the read form of three fields keeps an explicit null as a present value: the run result's structured output and the structured output of the run-completed and interaction-complete events. Nothing is written differently. Records already stored read again as they are, with no repair and no rewrite, and a session whose host ended at that moment is recovered at the next start and its completion is finalized. One difference a reader of events can see (see Breaking): a replayed `run_completed` or `interaction_complete` event of such a run (the durable event replay; the events of a mob member on another host) now carries `"structured_output": null`, as the live one always did; before, the member was gone after the reread (the Python SDK gives `None` either way; the TypeScript SDK sees `null` where it saw no member; the declared type is optional and unknown in both). Schema files and generated SDK types are unchanged. Going back to 0.9.16 on a store this release has used: the same bytes are written; a finished record with a null is not read at a start there, as before, and one that this release finalized no longer refuses the session. Affected: 0.8.11 through 0.9.16 (the check is in the source at every release tag from 0.8.11, by a walk of all tags by content; 0.8.0 to 0.8.10 were not read; run on 0.9.16 only); a Meta gateway keeps its runtime state in the same store (read from the source; not run). This ends the Known limitation of that name added under 0.9.16 on 2026-11-17. (Shown by tests: the two records that 0.9.16 wrote are read and written back byte-equal, and the recovery at the driver on a record the test builds. Shown by runs on 0.9.16: the unreadable record; and the refused session, on the published `rkat-rpc` ten of ten hosts killed at that moment. Shown by a run on a build of the fix's own commit: a new process over a copy of the store that 0.9.16 left at such a host end registered the session, answered a new prompt and finalized the old record, which still holds its null, with no error or warning line; the database file that the refused start of 0.9.16 itself leaves is byte-equal to that one's, so a session 0.9.16 has already refused comes back the same way. Limits of that run: the host end was made by a test executor that held the acknowledgement, at the runtime's own machine and not through a host's session service, and one start was run. Read from the source, not run: a realm kept in the host's own database through the host store interface, roots that admit null other than an object-or-null root, and going back.)
